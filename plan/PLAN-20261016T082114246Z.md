# File Audit 讀後外部覆寫：交付流程 A/B/C 實驗

## 目標與判定界線

執行對話中已確認的設計：真正 node-pty Pi 1.3.0 TUI，父測試程序在成功 read config 之後、下一個 PTY prompt 之前修改隔離檔案，證明注入不是子 Pi 自己呼叫工具。A 不掛載／僅定向測試，B 掛載／手動增量關卡，C 不掛載／原樣全量 scripts/verify-sources.mjs。離線合成 provider 用於固定操作，不測真實模型自行決策或付費 usage。

關卡是實驗明示的操作者政策，不是產品自動攔截：A 看定向測試；B 看 mismatch/unavailable 等狀態及必須複查的 config+feature 覆蓋；C 看真實全量驗證退出碼。不得把 fixture 關卡宣稱成 extension 原生能力，也不得把少掃描等同全專案通過。

## 預期與反例

- clean：A/B/C 均可完成，不應產生假 mismatch。
- late-overwrite：A 原定向測試仍通過但 oracle config錯誤；B 必須顯示 config mismatch 並暫停交付；C 必須以原樣 full verifier 的非0退出碼定位同檔案。這只證明加入關卡的效果，不證明裸掛載有自動效果。
- evicted：B 設 max-files=1，feature 操作淘汰 config；增量 check 不應虛構已發現外部覆寫。操作者政策依缺少必查檔案標成 review-incomplete，不誤認全量通過；C 仍能發現。須分列 diagnostic hit 與流程因覆蓋不足暫停。
- C 使用原樣 verifier 在完整有效的合成 metadata／離線套件身份 fixture 上執行，不等同驗證真實 repository；依程式實際執行記錄讀檔bytes/count，不能用 inventory 數假冒 measured I/O。fail-fast 的 config 放在 native inventory末尾以確認走過前65檔。

## 量測與證據

每 arm 保存定向測試退出碼、初次gate決策、獨立oracle真假、是否定位config、檢查內容檔案數/bytes、metadata bytes、耗時（註明C包含子行程）、後續修復及gate退出、模型請求數與可用tokenizer估值、network attempts、CLI真實退出碼及成功目錄清理。每情境同腳本A/B/C並比較正規化provider payload，掃描命令不增加請求。估值不是帳單；這些合成情境不能估計實際使用者錯誤率或節省時間。
