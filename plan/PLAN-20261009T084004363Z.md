# Blackhole 與工具共存：三類優先問題詳細規劃

## 1. 目標、授權與目前狀態

使用者要求先讓 bundled reviewer 掛載 note 作為唯一完整報告輸出，再為三類優先問題制定詳細計畫。此文件是後續修正方案，**不是三類問題已修正或已驗證的聲明**。目前僅 reviewer 定義／報告契約已調整；Subagent 專用前景 Shell 在另一個已授權工作中進行，不能重複派遣或覆寫。

三類問題：
1. 特定 `custom_message` 在摘要與 recall 中的證據保留。
2. 新工具 schema／結果格式與 Blackhole 的檔案、搜尋、PTY 擷取契約。
3. 非同步工作投遞、完成及恢復的生命週期。

基準：本專案 vendored Blackhole 0.5.12、實際 Pi 1.1.0、根 manifest 十一個本地入口及兩個 npm 擴充。沿用既有工具名稱、設定、trust、owner／generation／lease，禁止改個人設定與credentials。維持現有壓縮時機及 retention 設定，不自動回填舊session。

## 2. 證據與問題定義

原獨立審查 job `01M4FW1RSRVJMY04Z5DH9GCKEB` 已 terminal completed，十三個 reviewer task 均結束。審查只有唯讀來源與現有測試分析，沒有執行跨模組重現；多個 child 沒有 note，所以不能將簡短結論當完整驗收。初步彙整：`report/REPORT-20261009T082843245Z.md`，詳細依原生 transcript 追溯。

每個發現先登錄為以下之一：
- 已由父agent核對的靜態契約缺口。
- 有待驗證的競態／安全影響推論。
- 工具本身的一般問題，並非壓縮造成。
- 設計上限制，需要文件說明而不是改成虛假保證。
- 缺少測試，不等於已發生故障。

首個可核對入口：`modules/blackhole/src/core/global-indices.ts:14–16` 只計 persisted message。這是既有 `#N` 穩定編號契約，**不可以為了加入 custom_message 直接擴大 counted 集合，導致既有 #N 指向不同記錄**。

## 3. Reviewer 報告交付前置條件

### 已調整的契約
- `modules/subagents/agents/reviewer.md` 加入 note；保留 read/grep/find/ls/bash，不加入write/edit。
- 完整報告唯一透過 `note({ type: "report", content })`，檔名由原生note自動產生。
- 不用bash寫報告，不改被審查來源；完成只回一句結論與真實相對路徑。
- note不可用或失败則回blocked及原因，不虛構路徑、不使用替代寫入方式。
- 自訂同名agents仍遵循既有優先序，不擅改使用者定義；note操作限制不是OS sandbox。

### 驗證
已新增兩個純契約回歸，先red兩項、調整後green 2/2。實際discoverAgents確認当前解析到bundled reviewer且tools含note。此證據不是實際provider child成功寫報告：後續需离線真實host probe，確認tools選取、native note掛載、一次report寫入、無write/edit、被審查檔案不變、返回實際路徑。用隔離workspace/home/auth，providerCalls=0。修改packaged agent資源需納入package驗證。

## 4. 工作包 A：通知與恢復診斷的證據保留

### 範圍與來源
核心：Blackhole `core/global-indices.ts`、`core/load-messages.ts`、`hooks/before-compact.ts`、normalize／context／recall相關消費端。生產者：Shell `shell-job-completed`、Subagent實際task_result/query_result通知、Runtime恢復診斷、Schedule Prompt結果及background reconciliation。

### 步驟
1. 列出每種通知的實際persisted shape（type/customType/content/details）、provider projection及資料壽命。不憑事件名稱假設entry type；用Pi1.1.0產生的隔離fixture核對。
2. 選擇明確allowlist，僅將必要通知作為資料檢索。排除 `blackhole-pre-compaction-output` display-only副本、private query暫存、credentials、任何無關custom內容。
3. 保留舊 `#N` 編號。對新增證據採用已有可擴充穩定entry ID／獨立識別空間；若現有API不能無破壞擴充，先提出具體schema方案及相容性決策，不重編舊ref。
4. 抽出小型共享證據投影，讓summary與recall使用相同選取／信任規則，不建立通用plugin manager。
5. 投影保留job/task/query ID、權威status/exitCode、cleanupPending/asOf及已有log／報告路徑。內容為不可信回傳資料，不提升為system指令，不把completed等同cleanup完成。
6. 明確區分raw history有資料、一般recall可找到、summary有代表資訊，以及provider仍保留原文。摘要不必搬回全部輸出。
7. 為畸形／過大／重複entry fail closed，套用既有解析預算；不依賴已被清理的暫存log補造證據。

### 回歸與驗收
- 成功／失敗Shell批次通知在compact→resume後可按ID找到權威結果；長輸出正確標partial。
- Runtime診斷及Schedule結果在被移出model context後可檢索，且不觸發工作或模型。
- 相同compaction不重複索引；branch scope／scope:all行为正確。
- 舊session的#N保持指向原record；display-only副本不重複計數。
- credential遮罩、控制碼、惡意通知文字與超限fixture不造成指令提升。

## 5. 工作包 B：新工具與擷取端契約適配

### B1. Note與File Tools（先做）
- 來源：`note-tools/extensions/note.ts`；Blackhole `extract/file-touch.ts`、`extract/files.ts`、`core/content.ts`、`core/build-sections.ts`。
- Note呼叫只有type/content，實際路徑在結果relativePath；擷取須按toolCallId配對成功結果，再從結果取得路徑，不能猜時間戳或要求輸入path。
- 明確讓note建立活動、文件內容及檔案drill-down可發現；raw argument已有全文時保留既有budget，不無限索引8MiB文件。
- read/write/edit以實際成功結果決定活動分類；錯誤、provider合成未執行結果、取消不得列為成功修改。
- 重試記錄保留歷史錯誤但將最終狀態與錯誤史分開，不能因後來成功抹掉全部錯誤或把成功任務仍標失敗。
- Windows slash/大小寫/8.3 alias必須定義可驗證canonical identity。不得把任意路徑解析到工作目錄外、follow未信任symlink或單憑文字等價誤配。既有8.3問題記錄在 `issue/ISSUE-20261009T051539532Z.md`，需要端到端red而非只修fixture。

回歸：note成功與失敗、多並行toolCallId、長文件、相對cwd、write/edit錯誤與成功重試、Windowsalias、compact/resume檔案清單和drill-down；檔案實際byte與hash不因擷取而改變。

### B2. 搜尋與Web
- 搜尋摘要保留工具名、pattern、scope/root、exclude及pagination cursor的必要部分；保留足夠成功結果或可讀artifact ref，不將搜尋成功等同命中檔案已被修改。
- Web URL與snippet持久化必須在真正session訊息存在，不能僅依structuredContent（host未必persist）。若需artifact，採既有機制且明示生命週期與截斷，不把暫存全文當永久證據。
- FFF root/exclude/cursor問題先分類是否第三方一般缺陷。遵守不改npm第三方實作的專案規則：必要時提出上游issue／本地可授權的窄適配方案；不能直接patch node_modules交付。

回歸：外部root結果可定位、fuzzy fallback不丟exclude、失效cursor有可辨識結果、長snippet的persist/recall、來源URL保留、query及toolResult配對。

### B3. PTY
- summary保留必要sessionId/target/cursor與執行狀態，避免混合多PTY。
- 明示recall只恢復歷史，不復活process。重啟/reload後舊ID不得誤指新PTY；review提報的ID與shutdown問題須獨立核對。
- 高風險live resource問題可能先於摘要適配處理，但需單獨授权及測試邊界，不擴大成remote process清理保證。

回歸：多session輸出、cursor過期、reload舊ID、kill/cleanup失敗、remote transport未知狀態與歷史證據。

## 6. 工作包 C：非同步生命週期與恢復次序

### C1. Managed Child Shell（已另行授權）
在進行中的job `01M4FWGN4XBWQ9F69TJJGH29EZ` 實作同名前景專用Shell定義；父agent不重派。child不含background、沒有shell status/cancel、執行端拒絕外來參數，主agent背景能力不變。以明確managed child身份而非RPC/cwd辨識；覆蓋new/resume、載入順序、guard環境消耗、ready query與reload。不能宣稱禁止命令自行detach或形成sandbox。

### C2. Schedule Prompt
- 核對递迴防護檢查的entry shape，使用真实custom_message fixture，不只mock错误type。
- 檢查pi.sendMessage／prompt實際返回与异步失败通路；提交不等於送達／run完成。若host没有ack，不設計假的exactly-once，而是保留pending/submitted/unknown之可辨識狀態與錯誤證據。
- once是否停用及計次須明確代表trigger或成功執行；不得悄悄更改第三方既有session绑定／storage语义。先提具體兼容迁移方案。
- notify:false明確禁止喚醒，核對busy/steer/followUp行為，不靠省略值。

回歸：compaction期間投遞、同步throw與異步拒絕、once/interval、busy/idle、notify:false、shutdown/resume、最多一次合法提交、不自動replaydelivery_unknown。

### C3. Runtime與Blackhole
- 建立host事件順序圖：assistant error→agent_end/turn_end→retry/overflow處理→agent_before_settle draft→真正settled→Blackholecompact；inline模式另畫，不把off設定当全模式保障。
- reviewer提報「inline可能吞overflow恢復」僅為静態高風險候選，先用合成provider和事件barrier重現，核對model/context错误分類，不能依摘要直接改壓縮時機。
- 既有Runtime fixture禁用retry/compaction不足以驗證共存。新增兩模組實際載入且builtin retry/overflow路徑可用的離線probe。
- reservation在投遞前persist；withdrawn draft/取消不退款；跨branch/reload/compaction不補額度；真正新使用者任務才歸零，extension通知不歸零。使用者新任務重置與模板/改寫匹配缺口另列明確驗收。
- 修正TUI-only手動恢復與fixture舊RPC預期之矛盾；不宣稱extension可觀測idle host abort。不繞過policy，不自动反覆改寫拒絕。

回歸：普通輸入錯誤、transient builtin retry、overflow、政策拒絕、withdrawn draft、取消與确认失效、兩次cap、repeat suppression、新任務reset、template變換、branch/reload/compaction持久化。

## 7. 依賴、派遣與檔案所有權

順序：證據核實與host shape→A共享投影設計→B1→B2/B3→C2/C3→跨模組驗收。C1獨立進行，最終整合一次。

Blackhole共用來源不給多個worker平行改：單一worker依序處理A及B的消費端；生產者修改可按不重疊檔案並行，但parent管理ownership表。Schedule與Runtime各獨立scope，reviewer唯讀。根manifest/scripts/provenance由parent独占，刷新时读最新hash，不覆盖同期工作。

每次handoff必须带目标、可修改路径、非目标、真实host shape、证据路径、未驗證項；禁止使用后台Shell讓child提前final。reviewer只透过note报告，不承担实现。

## 8. 測試分組與驗收門檻

- 純選取／schema／配對／budget／ID測試放單元；需Pi CLI/host/browser/process者放對應單一模組整合。
- 每項確認缺陷先新增真實shape red；不回退程式造red、不弱化斷言、不增加timeout或sleep逼green。
- 依修改範圍跑 `npm run test:module -- blackhole`、相關producer modules；修改TS跑根typecheck，改程式跑根npm test。
- 多模組/shared helper/provenance/runner修改跑 `npm run test:cross`。一次最終整合跑所需all-module integration；packaged agents/入口或tarball資源變動跑test:package。Web若涉及實際瀏覽器才安裝與跑browser。
- logging明確記Pi1.1.0、case數、skip、exitCode、providerCalls=0；test runner完成不是model final text。現有四個platform skips若出現必須列出，不叫zero-skip。
- 進行中／前runtime outcome_unknown不重跑或當完成；使用distinct evidence filenames，按job/task/invocation辨識新舊結果。
- 最終獨立reviewer無未解must-fix；警告有具體處置/接受邊界，報告必保存並可讀；未跑真實provider／人工TUI不能聲稱已驗證。

## 9. 設計安全不變量

不改Blackhole觸發時機、保留政策或既有history；不把display-only副本當model訊息；不把不可信工具內容升權；不恢復/重跑outcome_unknown控制；不混淆送出和ack、完成和cleanup；取消不等於process tree死亡。維持guard/trust/ownership與32 submitted／8 active等既有界限。不改个人home/settings/auth或第三方npm源码，不发布、不commit。

## 10. 交付與尚需決策

每工作包交付具体來源差異、red/green证据、当前provenance、真实执行分组及未验证列表；最终note report附逐模块矩阵。此计划不提供未经测量的工时/效能承诺。

需在实现前決定：custom_message新证据ref如何兼容#N；Schedule计次/once兼容语义；第三方FFF问题上游或窄适配边界；PTY活体资源问题是否另立修复scope。已明确用户授权的C1和reviewer-note不需要重复询问，其余修正依后续授权推进。
