# web_search 原生搜尋：擴充 Gemini／Anthropic／DeepSeek 的可行性與實作計畫

日期：2026-10-17　基準：Pi 1.3.0、`modules/web-tools`

## 一、結論

| Provider | Pi 實際走的路 | 官方 hosted search | 結論 |
| --- | --- | --- | --- |
| OpenAI | `openai-responses` / `azure-openai-responses` / `openai-codex-responses` | ✅ `tools:[{type:"web_search"}]` | 已支援（現狀） |
| Google Gemini | `google-generative-ai`（`@google/genai` 2.21.0） | ✅ `tools:[{googleSearch:{}}]` | **可做**，但官方只保證 Gemini 3 能與 function calling 併用 |
| Anthropic | `anthropic-messages` | ✅ `tools:[{type:"web_search_20250305",name:"web_search"}]` | **注入可行，但目前不可用**：Pi 丟棄 `server_tool_use`／`web_search_tool_result`，官方要求多輪必須原樣回傳 `encrypted_content` |
| DeepSeek | `openai-completions`（Chat Completions） | ❌ Chat Completions 只支援 `function` | **Pi 的 deepseek provider 無法用**；hosted search 只存在於 DeepSeek 的 `/responses` 與獨立 `/v1/tools/search` |

## 二、關鍵證據

### Gemini（已自行複查官方頁）
- 官方頁 `https://ai.google.dev/gemini-api/docs/google-search`（2026-10-13 更新）：現行工具是 `google_search`；舊 `google_search_retrieval` 只用於更舊模型。支援模型含 2.0/2.5/3.x/4 Argon。
- 同頁明寫：「Gemini 3 models also support combining these built-in tools with custom tools (function calling)」→ 2.5/2.0 併用沒有官方保證；Vertex 文件甚至寫同一個 `generateContent` request 不支援混用搜尋與非搜尋工具。
- Gemini 3 併用需要 `toolConfig.includeServerSideToolInvocations: true`，且該 flag 開啟時 function calling 只支援 `VALIDATED` 模式。
- 計價：Gemini 3 起以「每個實際 search query」計費（每月 5,000 次免費後 $14/1,000）；2.5 及更舊以 prompt 計費。

### Anthropic（已自行複查官方頁）
- `https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool`：`web_search_20250305`（basic）／`_20260209`（dynamic filtering）／`_20260318`（response inclusion），文件未要求 beta header。
- 原文：「To continue a conversation that contains search results, send the assistant's content blocks back exactly as you received them, including each result's `encrypted_content`. … If `encrypted_content` is missing or modified, the request fails with a 400 validation error.」
- `pause_turn` 續傳時必須把 paused assistant message 原樣再送一次。
- 計價 $10/1,000 searches；Bedrock 不支援。

### DeepSeek
- `/responses` 的 `tools:[{type:"web_search"}]`（官方稱伺服器端執行）與獨立 `POST /v1/tools/search`（USD 0.75/千次、QPS 5）。
- Chat Completions 文件原文：「Currently, only functions are supported as a tool」→ Pi 的 deepseek provider 拿不到 hosted search。

### Pi 1.3.0 host 限制（程式碼查證）
- 注入管道本身是通用的：`before_provider_request` → `onPayload`，`anthropic-messages`、`google-generative-ai`、`openai-completions`、`openai-responses` 都支援替換 payload。
- Gemini：Pi 的 params 是 `{model,contents,config}`，注入點在 `params.config`。`@google/genai` 的 MLDev 轉換器只認 camelCase `googleSearch` 與 `toolConfig.includeServerSideToolInvocations`（`toolConfigToVertex` 對該 flag 直接 throw）。
- Anthropic：`content_block_start` 只處理 `text`／`thinking`／`redacted_thinking`／`tool_use`，`server_tool_use`、`web_search_tool_result` 直接忽略；text block 的 `citations` 也不保留；`pause_turn` 被映射成一般 stop，不會自動續傳。
- Gemini 回應的 `groundingMetadata` 同樣不被 Pi 解碼保留（與現行 OpenAI 註解「pi decoder does not preserve hosted-search source objects」同類問題）。

## 三、Phase 1：建議實作範圍（低風險）

1. **config**：新增 `provider: "native"` = 依目前模型的 API 自動選用該家的 hosted search；`"openai"` 維持原語意（僅 OpenAI 家族），`brave`／`exa` 不變。避免既有使用者切到 Claude/Gemini 模型時行為靜默改變。
2. **native adapter 表**（取代目前硬寫在 `native-openai.ts` 的判斷）：
   | `model.api` | 注入內容 |
   | --- | --- |
   | `openai-responses`／`azure-openai-responses`／`openai-codex-responses` | 現狀：`tools += {type:"web_search"}`、`include += "web_search_call.action.sources"` |
   | `google-generative-ai` | `config.tools += {googleSearch:{}}`；Gemini 3 系列另加 `config.toolConfig.includeServerSideToolInvocations = true` |
   | `anthropic-messages` | Phase 2（見第四節） |
   | `openai-completions` | 不支援，維持現行 inactive 警告 |
3. **Gemini 注入條件**：預設僅 Gemini 3 系列注入（避開 2.x 混用未保證的 400 風險），其他模型維持「inactive + 警告」，可用明確 opt-in 覆寫。
4. **指引文字**：`NATIVE_GUIDANCE` 拆成 per-API 版本，一律要求「引用要寫出完整 URL」，因為 Pi 不保留 hosted citation／grounding 物件。
5. **測試**：單元測試覆蓋注入結果（camelCase、不重複注入、與既有 tools/toolConfig 並存、Vertex 不注入 flag、非支援 API 不注入）。不新增真實 API 測試。

## 四、Phase 2（需要真實 API 驗證或 host 支援）

**Anthropic**：目前不建議直接開放，因為有兩個已知破口：
1. 來源與 citation 遺失（Pi 丟棄 block）。
2. 多輪可能 400（官方要求原樣回傳 `encrypted_content`；Pi 不會回傳），`pause_turn` 也不會自動續傳。

可選解法：(a) 等／要求 Pi host 保留未知 content block；(b) 在 extension 內用 `provider_stream_event` 攔下原始 block，於後續 `before_provider_request` 把它們 splice 回 `payload.messages`（冪等、需處理 `pause_turn`）。兩者都必須用真實 API 驗證「省略 block 是否真的 400」才能宣稱可用。

**來源擷取**：Gemini `groundingMetadata`、Anthropic `web_search_tool_result` 可比照現有 `providers.openai.captureSources` 做成 opt-in 的 custom entry。

## 五、DeepSeek 替代方案

`provider: "deepseek"`：把官方獨立 `POST /v1/tools/search` 當成與 Brave／Exa 同層的 REST 後端（`search.ts` 新增一個 adapter）。優點是完全不依賴 hosted tool，Pi 目前的 deepseek（Chat Completions）模型就能用；缺點是多一組 config 與 API key。

已存在的同類實作可參考 `C:\GitHub\pi-deepseek-search`（npm `pi-deepseek-search` v1.1.0，MIT）：以 `POST /v1/tools/search`／`/v1/tools/fetch` 註冊 `web_search`／`web_fetch`，Bearer auth、3 次重試、每次成功請求 $0.00075 成本顯示。該套件的 `prime/` 變體則走 DeepSeek 的 Anthropic 相容端點（`https://api.deepseek.com/anthropic/v1/messages`）加 server tool `{"type":"web_search_20260209","name":"web_search","max_uses":8}`，是「單次請求」用法（不涉及多輪 block 回送），可作為 DeepSeek 支援 hosted search 的旁證。

## 六、需要決定的事

1. config 形式：新增 `provider: "native"`（建議），或直接擴充成 `"anthropic"`／`"google"` 等多值？
2. Gemini 是否只對 Gemini 3 系列注入？
3. Anthropic 現在是否要動（建議 Phase 2，先不開放）？
4. DeepSeek 是否改走獨立 Search API 的 REST 後端？
5. 是否能提供 `ANTHROPIC_API_KEY`／`GEMINI_API_KEY` 做一次真實請求驗證？（會有小額費用；沒有驗證就不能宣稱可用）

## 七、未驗證事項

- Gemini 2.5／2.0 併用 `googleSearch` + functionDeclarations 究竟是 400、被忽略，還是可用（文件互相矛盾）。
- Gemini 3 的 `includeServerSideToolInvocations` 加上 Pi 現有 `toolConfig.functionCallingConfig.mode` 是否真的相容。
- Anthropic 省略整個 server block 是否 400（文件只明說 `encrypted_content` 缺失或修改會 400）。
- DeepSeek `/responses` 是否能被 Pi 的 `openai-responses` adapter ＋ 自訂 provider 正確驅動。
- DeepSeek Anthropic 相容端點的 server-side `web_search` 在 Pi 的多輪對話下是否同樣撞上 block 回送問題（`pi-deepseek-search/prime` 只做單次請求，未涵蓋）。

- `native` 是新值，**不改變 `provider: "openai"` 既有語意**（仍限 OpenAI 家族 API）。
