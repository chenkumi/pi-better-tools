# Subagents／Shell Tools 非同步模式可行性評估

## 結論與範圍

可行，Pi 1.0.0 已提供 session custom message 與 follow-up 機制，不必修改 Pi 核心。建議第一版為「Pi 開啟且原 session runtime 存活時的背景工作」，不是關閉 Pi 後仍執行的 daemon。此次只做文件與原始碼靜態調查，沒有實作或執行測試；0.99.1／0.99.2 的通知與生命週期相容性尚未驗證。

## 已確認的現況與證據

- `modules/subagents/extensions/subagent/index.ts:998–1164`：目前 single、parallel、chain、resume 均等待工作與結果；直接使用工具 AbortSignal。parallel 現有 sibling cancellation 與全部 child await 必須保留。
- 同檔 `:800–874`：child 結束後仍需 finalize transcript、checkpoint commit／rollback 及 writer release。完成通知應等待整個 runner 完成，而不是收到 child assistant 最後訊息或 process exit 就通知 ready。
- `modules/subagents/extensions/subagent/concurrency.ts` 與 README：既有 process-wide 8 active child 限制、每次最多 32 submitted tasks／steps、guard、argument builder、managed sessions 可沿用。背景模式仍需限制跨呼叫的待執行佇列，避免有限 active 卻無限 pending。
- `modules/shell-tools/extensions/timeout-ms.ts:31–71,74–85,121–173`：使用 host local operations 與內建 tool definition，只覆寫 idle timeout；可沿用執行、UTF-8、shell 設定與取消路徑。
- Pi 1.0.0 `node_modules/@earendil-works/pi-coding-agent/dist/core/tools/bash.js:169–174,285–294`：shell 有 outputSchema／structuredContent（output、exit_code、wall_time_seconds 等）。背景啟動的 job receipt 不是完成結果，不能不改 schema 就回傳不同格式，也不能用假的 exit_code=0 表示成功。
- Pi 1.0.0 `dist/core/extensions/types.d.ts:1213–1216`：`pi.sendMessage()` 支援 triggerTurn 與 steer／followUp／nextTurn。
- Pi 1.0.0 `dist/core/agent-session.js:1735–1780`：followUp + triggerTurn=true 可在執行中排後續工作、閒置時觸發模型；triggerTurn=false 在執行中延後到安全 tool-result 邊界加入；nextTurn 只排到下一次 user prompt，不能作為立即完成通知的唯一途徑。
- `types.d.ts:608–613`：session_shutdown 涵蓋 quit、reload、new、resume、fork。官方 extensions.md 說明 session replacement 使舊 context 失效；需保存純資料，不能跨 replacement 使用舊 ctx。
- 官方 `examples/extensions/file-trigger.ts` 展示外部事件使用 sendMessage + triggerTurn 通知模型，僅作 API 用法證據，不能把其未完整 cleanup 的 watcher 直接當 production 範本。

## 建議設計

### 1. 啟動與管理

- 現有同步模式維持預設；新增明確 opt-in 的 `background: true`（名稱為建議，尚未決定）。
- 提交經驗證／授權後立即回傳 `{ jobId, status: queued|running }`，不把「已接受」說成「已完成」。執行器仍由 module 自己負責。
- 提供 job status／result／cancel 操作；查詢以 jobId 與 owner session 限定，結果保留摘要及完整輸出路徑。
- jobId 是本次背景派遣；subagentSessionId 是可續接的 child conversation，兩者不可混用。parallel／chain 建議一個 batch jobId，內含各 task／step IDs。
- resume 也可背景執行，但需要明確修改目前只接受 resume/task/title 的驗證規則，並保留 busy／ready／writer lock 語意。
- schema、renderer、codemode structured output 需一起適配。Shell 若採 background 欄位，輸出契約需加入 receipt 分支而保留同步結果格式；若不允許擴大既有 outputSchema，改用獨立背景提交工具，但它必須確認對應 shell 已被選取，不能繞過 defaultActive／loadout 或工具授權。

### 2. 通知

- 完成先保存結果，再送短 custom message：jobId、種類、成功／失敗／取消／逾時、exitCode（可得時）、摘要、結果路徑，以及 subagent 的 canResume。
- 「通知」與「自動喚醒模型」分開：純通知使用 display=true + triggerTurn=false；需要 AI 自動整理或接續則使用 triggerTurn=true + deliverAs=followUp。
- 預設不要 steer 打斷主代理工作。大量完成事件應批次合併，避免一個 job 一個模型回合造成費用與干擾。
- UI notify 可輔助，但不是 session 訊息替代品；非互動模式仍需有可查結果。
- 發送前檢查 owner session ID、runtime generation 與 shutdown flag；generation 可防止 reload 後同一 session 的舊 callback 誤投遞。
- Pi ExtensionAPI 的 sendMessage 回傳 void，不是持久化送達確認；以 durable result 與 notification ID 支援恢復／去重，不承諾 exactly-once 通知。

### 3. 背景生命週期

- 提交前由工具 signal 管理取消；接受後由 job-owned AbortController 管理。不能一直綁住舊 turn signal，也不能直接刪掉取消機制。
- 第一版在 quit／reload／session replacement 時停止接受、抑制晚到通知、取消 owner jobs、有限等待 cleanup；不能把它們通知到新 session。
- tree navigation／branch 變化也需決策：建議第一版 owner 綁 session，通知註記來源 branch／toolCall，不宣稱 background side effects 隨 branch undo。若要求 branch isolation，需另加取消／延遲投遞政策。
- 保留 timeoutMs 的 stdout／stderr idle 語意；subagent 現有 inactivity、I/O stall、settled grace 與 kill escalation 不應被背景模式改寫。
- 超時與取消需區分「要求終止」與「確認已退出」；process tree 無法確認清空時應回報風險，不顯示已全部停止。
- Parent crash 後只辨認 orphan／interrupted 並保留診斷，不自動重跑具副作用的 command 或 agent。
- shell／agent 與 parent 仍共用 workspace；背景測試與同步改檔可能互相干擾，需在工具說明中要求避免同時改同一檔案，必要時使用獨立 worktree（不是自動建立或同步）。

### 4. 資源與用量

- 設定 active／queued／retained jobs 上限、輸出摘要上限與保留政策；stdout／stderr 持續消費，避免管線阻塞。避免 token log 全部塞回主 context。
- subagent 提交時還不知道最後 usage。現有 usage 是同步 result 的 asToolUsage，custom message details 的 usage 不能假設會自動加入宿主 totals。需先確認宿主公開計帳能力；最低可行方案為 job 顯示實際 usage 並明講不含於 host totals，或以顯式 result 工具一次結算並防重複計費。
- 共用部分限於小型 job lifecycle／notification helper；shell 執行與 subagent guard／managed session 維持各自 module，不建立新 plugin manager。是否抽共用 helper 依實作是否真的共享同一契約決定。

## 難度與階段（相對判斷，非工期估算）

1. Shell session-scoped background：中等；執行器易沿用，主要是 job registry、schema、cleanup、結果查詢與通知。
2. Subagent single／resume：中高；需處理 immutable dispatch snapshot、managed writer／commit、用量及 owner 驗證。
3. Parallel／chain：中高；保留 8 active、32 submitted、chain previous output、failure stop 及取消全部 child。
4. 跨 reload／session replacement 保持執行：高；需要 process-wide supervisor、generation／owner routing 與重新 attach，第一版不建議。
5. 關閉 Pi 仍繼續：另案；需獨立 supervisor／daemon、IPC／結果 mailbox 與重啟 recovery，現有 app-open 模型與 sendMessage 本身不足。

## 後續驗證計畫

- 單元：狀態轉移、完成／取消競態、快完成 job receipt 順序、generation 防誤送、通知去重、bounded queue、structured output 相容、usage 不重複、chain 失敗停止。
- 真實隔離 host／process：submit 即返回、主 session 可繼續、忙碌時 followUp／純通知行為、job cancel、reload／quit／switch 不誤投遞、subagent commit 後才 ready、parallel 共用 8 permits、stdout 洪流背壓、Windows Bash／PowerShell cleanup。
- 使用隔離 workspace／agentDir 與 fake provider，不改真實 settings／auth，不呼叫付費模型。不新增固定 sleep／idle timeout 測試；已有 timeout-ms 單元覆蓋其穩定語意。
- 實作跨兩個模組與 shared helper 時依專案規則執行 npm test、npm run typecheck、兩個 test:module 與 test:cross。若改入口／package files，另跑 package／matrix 等對應驗證。
- 本次以上驗證均未執行，不能算通過；僅確認靜態 API 與程式結構可支援此方向。

## 已確認需求與待決策

- 使用者已確認：離開 Pi 就中止背景工作，與目前同步執行的退出生命週期一致。不需要 daemon、關閉後繼續執行或重啟後自動恢復工作。退出時沿用現有終止／清理保障，不承諾異常強制退出能清除全部 process tree。
- 切換 session／reload 時取消仍為設計建議，尚未由使用者明確確認；不可把「離開 Pi 就中止」擴大解讀為這些操作已定案。
- 使用者已確認：非同步的目的是讓 agent 派遣背景任務後繼續其他工作；完成結果必須回到當前 owner session，讓 AI 自動接續，不只是 UI 通知。此決策取代上文「保守預設純通知」建議。
- 使用者提出 role=system 訊息的想法。技術建議使用 Pi 公開 `pi.sendMessage()` 的 custom message（模型投影由宿主處理），搭配 `{ triggerTurn: true, deliverAs: "followUp" }`；主代理忙碌時排後續處理，閒置時啟動新回合。這不需要、也不應將 shell／subagent 原始輸出提升為 system 權限。完成事件的可信 metadata 與不可信 task output 應分開標示。
- followUp 是不打斷当前工作的方案；若未來要求在 agent 長回合中更早消化結果，再評估 steer 的安全回合邊界行為，不把 followUp 宣稱為立即中斷／立即處理。
