## 發現

### BUG-001 sql-connector：唯讀 query 工具可繞過 policy 執行寫入／管理指令，不經使用者確認（資安、資料完整性）

- **嚴重度**：High。最壞後果為資料永久刪除或伺服器管理動作（SHUTDOWN／BACKUP／KILL）；前置條件為 trusted 專案已設定 pgsql 或 mssql 且 query 工具被載入，由模型（含被資料內容 prompt-injection 的模型）送出特製 SQL 觸發。未升級：需設定與工具載入；未降級：觸發輸入來自不受信任的模型輸出，且繞過的正是 README 承諾的「每次寫入須互動 UI 確認」。
- **狀態**：已確認（policy 層實測 + driver 原始碼靜態推導）；可重現度：policy 層高，DB 端未執行（無測試 DB）。
- **位置**：`modules/sql-connector/src/security/sql-policy.ts:9-101`（`codeOnly`／`validateSingleStatement`）、`:120-126`（`hasForbiddenReadConstruct`）；`modules/sql-connector/src/runtime.ts:196`（MSSQL `request.query(sql)`）、`:273`（PG `client.query({ text, values: params ?? [] })`）；`modules/sql-connector/src/tools.ts:112`。
- **觸發條件**：
  1. PostgreSQL：`codeOnly` 不認識 dollar-quoting（`$$…$$`），可用 `$$'$$` 讓 checker 把真正的分號／DELETE 視為字串。無 `params` 時 `values` 為 `[]`，pg 8.23.1 `Query.requiresPreparation()` 對空陣列回傳 false（`node_modules/pg/lib/query.js:35-58`），走 simple query protocol，允許多語句。
  2. MSSQL：T-SQL batch 不需分號即可多語句；禁用字只列 insert/update/delete/merge/truncate/create/alter/drop/grant/revoke/exec/call，`SHUTDOWN`、`BACKUP`、`RESTORE`、`KILL`、`DBCC`、`WAITFOR`、`DECLARE/SET`、`DENY`、`RECONFIGURE` 均放行；`OPENQUERY(linked,'DELETE …')` 的內容在字串中也被隱藏。
  3. MySQL 的 backslash 跳脫與 backtick 識別字同樣會讓 checker 判斷失準，但 `multipleStatements:false` + `execute()`（prepared）阻擋多語句 → 目前不可利用。
  4. PG 單語句內具副作用函式（`pg_terminate_backend`、`setval`、`dblink_exec`…）亦放行；README 已聲明「不是完整 SQL parser」，屬此根因的延伸。
- **行為與影響**：預期 `*_query` 只執行一個唯讀語句；實際 `assertReadOnlySql` 對下列輸入皆放行（`ALLOWED`）：
  `SELECT $$'$$ ; DELETE FROM t WHERE true; SELECT ' LIMIT 1 ' -- '`（pgsql）、`SELECT TOP 1 1 AS x SHUTDOWN WITH NOWAIT`、`… BACKUP DATABASE d TO DISK='C:/x.bak'`、`… DECLARE @k int SET @k = 1 KILL 55`、`… WAITFOR DELAY '00:05:00'`（mssql）。在真實 PG/MSSQL 上會執行寫入或管理指令，且不經 `ctx.ui.confirm`。
- **證據**：已觀察（policy 層）。`plan/evidence/scan-20261017/sql-policy-probe.mts`、`plan/evidence/scan-20261017/sql-policy-probe.out`（9/9 ALLOWED）；pg 行為依安裝版原始碼。DB 端未執行。
- **修復方向（參考，未實作）**：讀取一律走 DB 層的唯讀保證——PG `BEGIN READ ONLY`／extended protocol（強制非空 values 或 `queryMode:'extended'`）；MSSQL 用唯讀登入或 `SET PARSEONLY`/`sp_describe_first_result_set` 前驗；checker 補 dollar-quote、backtick、backslash 跳脫與 T-SQL 禁用字。

### BUG-002 sql-connector：MySQL 查詢沒有逾時（穩定性）

- **嚴重度**：Medium。慢查詢或鎖等待會讓 tool call 無限期等待，pool 只有 4 條連線、`queueLimit:0`（無上限排隊），4 個卡住的查詢後所有 MySQL 呼叫排隊；使用者中止可恢復。
- **狀態**：已確認（靜態）；可重現度低（需真實 MySQL）。
- **位置**：`modules/sql-connector/src/runtime.ts:8`（`QUERY_TIMEOUT_MS` 只套到 MSSQL `requestTimeout`、PG `statement_timeout/query_timeout`）、`:49-61`、`:99`、`:111`。
- **行為與影響**：MSSQL／PG 30 秒上限，MySQL 無；abort 時 `connection.destroy()` 只斷用戶端，伺服器端語句（含 autocommit 寫入）可能繼續並提交，而工具回報 TIMEOUT/cancelled。
- **證據**：未執行（無 DB）；靜態推導。修復方向：`execute({ sql, timeout: QUERY_TIMEOUT_MS }, params)` 並設 `queueLimit`。

### BUG-003 sqlite-tools：`sqlite_query` 同步全量載入結果，無列數／記憶體上限與取消（穩定性、效能）

- **嚴重度**：Medium。`SELECT * FROM big_table`（沒加 LIMIT 是合理會發生的模型輸入）在 Pi 主執行緒同步 `statement.all()`，期間整個 Pi（TUI、計時器、其他工具）凍結，大表可 OOM 使宿主崩潰；BLOB 欄位經 `json()` 轉成 `[...item]` 數字陣列＋縮排，體積放大約 6–8 倍。輸出截斷只發生在全部載入、序列化之後。
- **狀態**：已確認（靜態）；可重現度高（任意大表即可；未實測大表以免耗盡記憶體）。
- **位置**：`modules/sqlite-tools/src/sqlite-manager.ts:62-75`、`modules/sqlite-tools/src/index.ts:123-145`、`:223-226`。
- **修復方向**：用 `statement.iterate()` 邊讀邊計數，到 `DEFAULT_MAX_LINES`／位元組上限即停止；BLOB 改成長度摘要。

### BUG-004 sqlite-tools：開啟資料庫會永久改成 WAL 模式，且不存在的路徑會建立空資料庫（資料完整性）

- **嚴重度**：Medium。只是 `sqlite_open`／fixed mode 開檔讀取，就把使用者資料庫檔頭永久改為 WAL（跨重啟持續、無提示），並產生 `-wal`/`-shm` 旁檔；對網路磁碟、唯讀媒體、或要求 rollback journal 的其他程式會造成相容問題。路徑打錯時建立新的空 DB 並回報「Database opened」，後續查詢的「table not found」會誤導排查。升一級理由：靜默、跨重啟持續。
- **狀態**：已確認；可重現度高。
- **位置**：`modules/sqlite-tools/src/sqlite-manager.ts:16-28`（`new DatabaseSync(filePath)` + `PRAGMA journal_mode = WAL`）。
- **證據**：已觀察。`plan/evidence/scan-20261017/sqlite-wal-probe.mts`、`.out`：`before: delete` → `after open+read+close: wal`；`typo exists before: false` → `after open: true`（在 scratchpad 隔離目錄執行）。
- **修復方向**：預設不改 journal mode（或只在 fixed mode 明確設定時改）；manual open 先確認檔案存在，或提供 `create` 旗標。

### BUG-005 shell-tools：背景 job 每個輸出 chunk 都重算 widget 投影、JSON 簽章並呼叫 setWidget（效能）

- **嚴重度**：Low（輕微效能下降；最壞情況才明顯）。`details` 含 `Output bytes observed`，簽章每 chunk 都不同，因此 `BackgroundPanel.redraw()` 每 chunk 都 `setWidget` 新 factory，再加上 overlay refresh。
- **狀態**：已確認（靜態＋量測）；可重現度高。
- **位置**：`modules/shell-tools/src/background-jobs.ts:305`、`modules/shell-tools/src/widget-binding.ts:24-31`、`modules/shell-tools/src/background-panel.ts:116-153`、`modules/shell-tools/src/live-widget.ts:12-26`。
- **證據**：`plan/evidence/scan-20261017/shell-widget-cost.mts`／`.out`：32 個保留 job、8 KiB 指令時每 chunk 約 1.03 ms、簽章 285 KB（不含 TUI render）；高速輸出（每秒上千 chunk）時可吃滿主執行緒。一般單 job 短指令成本低很多。
- **修復方向**：以 microtask／`setImmediate` 合併同一輪的 refresh，或讓簽章排除位元組計數、改由 render 時讀取。

### BUG-006 sql-connector：`formatRows` 每列重新 stringify 全部候選列（效能，Low）

### BUG-009 sql-connector：MSSQL pool 在 connecting 期間 close 會被略過（資源，Low，待驗證）

### BUG-010 schedule-prompt：Windows 上 lock 目錄刪除不重試，暫時性 EBUSY/EPERM 會留下永久 lock（穩定性，Medium，待驗證）

## 已排除

- **E-1 subagents stdout 解析 O(n²)**：`protocol.ts:39-65` 已用逐段累加與 byte counter，無重掃。
- **E-2 subagents 字串截斷熱點**：`progress.ts:47-65` 只在超限時逐字元迴圈，且只走 delta 部分。

- **E-5 shell foreground handoff 遺失或重複輸出**：`foreground-handoff.ts:61-77` 在 runner 內同步 replay 後接管，replay 期間不回送 host。
- **E-6 web static fetch 無總時限**：`fetch/service.ts:189-191` 有包含排隊的總 deadline。
- **E-7 MySQL 唯讀繞過**：`multipleStatements:false` + prepared `execute()`，見 BUG-001 第 3 點。
