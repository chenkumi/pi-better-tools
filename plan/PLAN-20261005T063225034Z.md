# 主 Agent 與背景 Subagent 連動可行性評估

## 需求與結論

延續 `plan/PLAN-20261005T062224217Z.md`：背景工作讓主 agent 继续其他工作，結果以 custom message + followUp 自動送回 owner session；退出 Pi 時取消，不建 daemon。

新增需求：主 agent 可查看背景 subagent 對話，並發送 control／query。control 在 loop 邊界永久進入 child 主線，改變後續路線；query 從 child 的上下文建立一次性分支回答（例如進度），回答後分支消失，不改變 child 主線。

結論：三者可行，但不是只新增工具 schema。查看紀錄改動較小，control 需雙向 transport，query 需安全快照與隔離的模型請求。建議背景 child 採 RPC，query 採一次性 context snapshot，而不是在活躍 managed session 上 fork／切回。此為靜態評估，未實作或執行測試，未驗證其他 Pi 版本。

使用者提出直接回傳執行中 log 路徑，讓主 agent 用現有 read／shell 查閱。評估可行且比新增 history tool 更簡單；本修訂取代下方獨立 inspect/history 工具的第一版建議，其餘內容保留作早期方案與比較。

- 第一版不新增專用對話查閱工具。依後續使用者確認，非同步 receipt 只需回傳每個 task 的 jobId／taskId／subagentSessionId（已建立時）與 readable liveLogPath，不預先回傳 finalLogPath；最終有效 logPath 在完成通知提供。parallel／chain 尚未啟動的項目標示 queued／logPending，不回傳假裝已存在的檔案。
- 已確認 `subsession-log.ts:328–329,445–467`：執行中寫入 runs/<taskId>/transcript.jsonl.partial，finalize 會 rename 為同目錄 transcript.jsonl。`index.ts:504,835–846`：成功 commit 後主要 logPath 又變成 managed conversation transcript.jsonl。不能只回傳目前最終 logPath 就假設它包含正在執行的 run。
- receipt 在 live log 建立成功後才宣告可讀；若先回 queued，後續以 owner session 事件通知 log ready。沿用現有 partial → final rename／commit，不新增穩定別名或重複 log。
- 使用者提出由 read tool 辨識檔名規則並指引 agent 處理 rename 競態。建議僅在 ENOENT 且路徑符合 managed subagent run transcript 規則時，檢查同目錄 transcript.jsonl，若存在则回傳可重試路徑提示，不自動偷換讀取檔案或將一般 .partial 檔案套用此規則。若候選也不存在，保留原錯誤並提示等待完成通知，不把它判為已完成；EACCES 等錯誤不作 rename 推論。
- 同目錄 run transcript rename 保持內容與行次，可沿用 read offset；完成通知若改成 conversation aggregate log，不能直接沿用 run-local offset。此 read 提示仍需實作與 file-tools／跨模組驗證，尚未確認現有 read 有此功能。
- 現有 readable transcript 是持續追加已完成的 message／tool records，不是每個 token delta 即時落盤；不把它稱為 token 級 stdout 串流。若要求逐 token 進度，須另行設計 bounded progress log，不能宣称現有 transcript 已涵蓋。
- 主 agent 記住 read offset，後續增量讀取，避免重讀整份；JSONL 最後半筆記錄不當作完成訊息，必要時下一次重讀。大筆 user 記錄分段需按 messageId／part／last 重組；read 的輸出截斷仍適用。
- 不直接暴露 native pi/*.jsonl 作一般閱讀路徑；沿用已過濾 hidden reasoning 的 readable transcript。只讀 log，不能透過 edit／append log 發送 control。
- 檔案歷史不等於可靠的 job status：沒有新增內容不代表完成／卡住，完成／取消仍以 job lifecycle 結果為準；status／cancel 可放共用背景工作管理操作，不需要為查閱歷史再加工具。
- 主 agent 讀 log 不能取代 disposable query 的 canonical context snapshot（system／compaction／opaque metadata 等）或 control 的 IPC。message control／query 工具仍有必要。
- 路徑直讀沿用現有檔案權限，不提供 inspect tool 的 owner 驗證／獨立存取控制；不要宣稱它是隔離邊界。主 agent 本來就具檔案讀取權時，這是可接受的最小設計。
- 後續需驗證 live log 先建立再回 receipt、partial/final rename race、finalization 失敗仍可調閱、queued task path admission、read 增量與半筆 JSONL。此次未執行。

## 早期工具契約（歷史查閱部分已由上述修訂取代）

```json
{ "tool": "subagent_inspect", "jobId": "...", "taskId": "...", "view": "status|history", "cursor": "...", "limit": 50 }
```

```json
{ "tool": "subagent_message", "jobId": "...", "taskId": "...", "mode": "control", "message": "改採方案 B，停止新增功能，先修復測試。" }
```

```json
{ "tool": "subagent_message", "jobId": "...", "taskId": "...", "mode": "query", "message": "目前已完成哪些項目？遇到什麼阻礙？" }
```

- dispatch 保留現有 subagent；inspect 是讀取，message 是互動，不把所有管理能力塞進現有 four-mode dispatch 驗證。
- jobId 對應背景 batch；parallel／chain 必須有明確 child taskId，不能把一個 batch 訊息猜測為廣播到所有 child。第一版不做廣播或控制尚未啟動的 chain step。
- owner session／cwd／runtime generation 在每次 inspect／message 檢查；不得讓任意 agent 憑 ID 接管別的 parent session。
- inspect status 回傳 task 狀態、當前 tool、最後活動、queued controls／queries 等。history 預設分頁公開 user、assistant text、tool call／result，不回傳 hidden reasoning／thinking block。沿用既有敏感輸出警告，不宣稱自動移除所有機密。
- history 以 finalized records 為主，stream partial 另外標記；回傳 cursor、snapshot timestamp、source entry／sequence，不混淆 history 與當前 compacted context。
- control 提交立即回傳 messageId 與 accepted／queued（或 rejected）；加入主線後另外標記 applied 與 entryId／turn。不能以 RPC success 當 applied；用 child-side bridge 或 canonical user message 事件確認，處理 input handler 轉換／消耗情況。
- query 提交立即回傳 queryId；結果完成後送回 owner session，主 agent 不必阻塞等待。query 不得被算成原 task 已完成，通知需帶 event kind 區分 task_result／query_result／control_applied。

## Control 語意

建議使用 RPC steering 而非寫 native JSONL：

1. parent 驗證 target 正在 running，分配 messageId，提交文字 control。
2. child 在現有 turn／tool batch 結束後插入主線 user message；權限是委派指令，不把外部結果提為 system。
3. 下一個 provider request 能看到 control，child 正常改變路線。
4. readable transcript、native session、wire digest 都收錄實際被接受的內容。

正在執行的 shell／長工具不會被 steer 強行打斷；「停止方向」與「立即 cancel job」分開。有多個 controls 時保持 FIFO，第一版可沿用 one-at-a-time，避免 silently replace。

若已 settled／finalizing／completed，拒絕 running control 並指引等待 ready 後用現有 resume；不要自動復活 child。child 完成與 control submit 的競態需有 admission barrier，確保 accepted 後不是靜默丟棄；無法證明 consumed 時回報 not_applied／delivery_unknown，而非成功。

文本預設 literal：RPC steer 會展開 skill／prompt template，須以 child bridge 封裝文字或明確拒絕特殊命令前綴，避免控制訊息意外执行 slash commands／模板。不得為此把主 session 的全部歷史或 credentials 傳入 child。

## Query：一次性快照分支

```text
child main:  ... → safe snapshot S → tool / next turn → ...
                             └→ question → answer → dispose
                                      answer → parent followUp
```

建議：在 child-side bridge 取得安全的 canonical context snapshot，使用隔離 in-memory SessionManager／獨立模型請求回答，不移動 main leaf，不寫 main native file。query 一旦完成或失敗就 dispose；答案只進 parent，不回注 child。這是功能上的 disposable branch，不必真的寫入原生 session tree。

### 快照與正確性

- 快照取最近一個完整 assistant+tool-results 邊界，或已驗證無 pending tool calls 的更近 leaf；不能複製一半的 assistant streaming／未配對 tool results 給 provider。
- child 有 active 長工具時可立即用上個 safe snapshot，外加獨立 observation metadata（現在正在何 tool、已耗時、最近可見進度），答案清楚標示 asOf／stale／pending control IDs。
- 如要求涵蓋本輪所有結果，排到下一 safe boundary，不能承諾立即回答。
- 同時存在 control／query 要定義順序：query 預設取捕獲 snapshot 時已 applied 的 control；尚在 queue 的只作 metadata，不假裝已影響 child。如果要查詢套用某 control 後的狀態，可另加 afterMessageId，等待相應 safe boundary。
- 保留有效 system prompt、模型／thinking、compaction、工具結果 pairing 與 provider opaque metadata；不要只把 readable transcript 拼成新 user prompt 就宣稱 context 等價。對外 inspect 可過濾 reasoning，內部 replay metadata 的處理另行驗證 provider 相容性，不直接顯示。
- context snapshot 不是作業系統／檔案快照，也不能讀取模型未輸出的私有即時想法。進度答案依可見紀錄，不能當作測試或完成證據。

### 限制 query 副作用

- 第一版 query 是純問答：不提供可執行 tools，不載入主線可變更檔案的 extension hooks，不讓模型在查詢分支繼續原 task。
- 僅用 prompt 要求 read-only 不夠；若沿用 worker shell／edit，branch 消失也不會回復檔案與遠端副作用。原生 fork 的文件樹隔離不是 workspace sandbox。
- query 使用 child 已驗證的 provider/config 最穩妥；在 parent 直接呼叫模型可能有 provider registration／credential／hook 差異，不能假設 parent registry 與 child 完全一致。
- 以 child 內隔離模型請求實作時需 query concurrency limit、cancel signal、bounded transport、答案與 usage 匯報；不能把 query 的 message／agent_settled 混進主線事件。
- 若採獨立 helper child，必須另有 argument-builder mode、guard、owner／snapshot 驗證，而且計入 process-wide child 上限；不能繞過排除 subagent 與管理工具的規則。
- query 是額外模型請求，會產生 token／cost；分支消失不等於 usage 消失。parent 答案與 minimal queryId／asOf／usage audit 可保留，完整 ephemeral branch 不進 child 主線。

## Transport 選擇

### 建議：背景 child RPC + query bridge

沿用既有 argument builder／startup guard／managed persistence，為 background interactive mode 新增 RPC transport。新增 stdin bounded writer、request correlation、response/event demultiplexing、stdout continuous reader；以 get_state 驗證 native identity。首個 task 改以 RPC prompt 文字發送（RPC 不接受 @file prompt args），但依然不放 command line。

RPC 提供 control／history 基礎；query 需 child extension／runner 的附加 request-result bridge。不要用原 child 的 fork／clone 處理 query：會 runtime replacement，且 managed native 驗證拒絕 branched tree。query 的獨立結果通道需要具體設計與 probe，尚未驗證。

收到 agent_settled 後停止收新 control、排清已接受事項、orderly close stdin 使 child 退出，再執行現有 finalization／commit。不能沿用「RPC 尚活著就五秒強殺」作正常收尾；既有 grace／kill escalation 改為明確 shutdown deadline 保障。RPC query response／get_state records 不應被當主線 stdout activity，讓持續 poll 掩蓋真正卡住的 child。

### 替代：保留 JSON print child + 自訂 IPC extension

改動 CLI 協定較少，但自行維護 control mailbox、ack、literal input、query bridge 與 boundary delivery；要驗證最後一輪 settling 時的接收窗口，不因 print 自動退出漏訊。只有小量 control 可選此方向；有 history／query 長期需求時 RPC 的標準 bidirectional 原語較合理。兩者都不需修改 Pi 核心，但不是零成本 adapter。

## 生命週期與容量

- 對話主線只有一個 writer；parent/history readers 與 query 不接管 writer.lock。
- main task queue、control queue、query queue 都有容量；query 模型請求有獨立上限，避免頻繁進度詢問耗費資源或讓主線等不到資源。
- 離開 Pi 時取消 main jobs 與 queries、關閉通道、有限等待 cleanup。恢復不自動重跑 control／task 的副作用。
- parent task_result 與 query_result 可先後／交错抵達，用 IDs 與 asOf 判斷，不用抵達順序推斷因果。
- 新工具不得因 module 載入就繞過使用者 loadout；child 排除 orchestrator tools（除現有 subagent，新增 inspect/message 的暴露也要檢查），保留 32 submitted／8 active 的既有不變量。
