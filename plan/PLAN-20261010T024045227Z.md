## 1. Blackhole pi-owned 逾時

### 實測

基準 HEAD：`11423a04a95b626cf4fbe6f3c8bde478eee19b2e`。將 HEAD 的 modules/blackhole 匯出到臨時目錄，以臨時 node_modules junction 共用目前依賴；執行目前未修改的 pi-owned-host.mjs，分別指定 HEAD／working root。每個案例使用隔離 HOME、空 credentials、passive 與離線 synthetic provider，序列執行兩輪。所有 12 個 probe 子行程成功退出，契約斷言通過；臨時 snapshot、junction 與 homes 已清除。第一次準備 snapshot 因 Git Bash tar 將 Windows C: 解讀為遠端位址失敗；改用 System32/tar.exe 後完成。

| Scenario | HEAD 第一／二輪 ms | Working 第一／二輪 ms |
| --- | --- | --- |
| low-pressure | 8755 / 6387 | 6850 / 5886 |
| auto | 6673 / 6710 | 6478 / 6925 |
| reload-model | 9918 / 10326 | 9465 / 9638 |

這些數字是 process 啟動到退出的 wall time，不是 Blackhole hook 本身 CPU time；未包含 parent 移除 home 的耗時。HEAD reload-model 已單獨超過 Vitest 10000ms 預設。代表樣本沒有顯示 working 的一致退化；不能由此證明所有情境或整體負載均無退化，亦未定位 with/without 的完整差額。兩個來源路徑與 jiti cache 冷暖可能影響比較。

### 程式碼證據

- `modules/blackhole/vitest.config.ts`：testTimeout 10000；include 將 tests/integration/**/*.test.ts 一起納入。
- `scripts/blackhole-tests.mjs`：全 suite 使用 maxWorkers=2，沒有區分 unit／native host。
- `scripts/run-checks.mjs`：blackhole:test 進入 unit，因此真實 host 案例也被 npm test 執行。
- `modules/blackhole/tests/integration/pi-owned.test.ts`：每案 execFile 啟動新的 Pi／TS loader；reload-model 又 reload extension。execFile 沒有 timeout/signal，Vitest timeout 本身不明確取消並等待此子行程，可能讓後續案例承受殘留負載。

### 建議

1. 將 Blackhole Vitest unit 與 tests/integration/** 明確分組；保留來源 runner、alias、setup 和所有案例。unit 排除 native integration，但 integration／test:module -- blackhole 必須顯式執行它們；不可漏測或假稱 unit 已涵蓋。
2. Native host 分組獨立、序列執行（maxWorkers=1），不要降低全專案並行能力。
3. 保留 unit 10 秒；native lifecycle 案例採局部約 30 秒預算，最終值再依完整 native 組實測調整。這是涵蓋程序啟動與 loader 的 integration budget，不是產品效能合格線。
4. 讓 native test harness 有明確子行程期限／取消與 close 等待，再移除 home；外層 test budget 要包含收尾餘裕。不能將 kill 要求當成 Windows process tree cleanup 證明，也不要新增 sleep／watchdog 型 timeout 測試。
5. 若仍需產品優化，在 fixture 加入階段時間診斷（SDK import、loader.reload、bind、prompt/compact、reload、dispose），另比 cold/warm 與 without-blackhole；不能因總時間接近就宣称已找到效能瓶頸。

## 2. Package smoke 的 rg 前置依賴

### 程式碼與實測

- `tests/helpers/environment.mjs` 隔離 HOME／agentDir，但繼承 PATH 與 Path。
- Pi 1.1.0 `dist/utils/tools-manager.js` 先查 isolated agentDir/bin，再查 PATH；PI_OFFLINE=1 且找不到工具時不下載。
- `tests/fixtures/smoke.mjs:232` 確實執行 grep，並檢查結果，因此移除 grep 會降低覆蓋。
- 本次 shell 啟動的 isolated child 能執行 rg --version，版本 15.2.0；繼承 PATH 含使用者 .pi/agent/bin。因此本次沒有重現 rg 缺失。歷史失敗行程的 PATH 沒有取得，不能確證當時差异来源；HOME 隔離本身不等於 PATH 一定看不到真實 bin。
- 分別執行 full smoke：不預置 rg 與將既有 rg.exe 複製到 isolated agentDir/bin。兩次都越過 grep 斷言，但均在 smoke.mjs:245 的 Web NETWORK_BLOCKED 斷言失敗，實際錯誤為缺少 @asamuzakjp/css-color。另由 jsdom package scope 的 require.resolve 確認目前無法解析該依賴。兩次 smoke 都非通過；只是確認本次 grep 段落成功。

### 建議（選預置工具，不刪 grep）

1. 增加共用測試前置 helper：從明確測試 rg 路徑或 PATH 解析實體 binary，執行 --version 並要求 exit code 0，複製到每個 isolated agentDir/bin；Unix 保留執行權限。
2. 缺工具時以明確環境 prerequisite error 失敗，不 skip、不下載、不讀 auth/settings。CI 明確安裝／提供 rg，記錄實際路徑、版本；本機可只讀複製既有 binary，但不可硬編碼個人路徑或修改全域 PATH。
3. 在 source `tests/integration/package.test.mjs` 與 production `scripts/package-smoke.mjs` 的 smoke homes 都套用，避免只修 source 而 production 仍失敗。helper 屬開發測試基礎設施，不加入 runtime dependency／tarball。
4. 環境紀錄補充 Node、Pi、rg 版本與解析位置，避免測試結果隨父行程 PATH 隱性漂移。
5. jsdom 依賴阻礙已在隔離乾淨安裝中確認可排除，詳見下節。採既有 lockfile 重建依賴，不新增直接 runtime dependency、不修改版本或 Web 程式碼；目前共用 node_modules 尚未重裝。

## 3. jsdom 缺少依賴：已驗證排除方式

### 確認結果

- 目前 `node_modules/jsdom/package.json` 為 30.1.1，宣告必要依賴 `@asamuzakjp/css-color: ^7.0.0` 與 `@asamuzakjp/dom-selector: ^9.2.1`；兩者在目前依賴目錄均無法解析，css-color package.json 亦不存在。
- 根 lockfile 已包含 `node_modules/@asamuzakjp/css-color` 7.1.2 及 integrity／transitive dependencies，並完整記錄 jsdom 的依賴宣告。
- 判定為目前已安裝 dependency tree 不完整；沒有證據需要修改 manifest／lockfile，也沒有證據是乾淨安裝下的 jiti 相容性問題。缺檔的原始原因（安裝中斷、後續刪除或其他因素）尚未確定。

### 隔離端到端驗證

建立自有臨時 workspace，複製目前 modules／tests／scripts／docs 與根 package.json、package-lock.json、.npmrc，不共用 node_modules；使用隔離 HOME／agentDir、空 credentials、PI_OFFLINE=1、PI_BLACKHOLE_PASSIVE=true，npm 只使用既有本機 cache。

1. `npm ci --ignore-scripts --no-audit --no-fund --offline`：exit 0，新增 227 packages。
2. jsdom 最小 DOM／CSS probe：可解析 css-color 與 dom-selector；querySelector 返回預期元素，getComputedStyle 的 red 得到 rgb(255, 0, 0)，子行程 exit 0。
3. `npm run pty:install`：exit 0，以既有專案 installer 準備 node-pty，不授權其他套件 install scripts。
4. 將既有 rg.exe 只讀複製到 smoke 的隔離 agentDir/bin，執行 `tests/fixtures/smoke.mjs <temporary-workspace> full`：exit 0，loaded=true、Pi 1.1.0、14 extensions、3 prompts；包含原本失敗的 Web NETWORK_BLOCKED 斷言、grep、renderer、PTY 與 reload 檢查。
5. 比對 temporary workspace 與原 repo 的 package.json／package-lock.json：兩者內容均未改變。自有臨時 workspace／homes 已成功清除，原 repo 的共用 node_modules 未變更。

以上證明既有 lockfile 的乾淨安裝可以排除此阻礙，並保留原斷言；不是僅讓 module resolve 成功。尚未執行七模式 package.test.mjs 或完整 test:cross／test:package，單一 full smoke 不代表這些分組通過。

### 實際環境的排除步驟

先確定沒有其他測試或 Pi session 正在使用目前 repository 的 node_modules，再在 repository root 執行：

```sh
npm ci --ignore-scripts
npm run pty:install
```

- 若確定 npm cache 完整，可以加 `--offline`；本次隔離驗證已證明此機目前 cache 可完成該安裝，但不能推論其他機器也具備同一 cache。
- 保留根 .npmrc 的 legacy-peer-deps=true；不要在 modules/ 裝套件，不使用 npm install --save 臨時補直接依賴。
- npm ci 會替換現有 node_modules，所以不在其他行程仍使用它時執行。此次僅更新計畫，尚未對原 repo 執行重装。
- 若後續要跑真實 Web browser 分組，依專案流程另執行 `npm run browser:install`；本次 full smoke 沒有驗證瀏覽器啟動。
- 重建後先重跑 full smoke／七模式 package.test.mjs，再按照下一節驗收 cross 與 package；rg 的可重現前置 helper 仍須另實作。

npm ci 的 lockfile／既有 node_modules 移除及 ignore-scripts 語意參考官方文件：https://docs.npmjs.com/cli/commands/npm-ci/ 。本節根因與通過結果來自本機實測，不是由文件推論。
