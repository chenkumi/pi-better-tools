## G1-002：Fork pending inbox繞過retained限額（Medium）
- 位置：`modules/fork/src/manager.ts:69–70,95–98,163–166,184–205`；README:24每process保留32筆。
- 操作：真SessionManager、accept/onTurnEnd/snapshot/store與session replacement，每輪序列建立65份不同origin；受控child完成outcome，而非手動塞Map或record。每輪maxActive1、完成後active0。
- 預期：有界保留或容量拒絕，不能為清理pending而靜默遺失結果。
- 實際：3/3輪全部65份admit，retained65/pending65，沒有拒絕。兩倍限額觸發evict也無可移除pending，但沒有admission fail closed。
- 影響：超過明定retained界限的結果/任務payload與掃描成本可累積；未量測OOM/latency，不稱已證耗盡。
- 反證：active4限額正常、pending需要保留原session投遞，因此不能簡單刪pending；本項只要求有容量政策。受控child並未啟動65真Pi，結論限manager retention，不宣稱65-child E2E。

## G1-003：partial prompt轉送失敗留下無owner的prompt檔（Medium）
- 位置：`modules/fork/src/args.ts:14–34`、`manager.ts:84–88`。
- 操作：兩個不同prompt flags，第一份真fs寫入，第二份writeFileSync注入EIO；真acceptFork/SessionManager/store/catch。
- 預期：受理拒絕時清理自己已建立的第一份prompt，或保留可操作owner/診斷。
- 實際：3/3拒絕FORK_STORE_UNAVAILABLE，但第一份.prompt.txt仍在、registryJobs0、spawned0、metadata1。
- 根因：temporaryFiles函式區域陣列只有成功return才交manager，throw後catch看到空清單。
- 影響：失敗派遣留下行內prompt與awaiting_snapshot metadata；反覆失敗累積資料/誤導恢復。只用了非敏感測試文本。
- 反證：沒有重複CLI flag語意依賴，測的是兩個不同flag+EIO；不盲刪外來EEXIST檔。錯誤拒絕/no-spawn正常，缺的是partial cleanup。

## G1-004：取消於optional stats等待時，仍送初始prompt（Medium）
- 位置：`modules/fork/src/child.ts:146,158–165,173–178`。
- 操作：真startForkChild/RpcPipe、真Node OS child作Pi RPC協定stand-in；get_session_stats barrier發IPC，parent呼叫cancel，child實際記stdin命令。沒有在child執行Pi或模型。
- 預期：取消已被受理後不新增初始prompt工作。
- 實際：3/3命令序列`get_state → get_session_stats → prompt → abort`，prompt確實抵達另一程序；最终status cancelled、childClosed true/exit0。
- 根因：optional stats的catch吞掉CANCELLED，隨後呼叫pipe.request(prompt)產生副作用，再由外層race回取消。
- 反證：pre-verification cancel3/3只有abort無prompt；正常3/3正確完成。
- 影響/定級邊界：已取消仍發布任務協定訊息；沒有測真provider admission/工具副作用/成本，故不沿用static的High假說。

## G2-001：Shell自動handoff後retained output超出32KiB（Medium）
- 位置：`modules/shell-tools/extensions/timeout-ms.ts:238–260`、`src/foreground-handoff.ts:44–50,65–76`、`src/background-jobs.ts:412–425`；README的decoded head+tail32KiB契約。
- 操作：真registered powershell/host accumulator/local OS child；先輸出48KiB單行，完整output事件觸發產品auto-handoff timer原callback，不等待/sleep測timeout。收到背景receipt後透過fs.watch事件控制同一child完成。
- 預期：背景terminal snapshot retained head+tail≤32768bytes。
- 實際：3/3output49152、tail8192，合計57344bytes（56KiB），child正常exit0、backendcompleted，同一helper PID未重啟。
- 根因：foreground已灌入host accumulator的head未縮限，job直接保留原結果再加tail。
- 影響：背景status/structuredContent/retained result違反明定容量；仍有host1MiB上限，不稱無限洩漏。通知文字另有小上限，不代表status被限制。
- 反證：direct-background新output有capture cap；故本項只限foreground→background交接前既有output。

## G3-001：Monitor wall-clock回跳令通知delay及elapsed錯誤（Medium）
- 位置：`modules/monitor/src/core.ts:6,100,124,172,197`。
- 操作：實際MonitorRuntime，clock seam分離牆鐘與relative callback，先成功submit再回跳600000ms；不用改OS時間或等待10分鐘。
- 預期：elapsed非負，30秒progress throttle不因牆鐘校正增加10分鐘。
- 實際：3/3next scheduled delay630000ms、elapsed−600000；無回跳對照3/3delay30000ms。
- 根因：rolling/elapsed/progress都用Date.now，牆鐘差值被當經過時間。
- 影響：校時後pending觀察延後與錯誤elapsed；duration使用相對timer，不聲稱TTL必然失效。未做真Pi/Windows校時walltime量測，排程參數錯誤由產品clock路徑直接證實。

## G3-002：Web cleanup失敗被吞掉且失去browser owner（Medium）
- 位置：`modules/web-tools/src/fetch/service.ts:130–133,354–362`。
- 操作：實際產品getBrowser啟動已安裝Chromium；只對owned Browser.close注入拒絕，service.close走真產品路徑；之後檢查仍可建立真BrowserContext。無page/網路請求。
- 預期：close失敗回報/保留unknown cleanup owner，而非正常resolve且丟掉最後handle。
- 實際：3/3service.close resolved、browser stillConnected、仍可newContext、service.browser undefined、closingPromises0。
- 根因：close rejection被catch吞掉；先清browser再把closing promise從set刪除。
- 影響：cleanup故障後live browser被遺棄、reload無可操作失敗證據。只證故障處理，不稱自然Playwright rejection一定代表leak或發生率。
- 反證與清理：3/3復原original close後await並確認isConnected false；owned contexts先close；没有掃殺使用者Chrome。
