## Critical (must fix)

### F1 — P1：UI enable 未綁定使用者看見／確認的版本
- **位置：** `modules/schedule-prompt/src/ui/jobs-menu.ts:63-85`；`modules/schedule-prompt/src/ui/jobs-view.ts:130-147`。
- **觸發／影響：** dialog 顯示 command A，等待確認時另一 writer 改成 B；確認後只鎖內合併 `{enabled:true}`，實際 B 被啟用。若 cwd 在專案內，fire 不需要記憶體 approval，B 可直接執行。TUI 另有更大的窗口：畫面快照 A，peer 改 B，按 t 後重新讀 B 並直接 approve，未再展示 B；專案外 B 也會獲核准。
- **證據：** menu 在 await 前讀 fresh，84 行非條件更新；view 的 render 使用 sel 快照，145 行卻核准 fresh。`scheduler.ts:526-535,772-775` 以最新儲存內容執行，僅 outside 檢查 approval。工具 enable 已有相反的安全範例 `tool.ts:264-282`，但未套用 UI。
- **建議：** UI 完整展示同一 execution spec；鎖內比較 spec／session，變動則拒絕重問，再對實際保存版本核准。

### F2 — 原 P1，Parent 複核已失效：command update 確認後可能保存未確認的混合配置
- **位置：** `modules/schedule-prompt/src/tool.ts:385-400`。
- **觸發／影響：** 啟用中的 job 原為 shell S、cwd X；使用者確認 command 更新時，peer 改 cwd 為專案內 Y（或改 shell）。399 行只合併 updates，保存成新 command＋peer 的 Y／shell，而不是確認畫面的配置；timer fire 讀最新配置後執行。外層 storage lock 只防寫入互踩，無法保護先前確認。
- **證據：** 395 行 await，396 行批准舊 updated，399 行 `updateJob` 合併 fresh store（`storage.ts:236-243`）；沒有 enable 路徑的 compare-and-mutate。`test/review-g5.test.ts:22-50` 僅測 enable，未覆蓋 update。
- **建議：** 鎖內以確認前 spec 作 CAS，對合併後配置重驗 kind/deadline/session；不一致拒絕且不授予 approval。

## Warnings (should fix)

### F3 — P2：TUI 以截斷預覽授權完整 shell command
- **位置：** `modules/schedule-prompt/src/ui/jobs-view.ts:143-145,236-238`。
- **觸發／影響：** 載入／重啟後啟用長 command：例如安全前綴後填足 200 字，再接另一條 shell 指令。footer 固定只呈現前 197 字＋省略號，沒有完整確認畫面，按 t 卻核准整段及專案外 cwd；使用者無法在此流程檢查被授權的尾段。這與 F1 的版本競態不同，即使沒有任何並行 writer 仍存在。
- **證據：** schema 接受 8000 字（`types.ts:125-130`），view `truncate(...,200)`，enable 不開 dialog；`command-ui.test.ts:183-189` 只驗證直接按 t 成功。
- **建議：** command enable 使用可完整檢視／捲動的明確確認，不以摘要預覽代替完整 spec。

### F4 — P2：放棄等待 close 後，晚到輸出可復活 timer
- **位置：** `modules/schedule-prompt/src/scheduler.ts:881-888,904-915`；對照 `modules/shell-tools/src/monitor-exec.ts:54-70`。
- **觸發／影響：** abort 後 shell 未退出／未 close，5 秒 race 先結束；finally 清 timer、run 退出追蹤。backend 尚保留 stdout/stderr listeners，之後倖存 process 輸出仍呼叫 onData，重新配置 tail 並 arm timeout。持續輸出可在 shutdown／drain 回報 pending=0 後繼續維持 timer 與 callbacks；不是單純「取消不保證 process tree 結束」的既有限制。
- **證據：** onData/arm 沒有 settled gate；backend 只有 finish 才移除 listeners。現有 `command-scheduler.test.ts:331-340` 的 never-close mock 沒有送晚到輸出，不能排除此路徑。
- **建議：** finally 前關閉輸出接收／arm，晚到資料只 drain；backend 提供明確釋放回呼機制，未 close 與已完成清理分開追蹤。
