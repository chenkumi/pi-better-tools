## G5-001：command output注入後續模型context（High，正式）
- 位置：`modules/schedule-prompt/src/scheduler.ts:788–793,822–827,836–841,864–869`；README/根AGENTS明訂結果不回注模型、不喚醒parent。
- 真SDK ExtensionAPI/context/SessionManager、真CronScheduler/Storage與PowerShell backend，唯一非敏感token `SAFE_COMMAND_RESULT`。trusted-project狀態以ctx輸入seam設定，不繞過模型/OS認證，也不讀真credentials。
- 預期：display可見，但後續LLM context不含command output。
- 實際：3/3 native scheduled_prompt command_done content含token，下一次synthetic provider request context也含token；commandStatus success。
- 反證：idle command完成前後沒有自動provider request，需下一次prompt才看到output；本次只證idle後context污染，不宣稱busy steer/parent自動喚醒已重現。renderer清理不是model context filter。
- 根因：非空content用pi.sendMessage保存，host把custom_message投影給模型；display:true不是context排除。
- 影響：不打算給模型的command結果仍進上下文，可能包含敏感/不可信資料；本次全為非敏感token，不宣稱已外傳機密。
- 建議：command marker採純display/state通道，或避免將command/output放content並明確禁止triggerTurn；不能只調renderer。

## G5-002：confirm snapshot與實際enable/execute spec不一致（Medium，正式）
- 位置：`modules/schedule-prompt/src/tool.ts:251–268`、`storage.ts:236–247`，fire讀fresh job在`scheduler.ts:506–520`。
- 真雙CronStorage writer、真createCronTool入口、deferred UI approval barrier（受控UI替身，不當人工互動驗證）、真scheduler與PowerShell執行。
- 操作：disabled command A進confirm後，peer writer把同job改B；回覆approve A。
- 預期：compare-and-enable同一confirmed spec；不同則拒絕或重問。
- 實際：3/3 shown/returned為A，但persisted enabled=true的command為B，實際output也為`CHANGED_COMMAND_B`。
- 根因：跨await確認讀取snapshot，鎖內只寫enabled，沒有重驗command/shell/cwd/schedule等精確spec。
- 反證/定級：限trusted project同store peer writer；手改store本來可在信任範圍內執行，不是untrusted任意執行漏洞。因此不採static High假說，定為Medium的一致性/approval結果錯配。
- 建議：在mutation lock內比較confirmed spec，變更則拒絕/重新確認，回報fresh保存結果。
