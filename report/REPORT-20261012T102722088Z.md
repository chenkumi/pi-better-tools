## Critical (must fix)

### R1 — Medium／阻擋 SUB-02 結案：dispatch 與 rollback 的 implicit writable handles 不受新 close latch 保護

- **位置**：`modules/subagents/extensions/subagent/session-store.ts:514–515,451–452,460–464`；對照新 barrier `:257–272,490–498` 與 runner `modules/subagents/extensions/subagent/index.ts:560,1032–1040,1053–1060`。
- **缺口**：新增 registry 正確涵蓋 `writeMetadata()` 的 explicit metadata handles 與 commit aggregate handle，但 `begin()` 的 `fs.promises.writeFile(dispatchFile, …)`、`rollbackToCheckpoint()` 的兩個 `fs.promises.truncate()` 仍自行在 Node 內部開 writable handle。它們未增加 managed pending counter、未在 close rejection 時保留實際 handle，也沒有把 close-unsafe 狀態送進 `unsafeWriters`。
- **不是只憑 API 名稱猜測**：核對 Node v26.8.1 原始碼，path-based writeFile 在 internal open 後經 `handleFdClose(writeOp, fd.close)`；truncate 以 `r+` open 並經同一 close helper；close rejection 會向 caller 傳播，不會替此專案設定 `cleanupUnsafe`。這是 API 實作確認，不是本機動態故障重現。citeturn0view0
- **可達控制流 A（dispatch）**：acquire 已成功 → dispatch 寫入成功但 close 拒絕 → begin 拋錯、`runStarted` 尚為 false、尚無 SubsessionWriter → runner 的 local `writerCloseConfirmed` 仍為 true，io settled → `managed.assertWriterSafe()` 看不到 implicit handle → 直接 `managed.release()`。如該 close 故障仍留下 open resource，writer.lock 與 live nonce 會被移除，重現原始 SUB-02 的 ownership 缺口，只是 writer 換成 dispatch。Late begin failure 在 `io.whenIdle()` 後也没有補登記此資源。
- **可達控制流 B（rollback）**：truncate 的 close 拒絕會被 `rollbackToCheckpoint()` catch 當一般失配吞成 false，因原生錯誤不帶 `cleanupUnsafe`。normal `blocked(..., restore=true)` 可以接著發布 blocked 並 release；stale recovery 的 `initializeLock()` 則可以把這個 false 轉成一般失敗後移除新 lock。兩條都沒有 actual-close 證據或 retained handle 身份。
- **影響界限**：仍是原始報告的 Medium ownership／descriptor 安全問題；未動態證明資料毀損、第二 child 已啟動或所有 OS close EIO 都留下 open descriptor。既有程式碼不是本輪新增，但本輪要求核對「所有 writer」並結案 SUB-02，故屬未完成修復，不歸因成新增回歸。
- **最小方向**：將上述 managed-directory writable operations 納入 explicit-handle 的同一 close barrier，保留 exclusive dispatch 的 `wx` 與 duplicate-dispatch 語意；rollback 的 close-unsafe 必須向上傳播，不能降格為 checkpoint mismatch。增加 dispatch、native truncate、aggregate truncate 的正常／close 拒絕／late settlement 定向案例，斷言 actual handle、lock、nonce、release、其他 instance 的 acquire/query 拒絕。

## SUB-02 專項 ownership 核對

1. **Actual close latch**：metadata 的 close rejection 優先於 write error；aggregate close failure 也保存 handle/path/error，並持有 global nonce。promise settled 不會讓 registry 消失。
2. **已接入 writer**：owner.json、begin run/manifest、committing run/manifest、completed run、ready manifest、blocked run/manifest、rollback manifest、aggregate transcript；run-local transcript 沿用既有 finalize/abandon barrier。
3. **尚未接入 writer**：本範圍內的 dispatch writeFile 與 rollback truncate 是 R1。allocate manifest 也直接 atomicJson 無 onUnsafe，但尚未建立 managed writer.lock／未交付可用 session，屬 allocation failure orphan artifact 的獨立限制，未另列本次 blocker。輔助 spool 的 path-based writes 亦不代表已被 ManagedSession registry 自動涵蓋；本次不把未修改 spool 扩張成新修復範圍。
4. **Normal/late paths**：normal release 前 assertWriterSafe，release 自身再檢查 latch／pending；late cleanup 等 child、各 gate idle、iterator return、run-local abandon 後再 assertWriterSafe。對已登録 metadata／aggregate rejection 兩條都 fail closed，不會以 run-local handle 關閉代替。
5. **Release/query**：其他 instance 無本地 lock 身份也不能越過 live nonce／writer.lock；query acquire 不作 stale recovery。owner metadata close failure 即使 acquire 尚未回傳、runner lockHeld 尚未 true，初始化也因 cleanupUnsafe 保留 lock 與 nonce；公開 query cleanup 的 release 會拒絕 unsafe owner。這些保護不補足 R1 的未登記 implicit handles。
