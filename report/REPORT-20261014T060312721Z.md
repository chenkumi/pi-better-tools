# 專案各模組 Code Review：穩定性與效能最終報告

## 1. 結論

**本輪檢視14個本地模組，整理21個候選；最終成立12項缺陷：High 4項、Medium 8項，沒有成立的Critical項。每個正式項主要案例均至少3/3穩定重現。**

另有5項待驗證、3項效能候選在有限樣本未建立失效證據、1項已觀察但契約有歧義的限制。這些全部不計正式缺陷；「未發現／未成立」不等於模組沒有問題。

本次只審查與驗證，**未修復或修改產品程式碼／既有測試**。新增的是報告、進度紀錄、隔離重現腳本與證據。

> **重要基準限制：** 審查期間有其他工作改動Fork與Pi Runtime檔案。最終核對9個既有模組檔案改變、2個新檔增加；沒有覆寫或回復這些變動。Fork取消候選已針對改後runner再作固定SHA核對與3次重現；Runtime重新核對因來源再變而在開始前被hash fence拒絕，G6-001降為待驗證。此報告不是審查期間所有新變動的完整驗收。

### 3.1 G7-001 — 陣列長度約束被忽略
- 位置：`modules/json-schema/src/schema.ts:67–97,155–180`；`extensions/json-schema.ts:154–156,215–218`。
- 觸發：schema `{"type":"object","properties":{"xs":{"type":"array","minItems":1}},"required":["xs"]}`，模型最後prose為`{"xs":[]}`。
- 預期／實際：應拒絕資料或在啟動拒絕不支援schema；真Pi CLI 3/3 exit0、交付空陣列。加`items:{}`的對照3/3 exit1／未交付。
- 根因：audit允許converter無法忠實執行的schema；本機Zod無items分支未套minItems。影響是成功結果不符合宣告schema。
- 建議：補足忠實validator或啟動拒絕該shape。只確認minItems案例，maxItems未獨立實測。

### 3.2 G7-002 — 未宣告property的required未被檢查
- 位置：`modules/json-schema/src/schema.ts:67–68,155–180`。
- 觸發：`{"type":"object","required":["must"]}`與模型prose`{}`。
- 預期／實際：缺must應拒絕；3/3真CLI exit0、交付`{}`。明列`properties:{must:{}}`的對照3/3拒絕。
- 根因：converter只在properties迴圈套required，audit沒有補強。宿主工具參數驗證不保護prose recovery。
- 建議：獨立核對required欄位或拒絕無法忠實驗證的schema。

### 3.3 G7-004 — 原始資料交付被宿主coercion破壞
- 位置：`modules/json-schema/extensions/json-schema.ts:79–82`；README:31。
- 觸發：n為integer但模型工具原始arguments是`{"n":"7"}`；另optional string s收到`{"s":null}`。
- 預期／實際：不轉型、不刪資料，非法型別應工具錯誤；3/3前者交付`{"n":7}`，後者3/3交付`{}`，均exit0／工具成功。provider／tool_execution_start保留原始值，tool_result input已被轉換。
- 根因：execute clone的已是宿主normalized／coerced params，本地validator看不到原始invalid值。
- 建議：沿原始工具input建立不轉型驗證與交付；不能只改execute中的clone。

### 3.4 G5-001 — command output進入模型context
- 位置：`modules/schedule-prompt/src/scheduler.ts:788–793,822–827,836–841,864–869`。
- 觸發：trusted-project輸入下正常PowerShell command完成；使用無敏感資料token `SAFE_COMMAND_RESULT`。
- 預期／實際：可display，不應進LLM；真SDK／Scheduler／Storage／backend 3/3保存非空custom content，下一次synthetic provider request看見token。
- 根因：display:true不是context排除，非空pi.sendMessage content被host投影給模型。
- 影響與邊界：違反明訂no-model-output，可能把不打算分享的命令輸出加入模型上下文。本次只證idle後下一prompt，不宣稱busy自動喚醒或機密外傳已發生；trusted ctx為受控輸入seam。
- 建議：採display/state-only結果通道，不把command/output放model-visible content，明確處理triggerTurn而非只改renderer。

### 3.5 G7-003 — compound const使用identity而非JSON結構相等
- 位置：`modules/json-schema/src/schema.ts:74–83,160–180`。
- 觸發：x的const為`{"a":1}`，模型資料`{"x":{"a":1}}`。
- 預期／實際：合法結構相等值通過，或啟動先拒絕不支援schema；3/3請求後exit1、不交付。scalar const1對照3/3成功。
- 根因：literal validator採object identity，parse/clone產生新identity。array const／object enum未另行重現，不算額外問題。
- 建議：提供JSON結構相等驗證或明確拒絕compound literal。

### 3.6 G1-002 — pending inbox繞過retention
- 位置：`modules/fork/src/manager.ts:69–70,95–98,163–166,184–205`；README:24。
- 觸發：來源切換後結果保持pending，序列accept/snapshot/complete更多工作。
- 預期／實際：retained32有界或新工作容量拒絕；3/3輪65份全admit、retained65/pending65，每輪maxActive1／最終active0。
- 根因：evict不能移除pending，且失敗後沒有admission拒絕。
- 證據層級：真SessionManager／產品manager／native snapshot／store，child完成為受控outcome；不是手動塞Map，也沒有spawn195真Pi。只證retention契約，不宣稱OOM或性能退化幅度。
- 建議：pending不可遺失，但應有明確總容量拒絕或有界移交政策。

### 3.7 G1-003 — partial prompt寫入失敗漏清理
- 位置：`modules/fork/src/args.ts:14–34`、`manager.ts:84–88`。
- 觸發：兩個不同prompt flags；第一份真fs寫入，第二份注入EIO。
- 預期／實際：拒絕時清理已建立owned prompt；3/3拒絕FORK_STORE_UNAVAILABLE，仍殘留第一份prompt與metadata，registryJobs0／spawned0。
- 根因：temporaryFiles僅在helper成功return時交給manager，throw後catch拿到空清單。
- 建議：helper擁有partial-failure cleanup或在建立時同步交付ownership；不盲刪外來檔。

### 3.8 G1-004 — optional telemetry catch吞掉取消
- 位置：原`modules/fork/src/child.ts:160–165`；收尾改後版本`:148,157–163`。
- 觸發：guard／get_state完成，初次get_session_stats等待期間cancel。
- 預期／實際：cancel受理後不發布初始prompt；3/3真OS child收到`get_state → get_session_stats → prompt → abort`，最後cancelled/close/exit0。pre-verification cancel對照3/3無prompt。
- 根因：stats catch把CANCELLED當缺telemetry，仍先呼叫pipe.request(prompt)產生副作用。
- 證據：真startForkChild／RpcPipe／Node OS child的Pi RPC stand-in，不是真Pi模型；沒有證明provider成本或工具副作用，所以不採High。
- 改後核對：`native-current-rpc-results.json` before/after child與guard SHA相同，9個主/對照samples，runner exit0、cleanup true，主要仍3/3。不能由此宣稱完整新版guard E2E已驗收。
- 建議：取消例外不可降級成telemetry缺失；prompt enqueue前再設取消fence。

### 3.9 G2-001 — handoff retained output超限
- 位置：`modules/shell-tools/extensions/timeout-ms.ts:238–260`、`src/foreground-handoff.ts:44–50,65–76`、`src/background-jobs.ts:412–425`。
- 觸發：真registered PowerShell／local child先輸出48KiB，完整output事件控制執行產品handoff原callback，再事件控制同一child完成；未用sleep測timeout。
- 預期／實際：背景decoded output+tail≤32768bytes；3/3 output49152+tail8192=57344bytes（56KiB），backend正常completed／exit0。
- 根因：handoff前的host accumulator不縮限，背景直接保留原結果再加tail。
- 建議：採納後retained snapshot沿同一bounded head+tail政策；host仍有1MiB上限，不把本項誇大為無限洩漏。

### 3.10 G3-001 — 牆鐘回跳破壞elapsed／progress排程
- 位置：`modules/monitor/src/core.ts:6,100,124,172,197`。
- 觸發：實際核心先submit，再以clock seam回跳600000ms。
- 預期／實際：30秒throttle不受校時增加10分鐘、elapsed不為負；3/3 delay630000ms／elapsed−600000。無回跳對照3/3 delay30000ms。
- 證據層級：deterministic產品clock路徑，未修改OS時間或等待10分鐘，不宣稱真Windows walltime benchmark。duration相對timer不因此被判失效。
- 建議：elapsed／rolling／throttle用單調時間，日曆observedAt仍用牆鐘。

### 3.11 G3-002 — browser關閉拒絕被吞掉且owner消失
- 位置：`modules/web-tools/src/fetch/service.ts:130–133,354–362`。
- 觸發：真產品啟動Chromium，僅owned Browser.close注入拒絕。
- 預期／實際：應回報unknown cleanup或保留owner；3/3 service.close正常resolve、browser connected且可newContext，service owner undefined／closingPromises0。
- 根因：catch吞拒絕，先清reference再移除closing promise。
- 反證／清理：3/3恢復originalclose並await、確認disconnected；無page／網路請求，不宣稱自然Playwright rejection都等於leak。
- 建議：保留失敗close狀態/ownership與可操作診斷，不以resolved wrapper當成功清理。

### 3.12 G5-002 — 確認A卻enable／execute B
- 位置：`modules/schedule-prompt/src/tool.ts:251–268`、`storage.ts:236–247`、`scheduler.ts:506–520`。
- 觸發：真CronStorage兩writer，deferred UI approval期間peer把disabled job command A改B。
- 預期／實際：鎖內重驗confirmed spec，不同則拒絕／重新確認；3/3畫面與tool回報仍A，persisted enabled B且真backend輸出B。
- 根因：跨await後只寫enabled，沒有精確spec comparison。
- 限制／定級：UI為受控替身、非人工互動認證；限trusted-store peer情境，非untrusted任意執行漏洞，故Medium。
- 建議：mutation lock內compare-and-enable，回報fresh已保存結果。
