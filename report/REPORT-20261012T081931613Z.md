### SUB-20261012-01 — 可接受 wire record 在較小的 readable/spool 單筆上限失敗（Medium，待驗證）

**精確位置**

- `modules/subagents/extensions/subagent/subsession-log.ts:296,385–399`：`MAX_PENDING_LOG_BYTES=1 MiB` 同時當單筆序列化 record 上限；超過即將 writer 永久標為 failed。
- `modules/subagents/extensions/subagent/tool-result-spool.ts:15,196–204`：fallback 的完整序列化 envelope 也限1 MiB。
- `modules/subagents/extensions/subagent/index.ts:781–791,803–825,844,848`：tool_execution_end 先寫 spool；assistant 每個 text part 先無分段寫入 writer，後面才執行2 MiB aggregate retention 截斷。

**呼叫可達性與觸發**

`subagent.execute(single/parallel/chain)` → `runSingleAgent` → stdout pump → `processLine(message_end assistant)` → `writeRecord` → `SubsessionWriter.tryAppend`。一個正常 assistant text part 為1,100,000 ASCII bytes，其 wire JSON 小於8 MiB、retained output也未超2 MiB，卻因 readable envelope >1 MiB 在輸出擷取前失敗。tool result 的 `content` 若接近1 MiB，fallback envelope開銷或 JSON escaping也可使 `spool.put` 拒絕；不是只在 structuredContent 巨大時觸發。較短文字含大量需escape字元亦可能跨過 serialized cap。

**預期／靜態推導的實際差異與影響**

正常、位於公開8 MiB wire envelope內的輸出應有明確一致的容量行為；目前較小 hidden record門檻可導致 child被終止、task failed、partial log、首次session blocked，無法抵達既有「aggregate output只截斷不使成功run失敗」路徑。這是**單筆**容量落差，不是再次報告已修的累積identity/output共用預算問題。

**反證／取捨**

1. `userRecords:109–122` 已對user訊息分段，因此不能把大task也算此候選；assistant/tool沒有相同分段。
2. `compatibility.test.ts:99–112` 的大型shell case刻意把巨大資料放structuredContent，text content只有 `truncated summary`（fixture `child.mjs:68–71`）；這些green不能反證巨大文字content。
3. `runner.test.ts` 的aggregate-cap案例與fixture `child.mjs:98–104` 使用多筆256 KiB文字，不涵蓋單筆>1 MiB。
4. 1 MiB是有意防護，不主張移除任何上限。若產品明確定義readable單筆>1 MiB應拒絕，此項可能改判為契約／文件缺口，而不是實作錯誤；目前模組README的容量說明未列此更小單筆門檻，且writer是mandatory。
5. `REPORT-20261008T083208722Z.md:65` 曾記fixture碰writer capacity，這提供已知現象的歷史線索，但不是本輪獨立重現或已完成此契約修正的證明；本項不聲稱「完全首次發現」。

**可執行重現**：下方腳本 `large-text`，真實 writer、managed allocation及native bytes；只替代spawn，不呼叫provider。另行驗證tool分支可在同一fake child加入合法assistant toolCall → tool_execution_end(content大型文字) → canonical toolResult，觀察先於canonical發生spool拒絕。未執行。

### SUB-20261012-02 — begin/commit 的 close-unsafe 沒抵達 runner writer-release 仲裁（Medium，待驗證）

**精確位置**

- `modules/subagents/extensions/subagent/session-store.ts:106–122,475–486,518–536`：atomicJson可附 `cleanupUnsafe:true`；begin/commit有多次metadata寫入，commit aggregate output handle的close在 `:531`。
- `modules/subagents/extensions/subagent/index.ts:560,1004–1028,1032–1040`：`writerCloseConfirmed` 只代表run-local SubsessionWriter。begin/commit的metadata或aggregate close拒絕被一般catch處理後，沒有獨立close-unsafe旗標阻止block/release。

**呼叫可達性與觸發**

正常create/resume runner取得writer lock後：

A. `managed.begin` 的 `run.json.<ULID>.partial` 真handle已寫入/sync，但close拒絕；`runStarted`仍false、writer尚未建立、gates actual promise已rejected（pending=0），runner最後可直接 `managed.release`。

B. 正常child完成且run-local transcript已close → `managed.commit` 寫committing run metadata時close拒絕（帶cleanupUnsafe）；或aggregate transcript append handleclose拒絕 → finalize catch → SubsessionWriter.abandon已close的handle成功 → cleanup `managed.blocked`成功 → `managed.release`。後續blocked metadata close健康，並不證明前一個不同handle已close。

**影響與限制**

可失去仍未確認close的managed writer ownership barrier，且handle沒有被owner保留以供晚到收尾；重複故障可能累积descriptor／Windows檔案佔用。A在既有ready resume上的begin故障還可能留下ready manifest卻已釋放lock。**不宣稱**一個close rejection必然代表仍在寫native檔、已造成資料損壞或一定能啟動第二個child；blocked manifest及checkpoint仍是後续防護。

**反證與避免重報**

- 初始化R7、recovered rollback C2、fence W1均已修：initializeLock `:319`尊重cleanupUnsafe；rollback `:431–435`原樣rethrow；fence `:304–306`聚合故障。此項不是那些已修呼叫路徑。
- `review-lifecycle.test.ts:145–221` 只把close故障注入 `transcript.jsonl.partial`；並mock掉ManagedSession.commit/blocked/release來驗證run-local writer barrier，不能驗證本項真commit的別種handle。
- 正常close成功、close仍pending、rollback metadata close失敗而讓cleanupIo catch留鎖，均不能當作本項失敗證據。
- readBounded等讀取handleclose拒絕不是這個writer候選。

**可執行重現**：下方 `metadata-close`及`aggregate-close`；fault只替代一個**真實已open handle**的close、不實際關掉，結束前用handle.stat確認open，同時量測writer.lock是否存在。需另加begin模式，分別證明A/B，不以一次mock稱所有close故障成立。未執行。

### SUB-20261012-03 — ready-query stdout超限後繼續累積同一buffer（Medium；高輸出故障時可造成parent記憶體壓力，待驗證）

**精確位置**

- `modules/subagents/extensions/subagent/ready-query.ts:111–137`，特別 `:129–130`。
- 同檔 `:59–70,119,170–196`：故障安排orderly EOF／kill，但仍持續drain，直到actual close保留所有權。

**呼叫可達性與觸發**

`subagent_message(mode=query)` → ready session preflight/read lease → background runner → `runReadyQuery` → disposable child stdout data handler。child在startup或後續故障時輸出>8 MiB且沒有LF（例如錯誤extension寫stdout或壞RPCproducer），第一筆超限時 `buffer += decoder.write(chunk)` 已留下超限字串，throw在分行／slice前，catch不清buffer。child後續仍吐stdout，data listener每次繼續append到同一超限buffer，並對越來越大的字串 `Buffer.byteLength`；故障已被記錄仍沒有停止retention。

**預期／影響**

應繼續drain而不在已知協定故障後繼續保留payload。現在可在shutdown grace期間遠超8 MiB，產生CPU反覆掃描及heap膨脹；若close/termination無法確認，時間也沒有由此buffer本身的上限保護。不是要求提前釋放child permit或原lease。

**反證／觸發邊界**

- 只有正常短JSONL、readable query答案8 KiB、IPC envelope128 KiB時，不能觸發；不是普通query回答必然洩漏。
- 標準runner `protocol.ts:39–64` 在append fragment前检查，且fail時destroy pipes；不能把其容量保障套到ready-query另一套data reader。
- kill/EOF一般能很快结束child，限制实际增长时间，但不是配置/保留8 MiB上限的证明。
- stdin request／IPC query數量上限、temp snapshot8 MiB不会限制stdout错误producer。
- 僅聚焦**已超限的無LF尾段**，不以多筆合法JSON合計大於8 MiB誤判單筆超限。

**可執行重現**：附錄第二段腳本用受控PassThrough producer先吐8 MiB+1無LF，再吐1 MiB無LF，才actual close；spy只記`Buffer.byteLength`的數值，不改回值。預期看到測量由8,388,609增加到9,437,185，與故障notice；這是reader retention探針，不是真OS kill/process-tree測試。未執行。
