## Critical (must fix)

### A1 — P1：Shell content 的 object-valued error 可以進入「結構權威資料」
- `modules/blackhole/src/core/notification-evidence.ts:55–59, 23–37, 78, 129–137`。
- **靜態實證**：matching content record 的 `error` 沒有型別限制便複製到 source；共享 `pick()` 將 object-valued `error` 視為 container，且 `pick(source, false)` 仍遞迴保留其中的 `status`、`cleanupPending`、`asOf`、`jobs` 等欄位。這不是單純顯示不可信 error prose：content-origin lifecycle 欄位會出現在 structural summary。
- 最小輸入推導：details 為 `{jobs:[{jobId:"J",status:"failed",exitCode:7}]}`，content 為 `Returned data\n[{"jobId":"J","error":{"status":"completed","cleanupPending":false,"asOf":{"stale":false}}}]`。驗證器接受 details；structural 的 job 將同時含權威外層 failed/7 與來自 body 的 `error.status:"completed"`／cleanup/asOf。外層 status 並未被覆寫，但新 nested outcome claims 的來源與結構標籤已混淆。
- **影響推論**：畸形或被偽造通知正文可把純內容衍生的狀態／cleanup 宣告提升為摘要結構證據，違反第 57 行註解及交付報告第 21 行的權威 merge 契約。真實目前 Shell producer 的 error 是 string（`background-jobs.ts:119`），故這是 malformed-input 防線缺陷，不宣稱真實 producer 已產生這種 payload，更不宣稱可直接造成 process cleanup 或程式執行。
- 最低修正：content 提供的 output/outputTail/error 僅接受明確 string／boolean 型別；structural 必須直接由已驗證 details 建立，不經混入正文的 source。對 producer-specific containers 使用對應 schema，避免通用遞迴把 text 欄位的物件當 lifecycle 資料。
- **最低回歸**：以上真實 custom_message 外形，斷言 summary structural 完全沒有 body-origin status/cleanup/asOf，外層 failed/7 不變；tool、command ID 展開及第二次摘要均相同；正文 error 為正常 string 時仍能 recall，但不能進入 structural。
