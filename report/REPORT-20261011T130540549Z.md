## 逐項證據

### R6 — Confirmed controlled filesystem race，已修正

**保留案例**：`modules/subagents/tests/session-store.test.ts`，`R6 stale contender cannot replace an acquired live writer`。

- 真實 fixture 先 commit verified checkpoint，建立 same-pid 未註冊 nonce 的 orphan lock。
- B 已完成 stale 判斷，在真實 `fs.promises.rename(writer.lock, stale)` 前以 deferred event barrier 暫停；A 在 B 暫停期間 acquire 並 publish live owner；釋放 B。
- 原碼每次都在 `B replaced A's live nonce` assertion 失敗；不是 import／fixture／timeout failure。Fixture 也在 A owned 時 append native bytes，但 red 首先失敗於 nonce assertion，因此不將後面的 native-bytes assertion包裝成已執行的資料毀損驗證。
- 修正：新短期 `writer.acquire/` atomic-mkdir election fence 包住 stale 判斷、rename、fresh mkdir、owner publish及 recovery；writer／query fresh acquisition 均遵守。B持有 fence 時A拒絕 SESSION_BUSY；B收尾release後A可再acquire。
- 補充 green：orphan election fence 同時拒絕 fresh writer／query，不產生 writer.lock。
- **限制**：repro 是同 process 兩個獨立 ManagedSession、真實 filesystem＋外部 FS fault seam，不是兩個 OS parent process 的 IPC red。已證實 pathname replacement race，不宣稱觀察到 live child/native corruption。Fence使用跨 process atomic mkdir；沒有 Linux/macOS實機或混合版本race驗證。舊版 runtime 不尊重新增 fence，不能宣稱混合版本安全。
- **設計取捨**：fence不自動stale takeover，避免遞迴引入相同check-to-rename race；crash於此短區段可能留下fence，fail closed SESSION_BUSY，需確認實際I/O／writer已終止後人工檢查。

### R7 — Confirmed owner-publish orphan lock，已修正

**保留案例**：同 `session-store.test.ts`，`R7 failed owner publish releases its settled initialization ownership`。

- 真實 mkdir、metadata temp write/sync/close後，一次性 fault seam 對 owner.json rename 丟 EIO。
- 原碼 acquire 正確拒絕，但 writer.lock 仍存在：`Missing expected rejection`（期望 stat ENOENT）連續三次；不是測試未收到注入。
- 修正：在 election fence 下統一 `initializeLock`。只有 metadata handle 已close、directory dev/ino仍一致、owner nonce未變（或尚未publish）的settled初始化才刪除owned lock／registry。失敗保持原診斷；cleanup拒絕以AggregateError保留原始故障及cleanup unconfirmed。
- metadata實際close拒絕標記cleanupUnsafe，保留lock／live nonce，不假稱resource已close。Query初始化使用相同補償。
- 同案例 green 每次確認 lock不存在、下一 ManagedSession可acquire/release。
- 補充 green三分支：owned rm failure、foreign published owner、actual metadata FileHandle.close rejection；確認 retained nonce與directory存在，foreign nonce未被盲刪。Test teardown只在其owned handle真正close後清自己的fixture／registry。
- **限制**：cleanup failure／close未確認會fail closed保留診斷，不自動retry或承諾manual intervention-free recovery。未注入每個OS filesystem failure，也不把receipt rejection當writer已釋放。

### R8 — Confirmed pending prepare wait cannot cancel，已修正

**保留案例**：`modules/subagents/tests/review-background.test.ts`，`R8 cancelled preparation returns while actual allocation retains admission until settlement`。

- prepare以deferred event卡住，32 submitted已占用；使用現有job cancel，下一setImmediate事件邊界檢查caller是否已reject。這是event ordering檢查，不是wall-time threshold／sleep／watchdog測timeout。
- 原碼每次 `outcome === undefined`，期望rejected；finally解除barrier再await job settlement，不留卡住的測試工作。
- 修正：submitManaged以job-owned controller觀察prepare取消，受理前亦綁tool signal；prepare收到job signal。等待可reject，但actual prepare promise／ready admission／job.done仍保留直到settlement才release submitted容量，不放runner、不送未受理結果。成功accept後移除tool binding，背景lifetime仍job-owned。
- index background create在snapshot後／next allocation前核對preparation signal；不開始後續item。晚到配置完成的未受理managed session保持new，不虛構checkpoint／log。
- 同案例green驗證：caller立即reject、barrier未釋放仍submitted32/32、capacity仍拒絕；actual settlement後0/32、runner一直未執行。
- 補充真實I/O green：兩種cancel（tool／shutdown）在ManagedSession.allocate的實際manifest publish前暫停；callerreject且容量仍2/32，解除barrier後只完成第一allocation、第二不開始，保留真實state=new manifest，runner不執行。
- **限制**：red最小案例是prepare-lifetime barrier，補充actual manifest I/O案例在修正後新增，沒有偽造其原碼red。本修正處理取消而不是新增任意allocation deadline；OS I/O永久卡住仍持有capacity，shutdown registry清除不等於actual settlement。
