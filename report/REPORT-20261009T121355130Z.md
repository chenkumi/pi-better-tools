## Warnings (should fix)

### W1 — P2：停止要求已提交後，真正 close／terminal 的更新不再產生通知

- **位置：** `modules/monitor/src/core.ts:65–73,77–87,140–141`，尤其 `core.ts:83`。
- **靜態實證：** `requestStop()` 在 actual source close 前立即建立 stop-reason system event。若這批已提交，該 event 已從 `m.events` 移除，但 `m.lastSystemEvent` 仍保留相同 kind。稍後來源真正 close，`finally` 更新 `state`、`cleanupPending`、close evidence，再以相同 `stopReason` 呼叫 `system()`；第 83 行因 kind 相同直接 return。當沒有其他待送資料時，`schedule()` 也無 batch 可送。
- **具體順序：** 已送出 `started` → 合法下一投遞機會呼叫 stop → `stop_requested` batch 先提交，details 是 `stopping/cleanupPending:true/sourceClosed:false` → 延後釋放 close barrier → status 已成 `stopped/cleanupPending:false/sourceClosed:true`，卻沒有後續終結 batch。Expiry、limit、source fault 同樣可能發生，取決於 close 與 flush 的順序。
- **影響：** custom-message 歷史／producer consumer 可能永久只看到取消要求及 cleanup pending，真正終結／exit／close evidence 僅剩 session-local status。這不是錯稱 tree cleanup，也不是 host 無 ack 的既有限制：是 Monitor 本身沒有提交更新。對要求自動觀察終結、而非靠主代理再次 polling 的功能而言有實際可觀測性缺口。
- **現有測試為何沒抓到：** `tests/core.test.ts:52–56` 先 finish 再 flush；`tests/command.integration.test.ts:24–27` 主要核對 settled 後 status。二者都沒有讓「停止要求先提交、close 後到」的順序成立。
- **建議：** 原 stop-reason event 仍保持一次，另外以 `source_closed`／明確 terminal update 記錄 close evidence，或對 terminal metadata 設有界 dirty/pending bit；不得 replay 已 submitted data event，也不得由 stop request 假造 close。
- **最小離線回歸（未執行）：** 使用現有 FakeClock＋deferred launch。送出 started，advance 30000，stop，advance 0 並斷言已送 stopping batch；之後才 `finish()`／`settled()`，再 advance 30000。斷言新 batch 含 terminal receipt 的實際 close evidence，`stop_requested` event 仍只一次，且 processTreeState 仍 unknown。另覆蓋 expiry 或 source fault 的相同先後順序。無 OS process、無 sleep、無 provider。

### W2 — P2：flush 固定從最早 Monitor 抽完，後建立來源／terminal 通知沒有公平投遞機會

- **位置：** `modules/monitor/src/core.ts:119–128,147`。
- **靜態實證：** 每批從 Map insertion order 的第一個 Monitor 開始；逐個消耗其 events 到整批 32 events／byte cap，沒有 round-robin cursor、per-monitor quota 或 terminal metadata reservation。下一批又從最早 Monitor 開始。
- **具體可構造案例：** agent busy 時先建立 A/B/C 三個 command Monitor，各採納 60 筆短事件（各自合法 rolling rate），再建立並完成 D。A/B/C 各有 started＋60 data 共 61 events；D 的 started/data/source_closed 雖已存在，第一次 idle flush 和接下來多個 30 秒 batch 仍先抽 A/B/C。短文字不碰 byte cap 時，D 到第六批（首批後約 150 秒）才被選中。D 的 terminal event 並非不存在，而是被 earlier queues 延後。
- **影響：** 完成／失敗／清理證據可能被不相關的舊 progress 延遲數分鐘；早期來源持續補資料會放大此偏差。不是宣稱無限 starvation：TTL、600 total、pending bounds 仍限制總量；問題是沒有來源間公平性，也沒有 terminal 的可預期首次投遞機會。
- **現有測試為何沒抓到：** `tests/core.test.ts` 的 fixture 主要只有單一 Monitor；busy／ordering tests 未測四來源同時排隊。13/13 green 不能證明公平性。
- **建議：** 跨 Monitor 採 round-robin／每來源有界 quota，保留各自 sequence 順序；必要時預留 terminal metadata 機會，不以刪除 command/WS 歷史來換公平性。仍維持 owner 每 30 秒一次、整批 event/byte cap。
- **最小離線回歸（未執行）：** 用 FakeClock 同時保有四個 launch；busy 期間讓前三個各產生 60 個短 data，第四個完成。settled/idle 後第一批應至少讓每個有 pending 的來源獲得代表性事件，或依明確採用的公平政策在有界少量批次內包含 D 的 terminal metadata。核對每來源 event sequence、全部 batches 的 32 events／32KiB、30 秒節流及總 counts，不加 sleep／provider。

- owner 由 session ID＋canonical cwd 構成；core 每 callback／flush 核對 current owner 與 runtime generation，capability lease 在 read 前後核對 provider identity/revoke/valid。這裡依賴 adapter 的 authoritative projection，未另行批准其 producer 實作。
- receipt acceptance 前拒绝已 aborted；回 receipt 後工具 signal 不再用來管理來源，runtime-owned controller 管理 startup/TTL/stop。TTL timer 在 launch microtask 前建立，包含 startup，不是 Shell idle timeout。
- owner lost／shutdown 抑制舊 batch；shutdown 最多等待兩秒，不假稱未 close 的來源完成。未清 cleanup 的 generation 不能 bind 新 owner。普通 SDK `session.dispose()` 不是保證 dispatch session_shutdown 的 API；相關 Shell README 與 SDK runtime example 要求 await runtime.dispose。Monitor 遇到 stale ctx getter fail closed；安靜來源仍不能由「沒有 callback」推導立即 cleanup。
- command backend 明確分開 stdout/stderr、stdin ignore、close 而非 exit barrier，沿用 Pi Shell settings/env/cancellation；legacy stdin transport 明確拒绝。actual close evidence 與 processTreeState unknown 共存，沒有假 claim descendants 全部清理。跨平台 cancellation 僅 best effort，Windows taskkill 非同步啟動也不是 tree cleanup ack。
- job adapter 自己只有 timer／readonly lease；stop 不 cancel 被觀察 job、不 query 模型，不讀任意 private logs。直接依賴的 authoritative projection／root adapter integration 仍交另一 reviewer。

### Bounds／delivery／wake

- stdout raw storage 固定 16KiB；超長在 decode 前拒絕，UTF8 invalid 標 partial；stderr 8KiB tail 不成 data event。WS aggregate payload 由 installed receiver 的 haveLength 在 consume/reassembly 前拒絕；transport 另限制 fragments/chunks，compression 關閉。
- rolling window、600 total、stopAfterEvents、pending data/bytes、owner bytes、active/retained caps 均有静态限制；retained active／cleanup pending／pending events 不可 evict。source input、system vocabulary、stderr、timestamps/event queues 也有界，不見本 scope 無界歷史保存。
- event ULID uppercase，per-monitor sequence 單調；submitted events 从 queue 刪除，sync throw 保留原 event IDs／sequence；job coalesce 記 omitted。跨 Monitor 不保證全域 observedAt 排序，規格的 per-monitor ordering 有保留。
- agent_start／agent_settled 管 busy；before_agent_start 不立 latch，agent_end 不提前 flush。flush 有 reentry guard 与 owner/generation recheck；sync throw 最多三次、只下一合法 opportunity 重试，非 tight-loop。
- installed Pi send binding（agent-session.js:2703–2710）把 async rejection 轉 runtime send_message error，沒有 Monitor batch ack。因此 status 的 submitted／hostAcknowledgment unknown 是提交證據，不是 delivered/persisted；不能將無 batch association 的宿主 async error 歸因特定 Monitor。沒有 replay 已 submitted batch。
- **wakeAgent 混合判定：** `core.ts:130,137` 只對本批 selected monitors 做 OR。若 true 與 false 都在本批，該批要求一個 turn 是由明確 true 的 Monitor 授權；不能据此说 false 单独引发误 wake。若本批全為 false，即使另有未被选到的 true Monitor，也不會要求 turn。false 的資料仍会进入后續 model context，這是 display custom_message 的規格，不是永久 private/no-context 模式。建议補混合測試，而非把合理 OR 本身列成缺陷。
- 剩餘可靠性問題是 W1 的 terminal metadata 更新未提交與 W2 的 source fairness，不以以上單源 green 抹去。

### Network／public data

- ws/wss-only、userinfo／非法 port／過長 URL 拒绝；ws 与 private destinations 分开 explicit boolean opt-in。IPv4/IPv6/mapped classification 使用 ipaddr.process 的 public unicast 判斷，未授權 private／loopback/link-local 等拒绝；mixed DNS 集合任一未授權 IP 即整組拒绝。
- prepareEndpoint 保存验证後 address set；actual transport 自定义 lookup 从该集合返回，禁止不匹配 hostname，不再次 resolver。TLS 保留 hostname/SNI 与 rejectUnauthorized；agent:false 不靠共用 proxy/agent 再解析。TLS wrong-name／untrusted-CA 有真實 local transport evidence。
- redirect 不跟随、binary terminal failure、完整 fragmented text 才一筆 data、UTF8 validation 保留、no automatic reconnect、payload/fragment/chunk cap。error 不当作 close，直到 actual close 才補來源 evidence。
- URL query/fragment/path 不出現在自產 preview，command preview withheld，generic network/source failure 不公開原 error。來源資料是 untrusted returned data，custom message 明示不是指令；不承諾任意 stdout/text/closeReason 能全面去密（S2）。
