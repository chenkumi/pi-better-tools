## Host 契約基準與逐模組判定

### 共同契約

1. **Factory 只註冊／讀取設定，不建立長期資源。** `G/docs/extensions.md:54-60` 禁止 factory 啟動 process/socket/watcher/timer；`H/core/extensions/loader.js:510-522` 只 await factory，不會替未開始 session 的 extension 自動收拾這些資源。Loader 的失敗 discard 只處理註冊相關訂閱／待提交變更（446–453），不是通用 process/timer cleanup。
2. **Reload 與 replacement 是新的 runtime，不是恢復舊物件。** `H/core/agent-session.js:2936-2969` 先 shutdown、invalidate，再重載並 start；`H/core/agent-session-runtime.js:102-113` 先 abort、shutdown、dispose，new/resume/fork 路徑再建立 runtime。`types.d.ts:624-628` 明確包含 quit/reload/new/resume/fork。不能用缺少 session_start 重設來誤判 Web／PTY，因其正常 replacement 會重新跑 factory。
3. **Shutdown handler throw 不會否決 reload/replacement。** `runner.js:813-839` catch 後 emitError，繼續 dispatch；reload 的 2940 行仍 invalidate。故 extension 回報 cleanup 不完整，不等於 host 保留旧 registry 的工具存取權。
4. **ctx.signal 是當下 agent operation 的 signal，idle 可以是 undefined。** `types.d.ts:239-240`；`runner.js:662-665` 動態讀取；`agent-session.js:2755-2756` 提供 trust 與 agent.signal。工具第三參數也接受 signal，`tool-definition-wrapper.js:12` 原樣傳遞。Nested tool 的預設 signal 是呼叫工具的 signal（runner 696–719），不應把排程背景工作直接綁到父對話目前 turn 的 signal。
5. **工具可並行。** `pi-agent-core/dist/agent-loop.js:366-372` 有任一 sequential tool 才使同批 model tools sequential；nested calls 另由 `H/core/nested-tool-calls.js:118-150` 排他佇列處理。註冊七個 PTY tools 的 sequential 是有實際效果的，不是僅文件描述。
6. **agent_end 不等於最終完成。** `agent-session.js:1405-1450` 還會 retry、compact、queued continuation，最後才 emit settled；`types.d.ts:777-781` 與 `G/examples/extensions/notify.ts:51-56` 都採 settled 作「已不再自動繼續」通知。不能用 agent_end 清掉 persistent PTY 或每輪 browser，也不能在 notification-only settled 內要求 continuation。
7. **錯誤必須 throw 或帶 isError。** `pi-agent-core/dist/agent-loop.js:568-591` 的正常 return 僅以 `result.isError === true` 判錯；文字有「Error」或 `details.error` 不算失敗。`runner.js:900-955` 另允許 tool_result 改寫；僅改 content 而沒保留 structuredContent 會移除結構資料。

- **Parallel／signal：** 每次 fetch 149–195 有独立 controller/context，佇列 43–79 有界並刪取消 waiter；工具 signal 與 shutdown signal 合併（index 73、113）。REST search timeout／abort 在 `search.ts:39-55,88-97`。不需為獨立 web calls 強制 sequential。
- **Provider hooks：** `index.ts:132-150` 符合 runner 的 payload replacement 與 systemPromptOptions composition；衝突時先 ctx.abort 再 throw（136），對照 runner 1081–1090 的吞 hook error 行為是必要防護。Native OpenAI 沒註冊同名 REST function tool；不碰 OpenAI auth；virtual 不猜實際 provider。

### Schedule Prompt：factory 合格；安全與結果／UI 契約有確定缺陷

- `index.ts:22-40` factory 只註冊 getter tool／message renderer；scheduler/widget 真正於 session_start 44–64 建立，constructor scheduler 49–53 不開 timer；符合禁止 factory 資源規則。

## Critical (must fix)

### C1 — 未傳遞／未檢查 project trust，能自動執行未受信任專案排程，child 又回到 trusted 預設

- `modules/schedule-prompt/src/index.ts:44-58`：不檢查 `ctx.isProjectTrusted()` 即讀專案 settings/jobs 並 start。
- `modules/schedule-prompt/src/storage.ts:43-46,92-119` 直接讀 `.pi/schedule-prompts.json`；`scheduler.ts:63-80,393-406` 會接受 unbound enabled jobs。已全域啟用 extension 時，開啟含惡意 unbound job 的 cwd，即使父 host 拒絕 project trust，也仍可由 timer 自動注入 prompt 或啟動 model job。bare `.pi` 本身也不是 host protected-resource trigger（`G/docs/security.md:35-45`）。這不是只讓模型「可能被文字影響」，而是 extension 主動執行持久化未授權任務。
- `modules/schedule-prompt/src/subagent.ts:158-188,190-199`：loader 與 child settingsManager 都自行 create，沒有传入父 trust 值。Host `H/core/settings-manager.js:223-240` 的預設 `projectTrusted` 為 true；`resource-loader.js:243,352-365` 若沒有 resolveProjectTrust 就沿用該 trust；`sdk.js:69-82` 不替 supplied loader 自動重新做父 trust 決策。因此 child `extensions:true` 可載入父已拒絕的專案 extension/settings，含改變 PTY target/env 等能力。
- 影響：未批准的自動 model 請求／檔案或 shell 副作用；project trust 不是 sandbox，但其「不載入未批准 project executable resources」仍應保留。
- 修復方向：讀／啟用執行型專案 jobs 前有明確 trust/opt-in；child 使用同一份明確繼承 trust 的 SettingsManager，同時交給 loader 与 createAgentSession，不以 SDK trusted defaults 替代父決策。不得默默改真實 settings 或把 unbound job 改寫成其他 scope。
- 覆蓋缺口：subagent runtime tests 使用不存在 isProjectTrusted 的 mock context；沒有 untrusted parent + project jobs/settings/extensions 的離線 host probe。

### C2 — 開啟 extensions 的 in-process child 結束只 dispose，不送 session_shutdown；父 shutdown 也不等待 drain

- `modules/schedule-prompt/src/subagent.ts:203-205,258-264` bindExtensions 後，在 finally 僅 `session.dispose()`。
- 精確 host：`H/core/agent-session.js:992-1011` dispose 只 abort core work、invalidate、移除 listeners／core resources，**沒有 dispatch extension session_shutdown**；真正 host runtime 的 teardown 是 `agent-session-runtime.js:102-113,296-303` 額外 await emitSessionShutdownEvent 再 dispose。
- 因此 child 啟用 PTY 後留下的 persistent transport、Web browser／worker，以及其他 extension session_start timer/socket，其 shutdown handler 不會被調用。正常模型完成、prompt error、deadline admission skip 後都能漏掉 cleanup。Runner invalidation 只收 bus subscriptions（loader 141–150），不是擁有這些資源的替代清理。
- 父 `scheduler.ts:103-110` 只 abort/clear controllers；`index.ts:103-106` 不等待 in-flight child promises。取消發生在 loader.reload/create/bind 期間時，初始化可在父 shutdown 之後繼續；prompt admission guard 能防止模型開跑，但不能替已初始化 extension 收資源。abort requested 不等於 process/browser/socket 已退出。
- 修復方向：把 child shutdown dispatch 与 dispose 做成 idempotent、awaitable finally，追蹤 initializing/active promises，在父 teardown 等待終結；終結不成功不得釋放 ownership 或宣稱完全清理，保留 endAt 不取消已開始工作的既有語意。
- 覆蓋缺口：`test/stability-subagent.test.ts:23-46` 只 mock dispose；`deadline-subagent.test.ts:40,73-89` 只確認 skipped/dispose，沒有真實 extension shutdown receipt。真實 deadline fixture 72 行則在 **父** 主動 emit shutdown，沒有覆蓋 child。

- 保留錯誤 details 可採 `isError:true`，或 throw；若日後新增 outputSchema，資料型錯誤可以同時帶 structuredContent。現有 tool tests 多只断言 `details.error`（如 194–226），缺真實 event/nested/codemode isError 断言。

### W3 — 正常排程／shutdown log 直接寫 stdout，破壞 JSON/RPC framing

- `modules/schedule-prompt/src/scheduler.ts:403` 的 Executing log；`src/index.ts:85` 的 Auto-cleanup log，皆是 console.log，無 mode 分支。
- `G/docs/json.md:13-19` stdout 保留給 JSONL，診斷應 stderr；RPC 也使用 stdout 協定。到期 job 或 disabled cleanup 發生時，可混入非 JSON 行使 client decoder 失敗，並在 stdout 洩漏 job name/id。
- 修復：stderr 或既有模式感知的 UI/diagnostics，不修改工具 content。現有 tests 將 console.log spy 成空函式（如 checklist 25 行），真實 host fixture 的 wrapper 只解析最後一行 JSON（integration 16 行），會掩蓋 framing 損壞。

### W4 — Schedule 的 custom overlay／widget 未分 TUI 與 RPC，RPC 管理功能靜默失效

- `modules/schedule-prompt/src/index.ts:115-150` RPC 也提供 Jobs 選項，再調 ctx.ui.custom；`src/ui/cron-widget.ts:84-107` 一律傳 component factory，並可啟動無可見 widget 的 30s timer。
- Host `G/docs/rpc-extension-ui.md:14-25,129-144`：RPC custom 返回 undefined，widget 只支援 string[]；`H/modes/rpc/rpc-mode.js:123-133` 真正忽略 factory。
- 必須用 `ctx.mode === "tui"` 保護 overlay；RPC 用可支援的 dialogs/文字 widget 或清楚告知工具替代路徑。不要以 hasUI 代替 TUI 判斷，也不能因此停掉本應可 headless 運作的 scheduler。
- 補測：RPC client 選 Jobs 的回覆、非 TUI timer/resource count，以及真實 mode context；目前 cleanup test `stability-fixes.test.ts:80` 甚至用 `mode:'rpc', hasUI:false`，不是 host 的 RPC hasUI=true shape。

### W5 — PTY shutdown 失敗後 registry 雖保留，但 reload/replacement 仍使它不可重試

- `modules/pty-terminal/src/index.ts:198-200` 在 retained 時 throw；`src/pty-manager.ts:458-476` 把 transport 留在旧 manager，正常保留 ownership 的想法正確。
- Host `H/core/extensions/runner.js:827-835` catch handler error，`agent-session.js:2939-2940` 仍 invalidate；replacement runtime 同樣 `agent-session-runtime.js:106-112` 繼續 dispose。
- 结果：reload 後的新 manager 查不到舊 sessionId；仍存活的 transport/data listener 可留在 host，README 86 行「可重試 kill」對 manager 單獨呼叫成立，但不保證在 host reload 後可用。這是失敗分支缺陷，不是正常 cleanup 路徑全面壞掉。
- 修復方向：需 host-compatible 的存活資源 recovery/ownership 策略及可操作 PID/transport 診斷，或確保 teardown 收斂；單純 throw 不構成 reload cancellation。不得把 termination requested／registry retained 寫成成功。
- `tests/stability.test.ts:22-37` 直接再次 manager.shutdown，沒有 runner invalidate 與重新 factory 的 regression。

### W6 — Regex worker terminate 拒絕時仍歸還名額，可能失去仍活著 worker 的 ownership

- `modules/pty-terminal/src/matcher.ts:55-56` 為 `try await worker.terminate(); finally active--`；terminate rejected/throw、未實際 exit 時仍减 active，並且外層 manager 的 matches promise 已 settled，shutdown 不再追蹤該 worker。
- 與 README 10／86 行「終止確認後才歸還」不符；`pty-manager.ts:463` 的 Promise.allSettled 只等被拒絕的 promise，不是退出憑證。可重複造成容量計數偏低、孤立 regex threads；正常 terminate 成功不受影響。
- 修復：保留 worker ownership 到 exit 或 successful terminate，取消/計算结果與 cleanup receipt 分開。Web `extract.ts:56-74` 已有可參考的 fail-closed ownership 形狀。
- `tests/matcher.test.ts:68-90` 覆蓋延後 resolve，不覆蓋 terminate reject/throw + late exit。

### W7 — Child 以 aborted stop 結束仍可能回報 success

- `modules/schedule-prompt/src/subagent.ts:106-114,246-255` 只把 stopReason:error 或 timeout 判錯，未處理 stopReason:aborted。child 自己的 extension 呼叫 ctx.abort 時，scheduler controller 不一定 aborted；prompt 可正常 resolve，但 runner 返回 `{ok:true}`，scheduler 551–583 記 success、增加 runCount 並可能 notify。
- 父 stop 發生時的 controller-aborted suppress（scheduler 529–531）不能涵蓋 child 自行 abort。Host `agent-session.js:1405-1412` aborted run 仍走 settle；「已 settled」也不等於「成功完成」。
- 補測：fake finalized assistant aborted、真實離線 child extension abort，斷言 terminal state 不記 success。取消語意應明確與 skipped/provider-error 分開，不應把它當成功空文字。

## 待驗證事項（不列為已確定缺陷）

1. **Web cleanup failure／shared module pool 的 SDK 多 session 交互作用。** `fetch/service.ts:130-133` 吞 browser.close rejection，close 沒有一般總等待上限；`extract.ts` pool 是 module-level。是否在同一 SDK process 的兩個 extension runtime 共用 import instance、一个 close 誤殺另一個 extraction，需要真實 loader/cache probe；不能從單一 file state 就聲稱所有 reload 必定互相干擾。
2. **取消期間的 child 初始化與 provider hang。** subagent timeout 229 行在 reload/create/bind 之後才開始，初始化可能長期停住；active.abort 沒 await。確定缺少 drain 已列 C2，但各 provider/extension 最坏等待與進度需用 controlled fake SDK barriers，不呼叫真實 provider。
3. **Inline delivery acknowledgment。** 同步 sendUserMessage return 不代表 async delivery 已完成（host 2712–2719）；需 fake input handler handled/reject 与 queue hooks probe 確定 storage stats 的可保證語意。既有 README 已區分 delivered/not completed，不應改成 agent_end 就能完成追蹤。
4. **真實 WSL/SSH。** argv/quote/trust unit tests 不能證明 remote handshake、host config、退出/descendants cleanup；此次沒有連線，不宣稱三平台驗證通過。
5. **SSRF 限制。** 是否能在部署環境阻止所有 browser background/non-HTTP egress 應由 OS/network policy probe 驗證；現有逐回應 peer check 只能防 response use，盲 SSRF 仍是已知限制，不能據 public-address unit tests 宣稱安全沙箱。
