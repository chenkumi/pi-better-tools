## Critical (must fix)

### F1 — P1：Recall 允許任意同步 backtracking regex，可阻塞整個 Pi process

- **位置：** `modules/blackhole/src/core/search-entries.ts:65–70,90–91,263–273,538–602`；呼叫端 `modules/blackhole/src/tools/recall.ts:502–503,570–571`。
- **證據／清楚推論：** `safeRegex` 只捕捉編譯語法錯誤，並不判斷執行複雜度。`(a+)+$` 會直接編成 native RegExp，並由 `buildBM25Context` 對完整 document 執行 `.test()`；後續評分與 snippet 還會重複匹配。只需一則歷史 user 內容為 `"a".repeat(32) + "!"`，query 為 `(a+)+$`，即可構成巢狀量詞的失敗尾端 backtracking 輸入。這是未執行的最小 fixture／演算法推論，沒有量測秒數。
- **Impact：** 工具與命令共用此引擎，執行在宿主事件迴圈；即使結果上限 50 筆／48,000 chars，regex 已在限制前執行。Recall 的 `_signal` 沒被使用，主執行緒 regex 期間也無法处理 abort、TUI、shutdown 或背景工作 callback。Passive／空 credentials 不防止此問題。
- **最小修正：** 在 regex admission 使用保守且有測試的安全子集，不安全 pattern 明確拒絕或改 literal；若一定要保留完整 regex 語意，把整個匹配工作移入可終止且有 queue/input cap 的 worker。僅加 query 長度上限、try/catch 或 AbortSignal 不足。
- **測試建議：** 保留現有合法 regex／CJK／literal 語意；新增巢狀量詞、重疊 alternation、長失敗尾端案例。Admission 拒絕可作純單元；完整 regex 路徑需隔離 worker 並確認終止，不在測試主執行緒直接跑危險 pattern。
- **Confidence：** 高，靜態呼叫鏈直接可達；動態耗時尚未驗證。

## Warnings (should fix)

### F2 — P2：空／失敗的 active lineage 會擴張到全歷史，且空集合 cache key 與 scope:all 碰撞

- **位置：** `modules/blackhole/src/core/lineage.ts:13–24`、`core/load-messages.ts:25–35,109–115`；使用端 `tools/recall.ts:108–115,121–126`。
- **證據／清楚推論：** `getBranch()` 回 `[]` 或丟例外後，helper 會改取 `getEntries()` 的全部 IDs。Pi 1.1.0 的 `resetLeaf()` 明確把 leaf 設為 null（官方 `dist/core/session-manager.js:1172–1174`）；`getBranch()` 因此回空 path（1062–1072），但 `getEntries()` 仍保留所有歷史（1107–1109）。最小純 fixture：`getBranch:()=>[]`、`getEntries:()=>[{id:'old'}]`，helper 推導結果為 `Set{'old'}`，不是空 lineage。另外 cacheKey 只在 set.size > 0 時編入 IDs，所以 `undefined` 與 `new Set()` 有同一 key；即使只修 helper，先前 scope:all cache 仍可能被空 lineage 命中。
- **Impact：** 預設 lineage 的 recall、touched 及 e: inspection 可以暴露／引用已離開分支資料，與 `scope:'all'` 必須 explicit opt-in 的契約不符；不是跨使用者權限提升，但會造成 alternative-history/context 混入。Lookup failure 不應擴張權威。
- **最小修正：** 成功的空 branch 返回空 Set；branch lookup failure 返回明確 unavailable 或 fail-closed 空 Set，不使用全歷史 fallback。Cache key 必須區分 unfiltered 與 empty filtered scope（含空集合），不改既有 #N 編號。
- **測試建議：** 純單元覆蓋 empty/throwing branch 與非空 siblings；兩種順序測 `scope:all → empty lineage` 和反向，以現存 cache 測到隔離性。另用 Pi 1.1.0 inMemory manager 的 resetLeaf 核對真實 shape；持久化 recall probe 僅用隔離 HOME/auth/workspace、passive 與零外部呼叫。
- **Confidence：** 高，官方 host 與 consumer 的空分支行為可直接對照；未動態執行。

### F3 — P2：Generic history scan／cache 沒有 bytes 上限；分頁只限制輸出、不限制讀取與 retained memory

- **位置：** `modules/blackhole/src/core/session-lines.ts:63–94`、`core/load-messages.ts:21–23,98–117,128–129`、`core/search-entries.ts:563–596`；`tools/recall.ts:163–190,232–235`。
- **證據／清楚推論：** Scanner 的 64 KiB 是 read chunk，不是 line cap；遇到一條巨大或沒有 newline 的資料會持續累積 pending buffers，直到 EOF／newline 才 concat、UTF8 decode、JSON.parse。正常多筆 history 則被完整保留於 rawMessages/rendered/entryIds，expand:true 亦先載入全部才選 requested entry。LRU 限的是三個 cache records 而非總 bytes；TTL 只在 lookup 時惰性移除，不會在兩秒後自動釋放。Search 再構造完整 docs／排名／snippet，最後才切 50 hits／page。
- **Impact：** 長 session 或少量巨大 tool/file payload 可導致大量 transient allocation、GC、同步 I/O／CPU 停頓甚至 OOM；新 evidence scanner 的 32 MiB／64 KiB cap 不涵蓋這條共用 generic 路徑。Compaction 後 raw file 不縮小，因此正常使用會累積此風險。這是 README／recall docs 已揭露的 legacy 邊界，並非將 evidence patch 指控為 regression。
- **最小修正：** 給 generic scanner 明確 line/scan/retained-byte bounds，超額回 incomplete 並保持原始 #N 計數／穩定 ref；selected expansion 避免保留其他完整 payload。Cache 改總 byte budget，超大結果不缓存；不可只把三個 records 改成兩個。若要支援非常大歷史，另將 scan/search 移出 UI 主執行緒，不擴張本輪修正成新索引服務。
- **測試建議：** 最小隔離 fixture 覆蓋巨大單行、無 newline、多筆合法資料、超出 retained budget、只 expand 一筆與 scope filters；檢查 scanner buffer/retained counters、incomplete 與 #N 穩定，不只檢查輸出短於48,000。避免幾千案例全 suite或無界 stress。
- **Confidence：** 高，無界 allocation 明確；本輪未量測 heap peak／延遲。

### F4 — P2：Worker deadline 不涵蓋模型／auth resolution，永不 settle 的 resolver 可永久鎖住 consolidation

- **位置：** `modules/blackhole/src/om/runtime.ts:495–516,592–617,869–877`；`om/consolidation.ts:503–521,1167–1169,1263–1269`（reflector/dropper 同樣先 resolve 再 runWorkerAttempt）。
- **證據／清楚推論：** `getApiKeyAndHeaders()` 在 `runWorkerAttempt` 之前被 await，沒有 deadline／abort race；withResolvedAuthEndpoint 亦可 await getProviderAuth。候選 credential recheck（runtime.ts:501）甚至未傳 lifecycle signal。官方 Pi 1.1.0 ModelRegistry（`dist/core/model-registry.js:34–36,102–103`）把它們轉給 getAuth，該 facade 不接受 signal；不能假定多傳一個 signal 就會生效。最小 fake registry 可讓其中一個方法回 `new Promise(()=>{})`：程式會停在 resolution，永遠不進 worker timer。`consolidationInFlight` 直到 tracked task 的 finally 才清除，後續 launch gate 會持續拒絕。
- **Impact：** 即使設定正值 workerAttemptTimeoutMs，auth/provider resolver 停滯仍讓 observer/reflector/dropper 失去進度；branch epoch／dispose 可以撤銷 generation，但不能使這個 await 自行結束，舊 context/promise 可能持續被保留。未宣稱一般內建 provider 必然掛住，也未宣稱會造成 shutdown process hang。
- **最小修正：** 在 BH own resolution 邊界加 bounded elapsed deadline 與 lifecycle abort race，observe late rejection，late success 不可產生 side effect／提交；有支持的 API 才傳 cancellation。可沿用現有 attempt deadline設定的正值語意或明確 resolution bound，不改 Pi 主線 auth 或真實 credentials。
- **測試建議：** fake registry + deferred promise + event barrier／fake clock，分別卡住 candidate auth、session auth、endpoint、candidate recheck，驗證 deadline/branch revoke/dispose 能 settle BH tracked work、清 gate，late resolve 不 append 或啟動 model。這些全部是純 mock，不需要實際 provider/background model，也不需要固定 sleep。
- **Confidence：** 中高，hang 條件是明確模擬／推論；實際 auth backend 停滯未驗證。

### F5 — P2：根 runner 的 Windows cleanup 在 root close 後可能提前殺死還在回收子孫的 killer

- **位置：** `modules/file-tools/scripts/test-process.mjs:20–24,25–35,41–52,69–80`；根使用點 `scripts/run-checks.mjs:90–99`、`scripts/blackhole-tests.mjs:24–30`、`scripts/package-smoke.mjs:304–307`。
- **證據／清楚推論：** `completed` 只等被測 child 的 `close`。停止時另啟 taskkill／PowerShell descendant cleaner；一旦 root/pipes 先 close，就進 finally，清除 terminationDeadline，並對任何仍 running 的 killer 呼叫 kill/unref。`finished=true` 亦使晚到的 taskkill failure 不再啟動 fallback（recoverWindowsDescendants 首行）。因此事件序列「stop → cleaner 尚未完成 → root close → finally」會主動截斷 cleanup，而不等 killer 的 exit／結果；stdio ignored 的 descendants 不必持有 root pipe。這是有条件的事件排序推論，不是本輪已重現的 Windows orphan，也不是聲稱 taskkill 必然以 root-first 順序執行。
- **Impact：** 失敗 stage 可以在 descendants 尚存、檔案／lock 未釋放時返回，外層立刻 rm(temp) 或啟動下一 stage，造成 EBUSY／殘留 worker／後續測試互相污染。現存 `test-tooling.test.mjs:22–29` 覆蓋 live root／output cap，不足以證明此 cleanup ordering；不能拿 pipe close 當整棵 tree cleanup 確認。
- **最小修正：** child close 與 killer completion 分開追蹤；stop 路徑保留 bounded cleanup grace，root 先 close 不能殺掉正常回收中的 killer或禁用已需要的 fallback。到 grace 才停止 killer，明確回報 cleanup unconfirmed；仍不得宣稱所有 remote/detached descendants 已停止。
- **測試建議：** 注入 cleanup-spawn／killer event source，純單元以事件 barrier 控制 root-close-before-killer-exit、taskkill非零及 PowerShell recovery ordering，確認 runner 不提前 dispose cleaner。避免新增靠固定 sleep／idle watchdog 的 timeout 測試；必要 Windows tree probe再另列最小隔離整合與實際 descendants退出／暫存資源釋放證據。
- **Confidence：** 中，控制流程確定，但對實際 Windows tree 的影響尚未動態確認。
