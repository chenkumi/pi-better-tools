## Critical (must fix)

### F1 — P1：POSIX 回收已退出 PTY，仍向可被重用的 PID 發送 SIGHUP

- **位置**：`modules/pty-terminal/src/pty-manager.ts:212–215`；觸發點 `218–228`（retention／滿載回收）、`448–470`（explicit kill／shutdown）。依賴證據：`node_modules/node-pty/lib/unixTerminal.js:228–233`。
- **Confirmed-static**：`dispose()` 刪除 session 後無條件呼叫 `pty.kill()`；POSIX 分支傳 `SIGHUP`。已安裝 UnixTerminal 的 `kill()` 直接執行 `process.kill(this.pid, signal || 'SIGHUP')`，沒有 exited／PID identity 檢查，亦不是只釋放 native handles。`kill()` 對 `state === 'exited'` 的 session 跳過前段終止要求，最後仍進入 `dispose()`。
- **交錯**：PTY A 真正退出 → manager 保留 A 的 id／pid 與输出 → OS 將同一 PID 分配給 B → `pty_kill(A)`，或後續 `pty_list` 的 retention 回收，或滿載 `pty_spawn` eviction／shutdown → 對 B 發 SIGHUP。
- **Impact（conditional）**：若 PID 被重用且宿主有權送訊號，可誤終止與 PTY 無關的本機程序。十分鐘 exited retention 拉長風險窗口。這不是「遠端 tree cleanup 未保證」的既有限制，而是對錯誤本機 process identity 執行 destructive action。
- **最小修正**：已确认 exited 的 POSIX session 僅釋放 JS ownership／listeners，不再呼叫 signal-based `kill()`；將 Windows backend 的 handle-release 操作單獨保留。若 POSIX 尚有必需資源處理，使用不會 signal PID 的已核對清理 API，不以 `kill()` 充當 generic dispose。
- **最小離線驗證設計（未執行）**：注入 fake PTY，emit exit，然後分別 explicit kill、retention list、滿載 spawn、shutdown；POSIX 對 exited handle 的 kill 次數應為零。Windows handle-release 另作平台分支斷言，不需要製造真實 PID 重用。
- **既有測試缺口**：`tests/session-lifecycle.test.ts:34–43` 的 fake `kill()` 是空方法；`88–100`／`162–175` 驗證回收成功，卻未斷言 exited session 不再被送訊號。

### F2 — P2：once 成功回呼缺少 timer／job generation fence，會清掉同步重排的新排程

- **位置**：`modules/schedule-prompt/src/scheduler.ts:277–292`；對照 `174–180`、`301–304`、`480–488`。
- **Confirmed-static**：once callback 刪除舊 timer 後 `fire(job).then(...)`；成功分支無條件 `updateJob(id, { enabled:false })` 並 `unscheduleJob(id)`。相反地，false/skipped 分支在 `303` 檢查是否已裝 replacement timer。成功分支沒有相同保護，更沒有 job version／owner admission token。
- **可決定交錯**：once A 進入 inline run → `480–485` 記錄 runCount → `487` 同步 `cron:change` listener 看見完成並透過 storage＋`scheduler.updateJob(A, updated)` 將 A 改為未來 once 或 recurring → listener 返回、`executeJob` 返回 true → `fire` promise 的成功 `.then` 在 `285–287` 關閉 A 並清除剛新增的 timer。無須另一個 timer 恰好搶到 event loop；同步 change listener 就能構成此重入。
- **Impact**：使用者／extension 的有效 reschedule 被舊 run 覆寫，之後不會觸發；如 job 在同一 ID 下被重新綁定，成功分支也沒有重新檢查 session ownership。實際使用情境的頻率未測量。
- **最小修正**：每個 timer 持有 generation token，callback 與成功／失敗 continuation 都核對同一 token；新 update/remove/stop 撤銷舊 token。成功 auto-disable 應在 locked mutation 中核對原 once generation／session，而非只以 id 寫入。單加 `intervals.has(id)` 可擋部分案例，但擋不住 cron replacement，不足作完整修正。
- **最小驗證設計（未執行）**：fake timers＋同步 `cron:change` listener，當 runCount 第一次增長時重排同 ID；flush microtasks 後新 job 應維持 enabled，新 timer 不應被取消。再驗 once→cron replacement、stop 與 session rebind。
- **證據等級**：交錯與覆寫路徑 confirmed-static；沒有 real-host 重現，不宣稱已執行 regression。

### F3 — P2：全檔 synchronous storage 讓啟動／cleanup 呈 O(N·B)，固定平均 job 大小時為 O(N²)

- **位置**：`modules/schedule-prompt/src/scheduler.ts:75–84,255`；`src/storage.ts:92–119,273–283`；`src/index.ts:107–115`。Deadline 擴大成本的位置：`scheduler.ts:369–385`。
- **Confirmed-static／algorithmic evidence**：`getJob()` 每次呼叫都 `readFileSync`、JSON.parse、filter 全部 store，再線性 find。啟動 N 個 enabled、無 deadline、非 stale-running 的 interval jobs，`start()` 一次 getAllJobs，加每個 `scheduleJob` 在 `255` 一次 getJob，總 **N+1 次全檔同步讀取與 parse**。设全檔 B bytes，讀取／解析工作量至少 O(N·B)；job 平均大小固定則 B=Θ(N)，因此 Θ(N²)。
- **Cleanup**：disabled job 逐筆 `removeJob()`，每筆重新完整 read/filter/stringify/write；全為 disabled 的 N 筆清理會處理 N、N−1、…、1 筆資料，仍為 Θ(N²) 累積工作。每個 enabled deadline job 另有最多每 60 秒一次的全檔 getJob，產生 O(N·B) 的週期性 parse 波峰。
- **具體規模證據（推導、非 benchmark）**：N=1000、B=1 MiB 的上述 startup 分支，累積約 1001 MiB 全檔 read/parse 输入；不是同时占用 1001 MiB，也不是宣稱實測一秒耗時。所有工作在宿主 event loop synchronous 執行，沒有 job 數量／檔案大小 cap 去限制放大。
- **Impact**：較大 persisted store 在 startup／reload／shutdown 時造成 UI、stream consumption、Monitor expiry、PTY waits 的共同停滯；deadline timer 群也可能製造重複波峰。實際延遲取決於 filesystem／CPU，未測量。
- **最小修正**：startup 共用一次已讀 snapshot（傳入 scheduleJob），但真正 trigger admission 仍 fresh-read，不削弱 deadline/trust 安全核對；cleanup 合併成一次 locked read/filter/write，保留 session predicate。Deadline read 可按一輪 timer coalesce 共用 snapshot，必要 mutation 仍鎖內重讀。
- **最小驗證設計（未執行）**：隔離 store＋read/write/parse counter，N=10、100、1000，驗 startup read count 接近常數與 cleanup 一次 mutation；不使用 fixed sleep、真實 model 或真實排程資料。

### F4 — P2：persisted interval 缺少 schedule 一致性／最小間隔檢查，可變成 1ms 觸發熱點

- **位置**：`modules/schedule-prompt/src/storage.ts:19–29`；`src/scheduler.ts:218–225`；對照 tool 正常解析 `738–752,767–782`。
- **Confirmed-static**：load 只要求 intervalMs finite 且 >0；scheduleJob 只檢查 <=MAX_TIMER_MS。故 `{type:'interval', schedule:'1h', intervalMs:1, enabled:true, ...其餘有效欄位}` 是可接受 persisted job，會 `setInterval(..., 1)`。正常工具解析的最短正值是 `1s`，但 persisted 欄位繞過該語意。這不是 long interval 超過 MAX_TIMER_MS 的已修正 clamp 問題。
- **交錯**：合法 shape 的手編／舊版本 store 帶不一致 intervalMs → trusted startup → 建立 1ms interval；inline branch 每次 tick執行 fresh read、status write、marker、follow-up、stats write。model branch 雖有四個 active slots，也仍重複讀 store／skip logging。
- **Impact**：錯誤 persisted 數值可將聲稱 hourly 的工作變成接近毫秒級 timer 壓力，放大同步 I/O 與消息佇列。1ms 是設定的 timer delay，不代表實測 1000 次／秒；實際吞吐受 I/O／event-loop 限制。本項不把文件明訂的 inline queue 無背壓本身另報 mustfix。
- **最小修正**：load/admission 以 validateSchedule 重新 derive intervalMs，拒絕不一致或不符合支援最小間隔／整數／最大值的 persisted interval，並清楚診斷；不要默默把錯誤 hourly 配置改成高頻排程。亦可忽略 cached intervalMs，統一從 schedule 推導。
- **最小驗證設計（未執行）**：shape fixture intervalMs=1／0.5／與 schedule 不符，fake timer recorder 確認不產生短 timer；正常 1s／1h 保留。
