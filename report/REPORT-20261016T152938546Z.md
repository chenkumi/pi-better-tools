## Critical (must fix)

### R-HTTP-01 — HTTP 101 關閉連線後，headers promise 永不 settle
- **位置：** `modules/web-tools/src/fetch/http.ts:94–98`；放大影響的位置為 `service.ts:234`、`390–394`、`403–413`。
- **狀態／優先度：** 靜態確認，P1；尚未執行本地 socket 重現。
- **觸發：** 缺 browser 的 HTTP fallback 遇到回覆 `101 Switching Protocols`、`Connection: Upgrade`、`Upgrade: websocket` 的公開站點。它不需要成功完成 WebSocket 握手，也不涉及私網或 DNS rebinding。
- **缺陷：** 94–98 行只以 request 的 `response`／`error` 結束等待，沒有 headers-before-close 的拒絕路徑，也沒有獨立 signal settlement。Node 22.22.2 對 101 走 upgrade 分支，不 emit 普通 `response`；沒有 upgrade listener 時銷毀 socket。此時 `req.res` 已設定，socket close 分支只 emit request `close`，不 emit request `error`；之後對已 destroyed request 再 destroy 直接返回。因此此 promise 可以永久 pending，外層 finally 根本無法執行。此結論由受支援最低 Node 版本的原始碼確認，而非假設「所有 socket close 都會 error」。citeturn0view0
- **影響：** 總 deadline／手動取消只 abort controller，無法救回已關閉 request 的 pending promise；queue permit 與 operation cleanup 記錄不釋放。重複至 maxConcurrency 即耗盡抓取容量；新增的 `close()` 等待 `operationCleanup` 又會讓 session shutdown／reload 卡住。
- **最小修正：** headers 等待必須覆蓋「未收到 response 即 close」並 reject；讓 AbortSignal 能直接 settle 等待，不完全依賴 request 再 emit error。若顯式處理 `upgrade`，必須拒絕該協定並銷毀移交的 socket。保留一次 settlement、listener cleanup，以及原 finally 等待 request close 的規則。
- **最小回歸：** 本地 raw TCP／HTTP fixture 回傳上述 101，確認 fetch 直接失敗而非等待 timeout；再檢查取消、`service.close()` 可完成、operation 集合清空、queue 可再次取得。以事件 barrier 驗證，不新增靠固定 sleep 的 timeout 測試。現有 `tests/integration/static-http.test.ts:49–95` 覆蓋一般 response／redirect／body cancellation，沒有 101 分支。
- **可重查的版本來源：** `https://raw.githubusercontent.com/nodejs/node/v22.22.2/lib/_http_client.js`，`parserOnIncomingClient`、`socketOnData`、`socketCloseListener`、`ClientRequest.prototype.destroy`。

## Warnings (should fix)

### R-SETUP-01 — 安裝子程序切換 cwd，讓相對 browser cache 與 doctor／runtime 不一致
- **位置：** `setup/core.mjs:24`；對照同檔 `61–66` 與 `88`。
- **狀態／優先度：** 靜態確認，P2；未實際下載瀏覽器。
- **觸發：** 從非套件目錄 A 直接呼叫此 CLI，設定 `PLAYWRIGHT_BROWSERS_PATH=./browser-cache`，且沒有 `INIT_CWD`。
- **證據：** doctor 在原 cwd A 載入 Playwright；browserInvocation 卻讓 installer cwd 變成 packageRoot B，原樣傳入環境。Playwright 1.64.1 的 registry 初始化對相對 cache 使用 `INIT_CWD || process.cwd()` 轉絕對路徑，因此 doctor／同目錄 Pi 取 A/browser-cache，安裝則落到 B/browser-cache。相同環境與相同安裝實例仍無法保證安裝後可用。citeturn2view0
- **影響：** 安裝可成功但執行期仍缺 browser、持續 fallback 或 selector 失敗；唯讀 packageRoot 也可能讓原本可寫的相對 cache 安裝變成權限失敗。
- **最小修正：** browser 子程序保持呼叫者 cwd（Playwright CLI 已是依本實例解析的絕對路徑，不需靠 cwd 找依賴）；或在切換 cwd 前以 Playwright 相同規則將有效 cache 值轉成絕對路徑，保留 `0` 特殊語意，不修改全域環境／設定。優先選前者以縮小修改。
- **最小回歸：** 任意 cwd、相對 cache、無 INIT_CWD 下，對照 doctor 的 executable 與 installer 子程序解析到的目錄；可用唯讀 registry／stub CLI probe，毋須真實安裝。現有 `modules/pty-terminal/tests/setup.integration.test.mjs:16–25` 及 `scripts/package-smoke.mjs:143` 都使用絕對 cache，無法捕捉此差異。
- **可重查的版本來源：** `https://raw.githubusercontent.com/microsoft/playwright/v1.64.1/packages/playwright-core/src/server/registry/index.ts`，registryDirectory 的相對路徑解析。
