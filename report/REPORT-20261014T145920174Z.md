## Warnings (should fix)

### F1 — P2：背景 submitted 容量釋放早於實際晚到 I/O 清理

- **目前位置：** `modules/subagents/extensions/subagent/background.ts:438–439`；對應 `index.ts:1088–1101,1120–1122,1588–1589`。
- **觸發流程：** 背景 task 已開始，native／transcript 寫入或 finalization 的實際 promise 尚未完成；取消或 IoGate deadline 讓 runner 停止等待。`runSingleAgentUnlimited` 建立等待 actual I/O／writer／child 的 `lateCleanup`、`ownedSettlement`，但仍回傳失敗／取消 result。背景 run 隨 result 返回，`BackgroundJobs.submit` 的 finally 立即扣除 submittedTasks；產品背景路徑沒有等待 ownedSettlement，該 callback 只是可選觀察 seam。此時 managed writer lock 可以仍被正確保留。
- **穩定性／效能影響：** 新批次可再受理，32 submitted 不再涵蓋先前尚未結束的 owned I/O。反覆受阻／取消可累積超出 admission 預算的檔案操作、handle 與晚到清理 closure；若 child 已 close，active-child permit 也不能限制這些純 I/O 遺留工作。這是資源容量記帳問題，**不是重報已修正的 premature writer-lock release**。
- **修正建議：** 將 receipt settlement 與資源 admission release 分離；背景 runner 將實際 owned settlement barrier 交回 admission owner，名額在 barrier 完成後才釋放。已確認 writer close 拒絕等 cleanup-unsafe 情況需明確保留／標示容量，不因 receipt terminal 推定 cleanup 完成；保留立即回報失敗與既有 bounded shutdown。
- **驗證證據：** `IoGate.run`（io-gate.ts:37–54）分離 waiting rejection 與 actual pending；index.ts:1088–1101 明確 detached 等待晚到操作；1120–1122 只通知 observer；background.ts:439 無實際 barrier 判定。README:86–87 宣告取消直到清理完成才釋放容量。既有 `review-background.test.ts:9–28` 只驗證 prepare 階段的 retained capacity，沒有覆蓋已接受 runner 的晚到 I/O。
- **信心／未執行：** 靜態控制流程證據高；未量測累积資源數，未執行 runner I/O 測試或新增重現。建議以 deferred write barrier＋直接取消交錯，断言新 admission 仍拒絕，釋放 barrier 後容量才恢復；不使用 sleep。

### F2 — P2：宣稱 process-wide 的容量狀態只存在單一模組載入實例

- **目前位置：** `modules/subagents/extensions/subagent/index.ts:98–99`、`background.ts:54–57`、`rpc.ts:7`；舊 runtime 有界退出為 `background.ts:460–469`。
- **觸發流程：** 舊 extension generation 在 shutdown 預算結束後仍有未 close child、pending managed prepare／I/O 或未 terminal query；宿主重新載入 extension 模組。新載入實例建立新的 8-permit Semaphore、submittedTasks=0、activeQueries=0；舊 closure 仍持有旧實例的資源與計數。新 generation 可以在舊工作未確認結束時再次取得完整預算。不同 module evaluation 的 SDK host 亦有同類問題。
- **穩定性／效能影響：** 8 active child、32 submitted、8 query 的整個 process 合計上限可能突破；重複 reload 可放大資源占用及 provider work。保留每個舊實例的 permit 不等於新實例共用它。
- **修正建議：** 用版本化 `Symbol.for`／globalThis 保存真正 process-wide admission state，與既有 `message-reservation.ts:5–7`、`session-store.ts:245–252` 的跨 reload ownership registry 相同思路；一次性 releaser 必須繼續回到同一共享池，不重置仍 owned 的計數。避免把 job registry 或通知權限跨 generation 復活。
- **驗證證據：** 三個容量狀態均為 module-local。已查本機官方 loader：`C:/GitHub/pi/packages/coding-agent/src/core/extensions/loader.ts:576–581` 使用 `moduleCache:false`；`src/core/resource-loader.ts:512–514` 在 reload 清 cache。安裝版 loader.js:477–481 亦相同。既有 process-global lock／reservation 設計佐證本專案已處理其他跨載入 ownership，而容量未採同樣策略。
- **信心／不確定／未執行：** 多模組實例不共用容量是直接程式事實；實際 `/reload` 重現與 **Pi 1.2.0 loader 是否維持此合約尚未驗證**，本機證據為 1.1.0。未跑 host/reload integration。應以兩個獨立 loader evaluation＋deferred resource barrier 驗證共享上限，不以固定等待探測。

### F3 — P2：ready query 把非互動 UI 通知一律視為 fatal startup interaction

- **目前位置：** `modules/subagents/extensions/subagent/ready-query.ts:112–119`，尤其 116。
- **觸發流程：** 原 session 已 ready，建立 query worker；正常載入的受信任 extension 在 session_start 或後續 hook 呼叫 `ctx.ui.notify`、`setStatus`、`setWidget` 等 fire-and-forget API。RPC host 輸出 `extension_ui_request`，query worker 不檢查 method 就拋 `QUERY_STARTUP_INTERACTION`，停止 gate、要求 terminate，最後回 failed，即使配置／guard 正確，或模型答案已返回亦可能被移除。
- **穩定性／效能影響：** 無需用戶互動的 extension 也能令 ready query 失敗；浪費 worker startup／清理成本，若發生於回答後還可能浪費 query 模型成本。錯誤文字錯稱 child 需要 interactive configuration。
- **修正建議：** 依 method 分類：dialog 方法及未知需要回應的方法保持 fail closed；明確 fire-and-forget 方法只 bounded drain／忽略，不放寬 guard、禁止主線或 provider admission fence。
- **驗證證據：** 本機官方 `docs/rpc-extension-ui.md:5–8,97–144` 明確區分 dialog 與 fire-and-forget。`C:/GitHub/pi/packages/coding-agent/src/modes/rpc/rpc-mode.ts:152–176`、安裝版 rpc-mode.js:87–109 證明 notify/setStatus 使用相同 event type，且無回應需求。query worker 的判斷不含任何 method 白名單。現有 ready-query fault fixture 與 retention 測試涵蓋 malformed/mainline/capacity，未涵蓋非互動 UI record。
- **信心／不確定／未執行：** 對所查本機合約高信心；**1.2.0 合約未動態核對**，也未證明目前所有使用者 extension 都會發此事件。未執行 ready-query host 測試。建議以有效 get_state＋notify/setStatus record 的事件驅動 fixture，確認 query 仍受理；dialog record 則仍拒絕。

### F4 — P2：每回合 catalog 同步無界讀取全部 agent 定義，顯示上限不限制工作量

- **目前位置：** `modules/subagents/extensions/subagent/agents.ts:73–85,93,141–146`；呼叫端 `index.ts:1745–1752`，顯示截斷 `index.ts:254–263`。
- **觸發流程：** subagent 已選取，進入 before_agent_start；user agents 或已信任 project agents 目錄有大量 `.md`、單一很大的 `.md`，或 `.md` symlink 指向極大／非 regular target。discovery 先 `readdirSync` 所有 entries，對每個候選 `readFileSync` 全檔＋YAML parse；可信專案模式又分別 discovery user/project/both，重複讀取相同定義。直到全部讀完才 slice 顯示 64 項。即使本回合沒有派遣子代理仍執行。
- **穩定性／效能影響：** parent event loop 在 provider request 前被同步 I/O／parse 阻塞；abort 與其他 child 的 stream/IPC callback 也無法及時處理。大檔可產生無界記憶體配置；POSIX symlink 指向 FIFO／特殊檔案更可能同步卡住。dispatch snapshot 的 256 KiB bounded read 發生更晚，不能保護 catalog hook。後者特殊檔案案例是平台條件，並非聲稱 Windows 一定存在同類 FIFO。
- **修正建議：** bounded 且確認 regular target 的讀取，定義檔大小沿用既有 metadata policy；避免先無界 read 再判限。catalog 使用有界 discovery 預算／明示 omitted，且一次取得可供三種 scope 合成的定義；必要 cache 以來源身份及變更驗證失效，不弱化 dispatch/resume 的 config fingerprint/trust 檢查。
- **驗證證據：** agents.ts:80 明確接受 symlink，85 無 size／target 類型／讀取上限；catalog 的 64 項及 description cap 在完整 discovery 後才生效。對照 `session-store.ts:90–103` 已有 regular file＋256 KiB bounded read。`agent-catalog.test.ts` 只用少量小檔並驗證 prompt composition，未覆盖工作量限制。
- **信心／未執行：** 同步無界讀取與三次 discovery 為直接程式證據；未做 latency／memory benchmark，未建立特殊檔案或大型 fixture。可用 mock read/open 記錄工作量與 bounded buffer 檢查，不需寫大檔、模型或 sleep。
