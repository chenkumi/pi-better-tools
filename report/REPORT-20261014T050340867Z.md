### G3-001：Monitor 的牆鐘同時承擔 rolling window／progress elapsed 計算

- 位置／根因候選：`modules/monitor/src/core.ts:6` 的 `realClock.now = Date.now`；`:100–101` rolling timestamps、`:124` progress 排程、`:172` lastSubmit、`:197` elapsedMs；WS startup 使用同一 clock 於 `modules/monitor/src/sources.ts:29–32,36`。
- 狀態：待驗證；驗證结果：未執行；暫定嚴重度 **Medium**（時間語意／通知可用性，不是已觀察到的 TTL 失效）。
- 觸發條件：同一 owner 已有成功送出的 batch，之後系統牆鐘向後跳，再出現待送事件；或 rolling window 中發生前／後跳。不能修改使用者系統時間來驗證。
- 預期：30 秒節流與 60 秒 rolling window 以實際經過時間治理；時間校正不應額外延後事件或把正常低速來源判成超速。observedAt 等日曆時間仍可使用牆鐘。
- 靜態推導（不是實際結果）：若 lastSubmit 為 T，下一次 schedule 時 now 為 T−600000，`:124` 算出 630000 ms，而不是剩餘正常節流時間。這可能使 pending 通知延後，終結 receipts 仍佔用 retained capacity。`:100` 的未来 timestamp 也可能超過正常 rolling 期間仍被保留。
- 影響：受時間調整 session 的通知延遲、elapsed 顯示異常或 rate 判定偏差；未量測發生頻率及 Windows 實際 timer 行為。
- 反證／既有防護：duration 的終止 timer 在 `:56` 以相對 `setTimeout` 排程；不能由 Date.now 的疑點推論來源一定超過 duration。已讀 tests 使用 FakeClock／ManualClock，但排程與 now 同步前進，沒有分離 wall-clock 跳動與 timer elapsed。
- 缺少證據：真實 Pi 1.2.0 註冊工具／實際來源／sendMessage 路徑，控制 now 偏移但保留實際相對 timers，三次一致的 submission 間隔及 receipt 證據。
- 命令／log／exit／樣本：候選隔離 runner 尚未建立，無已執行命令、log 或 exit；完成樣本 0，不能記成 0/3 未命中。
- 清理：本次未建立 timers 或 sources；後續須 restore 時鐘替身、stop Monitor、await source close、shutdown/dispose 隔離 session，保留 unknown descendants 語意。

### G3-002：Web browser 關閉失敗被吞掉，可能遺失失敗／殘留資源證據

- 位置／根因候選：`modules/web-tools/src/fetch/service.ts:130–133` 的 `browser.close().catch(() => {})`；idle 在 `:139–145` 先清 browser reference；shutdown 在 `:354–359` 先清 reference、等待被轉成成功的 closing promise。launch 與 shutdown 相撞的直接 close 在 `:117,122–125` 也沒有另留 browser ownership evidence。
- 狀態：待驗證；驗證结果：未執行；暫定嚴重度 **Medium**（清理證據／資源生命周期）；真實 process 殘留未確認。
- 觸發條件：browser.close 拒絕且 browser/process 實際仍連線或存活；另需驗證 browser.close 長時間 pending 的情況。正常關閉不觸發此假說。
- 預期：清理失敗能被辨識，不因 promise 被 resolve 就視為已清理；實際仍活著的資源仍有 owner 或可操作的殘留證據，且不阻礙其它清理責任。
- 靜態推導（不是實際結果）：close 的 rejection 被忽略後，`:131` finally 將 closing promise 移出 set，`:362` close promise 可正常返回。若 browser 確實未關閉，已清掉的 browser reference 不提供再次處理路徑。沒有量測 process 是否因此殘留。
- 影響：使用者／reload 無從辨識一次 browser 清理失敗；若真實 browser 仍存活，可能積累 process／contexts。可能 hung 的 shutdown 尚未取得真實 Playwright/Windows 證據。
- 反證／既有防護：Playwright close 的某些錯誤可能只表示 transport／browser 已實際關閉，這種結果不能算 leak。現有整合測試 `modules/web-tools/tests/integration/fetch.test.ts:173–179,224–245` 明確檢查正常 close/disconnect，pending launch 也有清理路徑。worker shutdown 是獨立啟動的，不應聲稱 browser 問題必然阻止 worker termination。
- 缺少證據：實際 Chromium、固定 Playwright 1.63.0、Windows 的受控故障產品路徑；真實 browser disconnect／PID exit 和 service ownership 對照，三次一致結果。只讓假的 close() reject 不足以證明 process leak。
- 命令／log／exit／樣本：候選隔離 runner 尚未建立，無已執行命令、log 或 exit；完成樣本 0。
- 清理：本次未啟動 browser 或 workers；後續若真實 browser 沒退出，只可清理由 runner 自建並記錄的 PID，不能掃殺使用者 Chrome，也不能把 cancel/close 請求當 PID exit。
