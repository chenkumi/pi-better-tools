## Critical (must fix)

以下是合併前必修的 UI 正確性問題（P2），不是聲稱存在遠端執行或權限提升漏洞。

- **R1 / P2 — `modules/shell-tools/src/background-panel.ts:131–134`：overlay render 的 disposed-owner getter 沒有 fail-closed 防護。**
  - overlay 的 source 先直接呼叫 `ctx.sessionManager.getSessionId()`，再進入會捕捉 disposed getter 的 `validEntries()`。如果 More 已開啟後 getter 開始拋錯，`JobsOverlay.render()` 在 `job-view.ts:110` 呼叫 source 時便拋出，未能刪除 entry 或關閉 overlay。
  - `openMore()` 外層 try/catch 僅包住 custom 的建立／等待，不是日後每次 host render 的例外邊界；`refreshOverlay()` 也只要求 render。因此不能靠這些 catch 保證解除 overlay 或還原 editor focus。若工作安靜且沒有新的 producer callback，沒有下一次 widget.refresh() 可幫忙清理。
  - 最小核對情境：開 More → 將 owner getter 改為 throwing → 呼叫 overlay.render()；依目前程式會 throw，而不是安全 close。現有 disposed 測試 `background-panel.test.ts:110–120` 只經 panel.update，沒有覆盖這條 overlay-render 路徑。
  - 修正方向：在 overlay 的 owner/source 邊界捕捉 disposed getter，作 lease-owned、冪等 close，回傳空投影，不讓 getter 例外逃進 TUI；測試應核對 custom 結束、舊 component 失效與 host focus 還原。不改 registry 的 owner/cwd/epoch 或工作取消政策。

- **R2 / P2 — `modules/subagents/extensions/subagent/background.ts:186`：舊 progress 的 `usageReported:false` 會遮蔽後來已確認的 final usage。**
  - 現在只要 progress 存在且 usageReported 是 false，就直接取 undefined，即使 `task.result.usage` 已有有效且非零的 reported total。final result 優先權只在舊 progress 已為 true 的分支成立。
  - 不只是人工 callback 的情境：`index.ts:540–542` 在 canonical tool-result log write 前已把 source usage 加入 currentResult 並設 usageReported；若該 write 拒絕，`index.ts:826` 後面的 requestProgressUpdate 不會執行。最終 result 可以保留真實已觀察成本，但 registry 仍持有更早的 false progress，UI 顯示 unknown，隱藏已知成本。
  - 靜態最小情境：progress(false) → finish({usage: 有效正數}, failed/completed) → panelJobs；現在投影仍沒有 usage。既有 `panel-usage.test.ts:25–29` 只測 true progress 後的 final 優先權，未覆蓋 false → final-positive。
  - 修正方向：讓 final 的「實際有 reported evidence」在 private presentation 層具有優先權；保留初始化 emptyUsage 與實際 reported zero 的區別。不可簡單把所有 final zero 當 reported，也不需要改 public receipt/schema 或 accounting。增加 false→已知 final usage、真正 reported zero、初始化未回報 zero 三種回歸。

- **R3 / P2 — `modules/subagents/extensions/subagent/background.ts:184–198`：ready-query detail 繞過既有 authoritative/provisional 仲裁，可能把 worker fault 顯示成 completed 且不提示 cleanup pending。**
  - value 的 usage 會採 `readonlyQueryNotice`，但 detail 的 query status/cleanup 仍迭代原始 `handle.snapshot().queries`。notice 是 failed/cleanupPending:true、RPC snapshot 是 completed/cleanupPending:false 時，More detail 仍輸出 `Independent query … completed`，沒有 cleanup pending。
  - 這個交錯已由既有 `background.test.ts:54–68` 建立：worker failure 必須 outrank completed RPC snapshot。`view()` 在 `background.ts:230–246` 已實作 notice 優先、未 settlement 時強制 cleanupPending、completed→accepted，UI 卻沒有相同純投影仲裁。
  - 正常 ready-query 模型 completion、但 original lease 尚未釋放時也有同類問題：新投影讀 raw snapshot，不補 provisional cleanup。header 的 finalizing 是有幫助，但不能補救 detail 列出另一個 completed／無 pending 的矛盾訊息。
  - 修正方向：在純 UI 投影中採用相同的 ready-query 狀態優先權；active 時明說 worker/original lease cleanup 未確認，worker notice fault 優先，settled 後用最後 retained query receipt。usage 仍獨立，不能加入主 task totals 或暴露 query answer。將既有上述 worker-fault、provisional-success 測試情境同時斷言 panelJobs details。
