### G1-001 — Fork 的晚到 actual close 可能無法釋放已保留 permit

- 來源：`modules/fork/src/child.ts:97–101,140–145,180–191`；`modules/fork/src/manager.ts:131–142,224–238`。
- 類型／預估嚴重度：資源生命週期、容量；**High（待驗證）**。
- 觸發：取消或關閉梯級已完成但 child close 尚未確認，runner 回 `childClosed:false`；其後才觀察到真實 close。
- 靜態路徑：manager 的 complete 只在 done 的一次 outcome 上設定 released。child 的 close listener 後來只更新 local closed／exitCode 並 dispose RpcPipe；handle 沒有向 manager 公開 late-close 通道。manager 不會重新訂閱 close。四份這類 receipt 可能永久占滿行程的 4 個 Fork permits，即使 direct children 已全部 close，甚至 reload 後仍有 plain global registry。
- 預期：未知 close 時保留 permit，實際晚到 close 時更新同一工作的 cleanup 證據並釋放 permit；不可將失敗結果復活為成功。
- 實際：沒有執行觀察；上述是可追蹤的靜態推導。
- 反證：`manager.test.ts:167–179` 明確斷言未知 close 保留 permit；`child.test.ts:102–124` 測取消无 close／立即 close，但沒有 outcome 後晚到 close 的 manager reconciliation。正常 child 已在 grace 內 close 則 `manager.ts:140` 正確釋放。本項不是要求提前釋放未知程序，也不以 close 宣稱完整 descendants 都停止。
- 需要驗證：走真正 `startForkChild → handle.done → manager.complete`，不以 fakeChild 直接 return false 當作正式證明。離線真實 Pi child 加上有界 close 交錯／transport fault seam，保留真實 spawn、pipe、close 與 manager；事件 barrier 在 outcome false 後取得實際 close，核對 holdsPermit／activeCount／cleanup。必須區分 direct process exit 與 pipe close，並確認故障注入不是破壞 host shape。
- 若成立影響：同一 Pi process 不能再建立 Fork，剩餘作業可能在 quit/reload 的 terminal 篩選外；回報 cleanup 過期。
- 狀態：待驗證／未執行；命令、exit code、命中率、執行清理皆 N/A。

- `modules/fork/src/child.ts:102,113,130` 的 STDERR_TAIL_BYTES／MAX_LINE_BYTES 實際使用 string.length／slice（UTF-16 units），與文件 byte 表述不同；需 multibyte stdout/stderr 局部實驗及契約釐清。已有界限所以不直接稱為無界洩漏。
- Subagents `session-store.ts:520–527,552–605,613–626` 每次 validate／commit 全 conversation diskUsage 和 native inspection 的成本受歷史長度影響。已具 byte／entry／file-count caps，缺 benchmark；不在無量測下稱為效能缺陷，也不建議繞過 integrity checks。
