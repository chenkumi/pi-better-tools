## Warnings (should fix)

### SA-IO-001：成立，Medium；候選 helper 部分成立
使用者候選：`installIoFaultClock(t, targetLabels, wallTimeoutMs)`，runSingleAgent 移除 ioTimeoutMs override；test-local run wrapper 同步設定 activeLabel，直接呼叫原 run 並 finally 還原；global setTimeout wrapper 只縮短 target label 且 ms===300000 的 timer；slow 用 2000，其餘短故障用 300。

**成立部分：**
- 使用同一個真實 gate 與原 run 返回的 promise，原 pending／waiting／stop／whenIdle 全保留，不改 operation／this，不繞過取消，也不預造 ownership。相較 mock allocate／acquire／begin／metadata sync，確實更保守：真實 FS、election fence、owner metadata、close／late release 全繼續被驗證。
- `IoGate.run:37–50` 將 operation 排入 microtask，但同步建立 timer。因此 run wrapper 的 activeLabel 在 setTimeout 呼叫時存在；operation 本體執行時 activeLabel 已還原，不會把該 operation 裡面一般 timer 一起缩短。
- explicit ms===SUBAGENT_IO_TIMEOUT_MS 排除 IoGate(2000) 與其他不同預算；非 gate 的 300000 timer 在 run wrapper scope 外不受影響。inactivity、forceKill、settled grace、cleanup fixture timer 原樣委派。
- 不修改 private timeoutMs，原 error text 仍為 300000ms；這是 test clock compression，不是產品 deadline 修改。mode→label map 與使用者所列一致；slow 的 JSONL write 2000 可保留原本超過 inactivity 的 220ms 行為斷言。
- 即時 rename／unlink／spool failure 不縮短：仍由原錯誤觸發，所有正常 preparation／cleanup gate 使用 production 300000。

**必須校正的語意：**
- 候選在「目標 label 的 gate.run admission」就用 300ms 啟動 OS timer，並非在「指定 mock 確實受阻」後才開始。`finalize sub-session log` 內包含等待 write chain、真正 handle.sync、close、rename（subsession-log:463–480）；close-stall 案的非目標 sync 若慢逾 300ms，仍會在 close 的 entered 前終結。
- `create sub-session log` 包含真實 mkdir／open（subsession-log:339–352），header-abort 案只有 originalCreate 回傳後才阻塞（runner-io:113），故這些準備仍被壓到 300ms。read tool fallback 的 iterator.next 亦包括抵達 handle.read 前的真實 spool讀取準備。只避開 managed allocate／acquire／begin，不能宣稱所有非目標實際 I/O 已用 production budget。
- 因此：若使用者接受「整個指定 gate operation 的 envelope 為故障測試目標」，此候選可直接作最小方案；但是要明示只解耦 managed setup，不能保證不再發生 target-envelope 內的 pre-entered stall。對原要求嚴格的「非目標 I/O 保留 production budget」，它只能判 **部分成立**，尚不足完全符合。

**嚴格符合原要求的最小校正：**
- 保留候選 run wrapper／activeLabel／setTimeout capture 架構；目標 timer 最初仍以 300000 排程。
- 在既有 write／sync／close／header／spool read 的 entered mock barrier 才將「已捕捉且唯一尚活動的目標 timer」的原 callback 重排為 wallTimeoutMs（300 或 slow 2000）。不手動呼叫 gate.stop，不換 gate，不改 timeout error。
- 需要 test-local clearTimeout token mapping：IoGate closure 清除原 token 時，必須一併清除替代 token；已取消 token 不允許再 arm；正常 completion／abort／dispose 均不能留下 late callback。詳見先行報告的精確設計與 mode table。
- 此校正比直接縮短 label timer多幾個 token bookkeeping，但仍小於 mock storage，也保留真實 ownership。若堅持 helper只接受 targetLabels／wallTimeoutMs，需額外提供 fixture可呼叫的 entered/arm介面；不能在 helper 裡偷偷以 sleep／call ordinal 猜受阻 phase。

### helper 必要安全／回歸條件
1. run wrapper 同步、非 async，直接 `originalRun.call(this, operation, label)` 並原樣回傳 promise；activeLabel 以 stack 或保存 previous 值的 try/finally 還原，不要無條件設 undefined。test scope 不與其他測試並行；全域 setTimeout mock 只能對本 test own gates 生效。
2. 改善 activeLabel 只存 label 的邊界：同步 scope 可同时保存 gate identity；目前 run只同步建一個 timer，但 observer notify在其前面（io-gate:36）。一旦 observer自行建立相同300000 timer，單純 activeLabel也可能誤縮。現有 runner observer只調 inactivity，沒有這種衝突；仍須限定／斷言每run捕捉唯一 gate deadline，記錄這項 seam耦合，不能說任意非IoGate timer皆絕對安全。
3. 原 setTimeout 函式在mock前capture，wrapper保留callback、args、return handle；若用scope截獲timer，verify捕捉到的是預期deadline且只有一筆。不得嘗試修改Timeout內部private欄位。re-arm方案也必須以原timer函式排程，避免mock遞迴。
4. 真正 FS／pending IO／child cleanup完成前不可restore clock mock，否則gate的clearTimeout失去mapping。既有dispose收尾與spool-read-cleanup中先清理等待、後releaseRead的順序保留。
5. 無sleep seam單元回歸合理：capture delegate delay確認setup／non-target IoGate(300000)不縮、target300、slow2000、explicit IoGate(2000)原樣；一般global300000 timer在scope外原樣。再加run wrapper例外時scope恢復與nested scope恢復。
6. 手動觸發所capture的**原target timeout callback**，可以作純IoGate單元測試：同gate停止等待、原promise仍pending、whenIdle未settle、兩個actual operations全settle後才idle；first-stop原因不被第二次stop改寫。這不是直接mock stop，符合保留原gate。
7. 手動callback不能取代runner-io原本實際OS300ms timeout案例，否則只測helper wiring，不驗fixture與runner的既有timeout／cleanup交互。純unit捕捉timer不要留下真實300000timer；以專用fake scheduler管理、於finally取消，不能用seam驗證產生timer leak。
8. runner原17案與全部assertions保持；timeout案仍須到達entered、target callback只一次，abort案callback不得fired；不能把「entered未到先fail」改成接受fail。新增無sleep單元並不授權移除slow案例現有220ms凍結inactivity斷言。
