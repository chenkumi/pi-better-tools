### G4-001：新檔 hard-link fallback 保證不覆寫，但未提供完整內容的原子發布

- 來源：`modules/file-tools/src/file-operations.ts:1043–1071`；契約：`modules/file-tools/README.md:54,88`。
- 狀態／類型／暫定嚴重度：待驗證／持久化與並行／Medium。
- 觸發：建立新檔時 hard link 回報 `LINK_FALLBACK_CODES` 之一，轉入 `open(target, "wx")` 再寫內容的 fallback。
- 預期：README「新檔以不覆蓋的原子方式建立」若包含內容發布，並行唯讀者只能看到不存在或完整新內容。
- 靜態觀察：fallback 先建立最終路徑，才 `writeFile` 與 sync；因此與「先填滿 temp 再發布」路徑不同。尚未實際觀察中途可見的內容。
- 影響假說：不參與 queue 的讀者可能取得空檔／部分內容；崩潰期間也可能留下未完成新檔。是否屬契約違反需確認文件所稱原子性是否只指 exclusive no-overwrite。
- 反證／已有防護：hard-link 主路徑先完成 temp payload；fallback 的 `wx` 仍防覆寫；一般写入錯誤會清理自己建立的 target。正常支援 hard link 的 Windows 檔案系統未必會走 fallback。
- 真實產品入口：registered `write.execute` → `withFileMutationQueue` → `writeTextFile` → `atomicWrite`；不能以自行重寫 fallback 當重現。
