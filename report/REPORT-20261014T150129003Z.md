## Warnings (should fix)
1. **P2 — `modules/fork/src/child.ts:97–102`、`manager.ts:137–144`：晚到 close 永不釋放 permit。**
   - 觸發：termination ladder 結束時尚未 close，done 回傳 `childClosed:false`；之後才收到真實 close。
   - 證據：close handler 只更新 runner 私有變數；manager 僅在 done 完成一次時更新 cleanup/released，沒有晚到證據通道。`manager.ts:236,245` 又跳過終態工作。
   - 影響：已退出 child 永久占額度；四次即可耗盡容量，reload 仍保留 registry，widget 永久顯示 cleanup unconfirmed。
   - 建議：另提供一次性 close reconciliation，更新持久 cleanup、permit、UI；不復活答案或重送通知。現有 manager 測試200–212只驗未 close 時保留，未驗晚到 close。

2. **P2 — `modules/fork/src/child.ts:178–180`：finalizing 不響應取消。**
   - 觸發：最後文字或統計 RPC 未回覆時 cancel／quit／reload。
   - 證據：兩個 request 未包 `raceCancel`；abort 到187行才發送。RpcPipe 的每筆 deadline 為30秒（`rpc.ts:6,41`）。
   - 影響：取消可額外等待兩筆順序 RPC 約60秒，才進 shutdown ladder；quit/reload 的 waitDone 同受阻。
   - 建議：finalizing RPC 也競速取消，取消後不提交下一筆統計。現有取消回歸只覆蓋啟動前 stats。

3. **P2 — `modules/fork/src/store.ts:71`：先取 workspace 最新64筆，再篩 origin，舊 pending 永遠無法恢復。**
   - 觸發：A 有未送達完成結果；同 cwd 的 B 後續建立64筆更新紀錄，再重啟返回 A。
   - 證據：loadRecords 全域 slice 後，`manager.ts:198–199` 才比對 session/file；磁碟紀錄未隨 evict 刪除。
   - 影響：A 結果仍在磁碟但不入 registry、不通知，重複返回亦無效。
   - 建議：依 origin 建索引或可續頁的有界掃描；不能用其他 session 的最新歷史截斷 pending inbox。現有恢復測試只有三筆。

4. **P2 — `modules/fork/src/manager.ts:198–209`：恢復路徑繞過 retained 上限。**
   - 觸發：長存活 Pi 依序開啟多個 cwd 中有歷史結果的 session。
   - 證據：每次 session_start 可加入64筆，沒有容量檢查或 evict；限制只在 acceptFork 的71–73行。
   - 影響：不建立新 Fork 也能無界累積跨 workspace 的32KiB結果，所有 Map 掃描成本跟著增加。
   - 建議：恢復亦套全域 retention／lazy inbox admission，保留 pending 的可恢復性並明示 partial。新增 retained 回歸只測 acceptFork，不覆蓋恢復。

5. **P2 — `modules/fork/src/child.ts:115,132,178–194`：超大 final 被靜默丟棄，仍回 completed。**
   - 觸發：ASCII final 超過4MiB；最後文字 response 超過單行限制。
   - 證據：reader 丟掉 response，RPC deadline 後 catch 轉 undefined，最後仍 completed；32KiB截短位於 `manager.ts:139`，來不及保留答案。
   - 影響：多等30秒後得到無正文成功，沒有 outputTruncated。大型 message_end 亦可能使 stopReason/error 證據遺失。
   - 建議：child 端有界產生摘要，或把超限關聯回覆明確轉為 result-unavailable／failure；不可靜默成功。現有 oversized 測試只送垃圾行。

6. **P2 — `modules/fork/src/store.ts:44–49`：同步 retry 阻塞父 Pi event loop。**
   - 觸發：Windows rename 持續 EPERM／EBUSY／EACCES。
   - 證據：Atomics.wait 同步等待10至120ms，單次save累計780ms；四個 cancel 狀態寫入可串行阻塞約3.12秒，尚未計I/O。
   - 影響：TUI刷新、RPC drain、cancel timer與reload均被延後；不是背景非阻塞重試。
   - 建議：受理階段明確失敗，或改有界非阻塞持久化隊列並保持 terminal-before-delivery 次序。此為程式算術證據，未量測實機延遲。
