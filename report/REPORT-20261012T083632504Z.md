## MISC-003 — 已確認／已觀察，Medium

### 真實路徑及位置

`CronStorage` + `CronScheduler.start()` + `createCronTool(...).execute(...,{action:'list'},...,ctx)`，非仿製 list。可信 isolated cwd、owner session、合法 enabled 1h intervals、無deadline／lastStatus running，使用實體 JSON store。產品位置：

- `modules/schedule-prompt/src/tool.ts:322–359`：324–326讀所有 jobs，339每列 `getNextRun(job.id)`。
- `modules/schedule-prompt/src/scheduler.ts:191–212`：有本地nextRun才在207呼叫 `storage.getJob()`。
- `modules/schedule-prompt/src/storage.ts:93–126,297–307`：getAll/getJob 各重新 readFileSync、JSON.parse、shape/interval過濾，再find。

Instrument只計數隔離store的 `fs.readFileSync`，其後仍呼叫真實 read；不是 virtual FS回應。成本量測前完全還原 fs，避免將counter額外成本混入時間。假 timer 只保存callback從不執行，真scheduler bookkeeping保留。

### 三次一致的 operation count

| N | store bytes | 每次list全檔reads | 每次list累積read bytes | 三次觀察 |
|---:|---:|---:|---:|---|
|10|1832|11|20152|3/3相同|
|100|18302|101|1848502|3/3相同|
|500|92302|501|46243302|3/3相同|

成本判定依次數／bytes與來源，而不是僅靠毫秒曲線：正常active list讀 N+1 份 B-byte store，成本 O(N·B)；固定平均job大小時 B=Θ(N)，累積 Θ(N²)。parse/filter每次也重新處理所有jobs，且find增加線性掃描。

### 成本量測（獨立於counter）

每新process各N先warm一次，未插read counter的list量測3次，總共每N9樣本。`performance.now()`量wall、`process.cpuUsage()`另記user/system CPU原始值；CPU在Windows短樣本有粗粒度／0，不將0解釋成無CPU成本。

| N | wall min / median / max (ms) |
|---:|---|
|10|6.214 / 8.003 / 14.934|
|100|82.618 / 87.084 / 121.065|
|500|966.701 / 1021.849 / 1706.375|

這是本機、暖OS cache、假timer控制、含tool字串format的描述性成本，未控制主機其他負載，不是普遍延遲或TUI事故門檻。產品同步I/O/parse期間會阻擋同一event loop；未实际測TUI／abort latency。

### 反證與正常控制

各三次：startup恒1次全檔讀、N個受控timer；已知snapshot `getNextRun(id,job)` 全部回傳next且0讀；stop後list1讀；100disabled rows list1讀；100foreign rows list1讀且0列；全部timer callbacks/deliveries=0，stop後pending timers=0。

widget `ui/cron-widget.ts:201` 已傳knownJob；startup `scheduler.ts:78,263–264`已用snapshot。原R13測試覆蓋startup/cleanup，**不能反證剩餘list consumer**。不主張disabled/foreign/stopped也發生N+1，不重報startup。

## MISC-004 — 已確認／已觀察，Medium

### 輸入／正確判定

根draft-2020-12 object；W是object且 `properties.amount` 是number；required x引用 `#/$defs/W/properties/amount`。按pointer逐段解析，其目標就是number，因此 `{x:7}`有效、`{x:{}}`無效；判定不是用受測converter自行產生。

兩種：原始deep-sync，以及另加required string tag/pattern `^a+$` 的deep-worker（tag=`aaa`）。後者確保走真validation worker但不更改x指標目標。

### 三次重現，含可達consumer

兩種schema均3/3 compile成功、接受invalid object、拒絕valid number；錯誤原文：

```
x: Invalid input: expected object, received number
```

sync觀察poolSlots=0；worker觀察poolSlots=1，wrong tag=`bbb`確實被拒絕，證明不是pattern未跑。每種schema接著以真extension factory註冊hooks，offline stub dispatch：`session_start → input → message_end → agent_end → agent_settled(aborted:false) → session_shutdown`。沒有呼叫json_output execute、activeTools=[]、complete/fetch禁止；真prose中balanced JSON候選經recover被交付實體檔：

```json
{"x":{}}
```

worker版本交付：

```json
{"x":{},"tag":"aaa"}
```

原始縮排與換行bytes存log `raw`欄位，3/3兩路均同結果；modelCalls=0。正常inline number schema consumer提供「錯object候選後合法number候選」，實際交付 `{x:7}`，證明fake event不是任意無驗證write stub。淺 `#/$defs/W` compile可接受object／拒絕number；inline compile接受number／拒絕object。Provider tool parameters的deep pointer原樣保留（有斷言）。

### 根因位置與反證

- `modules/json-schema/src/schema.ts:58–63`只檢local/pointer形式及siblings，不拒tail；122–129预算明知converter僅definition級，並不修語意；153–158 compile接受；173–178同步validate／worker分流。
- runtime CJS/ESM converter只用path[1]拿definition（精確位置見前及audit）。Zod TS亦 `node_modules/zod/src/v4/classic/from-json-schema.ts:137–151`。
- `modules/json-schema/extensions/json-schema.ts:129–133`保存／抑制prose，154–156先在本地validate候選，204–222 shutdown實際寫file；此路徑不經host tool argument validator。
- worker `modules/json-schema/src/validation-worker.mjs:11–15`使用等價converter，真worker結果与sync一致。

host直接tool argument validation可能攔部分錯資料，但實驗不呼叫tool execute，因此不能阻止已觀察的prose交付。Safe pattern policy／worker只是安全與資源邊界，不能糾正pointer語意；淺refs正常不等於任意深pointer正常。既有R3 siblings和expanded-work/default等回歸與此不同；無需停用所有refs。Extraction-response consumer（extension187/197）共用同validator但本輪未動態測該分支，不能宣稱3次覆蓋它。
