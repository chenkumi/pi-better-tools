### BUG-002 — 成立，Medium，已確認
- `tests/fixtures/monitor-production.mjs:25,27,36` — subscription 只 resolve 清理已完成的 completed；已觀察快路徑亦只接受 completed。沒有 reject callback，failed／stopped／expired／limited 均不能終結 waiter。Monitor start 的非錯誤 receipt（line 35）不能排除之後的非同步來源失敗。
- `modules/monitor/src/core.ts:17,26,65–80,135–140` — 非成功 terminal 狀態確實存在，失敗路徑會終結並在 monitor_event 帶 state／stopReason／cleanup evidence。因此不需假設 host 沒有通知即可證明 waiter 缺陷。
- 已讀既有證據：`source-run.log:5–10` 記錄 command 在 722ms failed／source_error／startupFailed=true／sourceClosed=true／cleanupPending=false，而 WebSocket completed；lines 13–20 顯示原 completed-only barrier 直到診斷 65s 限制仍未結束。`original-package-tail.log:80–85` 記錄正式 stage 的 180000ms timeout。
- `scripts/package-smoke.mjs:235` 與 `modules/file-tools/scripts/test-process.mjs:94` — 此 180s 是測試 runner 的固定總期限，不是 shell-tools 輸出停滯 timeout；fixture heartbeat 不會重設它。不要因此改動產品 timeout 語意或增加正式測試期限。
- 最小修法審查：**接受 fixture 對非成功 terminal reject，保留成功清理與 data 斷言**，但應满足以下必要條件：
  1. waiter 同時保存 resolve／reject；後續通知與 `terminal(id)` 的已觀察快路徑共用同一判定，避免 failure 早於 waiter 註冊時仍卡住。
  2. 明確識別非成功 terminal 為 failed／stopped／expired／limited；不能把 starting／running／stopping 當失敗。
  3. 非成功 terminal 不應要求 cleanupPending=false 或 sourceClosed=true 才 reject；否則清理未確認的失敗仍會被隱藏。錯誤附 monitorId、state、stopReason、cleanupPending、cleanupEvidence 等安全診斷，不傾倒命令／敏感 URL。
  4. 成功仍需 completed、cleanupPending=false、cleanupEvidence.sourceClosed=true。現有 line 27 快路徑少了 sourceClosed 判定；應與 line 25 成功條件一致，而不是把 line 25 降低到快路徑條件。
  5. 保留 lines 37–40 的 status、secret redaction、data、custom_message／extension errors 斷言，以及 line 42 finally 的 heartbeat／WS／session 清理。reject 只是使测试失败及时可见，不能轉成 passed 或跳過來源。
- 影響：真正的 startup failure 被外層總期限覆蓋，並使同 host 後續 stages 未執行（`package-smoke.mjs:310–314`），而不是那些 stages 已經通過。
