## Warnings (should fix)

### F1 — P1 高風險推論：stale-lock 接管可能移走另一個 contender 剛建立的 live lock

- **位置**：`modules/subagents/extensions/subagent/session-store.ts:331-353`，尤其 `340-344`；stale 判斷在 `272-278`。`message-reservation.ts:5-11` 只提供 process-local contention，不能排除此跨 process 情境。
- **原因**：`lockIsStale()` 讀取的是舊 pathname 的 owner；之後 `rename(lockDir, uniqueStale)` 沒有綁定先前觀察到的 directory identity／nonce。每個 contender 的 destination 又是不同名稱，所以 rename 的原子性不能保證只有一位 winner。
- **具體交錯**（兩個 parent process 載入同一 parent session／cwd，接管同一已驗證 checkpoint 的 dead-owner lock）：
  1. A、B 都因 `mkdir(writer.lock)` 得到 EEXIST，且都完成對舊 dead-owner lock 的 stale 判斷。
  2. 暫停 B；A rename 舊鎖、刪除 stale directory，重新 mkdir，寫入新 live nonce，完成 rollback 並進入 invocation。
  3. B 用先前 stale 判斷繼續執行 line 343，rename 的來源此時已經是 A 的新 live lock；B 刪除它，建立自己的鎖並 rollback。
- **Impact（推論）**：A 的 child 可能已在寫 native file；B 卻可在其仍存活時 truncate 到 checkpoint，破壞獨占 writer／rollback 的安全前提。後續 `assertLock()` 可能讓 A 的 parent fail closed，但不能撤銷已執行的 truncate 或停止當時 child 的寫入。
- **最小修正方向**：將 stale recovery election 放在所有 acquire/query-lease 建立都尊重的短期跨 process fence 下，於 fence 內重新驗證 stale identity 後再 rename／建立 writer。單純再讀一次 nonce 仍有 check-to-rename gap，不應宣稱足以修復。
- **驗證證據**：靜態追蹤上述交錯；既有 `session-store.test.ts:126-150` 只測正常 live-owner exclusion 與 same-pid stale 判斷，未涵蓋「兩位 contender 已判 stale，A 已建立 live replacement 後 B 才 rename」的交錯。未執行 repro。
- **最小離線驗證建議**：隔離 workspace／session root，先建立 ready checkpoint，再用兩個離線 process 和 IPC barriers 控制 stale 判斷與 rename；斷言 B 不得移走 A 的 nonce、不得 truncate A 的新增 native bytes。無模型呼叫，不靠 sleep。

### F2 — P2：acquire 的 owner metadata publish 失敗後，runner 不知道自己已持有鎖

- **位置**：`modules/subagents/extensions/subagent/session-store.ts:347-352`；對應 `index.ts:554`、`1028-1049`。
- **Confirmed（code）**：`acquire()` 先設定 `this.lock`、將 nonce 加入 process-wide live registry，再 await `atomicJson(owner.json)`；不像 `acquireQueryLease():290-294`，這裡沒有失敗補償。runner 的 `lockHeld = true` 又只在整個 `acquire()` fulfilled 後才執行。
- **故障交錯**：mkdir 成功 → nonce 註冊 → owner.json 的 write/sync/rename 拒絕 → acquire rejects → runner 回傳 failed，`lockHeld` 仍 false，正常與晚到 cleanup 都跳過 managed release。
- **Impact（推論）**：若 owner.json 未 publish，`lockIsStale()` 因 missing file 永遠回 false；若 owner.json 已 publish、後續 recovered rollback 發生 exception，live registry 仍可能保留 nonce。即使沒有 child／pending I/O，該 session 也可能持續 SESSION_BUSY；reload 不會清理 global live-lock registry。這與「實際 writer close 失敗時有意保留鎖」不同，前者沒有可完成釋放的 owner cleanup 路徑。
- **最小修正**：`acquire()` 對 mkdir 後的初始化與 recovery 失敗保留明確 cleanup owner／settlement；只在實際 I/O 全部 settled 且 nonce identity 仍屬自己時移除 owned directory／registry。若 cleanup 失敗，要保留可追蹤 ownership 與診斷，不可盲刪可能已換 owner 的 pathname。
- **驗證證據**：控制流已確認；未動態注入。既有 intent／commit 故障測試在取得完整鎖之後注入（`session-store.test.ts:184-219`），`runner-io.test.ts:329-338` 是 transcript writer creation failure，皆不等同 acquire 的 owner.json publish fault。
- **最小驗證建議**：隔離 fixture 對 `owner.json` 的 atomic publish 注入一次性 EIO，等待實際 I/O settlement 後檢查 lock／nonce 不再無主保留，再確認第二次 acquire 可成功；另測 cleanup failure 誠實保留診斷。

### F3 — P2：background create 的受理前 allocation 未受取消／I/O gate 約束

- **位置**：`modules/subagents/extensions/subagent/index.ts:1514-1525`；`background.ts:236-255`、`291-292`、`342`、`362-371`。
- **Confirmed（code）**：background create 的 `snapshotConfig()`／`ManagedSession.allocate()` 是直接 await，沒有 runner 的 IoGate；只在每個 item 的 await 前後檢查 tool signal。`submitManaged()` 的 prepare 也沒有 job controller 的 abort wait barrier。
- **故障交錯**：submitted capacity 已增加、job.done 等待 admission → 卡在 config read／mkdir／metadata sync → tool signal 或 shutdown 取消 → prepare 的 await 尚未返回，無法到達 abort check／reject admission；shutdown 等 15 秒後清空 registry，但原工具 execute 與該 admission 可繼續 pending。
- **Impact（推論）**：取消不能迅速返回；受理前故障即可讓 submitted 名額長期占用，reload 後 capacity／卡住的 tool promise 與晚到 allocation 不易觀察。這不是要求中斷 OS I/O，而是目前連「停止等待並保留晚到 owner」都缺失。32 submitted 上限仍會防止無限數量，因此不聲稱無界 process spawn。
- **最小修正**：prepare 接入受理前取消／期限 gate，追蹤已開始的 actual allocation I/O；取消後停止等待和禁止後續 item／runner admission。尚有 actual I/O 時保留必要 ownership／容量，讓晚到 settlement 完成後釋放，不能只用 Promise.race 然後立即丟棄 owner。
- **驗證證據**：直接 await 與檢查位置已確認；未執行 stalled allocation repro。同步 runner 的 `index.ts:547-568` 已採 IoGate，形成可比較的既有做法。
- **最小驗證建議**：以 deferred barrier 卡住 background allocation 的 owner metadata 寫入，發送 tool abort／runtime shutdown；驗證等待能被取消、沒有 spawn、容量直到 actual settlement 才釋放，然後解除 barrier 確认 late allocation 收尾。測試不得修改產品源碼或以固定 sleep 判 timeout。

### F4 — P2：新 uppercase control IDs 無法進入 query 的 appliedControlIds

### F5 — P3 效能熱點：Shell 首次 submit 的全 tmpdir sweep 與刪除重試會阻塞主 event loop

- **位置**：`modules/shell-tools/src/background-jobs.ts:37-38`、`51-75`、`207-210`；retention eviction 亦同步刪除於 `201-203`。
- **Confirmed（code）**：首次背景 submission 同步 `readdirSync(tmpdir)`，逐一讀取／stat matching directories，對 stale entries 呼叫帶 retries 的 `rmSync`；沒有目錄數／本次清掃工作量上限。line 75 的 catch 只能隔離 exception，不能防止 synchronous I/O 阻塞。
- **Impact（推論，未 benchmark）**：tmpdir 大、累積很多 stale job dirs、Windows AV 暫時占用或慢磁碟時，receipt、Ctrl+C、其他 runner drain、通知與 TUI 全部可能延遲。每 job log bounded 不代表跨 crash 累積的清掃工作量 bounded。正常本機小 tmpdir 未證實有可感知 regression。
- **最小改善**：stale sweep 改為有工作量／批次限制的非同步 housekeeping；避免在受理主路徑同步等待多個 rm retries。維持 owner.pid／symlink／live-process 排除條件，不為效能弱化刪除資格判斷。
- **驗證證據**：同步 call graph 已確認；沒有時延測量，不列 must-fix。最小量測應只對隔離 tmp root 製造大量 matching entries，記錄掃描工作量與 event-loop delay；不要掃／刪使用者真實 tmpdir。
