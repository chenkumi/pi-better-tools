## Suggestions (consider)

### 1. Schedule Prompt：把三條成功路徑的相同統計提交收斂為 scheduler 私有操作

**位置：** `modules/schedule-prompt/src/scheduler.ts:561–569`、`:671–686`、`:814–823`；持久化契約為 `modules/schedule-prompt/src/storage.ts:254–265`。

**證據與呼叫鏈：**
- `executeJob()` 的 inline 路徑、`executeJobInSubagent()` 的成功 continuation、`executeJobAsCommand()` 的成功 continuation，都依序取 `getNextRun(job.id)`，透過 `updateJobWith` 寫入 `lastRun`／`lastStatus: "success"`／fresh `runCount + 1`／`nextRun`，然後 emit `{ type: "fire", job }`。三份成功提交的欄位、fallback 與事件相同。
- `storage.ts:255–263` 證明 compute 在 lock 內重新載入 job 後才執行；不能改成先 `getJob()` 再 `updateJob()`。
- `scheduler.ts:509–528` 是三種 execution 的分流呼叫端；extension 在 `src/index.ts:70–77` 建立並啟動 scheduler。

**建議：** 抽成一個 scheduler 私有成功提交操作，接收原本的 job snapshot，集中 next-run 查詢、鎖內 fresh-counter 更新及原有 fire event。三個 call site 仍在原成功位置呼叫；不要連帶合併執行方式、錯誤路徑或訊息 renderer。

**價值：** fresh-counter 及 terminal-status-before-marker 的重要規則不必維護三份；避免未來只修正一種 job 的成功統計。這是相同完成／交付統計規則的收斂，不是把三種工作假定為相同生命週期。

**風險與必保契約：**
- 低至中風險。inline 的 success 代表 prompt 已交付，不代表模型工作完成；subagent／command 則是其完成。helper 不應更名或升格成功語意。
- 必須保留 `(latest.runCount ?? job.runCount ?? 0) + 1` 在 lock 內計算，以及 `new Date().toISOString()` 的既有位置；不得提前計算整個 patch。
- 不得移動 abort checks（`:656`、`:813`）、把 skipped 視為 success、對失敗增加 runCount，或在 helper 中加入啟用／session／deadline 的新條件而改變現行行為。
- success persistence 及 fire event 仍在 completion marker 前；仍 emit 原 snapshot，不順便改成 fresh job。command 保留空 model-visible content／`triggerTurn:false`；subagent 保留 notify 分流。

**已查閱的既有驗證（本次未執行）：**
- `test/scheduler.test.ts:182–208`：subagent 成功累計、失敗不累計。
- `test/scheduler.test.ts:405–434`：completion marker throws 時，成功統計已持久化。
- `test/scheduler.test.ts:438–480`：inline follow-up 及空 marker 契約。
- `test/command-scheduler.test.ts:93–114`、`:126–151`：成功／非零 exit 統計及不向模型投影輸出。
- `test/command-scheduler.test.ts:314–324`、`:343–354`：stop 後不寫入／once 自動停用後仍接受完成結果。
- `test/review-fixes.test.ts:64–69`：storage 鎖內使用 fresh counter；此案例直接測 storage，不是三條 scheduler 路徑的 peer-race 完整驗證。

### 2. JSON Schema：由既有完整 audit 同時回傳 pattern 使用資訊，刪掉第二份 schema-position 遞迴

**位置：** `modules/json-schema/src/schema.ts:51–106`、`:108–118`、`:163–184`。

**證據與呼叫链：**
- `audit()` 在 `:56–57` 已讀取 pattern／patternProperties，並在 `:97–104` 依 `SUBSCHEMA`／`SUBSCHEMA_LIST`／`SUBSCHEMA_MAP` 遍歷所有 schema positions。
- `usesPattern()` 在 `:109–118` 以同三個集合重新遍歷；`compileSchema()` 已先 `audit(parsed)`，Zod 編譯後才再呼叫 `usesPattern(parsed)` 決定 worker／同步路徑。
- `extensions/json-schema.ts:62` 呼叫 compileSchema；`:86`、`:165–166`、`:197–208` 的 tool／prose／extraction validation 都共用 compiled validate。漏判 pattern 不只是效率問題，也會改變隔離選擇。

**建議：** 令私有 audit 回傳是否在 schema position 出現 pattern／patternProperties，遞迴時累積這個 boolean；compileSchema 保存 audit 結果供既有 isolated 分流使用，移除 usesPattern。公開 `CompiledSchema`、validate 的同步／Promise 回傳行為及 provider schema 不變。

**價值：** 消除兩份 schema-position walker 的維護分歧與第二次遞迴；新增 schema position 時，只需更新 audit 的 traversal 即可保持 pattern admission 與隔離選擇一致。不需建立全模組的通用 visitor framework。

**風險與必保契約：**
- 中風險，因 audit 是安全 admission。累積 boolean 絕不能用 `found || audit(child)` 這類短路方式跳過剩餘子 schema；每個 child 仍必須執行 audit、保留現在的錯誤順序及 path。
- pattern presence 要維持 `"pattern" in node || "patternProperties" in node` 語意，不能只看 truthy value／非空 map。
- 仍走 tuple `items`／`additionalItems`、兩種 definition map、propertyNames／patternProperties；default／enum／const／未知 annotation 內的 instance data 不得成為 schema positions。
- 不合併 `admitExpandedSchema()`：`:125–151` 是 reference 展開的另一種 traversal，刻意不把所有 definition map 當直接展開子樹，保留 converter map precedence、active-path cycles、重複 reference 計數及 2048／128 預算。
- 不改 `withoutSchemaDefaults()` 與 worker cache；保留主執行緒先編譯／exercise validator 再使用 worker 的 admission 邊界。

**已查閱的既有驗證（本次未執行）：**
- `tests/stability.test.ts:18–30`：pattern 安全拒絕涵蓋 definitions、propertyNames、patternProperties 與 tuple tail。
- `tests/workers.integration.test.mjs:9–16`、`:32–37`：真正 worker 驗證 refs、raw data；tuple tail 明確斷言回傳 Promise，確認隔離選擇。
- `tests/schema.test.ts:33–40`、`:61–85`：ref pointer、unsupported keywords、type-specific constraints 與 tuple audit。
- `tests/review-regressions.test.ts:42–55`、`tests/review-c1.test.ts:19–33`：expanded budget 及 definition-map precedence 不得被這個重構影響。
- `tests/review-guards.test.ts:11–32` 是 default-pruning 的 schema-position／annotation 證據，不是 usesPattern 的直接 negative test。已讀範圍未見 annotation 裡只有 pattern 時仍保持同步，以及第一個 pattern 後的 unsafe sibling 仍被 audit 的直接案例；若實作此候選，應先補小型 characterization coverage，而不是把既有間接測試當完整保障。

### 3. Blackhole：同一 pre-operation native window 的 eligibility 與 edits 一次衍生，避免重做 window selection

**位置：** `modules/blackhole/src/hooks/cosmetic-output.ts:128–135`；`modules/blackhole/src/core/native-compaction-input.ts:8–19`。

**證據與呼叫链：**
- selector 先 `nativeContextEntries(before)` 建立 eligible IDs（`:129`），下一行 `nativeEligibleEdits(before)` 內部又呼叫同一 `nativeContextEntries(branch)`（core `:18`）。因此同一 `before` snapshot 的最新 checkpoint、cut index 及 kept slice 重新算一次。
- `nativeContextEntries()` 沒有 I/O 或 host callback，只從傳入 branch 建立陣列；兩次 selection 的來源及 native semantics 相同。
- `cosmetic-output.ts:133` 額外取得 full current branch 的 edits，語意不同，必須保留。
- `blackhole/index.ts:84` 註冊 hook；`cosmetic-output.ts:211–236` 在成功 `session_compact` 取得 branch／retained IDs，呼叫 build → select，再 append plain custom display entry。

**建議：** 讓 native helper 的內部 edits collection 可使用已選好的 context entries，或提供狹窄的內部 snapshot 結果供 selector 同時取得 entries／edits；保留現有 `nativeContextEntries(branch)`／`nativeEligibleEdits(branch)` 呼叫介面及所有其他 consumer 的 branch 語意。selector 只重用同一 `before` 的 selected window，不建立跨 hook／跨 session cache。

**價值：** 將「哪些 entries eligible」與「哪些 edits 有效」明確綁定同一 native window，移除重複 cut selection；重點是契約可讀性與單一來源，不宣稱未量測的效能收益。建議優先度低於前兩項，若實作需大量新 wrapper／型別，則維持現況更划算。

**風險與必保契約：**
- 中風險，涉及防止重顯示 redacted text。不能刪除 current branch 的 `nativeEligibleEdits(branch)`，也不能以 current window 替換 before window；兩者分別保護 native retention omission 與 persistence 後的 edits。
- `Map.set` last-wins 順序及 explicit null tombstone 必須原樣保留。不得把 null 当成 absence。
- `counts` 必須仍來自完整 before，而不是 selected window；duplicate ID fail-closed、retained IDs、600-entry backwards budget、aborted 過濾不變。
- 不改 oldest-first host branch 的反向掃描、不改 native cut 或 summary、不將 custom entry 改成 custom_message，不持久化任何新 state，不回填歷史。

**已查閱的既有驗證（本次未執行）：**
- `tests/cosmetic-host-order.test.ts:11–39`：真實 chronological branch、boundary、scan budget 及 retained 排除。
- `tests/integration/pi-owned-review.test.ts:38–47`：實際 SessionManager／prepareCompaction 的 null edit 和 replacement 控制 display copy。
- 同檔 `:114–125`：actual Pi native edit eligibility 與 checkpoint window 一致。
- 同檔 `:156–173`：native cut、normal dropped final、duplicate IDs、raw history 不變、post-persistence null edit 不得重新顯示。
