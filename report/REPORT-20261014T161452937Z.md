## 七候選判定、邊界與驗收

### 1 — already-fixed（原 bad-value 反例）；仍有相關漏驗

- 原候選位置現在是 `modules/json-schema/src/validation-schema.mjs:13–16`；產品 compile／sync validate 位於 `src/schema.ts:160,174–179`。
- 三次實測 schema `{type:"object",required:["k"],additionalProperties:{type:"integer"}}`：`{k:"bad"}` 都回傳 `k: Invalid input: expected number, received string`，`{k:1}` 都成功。原報告的補 `{}` 造成 bad-value 放行已不成立，最新 governed 修正有效。
- 但相同 schema 對 `{}` 三次仍回傳 undefined；省略 governed key 同時遺失 required 檢查。另列為修正不足，不把 candidate 1 的原反例標 confirmed。
- 邊界：本地 validator 的 required／catchall 語意；未證明 Pi host 最終寫檔。
- 驗收：同時拒絕 `{k:"bad"}` 與 `{}`，接受 `{k:1}`；保留 provider 原始 schema，不能用補 properties 破壞 pattern／additional 分類。

### 2 — confirmed

- `modules/json-schema/src/validation-schema.mjs:12,16–17`；`src/schema.ts:160,177–178`。
- schema `{type:"object",required:["__proto__"]}`，`{}` 三次都成功；真實 normalization 顯示 properties 為空。
- control：普通 `required:["k"]` 對 `{}` 三次失敗、對 `{k:1}` 三次成功。不是 converter 根本沒做 required 的假陽性。
- 邊界：原型名稱 own-key required 遺失，不聲稱全域 prototype pollution。
- 驗收：缺少 own `__proto__` 必須失败；合法 own property 的支援或保守 admission 拒絕須明確；不能依 inherited setter 的賦值。

### 3 — confirmed

- `modules/json-schema/src/schema.ts:70–73`。
- schema `{type:"object",required:["k"],patternProperties:{"^k$":{type:"integer"}},additionalProperties:false}` 三次在 compile 抛出 unsatisfiable。
- JSON Schema 約束下 `{k:1}` 的 k 被 pattern 覆蓋，不屬 additional property，且 integer／required 均滿足；因此不是無解。
- control：加明確 `properties.k={type:"integer"}` 後，實際產品 worker 三次接受 `{k:1}` 且拒絕 `{k:"bad"}`。
- 邊界：初始化拒絕合法 schema；不是 invalid data 洩漏。README 沒列出 pattern-covered required 特例，既有「unsatisfiable」理由不忠實。
- 驗收：考慮 pattern coverage 與獨立 own-key required guard；若只保守拒絕，需誠實描述 converter limitation 而非無解，並同步文件。

### 4 — confirmed

- `modules/json-schema/src/schema.ts:57–58,156,160,175`；`src/validation-worker.mjs:11–15`。
- schema `{type:"object",patternProperties:{"^x":{type:"string"}},additionalProperties:{type:"integer"}}` 被 admission 接受。實際 worker 三次接受 `{other:"bad"}`（非法）與 `{other:1}`（合法），三次拒絕 `{x:1}`（匹配 pattern 但非字串）。
- 邊界：未匹配 pattern 的額外值漏驗，不把 worker 計時或 provider enforcement 當成本次證據。
- 驗收：拒絕 `{other:"bad"}` 或啟動時拒絕目前不能忠實驗證的組合；保留合法 control、pattern control 並分別覆蓋同步與 worker 路徑。
