### FILEWEB-001 — REST 搜尋 HTML snippet 清理先匹配完整欄位，再截斷；可能同步二次方掃描

- **位置**：`modules/web-tools/src/search.ts:9`；呼叫點 `81–84`；HTTP body admission `10–25`；期限／取消 `39–41,88–96`。註冊入口 `modules/web-tools/src/index.ts:90–128`。
- **等級／狀態**：Medium、待獨立驗證；演算法風險的靜態推導，動態驗證 **未執行**。不得寫成已穩定重現、已觀察長時間卡住或所有正常搜尋均受影響。
- **可達前提**：設定為 Brave／Exa，成功且小於 2 MiB 的 JSON 回應含一筆合法公開 HTTP(S) URL，description／title／highlight 字串含大量連續 `<` 而沒有 `>`。這是接收上游異常／病態資料的防護邊界；fake HTTP seam 與現有單元測試使用相同 SearchResponse 外形。不宣稱真實 Brave／Exa 已返回此欄位長度，亦不宣稱任意網站可直接操控 provider 的完整 JSON。
- **具體來源推導**：`clean()` 對完整字串先執行 `/<[^>]*>/g`，最後才 `.slice(0,max)`。對 `'<'.repeat(n)`，每個 `<` 都是可嘗試起點，`[^>]*` 能掃過剩餘所有字元，但尾端 `>` 不存在；一般回溯執行下可形成約 n(n+1)/2 的累積掃描。1500／300 字元結果上限只限制清理後結果，不能提前限制這個工作量。Exa 更先對完整 highlights 執行 filter/join，亦沒有單欄位 admission。
- **影響推論**：工作在 Pi process 的同步 JS 路徑，不在 Fetch 的 extraction worker。searchTimeoutMs 的 timer 與 AbortSignal 不能打斷正在執行的同步 RegExp；若 CPU 清理跨期限後正常完成，也沒有在 `64–87` 的處理完成後重新檢查 deadline，故可能遲到成功而非 TIMEOUT。具體時間與引擎優化須由獨立實驗確認，不能僅由 O(n²) 推論固定毫秒或必然 crash。
- **反證已查**：body stream 有 2 MiB cap（19–20）、numResults 有 1–10 cap（36–37）、正常 snippets 的輸出有 1500 cap（81–82），既有測試驗證 HTML tag 去除、2 MiB body 拒絕及 HTTP 等待取消（`tests/unit/search.test.ts:8–23,47–64,76–79`）。這些都未測清理前病態單欄位。provider 常態 snippets 短、Exa request 宣告 maxCharacters=1500（53），顯著降低正常情況風險，但接收程式未驗證上游是否遵守。Fetch JSDOM worker 的修正不覆蓋 REST search。
- **獨立判定／可排除條件**：先確認來源 SHA，在相同 Node/V8 版本跑下方 x control 與 `<` case，各三次。若原始 search 實測在大小翻倍下保持線性、沒有清理 CPU 放大，則將此候選排除或降為防禦建議，保留原始輸出。不以單一 timeout／慢機器／tsx 冷載入判定成立；若 response 太大、JSON shape invalid、import 失敗或外部安全期限先終止，需分別標成 fixture／環境阻礙或被截斷觀察。
- **若驗證成立的最小方向**：線性 tag scanner 或有界欄位 admission；保留現有去 tag 與 snippet 語意，不直接以「先 slice」假設所有 HTML 邊界語意相同。必要時對 post-HTTP 同步工作有明確預算並檢查完成後取消。此處不授權修正。

## Suggestions (consider)

### FILEWEB-COVERAGE-01 — File 大檔行索引：已知資源放大，未升格成新增候選

- `modules/file-tools/src/file-operations.ts:258–263,1493–1497`：edit 對整檔每個 LF 保存一個 number offset，且在 validateEdits 的 10 秒預算建立（1189）之前。即使 lineRange 很小，仍先建整檔 starts。
- 可重算資源數：`'a' + '\n'.repeat(50 * 1024 * 1024 - 1)` 合法正好 50 MiB，形成 52,428,800 個 starts entries；不是已量測 400／600 MiB，也不是能由 worker heap cap 保護的分配。
- **反證／排除理由**：50 MiB admission 是有限上限，不是無界 leak；line map 已不 materialize 每行文字。2026-10-11 四模組 report `:85` 已明列這個未量測的 edit line-start index 界線。昨日 R1 實際 200000 行 regression 原檔只有 original，主要驗證新輸出 formatter，不是現有數千萬行檔案的 map admission。本次沒有 RSS／CPU 實驗，故不符合使用者「只提穩定重現候選」门檻，**不計入 warning 候選數**。
- 後續若要評估，使用隔離 child 比較相同 bytes 的單長行 vs 1/4/8 MiB 高換行密度現有檔，兩者都以 `oldText:'a', newText:'a'` 走原始 editTextFile 至 NO_CHANGE（沒有產品提交）；量測準備前後 heap／maxRSS 並核對輸入未變。50 MiB stress 只能另經同意，在獨立 process heap／外部停止邊界內做。不可把限制 child heap 的 OOM 直接等同 default Pi 必 crash。
