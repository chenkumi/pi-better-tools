## Warnings (should fix)

### R1 — P2：sync send 重入採樣會把已提交 snapshot 計成 omitted，漏計 submitted

- **精確位置：** `modules/monitor/src/core.ts:102–104,160–171`，核心是 `core.ts:104` 的 coalescing 與 `core.ts:171` 只在 event 仍位於 queue 時才增加 submitted。
- **證據分類：靜態可構造 interleaving，未執行重現。** 此 finding 要求 send callback 同步重入同一 job Monitor 的 `sink.data()`；不是聲稱正常 timer 自動在同一同步 stack 中插入，也不是已由 production host log 證明發生。
- **具體控制流：**
  1. 一個 running `shell_job` Monitor 排有 started 與 snapshot S1。flush 已選取 S1，且第 160 行建立的 `details` 包含 S1。
  2. `send()` callback 返回前，同步採納 S2。job coalescing 在第 103–104 行仍能找到已選取、尚未從 queue 刪除的 S1，移除它並 `omitted++`，再把 S2 加入 queue。
  3. send 正常返回，表示本 batch 的提交 callback 成功。第 171 行查 S1 的 index 已是 -1，因此不增加 submitted。
  4. 外部實際提交的 batch 含 S1；receipt 卻是 adopted=2、submitted=0、omitted=1、buffered=1。S2 再成功送出後，兩份 snapshot 都在已提交 batches，receipt 仍顯示 submitted=1、omitted=1。
- **影響：** counts／omitted evidence 失真，將「已提交而無 host ack」誤計成「被 coalesce 省略」。這不是 message replay 或 sequence 逆序，也不是安全越權；但與本功能宣稱的 truthful submission／omitted 採樣計數不符。command reentry regression 的成功不能證明 job coalescing 的提交原子性。
- **現有測試缺口：** `tests/review-core.test.ts:85–90` 的同步 reentry 是 command source，callback 只做 stop／busy／opportunity；`tests/review-core.test.ts:96–105` 的 job refill 發生在兩次 flush 之間，沒有在 send callback 內覆寫 selected snapshot。
- **最小離線回歸（未執行）：** 用現有 FakeClock／fixture，source 換成 `shell_job`，held launch 提供 sink；採納 S1。第一次 send callback 內只重入一次 `sink.data(undefined,false,{revision:2,status:'running'})`，正常返回。断言首批確實含 S1、receipt submitted=1／omitted=0／buffered=1；advance 30000 後再断言 S2 提交，submitted=2／omitted=0／buffered=0、event IDs 不重播、sequence 遞增。另可用一次 throw 的 variant 核對 rollback／coalescing 政策，但不要以 sleep／真實 job／provider 測試此核心 interleaving。
- **修正方向：** 為 selected/in-flight data 建立 transaction／reservation，coalescing 不應把 in-flight、最後成功提交的 event 計成 omitted；successful-send 計數不應只依 callback 返回後的 queue membership。throw 路徑仍需保留真實未提交資料、正確 bytes 與 event identity，不能為修計數而假造 ack 或重播已提交事件。
