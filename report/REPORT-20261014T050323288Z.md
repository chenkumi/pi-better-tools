## Warnings (should fix)

### G6-001：100000-entry 停止恢復的檢查只在 restore，未涵蓋 session 持續成長

**狀態：待驗證／未執行；暫定 Medium，容量與行為契約候選，不計正式缺陷。**

- 產品位置：`modules/pi-runtime/src/index.ts:64–77`、`:44–62`、`:118–151`；規格 `modules/pi-runtime/README.md:32`。
- 規格預期：session 超過100000 entries 後停止恢復。
- 觸發假說：runtime 在低於門檻時正常啟動並保持 healthy；同一 session 持續新增 entries 超過100000，不 tree／reload；真正使用者 task 出現可修復錯誤，且同模型、持久 session、額度未耗盡。
- 靜態實際路徑：`restore` 在第77行檢查 entries 總數，但只有 session_start／session_tree 呼叫它（95–99）。正常 admission 126行、pending 137行與 reserve 57–62行未再檢查總數，`eligible` 52–55行也沒有容量檢查。因此可能仍返回 `continue:true` 與 recovery draft，或允許 TUI 手動 submission。
- 根因假說：總歷史停止條件實作成還原時檢查，而不是 submission admission 不變量。
- 影響：長 session 可能違反明訂的停止條件，繼續同步 branch 探索與 state append；每 task 最多額外兩次恢復，不能推論成無限 retry、資料損失或安全授權繞過。沒有延遲、RSS 或吞吐量量測，不能宣稱效能退化程度。
- 反證：啟動時已有合法 runtime state 且總 entries 超標，restore 確實 fail closed；tree／reload會重新檢查。LIMIT、handled IDs 與 fingerprints 防護依然存在。若100000只是 restore 的 inspection limit 而非所有恢復的門檻，需由規格 owner 澄清 README，而不能自行把它改解讀成已通過。
- 輔助容量觀察：restore 第66行先取得完整 branch，第76行先取得完整 entries 才檢查；host `session-manager.js:1062–1071` 建 branch，`:1107–1108` filter 複製全部 entries。故此檢查也不是 pre-allocation 記憶體硬上限；這只是靜態成本觀察，未獨立列效能缺陷。
- 現有測試反查：`recovery.test.ts` 覆蓋額度／reload／tree／corrupt state，但沒有100000邊界成長斷言；真實 `runtime-host.mjs:44–209` 的14 modes亦未建立這種超大 session。測試存在不等於本輪執行，更不能代替候選重現。
