## 真正 reload／different evaluation 證據

每次新 temp、新 ModelRuntime、新 SessionManager.inMemory、新 SettingsManager.inMemory、新 DefaultResourceLoader、新 createAgentSession。DefaultResourceLoader 的 additionalExtensionPaths 指向**工作樹原始** `modules/pty-terminal/src/index.ts`，不使用 querystring、copy 模組或手寫 capacity。

工具由真正 AgentSession 已綁定的 `agent.state.tools` wrapper 執行；未手造 product manager 或 hook。没有呼叫 session.prompt/provider；這是 host loader/reload＋工具 lifecycle 補验，而非模型 agent loop E2E。

1. 本機 native Node PTY 印 READY、readline 持續讀 stdin；事件等待 READY。
2. 執行16次 `pty_read {waitFor:'READY',timeoutMs:0,since:0}`：每次真正 matcher admission 建一個真 thread，收到有界 matched 結果，terminate 故障 reject；原結果不被覆蓋，worker 尚未 exit，名額仍保持。
3. 同 generation 第17次讀取 assert `/capacity exhausted/`，constructor 未被呼叫，records 保持16。證明不是把 capacity 判斷 mock 成永遠成功。
4. 讓 native PTY 讀一行、正常 exit(0)，pty_wait_exit/pty_kill 確認 release，pty_list 為空。
5. 呼叫真正 `await session.reload()`。事件紀錄可見 reason:reload 的 session_shutdown/session_start。新 extension object 與已綁定 read execute wrapper identity 都不同，load errors及host errors為空。
6. 舊16個 thread 沒有任何 exit，新的 native PTY READY 後，再讀取成功建第17個 thread；assert16舊 generation＋1新 generation，總存活17。
7. 新 PTY 同樣自然 exit/release。真正 shutdown handler 執行後，仍有17個 thread 沒有 exit，卻未回報 worker ownership incomplete。

**matcher different evaluation 判定：**除正常1.2.0 loader/moduleCache:false與新 extension/tool identity，還有行為對照：舊計數已飽和且其threads無exit，新generation仍可 admission。這是獨立容量狀態的實際證據；没有直接匯出／讀取／改寫 active，亦沒有用querystring替代reload。identity 本身只證明 extension/tool 新建，不單獨拿它當matcher計數重設證據。

事件 log 的 generation tag 在 session.reload 返回後才切成2，所以 reload 的 shutdown/start兩筆記作 generation1；reason:reload正確，並非略過新版session_start。

## Fault boundary 與影響界限

唯一 worker fault seam：替換 `node:worker_threads.Worker` 的外部建構 export，僅攔截 URL 正好指向產品 `modules/pty-terminal/src/match-worker.mjs` 的建構。非 matcher URL 原樣委派，沒有終止或修改其他 threads。

捕捉到的每個 Worker 都是繼承真 Node Worker 的**實際自有 thread**。它執行新增 `f2-owned-worker.mjs`：同樣用 source/flags/input 做小型 READY regex、post ready/matched，但以 parentPort listener 保持活著直到收到release；無 busy loop、catastrophic regex、OOM 或 sleep。保留產品傳入的 resourceLimits。每一 owned worker 的 terminate 只 reject一次呼叫，不真正停止；產品 matchPattern 的 finally/capacity/exit listener 均原版執行。此為受控的「termination failed且exit尚未確認」合法外部邊界，不是模擬 capacity。

**重要限制：**產品原 match-worker.mjs 雖未被修改，測試的 thread body 是外部 boundary fixture，不能宣稱正常worker一定會長留、terminate reject在實機自然發生或原 regex會卡死。確認的是產品在允許外部termination failure後，容量／ownership不能跨真reload維持；不是發現新的native Windows kill缺陷，不量測記憶體耗盡或CPU負載，不以51 threads數量推論資源利用量。

native PTY 真正conpty thread沒有替換；每run兩個PT Y均正常exit0。工具執行經真host wrapper但沒有LLM tool_call runner，本項確認不需要provider，也不宣稱provider整合驗收。

## 修復驗收／尚未執行

建議 capacity與worker ownership採process-wide、跨evaluation registry；terminate reject後shutdown不可只看已settled promise，應保留待exit的handle並回報 incomplete，舊worker exit後才恰一次歸還名額。
