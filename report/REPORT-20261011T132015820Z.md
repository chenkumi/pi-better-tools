## Critical (must fix)

### C1 — Expanded budget 與真正 Zod reference resolution 選到不同 definition map，可繞過 R10 admission
- **位置：`modules/json-schema/src/schema.ts:123–128`、`152–157`。**
- Budget 取 `root[parts[0]]` 作為 reference 目標；但目前 Zod 的 converter 在 `node_modules/zod/src/v4/classic/from-json-schema.ts:931–932`，以及實際 CJS `:896–897`，統一選擇 `normalized.$defs || normalized.definitions || {}`。其 `resolveRef()`（TS `:144–151`）只用 draft 決定允許的 pointer prefix，再從 **ctx.defs** 取名稱。當兩個 map 同時存在且同名定義不同時，budget 看 `definitions.S12`，真正 converter 卻看 `$defs.S12`。
- **最小靜態反例：** draft-07 根 object，同時提供 `$defs` 與 `definitions`；`properties.x.$ref = '#/definitions/S12'`。`definitions.S0..S12` 全部為 `{type:'string'}`；`$defs.S0` 為 required `v:string` 的 object，`$defs.Si` 為兩個 `#/definitions/S(i-1)` 的 anyOf。Audit 會掃兩個 map，但不做 expanded admission；budget 只沿淺的 definitions，converter 則沿 `$defs` 的重複 reference DAG。
- R10 現有測試只用 `$defs` 單一 map，沒有覆蓋此選擇差異。這不是要求完整 recursive-data CPU sandbox，而是**新 expanded-work gate 與其聲稱防護的 converter 不一致**。無 pattern 時之後仍在主執行緒 `validator.safeParse()`（`:175`）；已被 worker 原有 depth8 case 證明的失敗分支放大機制仍適用。
- **父代理最小驗證：** 先用 depth8／operation/leaf counter（最多256葉）證明解析到 `$defs`，不要使用深度20或時間壓力測試；再用 depth12 只測 `compileSchema()` 應以 expanded-budget diagnostic 拒絕的 assertion，重複3次。不得因目前它接受就執行無界大資料驗證。此 reviewer 未執行上述案例，4096葉是結構推導，不是實測數字。

### C2 — Stale recovery 吞掉 metadata close 的 cleanupUnsafe，初始化補償仍會釋放 writer ownership
- **位置：`modules/subagents/extensions/subagent/session-store.ts:301–303`，關聯 `:111–113`、`:412–415`、`:311–312`。**
- 新 `atomicJson()` 在 FileHandle.close 拒絕時附上 `cleanupUnsafe:true`，新 `initializeLock()` 也會對直接收到的這類故障保留 ownership；但 recovered 路徑先呼叫 `rollbackToCheckpoint()`。
- Rollback 在 `:412` 寫 manifest 時若 metadata handle.close 拒絕，`catch { return false; }`（`:415`）會把故障及 cleanupUnsafe 都吞掉。`initializeLock()` 因 false 在 `:301` 新造 `SESSION_BLOCKED`，此新錯誤沒有 cleanupUnsafe，接著 `:311–312` 刪掉 writer.lock 與 live nonce。結果是 **仍未確認 metadata writer close，卻移除禁止後續 writer 的所有權證據**，並失去原始 close 診斷。
- **最小父代理 fault-seam 設計：** 重用 R6 已提交 checkpoint／same-process orphan nonce fixture；只對 recovery 寫入 `manifest.json.<ULID>.partial` 的真實 FileHandle.close 注入 rejection，保留該 owned handle 到 teardown 才真正 close。正常 owner.json publish 必須成功。斷言 acquisition 拒絕包含 close diagnostic、writer.lock／live nonce仍保留，第二 writer／query拒絕；原碼按上述控制流會走刪除補償。只使用自己建立的檔案與 handle，不注入全域 credentials 或真 PID。
- 目前 R7 close regression 只攔 `writer.lock/...partial`，沒有涵蓋 recovered manifest close。這是 **R7 close safety 修正的剩餘分支**，不冒稱本輪首次造成資料毀損或已實測 pending OS write。
- **最小修正方向：** rollback 的不可安全 cleanup 故障不得退化成 boolean false；傳遞原始 ownership 診斷／標記，使 initializeLock 保留 lock與nonce。正常 hash不符／無 checkpoint仍可維持既有 false/refusal語意。先新增隔離 red3，再改碼；補 green3及既有 stale recovery/query lease guards。
