## 七候選逐項判定、影響、修正驗收

### 1. permit / lateclose — confirmed

位置：child.ts:97–102,135–146；manager.ts:138–148,239–253。

三次結果皆相同：實際 acceptFork 受理四筆 → onTurnEnd 實際 snapshot／runner → shutdown ladder 結束而 childClosed:false → fake process transport **之後才 emit 四個 close** → activeCount 仍為 4、record.cleanup.childClosed 仍 false、released 仍 false → 真實 acceptFork 第五筆仍拋 FORK_CAPACITY。log 欄位 realCloseEvents:4 指真實產品 close handler 收到的 **mock process close event**，並非四個 OS child 實際退出。

影響：晚到 close 缺少向 manager reconciliation，已觀察 close 後 permit 永久被保留。原 README 的「未 close 保留」不構成修復；confirmed 的是 close 已到仍未釋放。

修正驗收：done childClosed:false 之後的 close 必須更新持久 cleanup/exit、釋放 permit、刷新 UI；四個 close 後第五筆可受理，不重新完成答案／重送通知；close 前仍保留 permit。

### 2. finalizingcancel — confirmed

位置：child.ts:175–187；RpcPipe rpc.ts:41。

三次皆 capture get_last_assistant_text 待回覆 → handle.cancel 已接受 → 明確釋放該 request 已註冊 30000ms deadline → 仍送 get_session_stats → 才觀察 abort，最後 cancelled／childClosed:true。commands 皆 get_state,get_session_stats,prompt,get_last_assistant_text,get_session_stats,abort。

影響：finalizing 不以 cancelSignal 競速，取消可能卡住 final RPC deadline；並可在取消後繼續送下一筆 stats。沒有實測兩筆都 timeout，因此不宣稱已實測 60 秒延遲。

核最新修復：child.ts:160 的 raceCancel 只修啟動前 stats，178/180 仍裸 request，不能算本項 already-fixed。

修正驗收：分別 hold final text／final stats，cancel 不需放行其 RPC deadline 就進 abort／EOF／close；不得在 cancel 後新增 stats request；quit/reload 路徑同樣驗證。

### 3. origin load64 — confirmed

位置：store.ts:69–75；manager.ts:202–214。

三次各寫 A 一筆舊 pending、B 64 筆 lexicographically newer 合法 ULID metadata，共 65 files；loadRecords 得 64 筆但沒有 A。onSessionStart(A) 兩次，registry A=0、notifications=0，A 檔仍存在。

影響：來源 A pending inbox 被其他 origin 的新歷史遮蔽，返回原 session 也無法投遞。

修正驗收：新重啟 registry 下 A 的 pending 即使落在其他 origin 64 筆之後仍可恢復／投遞，且不能誤送 B；以有界掃描／索引保留恢復進度。

### 4. restore retention — confirmed

位置：manager.ts:202–217（對照 admission cap 71–76、evict 102–105）。

三次均於三個自有 workspace 各保存 64 筆已送達 completed，依序 session_start；真實 registry size=64→128→192，activeCount=0，沒有 accept 新工作。不是 OOM／推測無窮跑到耗盡。

影響：restore 不受 admission 的 64 safety cap 或 README 32 retained 保護，多 workspace 恢復可重複增加常駐 metadata；本次證明有限三階段增長，不假稱已量測無限記憶體。

核最新修復：現有 review-fixes 的 acceptFork retained cap 可防新 admission 增長，但不防 restore，本項未修。

修正驗收：多 workspace 恢復也有明確全域 retained bound／lazy inbox；不能以截斷尚未送達 inbox「修」此項而引入第3項。

### 5. 大 final silent success — confirmed

位置：child.ts:113–132,178–194；manager.ts:143–145。

三次皆讓真正 correlated get_last_assistant_text response 帶 ASCII 4194305 bytes text（不是垃圾輸出行），超過 4 MiB reader limit，放行其真實註冊的 30000ms RPC deadline，再正常 stats／EOF／close。outcome completed、childClosed:true、exitCode:0，沒有 output、errorCode 或 truncation signal。

影響：成功但答案靜默遺失。manager 的 32 KiB truncate 發生在取得 output 之後，救不回被 reader 丟棄的 correlated response；既有 oversized-garbage 測試不是本情境驗收。

修正驗收：同尺寸真實 correlated response 必須有界保留答案摘要且標明截斷，或明確 result-unavailable/failure；不能無內容 completed。保留有界 drain。

### 6. Atomicsretry — confirmed

位置：store.ts:43–51。

三次各一個真實 saveRecord，在 rename boundary 持續 EPERM：每次 13 rename calls、12 次原生 Atomics.wait，requested 10,20,…120ms，總 requested=780ms；save 同步 wall-time 分別 **861.8585、873.7954、856.4767 ms**。各次逐 wait duration／timed-out 結果均在 raw logs。失敗後 tmp 檔已清除。

影響：同步主 JS 呼叫約 0.86–0.87 秒不返回；不是 async background retry。未實測四筆 cancel、不宣稱 3.12 秒的外推是實測；未操作真實 Windows sharing lock，fault 為外部 rename EPERM 模擬。

修正驗收：rename-sharing fault 下不使用同步 Atomics.wait 阻塞 event loop；明確受理失敗或有界非阻塞隊列，維持 terminal persistence-before-delivery，不丟取消／close reconcile。

### 7. UI delivery — confirmed

位置：manager.ts:158–161,172–189,275–277；live-widget.ts:26–40,59–65；background-panel.ts:37–41,124–139。

三次皆實際 acceptFork → cancel-before-start terminal publication → sendMessage boundary 加入 journal → own setImmediate ack 確認 observed → 實際 panel.openMore('fork')、render list、Enter Details。record/disk delivery=observed、notifications=1，但真正 JobsOverlay Details 仍顯示 delivery pending。畫面全文保留於各 log。

影響：More 可持續呈現舊投遞狀態；此實測為取消終態，與 completed 共用同一 publishTerminal/deliver 路徑。沒有宣稱人工 TUI 或 persistError 全情境皆實測。

修正驗收：submitted/observed/unknown 與 persistError 改變後刷新 snapshot；完成與取消、已存在 journal ack、send throw 分別驗證；UI 例外不得影響 permit／結果投遞。
