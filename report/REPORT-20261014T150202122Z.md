## Warnings (should fix)
### F1 — P2：Windows kill 在首筆 output 前只是排隊
- **位置：** `modules/pty-terminal/src/pty-manager.ts:458–466`。
- **觸發／影響：** Windows transport 尚未產生首筆 data（例如啟動卡住）時，kill／shutdown 呼叫 backend kill，但實際終止操作被 deferred；2 秒後只回 retained，reload 重試仍無法真正終止這個 transport。不能靠 Ctrl-C 解救，write 同樣排隊。
- **證據：** 已安裝 `node-pty/lib/windowsTerminal.js:71–86` 僅在首筆 data 設 ready；`:157–177` 的 kill 經 `_deferNoArgs` 排隊。`windowsPtyAgent.js:153–172` 雖可清除 pending connection，公開 kill 未 ready 時到不了這裡。產品未繞過此限制；現有 real-PTY kill 測試先讀 READY。
- **建議：** 採用／適配具備 pre-ready cancellation 的 backend，建立「未收到首筆 data 仍可取消」契約測試；勿以 retained/recovery 冒充有效終止。此為靜態控制流證據，未實機重現啟動停滯。

### F2 — P2：未退出 matcher 的容量跨 reload 歸零
- **位置：** `modules/pty-terminal/src/matcher.ts:7`、`:59–69`；`modules/pty-terminal/src/pty-manager.ts:406`、`:513`。
- **觸發／影響：** terminate reject 且 worker 尚未 exit 時，函式保留舊模組 active 名額，但 Promise 已 settlement，manager 隨即移出 matches；shutdown 可完成且不再管理該 worker。reload 載入新模組後 active=0，允許再開 16 個；重複失敗／reload 可突破宣稱容量，累積 CPU／記憶體與活著的 threads。
- **證據：** 本機 Pi `dist/core/resource-loader.js:354–355` 清 cache；`dist/core/extensions/loader.js:477–480` 使用 moduleCache:false。`tests/matcher.test.ts:93–114` 證明同模組 terminate-reject 名額保留，但未覆蓋 reload；worker 沒有跨 generation registry。
- **建議：** 讓 worker ownership／capacity 使用行程級 registry，shutdown 回報尚未確認退出並保留重試 handle；名額只在 exit 證據後釋放。reload 證據來自本機 Pi 1.1.0，尚未核實 1.2.0 loader 是否相同。

### F3 — P2：interactive input 沒有 retained-byte／背壓限制
- **位置：** `modules/pty-terminal/src/index.ts:84–93`；`modules/pty-terminal/src/pty-manager.ts:287`。
- **觸發／影響：** Windows 首筆 data 尚未出現，或目標不讀 stdin 時，持續 pty_write 可無界保存輸入；每次仍回 ok。16-session／output ring 上限完全不涵蓋此輸入佇列，可耗盡 Pi 記憶體。
- **證據：** schema 無 data maxLength／keys maxItems。本機 `node-pty/lib/windowsTerminal.js:119–124`、`:179–189` 在未 ready 時保存每次 data closure；ready 後忽略 Socket.write 回傳的背壓訊號。未量測吞吐或 heap，不宣稱 POSIX 實機也有相同程度問題。
- **建議：** 限制單筆 decoded input 與各 session 累計 pending bytes，使用能觀測 drain 的 transport adapter；容量不足明確拒絕且不得默默丟輸入。用受控未-ready／blocked-write fake backend 驗證，不使用 idle 等待。

## Suggestions (consider)
### F4 — P3：Windows PID 永久保存初始 0
- **位置：** `modules/pty-terminal/src/pty-manager.ts:256`、`:279`、`:478`。
- **觸發／影響：** Windows spawn 非同步完成連線；manager 在返回當下複製 pid，後續 list／renderer 不刷新，因此正常連線後仍顯示 Local transport PID:0，妨礙人工核對／清理。
- **證據：** 本機 `node-pty/lib/windowsPtyAgent.js:33` 初始 innerPid=0、`:125–126` 後續更新；`lib/windowsTerminal.js:62–69` 更新 getter 所依據的值，產品保存的 number 不會跟著變。
- **建議：** PID 尚未知明示 unknown；summary 讀取 backend 最新 pid，或 readiness 後更新。未啟動 native PTY 驗證。
