# File Audit 讀後外部覆寫：真正 PTY 交付流程 A/B/C 實驗結果

## 結論

實驗完成：**在近期候選仍涵蓋 config 時，File Audit 加上明示的交付前手動關卡，能阻止原定向測試流程放行的錯誤產物，且以較小內容讀取範圍提供與本次全量驗證相同的關鍵定位。** 它沒有自動讓模型發現或修復問題；掛載但不執行 check 不等於有這個效果。

同時確認限制：config 被容量淘汰時，增量檢查只得到 feature matched，不能發現 config 已變更。實驗的操作者政策因缺少必查檔案而暫停，但這不是產品自動 gate。若誤把 matched=1 當全部安全，仍會錯誤交付。

## 實驗設計與真實性

- 真正 Pi 1.3.0 fullscreen TUI，node-pty 送入 prompt／slash commands，不使用 print/RPC 或假通知替代畫面。
- 三情境 clean／late-overwrite／evicted，分別輪替 A→B→C、C→A→B、B→C→A；最終共9個真實 CLI，隔離 home/agentDir/cwd/空auth，全部退出0並有shutdown記錄，成功工作目錄已刪除。
- A：不掛載 File Audit，交付政策只看原 feature 定向測試。
- B：掛載 File Audit，操作者在交付前手動 status/check；政策要求 config+feature 都有覆蓋，且不存在 mismatch/unavailable/untracked 等未解項目。
- C：不掛載，測試專用 `/workflow-full` 執行與 repository **逐bytes相同**的 `scripts/verify-sources.mjs`。它對相同受控 workspace 的有效 provenance 做完整驗證；不是拿手寫 hash comparator 冒充原驗證器。
- 比較器 fixture 提供最小有效的套件身份 metadata 與 inert entry files，沒有 npm 安裝或真實套件載入。全量內容inventory為 config、feature、64個16KiB無關原生檔，合計66檔；preload只計數真實 readFile，不改內容/hash/斷言。config刻意放最後以觀察fail-fast前完整讀取量，不能外推成正式repository的平均效能。
- 離線合成 provider 固定各組相同操作；真實工具讀／編輯、父程序外部覆寫、真實 Node 定向測試、原樣全量驗證器、新 Node 執行產物皆實際執行。沒有呼叫付費 provider，不能將固定腳本視為真實模型自主推理或錯誤率測量。

## 故障與獨立 oracle

任務要求：修改 feature.answer 為2，同時保持 rollout=true。

```javascript
// config.mjs 原先內容
export const enabled = true;

// feature.mjs 由工具把 answer=1 改成2
import { enabled } from './config.mjs';
export const answer = 2;
export const rollout = enabled;
```

Pi 成功 read config=true 並完成該 run 後，父程序才把 config 改成 false，然後透過下一個 PTY prompt 讓 Pi 繼續讀／編輯 feature，並在真正 Node 子行程跑只斷言 answer=2 的定向測試。測試仍通過，但 rollout 已變 false。

父程序另以新 Node 程序載入產物，獨立檢查 `{answer:2,rollout:true}` 及已知需求bytes；此 oracle 不使用 Audit結果或 provenance parser。關卡決策先完成，才讀 oracle；因此沒有偷用故障旗標或oracle決定是否攔截。

為排除正常開發變更的雜訊，三組都由 fixture 的模擬收尾人員只更新已核准 feature 的 expected hash，**config 的 expected hash 保持原值**。這不是產品自動補簽；注入及修復 config 均確認metadata未變。

## 正式結果

| 情境 | A 原定向流程 | B 掛載＋手動增量關卡 | C 原樣全量驗證 |
| --- | --- | --- | --- |
| clean | 測試通過，允許交付；runtime正確 | matched=2、覆蓋完整，允許交付；無假警報 | exit0，允許交付；runtime正確 |
| late-overwrite | 測試exit0仍允許交付，但 runtime.rollout=false | 定位config mismatch，政策blocked；操作者依診斷修復後重查通過，rollout=true | exit1定位同config，政策blocked；修復後exit0，rollout=true |
| evicted（B容量=1） | 測試exit0仍允許交付，但 rollout=false | config被feature活動淘汰，只有feature matched=1，**沒有發現config異常**；政策因缺必查config標review-incomplete，未修復，rollout仍false | 仍exit1定位config，修復後exit0、rollout=true |

A 在兩個刻意植入異常的腳本中都被原政策放行；這不是「真實模型錯誤率100%」。B在範圍內案例提供可操作診斷，在範圍外案例無法診斷；C兩種都定位。B/C後續修復是依可見檔名由父程序模擬操作者執行，不是模型或extension自動修復。

### 正式主案例 B 的保存時間線（UTC）

1. `08:38:51.575`：Pi read config成功，讀到true。
2. `08:38:51.590`：父PID29248覆寫，Pi PID23472；兩PID不同、config hash改變、metadata未變。
3. `08:38:51.981`：feature-only Node測試退出0。
4. `08:38:52.000`：只收尾核准的feature metadata。
5. `08:38:52.145`：手動檢查顯示config mismatch，操作者政策blocked。

時間間隔是fixture自動化操作，不是真人收尾時間，不能拿來宣稱節省人工秒數。

## 請求與 tokens

- 每情境每arm均7次合成模型請求；正式workflow共63次，外部模型／fetch calls=0。
- status/check、全量比較器及修復重查皆未新增模型請求，之後相同context probe也沒有報告注入。
- 每情境A/B/C的正規化語意payload逐次完全一致；使用先前隔離安裝的 `js-tiktoken@1.0.21 o200k_base`，各arm序列化輸入估值14,227 tokens，B−A與C−A均0。
- 正規化只處理受控根路徑，沒有移除報告來湊相等；完整未修改transcript另存。估值不是provider framing、reported usage、cache或帳單，也不含開發測試對話。
- 真正把診斷貼回模型、請模型修復時會有額外context與回合；本實驗的人工修復流程不量測該成本。

## 建議如何使用

把 `/file-audit status`／`check` 當作交付前的低成本近期檔案複查，發現不符再決定修復／確認變更／正常更新provenance。必查檔案不在候選、已有淘汰、metadata不可用或需要完整專案保證時，改做完整驗證，而不是把局部matched當安全認證。這是本次實驗支持的流程價值；不支持「裸掛載就自動避免所有錯誤」的主張。
