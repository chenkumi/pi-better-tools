## W3 清除依據

### 1. Delete 成功後替換真正 Save buffer

`config-flow.ts:401–414` 的成功路徑現在依序：
1. await 指定 scope 的 deletion callback；
2. 對 Global/Project 重新讀 scope source，若檔案仍存在則拋錯；
3. 讀取 fresh lower-layer values；
4. `:409–410` 清掉 `currentValues` 所有原 keys，再 assign fresh values；
5. `:411–414` 更新 body rows、清 flow dirty keys、重取 inspection，最後 dismiss overlay。

這是 **replace，不是 merge**，所以已刪 scope 的 stale values、old-scope unknown keys 與 ignored controls 不會殘留於 Save buffer。`saveEdit:307–310` 仍將 buffer 複本交給真正 Save；沒有關閉 Save、繞過 confirm 或另換保存來源來遮蔽問題。Delete 後明確 Save 可以重新建立檔案，提交的是 fresh 畫面值；只改 debug 也不會讓未碰欄位復活。

必要依賴 `body.ts:208–224` 仍只更新 body rows／initial values／dirty state，不會自行更新 flow buffer；因此新增 clear＋assign 正好修復前報已確認的缺口。Reset `config-flow.ts:365–374` 保持已接受的相同替換邏輯，本次沒有重構或改其保存語意。

### 2. 可觀察 unlink refusal 不再假成功 refresh

既有 `config.ts:173–181` 會吞 `rmSync` 錯誤，單憑 deletion callback 正常返回不能確認檔案不存在。新增 `config-flow.ts:404–405` 在任何 buffer/display/dirty 更新前检查 Global/Project `scopeSources().exists`；檔案仍存在則 throw，走 `:415–416` 原 error path。

`ConfigManager.openSettings:1084–1096` 的 layerValues、inspection、scopeSources、save/delete callbacks 使用同一 cwd/configDir；`scopeSources:790–812` 以實際對應檔案的 fresh `existsSync` 決定 exists。此受支援接線中，guard 不是 UI 快取，且沒有查 unrelated scope 或觸碰 SDK。

確認取消會在 `:395–397` 返回；async callback refusal 在 await 處拋錯；observable unlink failure 在 guard 處拋錯。這些路徑都不執行成功 refresh、buffer replacement、dirty clear 或成功 dismiss。既有 Save write refusal 由 `saveEdit:318–320` 處理，沒有提早清 dirty state。

**限定保證：** guard 是受信 CM scope-source 的可觀察 postcondition，不是通用 filesystem transaction，不保證任意 callback/source implementation、stat permission/symlink 情況或跨 process external writer 原子性，也不 rollback 已發生的部分副作用。本轮沒有以未知外部 writer 假設增加 must-fix。
