## P2 — confirmed

三個獨立 Node 行程、全新 OS temp home／agentDir／workspace，逐次 reset mode/counters。真實 entry import 後先跑正常成功，再跑 write fault 清理對照，最後跑 close fault 與正常重試。

- 正常：wx/open、write、close 真實 OS 操作，成功回報相對路徑，磁碟內容一致。
- write fault：在真實寫入 partial 後 FileHandle 邊界拋 ENOSPC；產品原 catch 自行 close/rm，目錄無殘檔。這證明測試没有替換產品 cleanup。
- close fault：真實 write 成功、真實 OS close 完成後，FileHandle adapter 回報 EIO。產品 close 在 write catch 外，保留原 Error identity、execute reject、無 result/relativePath，磁碟卻有一份內容完整的檔案。open/write/close 各 1 次。
- 解除 fault 後正常重試：原殘留仍在，產生另一份完整檔案；每輪 assert 檔案數為 2 且路徑不同。

三輪原殘留分別為 PLAN-20261014T160704636Z.md、PLAN-20261014T160721499Z.md、PLAN-20261014T160739142Z.md；具體重試檔名與內容斷言見各 raw log／source。

### Mock 邊界及驗收影響

僅 node:fs/promises.open 回傳的 FileHandle write/close adapter 注入 boundary fault，透過 syncBuiltinESMExports 供產品 named import；open、實際寫入、實際 close、mkdir、realpath、rm、host mutation queue 均實際執行，未置換產品 catch/cleanup/execute。registerTool 是最小收集 adapter，不冒稱真實 CLI 註冊驗收。

close EIO 為人工邊界注入：證明「close reject 時未清理、失敗後無路徑且重試產生副本」的現行控制流程，不證明這台磁碟曾自然發生 delayed I/O error，也不證明資料毀損。真實 close 先完成避免測試留下 OS handle；此 fault model 刻意涵蓋 close 回報失敗但內容已落檔的合法不確定性。未注入 cleanup failure，也不聲稱驗證刪除失敗的呈現契約。

## P3 — refuted（作為缺陷；优化建議仍可保留）

確認產品先呼叫 Unicode regex，再 Buffer.byteLength，之後才取消檢查。單獨工作量 probe 用代理轉呼原生 regex／byteLength，每組記錄一次 regex 呼叫、輸入 16/32/64 Mi UTF-16 code units、一次 byteLength；此為傳入引擎的工作量，不等於 VM 實際逐字元掃描次數（ASCII 可有引擎优化）。

效能測量完全恢復 regex/Buffer/fs 邊界。用合法 ASCII x 與 BMP 文，建構 16/32/64 Mi units 字串；計時前一次原生 byteLength 將 repeat 字串 materialize，排除首次字串展平成本。產品與 byte-first、length-first 最小拒絕對照輪替順序；每組 3 輪 warmup + 9 輪正式樣本，三個独立行程。對照不是修改後產品，只隔離拒絕前必要工作，不能當成功能等價替代驗收。每次 assert NOTE_TOO_LARGE，perf workspace 一直沒有新增目錄或檔案。
