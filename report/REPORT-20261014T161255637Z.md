## F1 — confirmed（縮限至已受理 runner 的 transcript-open 晚到 I/O）

### 目前位置

- `background.ts:356–382,435–439`：submit 受理、await runner、finally 釋放 submitted。
- `index.ts:383–392,1088–1101,1120–1122`：active permit、晚到 owned cleanup、純觀察 settlement seam。

- hash 見上表。

### 實際差異與三次結果

1. 真正 BackgroundJobs.submit 受理 1 task，真實 runSingleAgent 進入 managed writer/實際 transcript open；open 已取得真正 FileHandle，但回傳被 deferred barrier 保留。
2. 透過產品 jobs.cancel 要求取消。產品 result 為 aborted、task_result 已通知、load 已變 submitted 0/32；onOwnedSettlement 尚未完成、真正 handle 未 close、真正 writer.lock 仍存在。
3. 預期：舊 owned I/O 仍占 1 名額，新 32-task batch 應回 BACKGROUND_CAPACITY。實際：真實 submit 接受完整 32 tasks，load 32/32，合計受理所有權為 33。
4. release deferred barrier 後 await 真實 owned settlement，assert 真正 handle closed、writer.lock removed；釋放第二批受控 runner barrier 並 shutdown，submitted 回 0/32。
5. 上表三次相同命令都得到相同差異、exit 0。沒有啟動 child；因此沒有用 1.1 host 冒充 RPC startup。

### 邊界、反例與影響

- 第二批 runner callback 僅以 deferred barrier 保留合法受理工作；沒有製造 32 個真實 child/provider，所證明的是 **admission ownership 超過 32**，不是 OS 同時有 33 個 FileHandle 或 child。
- F1 成立路徑是「已接受且已進入 runner」，不是 submitManaged 尚在 managed prepare 的 admission；也不是 writer lock 提早釋放。實際鎖正確保留。
- existing preparation unit 仍成功保留名額，不能宣稱所有取消路徑都提早釋放。沒有將此正常反例誤判成 F1 already-fixed。
- 重複阻塞可造成舊 I/O 不被 submitted accounting 覆蓋；本次不以算術或一次耗時宣稱已實測大量資源累積。

### 修正驗收

- receipt 可以立即 aborted/failed，但該 task 的 submitted permit 必須由 actual owned settlement/resource safety 管理，不因 runner 回傳而釋放。
- 本脚本場景取消後仍 load 1/32，新 32 tasks 被 BACKGROUND_CAPACITY 拒絕；barrier settlement 後 load 0/32，正常可再接受。
- 保留 existing managed-prepare retention；close rejection/cleanupUnsafe 不得假稱所有權已釋放；bounded shutdown 不應復活舊通知。

真實 entry register 的 catalog hook 在 selectedTools=[subagent]、trusted project、沒有 child dispatch/provider 的相同設定下，兩個 temporary directory 各配置 16/80/160 個有效 agent 定義。

|---|---|---|---|---|
| 16 | 32 | 64 | 2 | 2161648 |
| 80 | 160 | 320 | 2 | 2436336 |
| 160 | 320 | 640 | 2 | 2780176 |

每次最大單檔 = **524335 bytes**，完整讀取後參與真實 parse/catalog；遠大於既有 256 KiB dispatch metadata policy。80/160 的 catalog 有 omitted 顯示，但讀取工作量沒有被 64 display limit 限制。三次獨立 Node process 得到完全相同上述數量／bytes，全部 assert 與 terminal exit 0。

預期：catalog 的定義檔 allocation/工作量應先有明確界限，不應把 display truncation 誤當 I/O/parse 預算。實際：來源定義增加時全量讀取同比增長；trusted user/project/both 合成讓相同來源每回合各讀兩次。

### 邊界／影響

- 確認同步全檔讀取、重複讀取以及顯示上限不限制來源工作量。不是用一筆耗時直接定缺陷，也不對受 AV/磁碟影響的 elapsed times 下門檻結論。
- 未測 FIFO、特殊檔案、symlink、無限增長檔案、實際 peak RSS、並行 provider/abort latency，該等原報告延伸情境仍未證實。
- hooks 手動由相符輸入子集觸發，未驗證 1.2.0 host 事件發送；缺陷範圍是當前產品 catalog/discovery 函式在合法 cwd/trust/agent input 的 I/O 工作量，並不需要新 host loader/RPC 合約才能成立。

### 修正驗收

在 catalog/discovery 前設 regular target／bounded single-file read 與明確 discovery workload budget，超量明示 omitted，不先全檔讀再檢限；trusted 多 scope 合成避免重讀同來源。以相同 16/80/160 對照與 >256 KiB fixture 驗證工作量/單檔界限，保留正常小檔 precedence/catalog composition、dispatch/resume config fingerprint/trust fence。
