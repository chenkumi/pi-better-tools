## Suggestions (consider)

### 1. 合併 readonly capability publisher 的 scope／epoch validity 建構，不合併兩個 job registry

**位置**

- `modules/shell-tools/src/monitor-publisher.ts:13–16`。
- `modules/subagents/extensions/subagent/monitor-capability.ts:30–34`。
- 共用邊界：`modules/shell-tools/src/monitor-capability.ts:13–24`。

**證據與價值**

兩個 publisher 都在 publication 時捕捉 `sessionId`、canonical cwd、epoch，並在 `valid` callback 中逐次重讀 epoch／session ID／canonical cwd，以相同 `try/catch → false` fail-closed 語意判斷有效性。差異是 epoch getter (`monitorEpoch`／`epoch`)、snapshot reader 和 active-count callback，不是 owner 驗證原理。

現有共享 rendezvous 已由 Subagents 匯入，不需要新增 plugin manager 或新的模組依賴方向。把同一 validity predicate 的建構集中，能避免其中一個 provider 未來漏更新 cwd／epoch 條件，同時減少兩份相同 closure 邏輯。

**建議**

在現有 capability helper 內抽取一個小型 publisher／validity factory，接收 context、epoch getter、reader 與 count callback；publication 時捕捉 scope／epoch，callback 時重讀現值。外層 Shell `start/stop` 與 Subagent `revokeMonitor` lifecycle 原樣保留，reader 和 count 仍由各模組提供。不要為兩種 registry 建立共同 superclass。

**必須保留與風險（中）**

- `acquireCapability()` 在 reader **之前與之後**的 assert（`monitor-capability.ts:22–24`）不是重複：reader 可能使 capability 失效。
- Registry 內的替換／revoke identity 防線（13–18）原樣保留。
- Shell 的 `monitorSnapshot()` 二次 owner/cwd/epoch 驗證（`background-jobs.ts:445–451`）和 Subagent 的 `jobs.get()`＋provisional view（`background.ts:238–273`）原樣保留；它們是資料源防線，不是 publication predicate 的替代品。
- 不共用 active-status 集合：Shell 計 `running/cancelling`，Subagent 計 `queued/running`，各自狀態契約不同。
- Revocation 仍在 shutdown 的 await 之前：Shell 呼叫端 `timeout-ms.ts:292,297`；Subagents `index.ts:1260–1269`。不把兩套生命週期硬合併。
- 不存可執行 child handle、不改 canonical cwd 失敗處理、不建立 timer／模型請求／新的持久化欄位。

**既有驗證測試（只閱讀，未執行）**

- `modules/shell-tools/tests/monitor-capability.test.ts:9–15`：provider 替換後舊 lease 無效，舊 revoke 不刪新 provider。
- 同檔 `25–47`：正向 Shell job、foreign owner/cwd、epoch、held lease、cleanup 前 revoke。
- 同檔 `49–52`：snapshot reader 返回後重新驗證，不能刪除此檢查。
- `modules/subagents/tests/monitor-capability.test.ts:9–23`：不公開 private worker/query answer、不假稱原 lease 已釋放。
- 同檔 `25–43`：正向 Subagent lease、owner/cwd、替換/revoke/shutdown。
- 下游 `modules/monitor/tests/sources.integration.test.ts:63–72`：job adapter 只讀 snapshot／擁有 sampling timer，不取消 job 或 query 模型。

### 2. Fork 終結路径集中相同收尾序列，保留「沒有啟動 child」與「實際 close」的不同證據

**位置**

- `modules/fork/src/manager.ts:136–154`，尤其共同尾段 `143–145` 與 `152–154`。
- 狀態保存 `manager.ts:51–56`；來源綁定投遞 `164–182`。

**證據與價值**

`complete()` 和 `finishWithoutChild()` 各自建立 result、cleanup 和 permit 證據後，均依相同次序執行：`removeTemporary()` → `setStatus()`（含 persist／UI refresh）→ `deliver()`。這是同一個 manager 內的同一終結發布流程；兩份尾段將來增加 metadata／投遞處理時容易只改一個路徑，導致正常完成與 snapshot/spawn failure 的收尾政策分歧。

確認呼叫端：`onTurnEnd()` 在 snapshot 失敗／取消／origin abort 走 `finishWithoutChild()`（103–118）；`launch()` 的 spawn throw 亦走該路徑（129–133）；runner 的 `handle.done` 成功／拒絕走 `complete()`（133）；`requestCancel()` 的 pre-start cancel 走無 child 路徑（234–240）。

**建議**

僅抽取同檔的三步終結尾段 helper，接受 `job` 和 terminal status。Result 建構、bounded output、usageUnknown、childClosed 及 `released` 更新仍留在原分支中，兩分支建立完證據後再呼叫共同尾段。若只是為減少行數而引入通用「completion state machine」則不值得做。

**必須保留與風險（低至中）**

- 無 child 的路径有理由設 `childClosed:true/released:true`（149–151），但真 child 只在 `outcome.childClosed` 為 true 時釋放 permit（141–142）。不要以 terminal status 取代 actual-close 證據。
- `setStatus()` 的 endedAt／persist／UI refresh 和 `deliver()` 次序不變；不提前通知或將 helper detached/async 化。
- Result ID 仍每次終結建立 uppercase ULID，不改 record schema、來源 session/file/cwd 比對、pending/submitted/observed/unknown 投遞語意。
- 不把 `cancelRequested` 當 actual close；child runner 仍有 RPC abort／EOF／TERM／KILL ladder（`child.ts:135–146,187–194`）。
- 共用收尾不包含 orphan record 重建（`manager.ts:195–201`）；那是 session-load 核對，不是 live runner completion。

**既有驗證測試（只閱讀，未執行）**

- `modules/fork/tests/manager.test.ts:75–112`：boundary snapshot、正常結果、usage、persisted status、permit release。
- 同檔 `114–148`：A→B 不誤投遞、回 A 一次投遞、journal 去重。
- 同檔 `150–179`：reload/quit 扇出取消，未確認 close 保留 permit。
- 同檔 `181–198`：無 child 的 unpaired/abort/lost-origin 失敗與沒有捏造 snapshot。
- 同檔 `200–217`：owner gone 不重跑、pending 結果回來源。
- 現有測試沒有直接斷言兩個終結路径完全相同的 temp cleanup／persist／deliver 呼叫順序；若實作此候選，应以局部 characterization 覆蓋這個缺口，而非僅由上述結果斷言推論順序已被鎖定。

### 3. Shell 兩層 catch 共用 timeout exception 正規化，兩層 catch 和 diagnostics ownership 不合併

**位置**

- `modules/shell-tools/extensions/timeout-ms.ts:201–207` 與 `267–274`。
- 已有 trailing-only formatter：同檔 `64–71`。

**證據與價值**

兩個 catch 都檢查 `Error`＋`input.timeoutMs !== undefined`，呼叫 `timedOutMessage(error.message, foregroundOnly)`，只在文字變化時建立 `new Error(timedOut, { cause: error })`，否則原样 throw。兩份 exception wrapper 邏輯是同一語意；formatter 已共用，但 cause／instanceof／非 timeout identity 的轉換仍重複。此候選價值是防止兩種路徑的診斷／cause 漂移，不是刪除一層 try/catch。

**建議**

抽取局部 exception 正規化函式，接收 unknown error、是否提供 timeoutMs 及 foregroundOnly；無需改寫就返回原 error，需改寫才返回帶原 cause 的新 Error。兩個既有 catch 保持目前 logFailure 條件與時機，然後 `throw` 正規化後的 error。這是小型、低優先序整理，不值得另增檔案或重設 diagnostics 架構。

**必須保留與風險（低）**

- 內層 catch 有背景／handoff ownership 判斷（202），外層 catch 包括 argument/settings/admission 等錯誤；不能因轉換程式碼相似就合併 catches、移除 logging 或變更失敗記錄次數。
- Formatter 仍只匹配宿主尾端診斷（67），不得搜尋／替換任意命令輸出；二次轉換保持冪等。
- 非 Error、沒有 timeoutMs、沒有匹配尾端文字皆返回原值，保留 object identity；不能全面包成 Error 丟失原始故障。
- foregroundOnly 仍不推薦 background:true；不改 timeoutMs、tool signal、handoff、status 判定或 outputSchema。

**既有驗證測試（只閱讀，未執行）**

- `modules/shell-tools/tests/timeout-diagnostics.integration.test.mjs:21–35`：命令輸出含 timeout 字樣的非零 exit 不改成 timeout。
- 同檔 `53–65`：只改實際尾端 timeout、跨兩層 catch 只出現一次 marker、背景 timed_out。
- 同檔 `67–78`：偽造 marker 不變 timed_out、取消不改成 timeout。
- Fixture `modules/shell-tools/tests/fixtures/timeout-diagnostics-host.mjs:17–24,37–60`：fake backend 經真實 extension／宿主 shell definition 的相關呼叫路径。
- 既有 D17 斷言主要驗文字／status，未直接驗非 Error identity 與 cause chain；實作時需局部補足這兩個 characterization，而非宣稱既有 coverage 已完整。

## 不列為冗餘的候選

- **Pi Runtime admission 三階段與 WeakSet**：`src/index.ts:36–43,122–147` 不只是重複狀態，而是 input→preflight→agent_start→實際 user message 的一次性證據鏈。`tests/recovery.test.ts:214–255,289–295` 已示範 handled/queued/custom/extension input 與轉換文字差異；不建議合併成單一「見到 input 即新 task」旗標。
- **Runtime 持久化 branch snapshot＋session-wide reservations**：`src/index.ts:84–113` 是不同檢查範圍，`tests/recovery.test.ts:151–166,188–213` 保護 reload／tree 不退款及 corrupt fail-closed，不當成重複掃描刪除。
- **Runtime confirmation 前後檢查／generation**：`src/index.ts:210–239`，前置 eligibility 和批准後 `reserve()` 重驗處理不同時間點；`tests/recovery.test.ts:143–150,258–288,382–389` 顯示往返切換亦須失效。不缓存 approval 前的安全結論以省略後檢查。
- **Monitor job/command/WS cleanup**：`sources.ts:14–16,50–58,63–79` 分別依 process close、transport close、sampling timer cleared 建立證據，不能抽成單一「promise settle = close」共用邏輯。WS startup deadline、DNS pin 和 binary/payload 防護不是多餘流程。
- **Monitor auto/manual admission**：`src/index.ts:21–30,45–61` 雖共用部分 job preflight，但 auto best-effort、固定 display-only policy 與 manual signal/error contract 不同；目前重複量不大，本輪不建議以通用 dispatch 抽象換掉清楚的兩條入口。
