# JSON Schema：native retry 成功仍被 sticky failure 拒絕的聚焦審查

**判定：當前實作確實會拒絕最終成功的 Pi native retry；另有成功重試後 stdout 說明文字未被抑制的風險，應保留 agent_end 的逐 run transcript 收集，而非機械替換事件。**

## Critical (must fix)

### C1 — sticky failure 使恢復成功的 run 無法交付；若最後為 text，還失去 stdout 抑制

- `modules/json-schema/extensions/json-schema.ts:114–116` 在任一 assistant error／aborted 的 message_end 呼叫 fail；`:139–141` 又在低階 agent_end 判定同類錯誤。fail 在 `:41–45` 永久設定 failure 並立即設 process.exitCode=1。
- Pi 在 `node_modules/@earendil-works/pi-coding-agent/dist/core/agent-session.js:1390–1402` 等低階 agent.prompt 返回之後，再由 `_handlePostAgentRun()` 決定是否繼續；`:1426–1430` 可準備 native retry，`:1445–1450` 可進行 compaction／其他 continuation；`:1412` 才發最終 settlement。故低階 agent_end 的 error 不等於最終失敗。
- 重試成功呼叫 json_output 時，`modules/json-schema/extensions/json-schema.ts:78–89` 可以接受合法結果，卻不會清除 failure；shutdown 在 `:203` 先返回，連 `:204` 的 accepted.data 都不取。結果是宿主已恢復成功，extension 仍無 JSON、保留失敗狀態。
- 若重試成功只產生 assistant text，`:110` 因 failure 已存在直接返回，導致 `:119–123` 的 lastText 收集與文字抑制都不執行。宿主 `dist/modes/print-mode.js:110–125` 會印最後成功 assistant 的文字，shutdown 卻仍不交付 JSON。這條靜態路徑與模組 README:29 的 structured stdout 契約衝突；**stdout prose 外洩尚未受控實測**。
- `dist/modes/print-mode.js:115–117` 對原生 print 的 error 判定採最後 assistant，而非所有歷史嘗試；`dist/main.js:820–822` 只在 print 返回非零時賦值 process.exitCode，返回零不會清除 extension 先前設的 1。因此成功重試通常仍 exit 1，不可期待宿主自行還原。

**具體序列：**暫時 provider error → message_end 將 failure／exitCode 設為失敗 → 低階 agent_end → Pi native retry → 最後成功 tool submission 或成功 text → extension 的 failure 仍存在 → shutdown 不交付；text 分支還可能被普通 print 印出。

## Warnings (should fix)

### W1 — 既有 README 留有 fail-fast 政策歧義，不應宣稱一定違反其所有條文

- `modules/json-schema/README.md:42` 的文字把 upstream 請求出錯／中止列為不交付條件，若將「任何一次嘗試」都解讀為失敗，當前 sticky behavior 與這項嚴格政策一致。
- 但這不等於與 Pi native print recovery 相容：模組沒有停止宿主的後續 retry，可能付出後續請求成本卻永遠拒絕成功結果；text 抑制提前失效又與 README:29 不一致。
- 因而精確判定是：**已確認 native retry 的最終成功會被拒絕；要不要接受 recovered success 是需要明確化的產品政策，stdout 契約則不能因選擇 fail-fast 就放棄。**不把文件歧義當成測試已證實的意圖。

## Suggestions (consider)

### S1 — 分離逐嘗試資料、最終 run 狀態與不可恢復的交付錯誤

1. **保留 `agent_end:126–138`。**它負責每個低階 run 的 messages 收集，並用 suppressedContent 還原抽取 transcript；agent_settled 不帶相同 messages 資料，直接換事件會破壞多段 transcript 收集。
2. **保留 message_end 的文字抑制與 actual-model 記錄。**把低階 provider error 暫存為可被後續成功取代的 attempt 狀態，不要因此提前停掉 stdout suppression。
3. **把最終判定放在 settlement。**用 agent_settled 的 aborted，加上透過公開 context／觀察到的最終 assistant outcome，判斷該高階 prompt run 是否真的失敗。agent_settled 只通知，不能在它返回 continue 期待 recovery；before-settle handler 仍可引發下一個低階 run，不能更早把 outcome 固化。
4. **保留真正的 sticky failure。**無效啟動 schema、conflicting submissions、交付 I/O 失敗等可以維持不可恢復；不要把所有 failure 統一在成功 retry 時清掉，也不要無條件 process.exitCode=0，否則可能抹掉其他 extension 的失敗。
5. **交付仍可保留在 session_shutdown。**只需先取得可靠 final run 狀態；不必為修 retry 把逐 run transcript 或檔案交付全部搬到 settled。shutdown 原子交付與 worker close 的既有生命週期仍有價值。
6. **多 prompt 要明確分層。**file 模式允許數個 prompt、交付最後一個結果；attempt outcome 應按高階 input/run 重置，但真正的全執行衝突／設定／交付 failure 不應被無意清除。

### S2 — 最小定向驗證，不重跑全套

後續由父層或取得測試執行權限者使用隔離 HOME／agentDir、空 credentials 與離線 mock provider，定向覆蓋：

- retry enabled：一次可重試錯誤，後續成功 json_output；應依選定政策交付一次並給正確 exit status。
- 同上，但最終成功 text；若採 recovered-success，解析合法 JSON並只輸出一行；若仍 fail-fast，stdout 至少應保持無 prose／不交付。
- retry exhausted／非可重試錯誤：exit 1、stdout 不交付、舊輸出檔不變。
- agent_before_settle continuation／overflow compaction：多個低階 agent_end 收集不遺漏、不重複，最終 outcome 才裁決。
- 真正 aborted（含無 process signal 的宿主取消）仍不得交付。
- conflicting json_output 等真 sticky failure 不被後續成功清除；其他 extension 設定的 exitCode 不被本模組覆蓋成 0。

以 provider request count 與事件 barrier 驗證，不依賴固定 sleep、不使用真實模型；不需要為此重跑全部 module/integration/package suites。

## Summary

對原生 print structured-output 的恢復成功語意而言，當前低階錯誤立即 sticky fail 確實會誤拒最終成功 retry，且可能令最後的說明文字繞過 stdout 抑制；這是程式與宿主控制流程能確認的結果，尚未動態重現。修正應把「attempt error」與「final run failure」分開，保留 agent_end 的逐 run transcript 收集及 shutdown 的交付生命週期，而不是機械更換 hook。父層已完成的其他驗證與 probes 未被重跑，也未被誇稱為此情境的通過證據。
