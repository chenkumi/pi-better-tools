## Warnings (should fix)

### 1. 原缺陷仍未修：run-local close 成功不足以授權釋放所有 managed 資源

- `session-store.ts:106–122`：atomicJson close 拒絕會產生 `cleanupUnsafe:true`，但沒有 ManagedSession 層級的持久鎖存，也沒有保留 FileHandle 的明確資源責任記錄。
- `session-store.ts:522–531`：aggregate append 的 `output.close()` 拒絕是原始例外，**目前沒有 cleanupUnsafe 標記**；finally 的 close 例外也可能遮蔽 append/stat/sync 的主要例外。原報告「metadata/aggregate cleanupUnsafe 沒進仲裁」應精確理解為：metadata 已標記但未使用；aggregate 尚未標記。
- `index.ts:421,560,952–958,1032–1039`：begin 失敗時 runStarted 仍 false，writer 不存在，writerCloseConfirmed 初值 true；一般清理可以跳過 blocked 後直接 release。
- `index.ts:998–1027,1032–1039`：commit close 故障之前 run-local writer 已 finalize 關閉；abandon 成功只再次確認該 run-local handle，不代表 committing metadata／aggregate handle 已關閉。catch 未辨識 cleanupUnsafe，之後仍可能 blocked/release。
- `index.ts:1045–1057`：晚到清理只等待 gate idle、child close、iterator 等。gate 的 actual promise rejection 也會令 pending 歸零；它不是實際 handle close 成功證據。
- `session-store.ts:460–465`：release 只驗 nonce、刪 writer.lock 與 live nonce，沒有 close-unsafe 防線。僅加 runner boolean gate 仍會漏掉其他 caller 與 timeout 後才發生的拒絕。

### 2. acquisition/query caller 必須一併納入，不能只修 commit catch

- `index.ts:554`：lockHeld 只在 acquire 完整成功返回後才設 true；owner.json close、recovered rollback close、成功初始化後 fence cleanup 拒絕，都可能已持有 this.lock/live nonce，但 runner lockHeld=false。保留磁碟鎖是正確行為，診斷與 owned settlement 不可將之冒稱已清理。
- `index.ts:1311,1322,1347–1351`：ready-query preflight 失敗的 cleanup 無條件呼叫 managed.release。即使 initializeLock 已因 owner metadata close 拒絕保留 ownership，外層仍會嘗試 release。owner.json 未 publish 時現況可能因讀不到它而拒絕 release，但這不是可依賴的 close barrier；其他 acquisition 故障時 owner.json 已存在。此為静態 caller 覆蓋需求，本次未動態重現新增 query 案例。

## Suggestions (consider)

### A. 建議的最小、完整設計（不修改產品；非實作完成）

採「ManagedSession 自有 close-unsafe latch／resource record + 既有 run-local writer barrier」，不新增 plugin manager、全域通用 resource 框架、設定鍵或磁碟格式。

1. **在實際 close 拒絕的位置登記，而非在 gate.run 的等待 catch 才登記。**
   - ManagedSession 增加私有、單調的 unsafe writer 狀態；保留 resource kind、path、原始錯誤與尚未確認關閉的 FileHandle 強引用（或等效明確 owner record）。正常成功 close 不留下 unsafe 記錄。
   - 讓 session-owned atomicJson 有局部 wrapper／callback，把真正 close 拒絕登記到所屬 session，再拋帶 cleanupUnsafe/cause 的錯誤；aggregate 使用相同登記語意。
   - 不保存 payload／credentials，不以錯誤字串辨識 ownership。
   - **不能只在 begin/commit 外層 await gate.run 的 catch 設旗標**：`io-gate.ts:37–54` 會在 timeout/abort 後繼續執行 actual operation；晚到拒絕可能不再送回等待 caller，但必須在 actual operation 內更新 owner。

2. **統一不可越過的防線。**
   - release 開始、讀 owner.json 之後／刪鎖之前均不得忽略 unsafe latch；有未確認 owned writer 時拒絕 release，保留 writer.lock、nonce registry 與資源身份。caller 仍須先等既有 child/native/transcript gate，避免在 pending operation 尚未登記 unsafe 時偷跑。
   - blocked／rollbackToCheckpoint／commit／publish 的 managed mutation admission 需受此 latch 約束；既有 unsafe 後不得用新的 metadata publish、truncate 或 ready 恢復冒充安全收尾。特別是 rollbackToCheckpoint 必須在 truncate 之前檢查，不是僅在末尾 atomicJson 才檢查。
   - blocked 若自己的 metadata close 拒絕，當次即登記並拋出；後續 release 仍被 owner 層拒絕。
   - run-local SubsessionWriter 的 close barrier 保持原樣；不要讓其 abandon 成功清除 managed unsafe latch。
   - close 拒絕不自動 retry、不按 fd 數字猜測已關閉、不依 final result/blocked/pending=0 清除 unsafe。永久不確認時誠實保留 ownership；人工移除鎖前需外部資源終止證據。

3. **caller 仲裁與診斷保持一致。**
   - 一般 cleanup 與晚到 cleanup 在所有 actual gate idle 之後查同一 ManagedSession barrier；unsafe 時不 blocked/rollback/release，回報失敗與 retained ownership。
   - caller catch 可以遞迴辨識 cleanupUnsafe 以改善診斷，但**遞迴 helper 不是 owner latch 的替代品**。
   - 保留主要故障與 close cause，避免既有 `??=` 讓後續 close-unsafe 訊息消失；保持 bounded error text 與原公開 schema。
   - `onOwnedSettlement` 可表示實際 operations 已 settle，包括拒絕，不可把 promise fulfilled 解讀為所有 handle 已關閉。若納入 rejecting unsafe barrier，需同步調整測試 helper，讓拒絕可觀察、teardown 仍由測試 owner 真正關 handle；不可為了讓測試 await 結束而清除產品 latch。

**必要範圍界線：** allocate 在取得 writer.lock 前寫 manifest（`session-store.ts:258–267`）；可保留獨立 allocation resource 診斷，但不能要求尚不存在的 writer.lock 充當 barrier。`readBounded`／readQuerySnapshot 等唯讀 handle 的 close 是另一類租約／descriptor 問題，不把 SUB-02 擴大為所有 filesystem API 重構；若要擴大到 reader close，應另立明確契約與測試。

### C. cleanupUnsafe 是否包在 AggregateError／causes：精確確認

1. `atomicJson`（119）：回傳普通 Error，**頂層 cleanupUnsafe=true，單數 cause=原始 close 拒絕**；不是 AggregateError。當 write/sync 與 close 同時失败，現況以 close 優先，但不保存 write/sync error；既有測試 227–270 明確驗這個優先序。
2. `acquisitionFence`（304–305）：rmdir 失敗會產生 **AggregateError.errors**，按 `[primaryError, cleanupError]` 或 `[cleanupError]` 排列，**aggregate 頂層另標 cleanupUnsafe=true**。若 primary 是 metadata-close Error，其 cleanupUnsafe/cause 同時仍存在於 `errors[0]`；可形成巢狀 error tree。
3. `initializeLock` cleanup 失敗（329）：產生 **AggregateError([error, cleanupError])，頂層未標 cleanupUnsafe、未設 cause**。可能包含另一個帶 marker 的 cleanup error，但不是每個 child 都帶 marker。不能因頂層沒 marker 就聲称 cleanup 已安全，也不能把所有 AggregateError 都直接當 close failure。
4. aggregate transcript（531）：原始 output.close rejection **未包 marker／cause／AggregateError**，因此目前 recursive detector 也無法辨識它；必须先在源頭建立 close-unsafe 語意。
5. 現有 `initializeLock:319`／`rollbackToCheckpoint:434` **只看頂層 marker**，沒有遞迴掃 `cause` 或 AggregateError.errors。runner 亦未處理這些 marker。
6. **程式目前沒有名為 `causes` 的複數屬性契約**。標準 cause 是單数；AggregateError children 是 errors。若說「causes」，只能泛指因果鏈，不可實作成讀 `.causes`。

建議局部 `isCleanupUnsafe(error)`（名稱僅示意）檢查 `cleanupUnsafe === true`、單數 cause、AggregateError.errors；以 visited Set 防循環，處理 null/falsy/non-object，不靠 `instanceof Error` 將 marked plain object 丟掉。若跨 reload/realm 需支援 aggregate shape，限定 errors 的合理結構、保守處理，不任意遍歷所有物件欄位。不要改寫上游原始錯誤；owner latch 是裁決依據，helper 用於不吞錯與診斷。
