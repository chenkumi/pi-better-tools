## 3. 已確認問題詳情

### MISC-001 — High：保存失敗仍推進 coverage cursor

**位置**：`modules/blackhole/src/om/pending.ts:123–133,161–176,257–264,334–339`；caller `consolidation.ts:1325–1340`；cursor flush `runtime.ts:898–906`。

**觸發**：memory/manual 模式下 observer 已產生有效 observation，pending main 單次 write 發生 ENOSPC 類錯誤；之後 cursor write 恢復正常。

**預期**：保存失敗不可認可該 source 已記錄；應保留舊 batch，並讓未保存部分仍可處理。

**實際／根因**：主檔先被 rename 為 stale，再寫新主檔；write 失敗被吞掉。caller 無條件 advanceCursor(recorded)，flush 讀不到主檔就建立 cursor-only state。新 Runtime reload 此 cursor 後，不再處理同 source；再次 cursor write 可覆蓋仍含舊 batch 的 stale。

**獨立觀察**：helper 故障 3/3：batches=0、raw-b/recorded、舊 A 備份消失；production `runConsolidationPipeline` caller 故障 3/3：workerCalls=1、batches=0、reloadedDue=false，重進同 source workerCalls 仍為 1。正常控制保存的 batch 可讀。caller／helper 的故障與控制各三次新行程，皆正常退出並完成 fixture 清理。

**影響與嚴重度**：未 flush 的 memory 靜默缺失，coverage 卻已越過它，可能永久跳過。High 依資料完整性；raw transcript 仍存在，不能說整個 session 被刪除。

**反證／限制**：generation/branch fence 有效但不能證明保存成功；stale 人工救援不等於自動恢復。本次沒有觀察到 recorded toast，因正常 running 通知先消耗了 once gate。使用 synthetic model resolver／workers及真 persistence/pipeline，不測真 provider 或完整 agent_start dispatcher；reflection/drop 同根因未另動態重播。

**最小處理方向**：保存須回傳／拋出可觀察的成功失敗；失敗不得推 cursor，且避免破壞唯一可恢復舊 generation。

**證據**：[獨立完整報告](REPORT-20261012T084543011Z.md)、[caller 原始故障輸出](../plan/review-20261012-evidence/verify-blackhole/pending-caller-fault-1.stdout.log)、[全部退出與控制](../plan/review-20261012-evidence/verify-blackhole/summary.json)。

### MISC-002 — High：scan failure 被誤判 orphan，cleanup 可刪 live pending

**位置**：`modules/blackhole/src/om/cleanup.ts:109–150,201–208,221–246,289–328`；`src/commands/cleanup.ts:230–236,267–300`；公開接線 `src/commands/pi-vcc.ts:120–123`。

**觸發**：live session JSONL 實際存在，但掃描讀取其 header 發生 EACCES；使用者在 `/blackhole cleanup` 的 orphan picker 按 Enter。

**預期**：掃描不可讀應是 unknown/incomplete，而不是證明 session 不存在；不應授權刪除其 pending。

**實際／根因**：scan skip 讀取失敗且沒有 completeness 訊號；Set 沒有 sid 即分類 orphan。公開 command 使用此分類，未保護當前 live session，Enter 實際 unlink pending。

**獨立觀察**：helper 故障 3/3：active=0、orphaned=1、deleted=1，pending 不在而 live JSONL 仍在。透過 production `registerPiVccCommand` 捕獲公開 handler、真正 picker render 與 `handleInput('\r')` 的 command 故障亦 3/3：顯示 Orphaned Pending Files，Enter 後 pending 實際消失。正常控制 active=1、沒有 orphan picker、不刪除；每組皆三次新行程。

**影響**：誤導性 orphan 分類可導致仍在使用的未 flush memory 被刪除。High；需要明確 TUI 操作，不是背景自動刪除或無權限攻擊。raw session 不被刪。

**反證／限制**：sid/path containment 只防越界，不證明 orphan；non-TUI 只列舉防護仍有效。EACCES 為隔離檔案的精確故障注入、刪除用真 FS；UI 使用 synthetic context，不冒稱人工 fullscreen 測試。其他 scan error/custom sessionDir 未另重播。

**最小方向**：scan completeness fail closed；保護 live session；破壞性操作前重查，不能把不可讀當不存在。

**證據**：[獨立完整報告](REPORT-20261012T084543011Z.md)、[公開 command 原始輸出](../plan/review-20261012-evidence/verify-blackhole/orphan-command-fault-1.stdout.log)、[全部退出](../plan/review-20261012-evidence/verify-blackhole/summary.json)。

### MISC-004 — Medium：深層 `$ref` 驗證語意錯誤，prose fallback 可交付錯誤資料

**位置**：`modules/json-schema/src/schema.ts:58–63,122–129,153–178`；`extensions/json-schema.ts:154–156,204–222`；`src/validation-worker.mjs:11–15`。實際 Zod converter 只以 definition 名稱解析 ref，忽略尾端。

**重現輸入**：root object 的 `$defs.W` 是 object，其 `properties.amount` 是 number；required x 指向 `#/$defs/W/properties/amount`。正確目標應是 number，因此 `{x:7}` 有效，`{x:{}}` 無效。

**實際**：compile 接受此 pointer，但 validate 接受 `{x:{}}`、拒絕 `{x:7}`，原文 `x: Invalid input: expected object, received number`。同一現象在同步及含 pattern 的真 validation worker 都 3/3 重現。production extension factory 的離線 hooks 驅動 prose fallback，實際寫出 `{"x":{}}`；worker 版本亦寫出 `{"x":{},"tag":"aaa"}`。

**影響**：structured delivery 可能拒絕正確資料或把錯型別資料交付下游，Medium 資料正確性。

**反證／限制**：inline number、淺 definition ref、pattern 不匹配等正常對照皆正確；直接 host tool argument validator 不涵蓋本次 prose recovery 路徑。不測完整 Pi CLI或真模型；extraction-response 分支共用 validator，但未另動態執行。

**最小方向**：無法忠實解析的 deeper pointer 必須啟動時拒絕，或實作正確 resolution；不可悄悄退成整個 definition。

**證據**：[獨立報告](REPORT-20261012T083632504Z.md)、[compile／worker／實際交付原始日誌](../plan/review-20261012-evidence/verify-schedule-schema/schema-1.log)、[全部三次退出](../plan/review-20261012-evidence/verify-schedule-schema/summary.json)。

### SUB-20261012-02 — Medium：其他 writer handle close 故障未守住 ownership release

**位置**：`modules/subagents/extensions/subagent/session-store.ts:106–122,475–486,518–536`；runner `index.ts:1004–1040`，尤其 release gate。

**觸發**：begin run metadata、commit 的 committing metadata、或 aggregate transcript append 的真實 FileHandle.close 拒絕，實際 handle 尚未關閉。

**預期**：該 writer resource 尚未確認關閉前，保留 managed ownership／可追蹤清理責任，不能以另一個 handle 已關閉代替。

**實際**：writerCloseConfirmed 只代表 run-local SubsessionWriter。commit fault 後 abandon 關閉的是已關閉的 run-local handle；metadata/aggregate cleanupUnsafe 沒進 release 仲裁，gate pending=0 時仍 release lock。begin 尚未產生 writer 也可釋放。

**獨立觀察**：begin／metadata commit／aggregate 各 3/3，在 production ownedSettlement 後同時得到 `handleStillOpen=true`、`lockPresent=false`。使用真 open/write/sync/managed commit/blocked/release，只攔一個 close 拒絕、不執行原 close；事後由實驗 owner 原 close 清理並用 stat 驗證 closed，才移除 fixture。正常控制 3/3 ready、canResume=true。

**影響與界限**：失去尚未關閉資源的 ownership barrier，可能留下 descriptor／檔案佔用；Medium。blocked/checkpoint 仍阻止一般 resume；未證明第二 child 已啟動、資料損毀或 handle 還在寫，不推論所有 OS close rejection 都等同 still-open。

**最小方向**：所有 owned writer handle 的 close-unsafe 狀態納入同一 release barrier，保留未確認 handle 的收尾身份。

**證據**：[独立報告](REPORT-20261012T084147069Z.md)、[metadata 真 handle 日誌](../plan/review-20261012-evidence/verify-subagents/metadata-close-1.stdout.log)、[各模式觀察與退出](../plan/review-20261012-evidence/verify-subagents/observations.json)。

### FILEWEB-001 — Medium：REST snippet 同步清理 CPU 放大

**位置**：`modules/web-tools/src/search.ts:9,81–84`；期限 `39–41,94–96`。

**觸發**：Brave/Exa REST 回應欄位含大量 `<` 且沒有 `>`。本次測 Brave 合法 JSON description；body 約 32K／64K，遠低於 2 MiB admission。

**預期**：snippet 清理成本應有界；1500 字元輸出上限不應在清理完整病態欄位後才生效。

**實際**：`/<[^>]*>/g` 在完整欄位上同步嘗試，再 slice。注入 HTTP seam、保留真 search，imports及payload建立後計時；每大小各三次新行程：

|description 長度|普通 x 中位數|連續 `<` 中位數|
|---:|---:|---:|
|32768|34.5 ms|1136.2 ms|
|65536|30.6 ms|5013.6 ms|

大小翻倍、病態總時間中位數約 4.41 倍，post-read 約 4.50 倍；支持二次方掃描推導。1000ms search timeout 下仍成功返回、signal 未 aborted，因同步清理期間 timer 無法執行。這是本機實測，不是所有 V8／主機的固定效能保證。

**影響**：異常上游資料可令同 Pi process 的同步路徑佔用數秒；Medium，不宣稱真供應商曾返回該資料、任意網站能操控欄位或多租戶攻擊已證明。

**反證／限制**：2 MiB body、結果數及輸出 caps 均有效，但不約束清理前工作量；普通控制稳定快。128K 病態輸入三次由 child 15 秒外部安全期限終止、已確認 close，屬截斷觀察，**不算通過、不捏造完成時間**。未測 Exa、實際 TUI 或 heartbeat。

**最小方向**：線性 scanner 或清理前有界欄位 admission，保留 HTML 清理語意；必要時檢查 post-HTTP 完成後取消／期限。

**證據**：[独立報告](REPORT-20261012T083757979Z.md)、[64K 原始計時](../plan/review-20261012-evidence/verify-pty-web/v2/web-angles-65536-r1.stdout.log)、[三次控制／截斷分類](../plan/review-20261012-evidence/verify-pty-web/audit.json)。

### MISC-003 — Medium：Schedule list 全檔重讀呈累積二次方成本

**位置**：`modules/schedule-prompt/src/tool.ts:324–339`；`scheduler.ts:191–212`；`storage.ts:93–126,297–307`。

**證據**：[獨立報告](REPORT-20261012T083632504Z.md)、[原始 operation count及控制](../plan/review-20261012-evidence/verify-schedule-schema/schedule-1.log)、[全部退出](../plan/review-20261012-evidence/verify-schedule-schema/summary.json)。

### SUB-20261012-03 — Medium：ready-query stdout fault 後持續保留 buffer

**位置**：`modules/subagents/extensions/subagent/ready-query.ts:111–137`，append 在129、容量檢查130、catch136未清 buffer。

**觸發**：壞 RPC producer 輸出超過8 MiB且沒有LF；已被判 capacity failure後，child 在關閉前繼續輸出。

**預期**：保持 drain/close ownership，但故障後不再保留已拒絕 payload。

**獨立觀察**：production reader、IoGate、RPC 邏輯不替換，受控 PassThrough producer先送8 MiB+1，再送1 MiB。real Buffer.byteLength spy不改回值；fault 3/3 測到已故障後同 buffer由 **8,388,609 → 9,437,185 bytes**，querySends=0，close前permit未釋放。正常短JSONL控制 3/3 completed且正常清理。

**最小方向**：fault latch 後 drain 但不 retention，並避免繼續對已拒絕尾段反覆 byteLength。

**證據**：[獨立報告](REPORT-20261012T084147069Z.md)、[原始 retention／fault順序](../plan/review-20261012-evidence/verify-subagents/ready-fault-1.stdout.log)、[全部模式](../plan/review-20261012-evidence/verify-subagents/observations.json)。

### LIFECYCLE-002 — Medium：waitFor 漏搜仍未讀 prefix

**位置**：`modules/pty-terminal/src/pty-manager.ts:67–68,385–400`，尤其397的suffix截取；公開契約稱匹配未讀 ANSI-stripped output。

**重現**：保留的 unread buffer=`READY\n`＋262144個x，總262150字元，沒有ring overflow/drop；`readEx(...,{timeoutMs:0,waitFor:/READY/})`。

**預期**：READY仍在未讀buffer，應matched，或至少明確回報沒有搜尋的前綴；不應静默timeout。

**獨立觀察**：prefix 3/3 timeout；恰262144字元的 within control 3/3 matched；同262150字元但READY在尾部的suffix control 3/3 matched。snapshot完整等於輸入、READY仍存在、dropped未設。只fake transport，實際 matcher worker未mock，每次worker／manager清理成功。

**根因／影響**：matcher只看最後256Ki字元而不提供omitted標記，可誤判readiness、造成無謂等待／重試。Medium；不是regex卡死。

**反證／限制**：2Mi ring、worker budget/capacity等成本防護均存在。未測原生 PTY、正值timeout/settle或多平台；缺陷在可達 buffer／worker路徑已證明，不等於端到端transport全驗收。

**最小方向**：保留計算預算下處理完整 retained unread input，或明確設計并回報搜尋不完整；不能 silently把prefix omission當未匹配。

**證據**：[獨立報告](REPORT-20261012T083757979Z.md)、[prefix 原始結果](../plan/review-20261012-evidence/verify-pty-web/v2/wait-prefix-0-r1.stdout.log)、[三組控制與退出稽核](../plan/review-20261012-evidence/verify-pty-web/audit.json)。

## 4. 不計入確認缺陷的候選
