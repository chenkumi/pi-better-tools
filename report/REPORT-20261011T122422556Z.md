## Critical (must fix)

### F1 — P1：大 hunk 在提交後以 variadic push 崩潰，40 行輸出 cap 沒有保護 formatter

- **Location**：`modules/file-tools/src/file-operations.ts:1587`（相關 1554–1596）；`modules/file-tools/extensions/file-tools.ts:638–640`；提交點 `src/file-operations.ts:1538`。
- **原因**：`compactPatch()` 對整個 hunk 執行 `out.push(...body)`，直到之後才截成 40 行。JavaScript argument count 有有限上限；合法的大量短行 patch 即使遠小於 50 MiB 也能超過它。且 extension 先 await 已提交的 `editTextFile()`，才格式化 feedback；同一 patch 還格式化兩次。
- **Impact**：成功修改磁碟後拋出 RangeError，宿主將其當工具錯誤；模型可能重試，卻拿不到這次成功的 hash／結果。worker 的 diff timeout、heap cap 與輸出 byte cap 無法防止 parent formatter 的 argument overflow。
- **Evidence／量化**：單一 hunk 的 `+x\n` 重複 200,000 次只有約 600,000 bytes，卻產生約 200,000 個 push arguments；這不是任意巨大無效輸入。現有 feedback 測試只用 10,000 行（`tests/file-operations.test.ts:1173–1198`），沒有跨越 argument-count 邊界。
- **最小修正**：不要 spread 不受 line-count 限制的 body；逐行統計 added／removed／omitted，最多保留 40 行並當場截長度。單次格式化重用結果，並在 commit 前準備所有可能失敗的成功 feedback，或保證 commit 後 formatter 不會因合法有界輸入失敗。不要靠捕捉 RangeError 後回傳假失敗。
- **Confirmed vs inference**：Confirmed-static：bounded bytes 不等於 bounded argument count，且 formatter 在 commit 後。Conditional inference：200,000 行案例的實際 V8 threshold 與完整 diff 是否在 2 秒內完成，本次未實測；因此不聲稱已觀察磁碟變更後失敗。
- **待驗證**：先離線直接呼叫原始 `compactPatch()` 對 200,000 短行 patch，確認不應拋錯且輸出有界；再於隔離 temp workspace 經 registered edit 做「一處替換插入大量短行」，確認回傳成功／hash 與磁碟一致；如 diff timeout，該 end-to-end 個案不算 formatter repro，應另外保留純函式 repro。

### F2 — P1：Zod default 讓缺少 required 的原始資料通過 recovery

- **Location**：`modules/json-schema/src/schema.ts:121–139`；`modules/json-schema/extensions/json-schema.ts:154–157,215–218`；worker 同問題在 `src/validation-worker.mjs:10–14`。
- **原因**：`fromJSONSchema()` 將 schema 的 default 轉成 Zod `.default()`。本機 converter `from-json-schema.ts:635–639,857–860` 與 core `schemas.js:2128–2143` 確認 undefined 直接變 default，且不驗證該 default。模組只看 safeParse.success，再交付**未被修改的原始 data**，因此「不把 default 寫回 data」不代表 default 沒有改變驗證結果。
- **精確反例**：schema `{"type":"object","properties":{"a":{"type":"string","default":"x"}},"required":["a"]}`；候選 `{}`。Zod 以 default 接受 missing `a`，validate 回傳 undefined；recovery 第一個候選即可被採用，交付的仍是 `{}`，違反 required。
- **Impact**：best-effort 回收或額外抽取的 arguments 路徑會輸出 schema-invalid JSON。Pi 直接 tool-call 前的 required 驗證不會保護 recovery，不能把此問題誤稱所有直接工具呼叫都能穿透。
- **最小修正**：建立 validator 前，只在 schema positions 移除 default（包含 $defs／definitions、tuple、各種 subschema），不改 enum／const／annotation 中的 instance data；worker 必須使用相同清理語意。provider parameters 可以保留 annotation，但本地驗證不可用它填補 required。交付仍保留原始資料。
- **Confirmed vs inference**：Confirmed-static，由本機 converter/default/object parser 與 recovery 的分支確定；未執行 runtime 或真實 host repro。
- **待驗證**：上述 schema 的 `validate({})` 應回傳錯誤；加入含 pattern 的等效案例覆蓋 worker。離線 hook harness 提供 assistant text `'{} then {"a":"ok"}'`，並讓 modelRegistry.complete 一旦被呼叫就 fail；應只交付後者。現有 `schema.test.ts:33–38` 只驗證 optional default 不改原物件，不覆蓋 required-default。

### F3 — P1：audit 允許 $ref 同層 constraints，但 Zod 忽略它們

- **Location**：`modules/json-schema/src/schema.ts:57–60,80–82,121`；`extensions/json-schema.ts:154–157,186–190`。
- **原因**：audit 把 `$ref` 當有型別依據，未禁止 sibling 型別／bounds。Zod `from-json-schema.ts:412–435` 遇 $ref 直接回傳 referenced validator，未套用同層 minLength 等限制。
- **精確反例**：`{"$schema":"https://json-schema.org/draft/2020-12/schema","type":"object","$defs":{"s":{"type":"string"}},"properties":{"a":{"$ref":"#/$defs/s","type":"string","minLength":3}},"required":["a"]}`；候選 `{"a":"x"}`。draft-2020-12 的 sibling minLength 應生效；本地只驗證 referenced string，所以接受。明列 draft 避免與 draft-07 的 ref sibling 語意混淆。
- **Impact**：本地聲稱的 schema-valid 交付不成立；尤其 recovery／extract reply 不經 Pi tool-argument validator。這是模組 audit 契約缺口，不是要求修改上游 Zod。
- **最小修正**：先在啟動 audit 拒絕 $ref 與 Zod 會忽略的 sibling validation keywords 共存，並提供改寫成 explicit-type allOf 的提示；若改成合成 intersection，須另外處理 draft 語意及引用回圈，不必為這個修正全面重寫 validator。
- **Confirmed vs inference**：Confirmed-static，由 audit 與本機 Zod 的 early-return 分支確定；未執行 repro。
- **待驗證**：上述 schema 應在 startup 明確拒絕，或 validate 短字串為失敗；長字串成功。涵蓋 `$ref` 命中 cache 的第二處 reference、pattern worker 路徑與 recovery。既有 ref 測試 `schema.test.ts:28–30` 只有 bare ref。

## Warnings (should fix)

### F4 — P2：沒有 pattern 的小型 $ref DAG 可造成指數級同步驗證

- **Location**：`modules/json-schema/src/schema.ts:132–139`（只用 usesPattern 選 worker）；tool 註冊 `extensions/json-schema.ts:79`。
- **原因／演算法證據**：令 `$defs.S0={type:"object",properties:{v:{type:"string"}},required:["v"]}`；每個 `Si={anyOf:[{$ref:"#/$defs/S(i-1)"},{$ref:"#/$defs/S(i-1)"}]}`，i=1..20。root 使用 optional property `x:{$ref:"#/$defs/S20"}`。schema 為 O(d) 大小、沒有 pattern，啟動的 safeParse({}) 可跳過 optional x；對 `{"x":{"v":1}}` 驗證時每層的兩個失敗選項都被執行。
- 本機 Zod converter 有 ref cache，能使 compilation 保持緊湊，但 union parser `v4/core/schemas.js:1237–1259` 每次逐一執行所有失敗選項，沒有此路徑的失敗結果 memoization。因此 leaf 檢查數為 `2^d`；d=20 是 **1,048,576** 次，同時形成大量巢狀 union errors。`issues.slice(0,5)` 只在全部驗證及 error 建立後才執行，不限制這些成本。
- **Impact**：主 event loop 的 cancel／timer／shutdown 無法及時處理；非常小的候選資料即可掛住 structured-output recovery。不能因為 pattern 已是線性子集，就推論所有同步 schema 都有廉價上限。
- **最小修正**：audit $ref graph／組合分支的 expanded-work 預算，拒絕會造成不受控 multiplicity 的 schema；保留一般 ref。將其他複雜本地驗證放 worker 可改善 recovery，但不是完整修正：Pi 在 execute 前仍同步驗證原始 tool schema，故必須先拒絕／限制 host 邊界的高複雜度 schema，而非僅加 worker。
- **Confirmed vs inference**：Algorithmic：分支數與非 pattern 同步選路已確認。未量測毫秒／RSS，未確認 Pi TypeBox 對此特定 DAG 的 exact cost；不把 Zod 的 recurrence 冒稱 TypeBox benchmark。
- **待驗證**：離線隔離 child，原始 compileSchema 使用 d=8、12、16 的失敗候選，輸出英文進度／時間／記憶體；設 child 外部硬期限，不在主 Pi process 試 d=20。另以本機 validateToolArguments 獨立檢視 host 邊界。這些只是待執行驗證，不是本次量測。

### F5 — P2：JSON output 暫存 basename 加長 32 字元，合法目標路徑也不能交付

- **Location**：`modules/json-schema/src/delivery.ts:28–30`。
- **原因／量化**：暫存名 `.${basename}.${ULID}.tmp` 的 ASCII 長度為 `basename.length + 32`。在單一 component 上限 255 的檔案系統，224 字元目標仍合法，但暫存 component 長達 256，writeFile 在 rename 前即失敗。File Tools 已採固定短 ULID temp 名（`src/file-operations.ts:1010`），此修正未涵蓋 JSON delivery。
- **Impact**：模型工作完成後，合法 `--json-output` 路徑不能交付且 exit code 1；舊檔保留，並非舊檔毀損。較深的 Windows path 也因增加長度承受額外風險，但本次未驗證 long-path 設定。
- **最小修正**：同目錄固定長度 `.pi-json-${ulid().toUpperCase()}.tmp`，以 exclusive create 建立，再維持既有 bounded rename retry／cleanup；不要截斷使用者目標名，也不要變成非原子覆寫。
- **Confirmed vs inference**：Confirmed-static 的長度計算；實際 ENAMETOOLONG／Windows 錯誤碼依檔案系統與 OS，未執行。
- **待驗證**：isolated temp 目錄使用 224 ASCII 字元 basename，先建立舊結果再呼叫原始 writeJsonFile，應成功替換且無 tmp 殘留；保留 rename failure 舊檔不變與 cleanup 測試。

## Suggestions (consider)

以下為審查覆蓋與已知界線，不另外增加主要 findings：

- **File caps／regex／diff**：保留完整 SHA-256 重驗、每次 rename retry 的 fingerprint／hash 檢查、UTF-8／surrogate 驗證及 regex worker 時限；這些是正確性／安全保護，不應被列作「無效全檔成本」。read 已避免整檔 split，diff 使用變更 window；但 edit 的 line-start 索引仍隨行數成長，並行不同檔案也沒有整個程序的總 memory cap。本次未有 RSS 證據，不另判成 bug。圖片沿用宿主處理／取消契約，不將 50 MiB 壓縮檔案上限說成 decoded-pixel peak-memory 上限。
- **Web init／shutdown**：`src/index.ts:31–38` import resolve 後先檢查 stopped，`service.ts:107–127,347–363` launch 完成後對 closed service 關閉 browser，且 shutdown 等候 pending launch；未找到可由目前分支證明的 orphan launch 新 bug。newContext late cancellation 亦有 cleanup。5 秒 context close 上限與未完成 close 釋放 queue 是 README 已揭露限制；未實測持續忙碌下的 context 累積，不能當成已證明的新 regression。
- **Extraction workers／validation pool**：檢查到 bounded ownership、retiring slot 保留、取消 waiter 移除、exit/error 清理及 shutdown 等候。終止失败後仍保留 slot／等待 real exit 是 fail-closed 資源保護，不應要求先釋放來改善表面吞吐。共享 extraction module 在 host 也 import jsdom（`extract.ts:2`），有 cold-load 重複依賴圖，但未量化，未列主要效能 finding。
- **DNS／private／redirect**：初始／子資源／redirect URL 驗證、實際 peer public-address 檢查、手動跳轉、跨 origin 移除 auth 與逐 hop cookie/host 重建都有實作。**沒有真正 DNS IP pinning**；事後 serverAddr 不能阻止已送出的 blind SSRF（`service.ts:228–236`），README 145–146 已明確揭露並記錄 todo。這是既有威脅模型限制，不冒稱本次新發現、也不稱為完整 SSRF 防護。Playwright 先 buffer 再看 content-length/body caps 是已揭露 transfer-peak 限制，不把 cap 說成無效成本或真串流上限。
- **Notes／atomic filesystem**：note enum 路徑、segment-aware realpath、wx 不覆寫、碰撞重試與 partial cleanup 均存在。ancestor symlink/junction TOCTOU 是 README 已知界線；本次沒有替換目錄。notes 的 exclusive-create 不表示讀者永遠看不到寫入中的 prefix；同樣 File Tools 不支援 hard link 時的 wx fallback 是不覆寫保護而非 rename 式全內容可見原子性。需要文件精確區分 visibility atomicity 與 no-clobber，不改成不安全覆寫。
- **FFF**：scope 沒有第三方 npm FFF 修改；本次未讀其實作或重跑已知上游 finder capacity/shutdown TODO，不把上游既有議題算作此四模組的新 bug。
