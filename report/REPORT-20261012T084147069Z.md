## SUB-20261012-01 — 容量差異確認；不將 intentional reject 算實作缺陷

原碼位置：subsession-log.ts:296,385–399；tool-result-spool.ts:196–204；index.ts:803–825。輸入正常assistant text part為1,100,000 ASCII bytes，小於2MiB retained budget，wire JSON record為1,100,125 bytes，小於8MiB。真runner拒絕，`errorMessage`精確為 `Subagent stdout processing failed: Sub-session log record exceeds writer capacity`，manifest blocked；短 `done` control真commit成功。

**反證：** `subsession-log.test.ts:274–280` 明確要求 oversized writer record立即failed而不是無限等待，證明1MiB單筆防護有意設計。README:173 是 wire safety上限與aggregate retained-output截斷，不能推出所有較小wire一定可成功；8MiB parser cap和1MiB writer admission可以有合法分層。`session-store.test.ts:79–94` user chunks刻意適配此cap；不能把大task rejection納入。Bundled output契約亦要求短摘要。

因此排除「下層拒絕本身是錯誤」的實作bug判定。**Low文件缺口**仍確認：完整README的上限段沒有明列mandatory readable單筆1MiB及spool序列化1MiB，使用者可能只見8MiB wire／2MiB aggregate。是否要支援較大單筆assistant/tool或補文件，須產品契約決策；不建議拿掉cap。

原候選fixture要求logError包含capacity，但logError是finalization interrupted診斷；產品原因在errorMessage。保留原3次exit1。修正改為**精確errorMessage等值**、另assert logError interruption、blocked、wire區間，不是放寬斷言；修正3次exit0。工具large文字分支未另外動態執行，因此不聲稱spool可達性已動態驗證。

## SUB-20261012-02 — 已確認：其他writer close-unsafe沒抵達release barrier（Medium）
