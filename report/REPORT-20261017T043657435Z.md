## 2. 為什麼看起來像「卡在 Working」

- 宿主把該錯誤判定為可重試：`packages/ai/src/utils/retry.ts` 的 retryable pattern 含 `server.?error` 與 `upstream.?request.?failed`，此錯誤字串同時命中 → `isRetryableAssistantError=true`。
- `packages/coding-agent/src/core/agent-session.ts:3739 _isRetryableError` → `3792 _prepareRetry`：先 emit `auto_retry_start`，`1240 _omitRecoveryAttempt` 寫下 context_edit，然後 `sleep(retryDelayMs)` 2 秒後 `1954` 重送。
- TUI 於 `auto_retry_start` 顯示 `RetryStatusIndicator`（`modes/interactive/interactive-mode.ts:3746`、`components/status-indicator.ts:51`）：文字為 `Retrying (1/3) in 2s... (Esc to cancel)`，倒數到 **0s 後就凍結**，直到重送請求成功才由 `auto_retry_end` 清除。重送的請求 123.5 秒沒有輸出，因此使用者看到的畫面就是「一句錯誤 + 停住不動的狀態」。
- 錯誤文字本身來自 `components/assistant-message.ts:195-199`（`Error: <errorMessage>`），與使用者引用的字串完全一致。

## 3. 是否會造成問題

已實際發生：

- **並行 session 與未預期的檔案變更**。使用者誤判為停止後於 04:29:15 另開 session，但原 session 仍活著：04:33:40 與 04:35:56 兩次 `edit modules/shell-tools/tests/fixtures/notification-batching-host.mjs`，一直到 04:36:19 仍持續寫入 log（調查當時仍在執行）。`git status` 顯示該檔為 modified 未 commit。風險：同一 workspace 兩個活躍 session 可能造成重複或衝突的編輯，且原 run 的結果回到使用者已不再注視的 session。

結構性（本次未造成損害，但值得知道）：

- **可重試判斷是純文字比對**。`400 unsupported_request` 只因 body 含 `server_error`／`Upstream request failed` 就被視為 transient；provider-level 迴圈（`packages/ai/src/utils/provider-retry.ts`）會尊重 `x-should-retry`／HTTP status，agent-level 這條只看文字，因此不會被 `x-should-retry:false` 擋下。代價是每次重試都重送整個 context（本例 `input≈585k` tokens ≈ $0.088/次），上限 3 次加上 2/4/8 秒延遲。不影響 session 狀態與安全，只是延後暴露確定性失敗。
- **錯誤字面的「512 text messages」不可信**：失敗前後同形狀請求都成功，且投影中帶內容的訊息早已約 675 則；真正的慢因是 585k-token 的巨大 context（上一輪 55.1s、重送輪 123.5s）。不要照字面去追 512。
- 未發現卡死或狀態損毀路徑：Esc 可中止 backoff 與串流；HTTP idle timeout 預設 300s（`httpIdleTimeoutMs`）會中止真正斷掉的串流；`pi-runtime` 殘留的 `pending:host` 不會被任何邏輯 gate，下一個成功 turn 即清除。
- 僅一處理論風險（本次未觸發、未修改）：`agent-session.ts:1246` `_omitRecoveryAttempt` 在無法把失敗訊息映射到 persisted entry 時丟錯，該錯誤會穿出 run loop（`1846-1875` 的 try/finally 未 catch `_handlePostAgentRun`），結果會直接結束該輪而非重試。

## 4. 與 pi-runtime 恢復機制的關係：無

- 該錯誤被 `modules/pi-runtime/src/policy.ts:19-28` 分類為 `host`（`isRetryableAssistantError` 命中）。
- `host` 依設計不自動恢復：`modules/pi-runtime/src/index.ts:146-150` 只對 `repairable` 追加 draft 並 `continue`；`host` 連 notify 都沒有；`/runtime-recover`（`index.ts:175`）也只接受 `policy/review/repairable`。README「網路／transient、context overflow、auth／billing／quota：維持宿主處理，不增加另一層 retry」即此語意。
- 證據：該 session 從未提交任何 `pi-runtime-recovery` custom message，`used` 全程 0/2，沒有任何額度被消耗；整個檔案只有 4 個 context_edit，其中本次那個來自宿主 retry。
- 失效情境對照：若宿主重試耗盡，pi-runtime 仍保持沉默，由宿主自行顯示 `Retry failed after N attempts: ...`；`pending:host` 會被下一次錯誤覆寫。無雙層重試、無錯誤狀態。

## 5. 可行動事項（未修改任何程式碼）

1. 看到單一 `Retrying (1/3) in 0s...` 且長時間無輸出時，先視為「大型 context 的慢請求」；要停止請按 Esc 中止該次請求，不要直接另開 session（避免並行 session 同時改同一 workspace）。
2. 目前仍有一個舊 session 持續在跑並改檔（見上）；是否保留、以及 `notification-batching-host.mjs` 的未提交變更如何處理，交由使用者決定。
3. 真正的體感來源是 585k-token context；若要縮短每輪 1–2 分鐘的等待，方向是降低 context（compaction 相關設定），而非 retry 設定。
4. 若要向上游 Pi 提改善（非本專案範圍）：重試指示在倒數結束後改顯示已等待時間，並讓 agent-level 可重試判斷能參考 `x-should-retry`／400 語意，避免對確定性 4xx 重送整個 context。
