# 輸入時 context 超過 80% 先壓縮再執行：Pi 1.1.0 可行性與紀錄結構

研究日期：2026-10-12。範圍：本機實際安裝的 Pi 1.1.0 與 pi-better-tools 的現行 Blackhole。只研究，未修改程式、設定或真實 session，未呼叫模型／credentials。

## 結論

可以做到，但須區分兩種需求：

1. **一般容量保護**：既有 Pi 已在 idle 新 prompt 開始前檢查自動壓縮；以 reserveTokens 設為模型 contextWindow 的 20%，可讓原生 threshold 對應超過 80%。這是最小變更，維持 Pi-only trigger ownership。
2. **嚴格 input gate**：若要求以畫面用量 percent > 80 判斷、只在提交文字時觸發、最多一次、且必須成功才執行任務，單靠設定不足。可研究以公開 input hook 加 callback completion gate 實作，或在自有 SDK caller await session.compact() 後呼叫 prompt()；尚未做這種完整 input lifecycle 整合驗證，不宣稱已實作。

既有檢查不等於「當次新文字加入後的 projected request 超過 80%」。如果需要這種語意，必須另估新文字／技能或模板展開／圖片／system/tool loadout 的請求增量，不能假稱 getContextUsage 已包含新輸入。

## 一、實際生命週期

本機 dist/core/agent-session.js:1517–1631 的 idle prompt 順序：

```text
收到提交文字
→ extension command 分流（若是已註冊指令則可能不執行一般 prompt）
→ input handlers（await）
→ skill/template 展開
→ 若目前 streaming：走 steer/followUp queue，離開此 idle 路徑
→ flush pending bash/custom messages
→ model/auth 驗證
→ 找最後一則 assistant
→ 若存在：await _checkCompaction(lastAssistant, false)
→ before_agent_start
→ 圖片正規化／建立本次 user message／system loadout delta
→ _runAgentPrompt(messages)
```

因此，新文字在原生 pre-prompt 壓縮時還不是 session 的一部分；壓縮成功後才進入任務 context。本次新任務不被這一次 pre-prompt 壓縮摘要化，保留在最後的 user message（仍會經合法 input transformation／模板展開／圖片提示等處理，並非所有輸入都 byte-for-byte 不變）。

本機 _checkCompaction:2329–2447 有額外條件：auto enabled、有 assistant、忽略早於最新 compaction 的 assistant；依情況使用 usage 或 projected estimate。不能把 reserveTokens 換算成 80% 後宣稱所有 input 一律由畫面百分比觸發。

Pi 亦會在任務中 tools results 後／下一回應前，以及 run 結束後的相關檢查／恢復路徑進行自動壓縮。因此，原生設定不是「只在使用者提交文字時」的 policy，也不是整個任務最多壓縮一次。

## 二、80% 門檻與最小設定方案

本機 dist/core/compaction/compaction.js:173–176：

```text
contextTokens > contextWindow - reserveTokens
```

若 model contextWindow = W，設定 reserveTokens = W × 0.2，即對應大於 0.8W（token budget 必須是非負安全整數，W 無法整除時需決定 rounding）。

例：W = 128000，reserveTokens = 25600，門檻為 contextTokens > 102400。

僅為研究示例，不是對真實設定的修改：

```json
{
  "compaction": {
    "enabled": true,
    "reserveTokens": 25600,
    "keepRecentTokens": 20000
  }
}
```

此示例只適用 W=128000 的模型；多模型應用 compaction.modelOverrides 依 exact provider/modelId 分別設定。預設 reserveTokens=16384 不代表固定 80%。reserveTokens 也影響原生摘要輸出上限，並非獨立 percentage threshold；keepRecentTokens 則是切點的近期保留目標，不是壓縮觸發門檻，也不保證最終 context 的精確大小。

## 三、若要嚴格 input gate

公開契約提供 input event、ctx.isIdle()、ctx.getContextUsage() 與 ctx.compact(options)。getContextUsage 的 percent 是 0–100，而非 0–1；undefined／null 為 unknown，不是 0。尤其壓縮後尚未有新的有效 assistant usage 時，Pi 返回 tokens:null、percent:null。

重要：ctx.compact() 回傳 void，不是 Promise。`await ctx.compact()` 不會等待壓縮完成；要把 onComplete/onError 包成 Promise，或在自有 SDK caller 使用真正 async 的 session.compact()。本機 extension action 實作在 agent-session.js:2769–2779，SDK compact 在 2168–2292。

候選設計（尚未實作或整合測試）：

```text
idle 一般文字 input
→ 取得有效 usage.percent
→ 若 >80：以每 input gate 防重入，只呼叫一次公開 compact
→ await callback terminal outcome
→ 成功：繼續原 input，不重新 sendUserMessage 造成重送
→ 失敗／取消：保留待處理輸入並明確 handled，不放行任務
→ unknown：採明確 policy，不反覆使用舊 usage 或無限壓縮
```

不可直接用 throw 阻止任務：runner.js:1202–1236 會捕捉 input handler error 並繼續 handler chain。失敗分支必須明確返回 handled／使用相應 caller control。Streaming 時不可直接呼叫 compact：SDK manual compact 先 await abort()，會中斷當前 agent operation。Steer/followUp、同時第二筆 input、reload/session/branch/model 切換、cancel、重複摘要的舊 receipt 都需隔離驗證。

公開 ctx.compact 走 manual entry，因此即使是自動化 input gate 呼叫，事件 reason 仍是 manual，不是 threshold。本專案目前規則是 Pi owns trigger；新增自動 input trigger 屬於 policy 變更，需要另行決定，不宜偷偷塞入 Blackhole 或復活 legacy threshold knobs。

原生 _runAutoCompaction:2459–2585 的失敗被捕捉並回傳 false；prompt 的 pre-check 之後仍進入後續流程。故「嘗試壓縮後再執行」與「壓縮成功才執行」不是同一保證。

## 四、壓縮後紀錄的三層結構

### 4.1 原始 JSONL／branch

未建立新 session、未清空或覆寫舊歷史。一般為在同一 branch 尾端追加 compaction entry，之後追加新 user／assistant。中間也可能有 custom ledger、display-only copy、system delta 等 entry；以下是省略 metadata 的示意：

```text
session header（不是 tree entry）
system S
old user U1
old assistant A1
recent user U2  ← firstKeptEntryId
recent assistant A2
compaction C    ← parentId 指前一 leaf
new user U3     ← parentId 指 C（若中間無其他追加）
new assistant A3
```

簡化 CompactionEntry 欄位：

```typescript
{
  type: "compaction",
  id: "C",
  parentId: "A2",
  timestamp: "ISO-8601",
  summary: "舊歷史摘要",
  firstKeptEntryId: "U2",
  tokensBefore: 85000,
  systemMessage?: /* 完整 prompt/tool checkpoint */,
  fromHook?: boolean,
  details?: /* 摘要提供者資料 */,
  usage?: /* 產生摘要的模型 usage */
}
```

firstKeptEntryId 是切點，不是新 session ID；tokensBefore 是壓縮前 context 計算值，不是當次新任務的 token 數。systemMessage 在可取得 system state 時由 appendCompaction 存入；舊 session entry 可能没有。fromHook=true 表示 extension 提供摘要，不表示磁碟格式改成 Blackhole 專用格式。若 retain-none，firstKeptEntryId 可為 compaction 自己的 ID。

舊 entry 還在 raw history，但其逐字內容不自動進入新的模型 context。既有 context_edit omissions/replacements 仍適用，不能因壓縮就復活被省略資料。

### 4.2 Pi 內部 AgentMessage context

```text
system checkpoint
compactionSummary(summary, tokensBefore, timestamp)
保留的近期 non-system messages（依切點與 context_edit projection）
compaction 之後的 context-producing entries
本次新 user message
```

latest compaction 決定 active context。summary 不是一則新的 assistant 回答；它在 Pi 內部的 role 為 compactionSummary。壓縮前 kept range 的 system entries 被 checkpoint 吸收，不再逐則重播；壓縮後的新 system delta 可以繼續存在。

### 4.3 Provider-neutral LLM messages

本機 messages.js:103–109 把 compactionSummary 轉為 user-role 文字：

```text
system: prompt/tool checkpoint
user: 摘要說明 + <summary>摘要正文</summary>
user / assistant / toolResult: 保留近期訊息
user: 本次新任務
```

因此，「摘要」語意上是歷史摘要，但不是 provider 的獨立 role，也不是把新任務塞進 system prompt。各 provider adapter 仍可合併連續 user、轉換 tool schema 或摺疊 system state；這裡描述 Pi canonical／convertToLlm 結構，不宣稱每家 HTTP payload 完全相同。

## 五、Blackhole 對結果的影響

modules/blackhole/README.md:5–23 是本地現行契約，比後面的保留上游 README 更具權威：Pi 控制 threshold／cut／persist/rebuild／retry/cancel；BH 只在 session_before_compact 提供 summary，維持 preparation.firstKeptEntryId 和 tokensBefore。

所以是否使用 Blackhole，不改上述 JSONL／context 結構，主要改 summary 正文與 details。BH 的結構式目標、檔案變更、偏好、brief、以及在有效 memory/config 下的 Observations／Reflections，是摘要字串內容，不是額外 assistant turn。顯示用 pre-compaction copy 不入 model context。摘要不是 lossless 歷史備份；raw history／bounded recall 是回查來源。

legacy compactAfterRatio／compactAfterTokens 等在本地不再控制 trigger，不建議靠這些設定實現 80%。是否在實際使用者環境採用 BH、原生 default 或其他 hook 仍取決於有效設定；本次未讀取私人 credentials 或改動個人 settings。

## 六、驗證結果與界限

已用 Node 直接載入實際安裝的 Pi 1.1.0 SessionManager.inMemory 與 convertToLlm，建立 synthetic system／兩段 user-assistant／compaction／new user，執行 assert（exitCode 0）：

- raw message 數仍為 6，舊歷史沒有刪除。
- new user parentId 等於 compaction ID（此 fixture 中無額外 extension entry）。
- firstKeptEntryId 對應 recent user。
- internal roles = system, compactionSummary, user, assistant, user。
- provider-neutral roles = system, user, user, assistant, user。
- 新輸入 literal `NEW TASK VERBATIM` 在此未套 transformations 的 fixture 中保持不變。
- compaction entry 確認含 systemMessage checkpoint。

這是**真實 host 模組的離線資料結構驗證**，不是完整 prompt/auto-trigger/Blackhole runtime 試驗；summary 是 synthetic，未觸發 LLM compaction。

未執行 npm test、test:module、test:cross、typecheck 或全量 integration/package：本次沒有修改 runtime／types／manifest，只有研究文件與一次範圍最小的唯記憶體 probe。沒有驗證真實 provider HTTP payload、80% input gate runtime、failure/cancel/reload/concurrent input 或不同模型設定的端到端行為，均不算通過。
