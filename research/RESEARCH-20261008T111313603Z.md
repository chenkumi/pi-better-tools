# Subagents 背景工作退出與載入通知：唯讀調查

## 結論
目前 Subagents 沒有 session 載入時的背景中斷通知，也不從磁碟重建 background job registry。可在 session_start 加入唯讀 reconciliation 並發送模型可見 custom message，但不能把歷史 queued/running、stale parent lock 或取消要求描述成確認整棵 process tree 已停止。sendMessage 不是 role=system API。

## 調查範圍／限制

## Architecture / ownership
入口轉接 extensions/subagent/index.ts；factory 每次建立新的 BackgroundJobs。background.ts:26-35 的 Job 擁有 owner session ID、canonical cwd、generation、AbortController 與 done promise；99-111 只有 in-memory Map，沒有 storage loader。151-174 的 list/get 僅能讀同 owner/cwd/generation；233-234 為每次 invocation 產生 jobId/taskId。退出後原 jobId 無法查找。Submitted budget 是 process-wide，取消到 runner 結束前仍占容量（36-41、235-237、286-287）。

磁碟不是 job manifest：session-store.ts:44-63 為每個 child conversation 的 SessionManifest / RunIntent，owner={parentSessionId,parentCwd}，states=new/running/committing/ready/blocked。metadata 沒有 jobId、batch relationship、durable cancelRequested、shutdown reason、notification ack。begin():387-399 寫 runs/taskId/run.json 與 running manifest；blocked():400-407 保存 run.result 後可rollback；commit():409-449 保存結果及 checkpoint 再 ready；publish():450-455 保存 lastRun。Queue receipt 前已有 managed child ID，未啟動可能一直 state=new，不能稱執行中或已有checkpoint。

## Stale recovery 與高風險辨識
session-store.ts:127-130 pidAlive使用process.kill(pid,0)，EPERM視alive；其他錯誤視not alive。229-233 的 Symbol.for liveLockNonces跨reload共享。271-292 stale只有owner pid不活，或same pid nonce不在live registry；malformed／無法讀lock→非stale。這是parent writer owner證據，不是child/tree存活檢測，PID reuse亦有best-effort限制。

acquire():294-317才會rename/delete stale lock並rollback；rollbackToCheckpoint():323-348會truncate native/readable與改manifest=ready。不可拿acquire／rollback當載入檢查！assertResumable雖不寫檔，但 stale+checkpoint存在只允許之後acquire驗證，並不是已確認ready／checkpoint有效。

index.ts:625-645 kill後仍未close會回報may still be running並保留permit/lock。1020-1031 rollback eligibility要求childGone與無integrity/commit故障；1033-1048晚cleanup等childExited、實際I/O及writer close，最後blocked，不發布ready。close拒絕可能留下running/committing manifest與live writer lock（README:162）。不存在自動TTL/pruning（README:241）。

## 可確認事實 vs unknown
- 可確認：fresh runtime沒有原job manager；parent shutdown提出取消；持久化run.result明確aborted/failed可報「上次invocation紀錄為aborted/failed」。不能由此宣稱所有副作用回滾或tree終止。
- ready+checkpoint：證明conversation有提交點，不證明最後一次resume成功；失敗resume可rollback到舊checkpoint，應對照lastRun/run.result與checkpoint.completedTaskId。
- new且無run：僅配置、未有開始的持久化證據，避免誤報中斷執行。
- running/committing、missing/invalid metadata、stale lock或已失去runtime：最後執行／通知／process-tree狀態unknown，建議措辭「前次背景管理已結束；此工作未有可確認完成紀錄，程序可能仍存活；請先檢查。」
- Parent tool queued/log_ready沒有terminal message：只能證明收過受理／進度；不能把通知缺席當task失敗。Job結果、manifest checkpoint、parent通知是三個不同證據面。
- background.ts:88-131每次callback證據hostAcknowledgment永遠unknown，returned不是持久化ack，且只是memory diagnostic，禁止自動重送。

## sendMessage API與建議
index.ts:1193-1194現有完成通知customType=subagent_background、deliverAs=followUp、triggerTurn=true（log_ready=false）。Pi types:1213-1216 sendMessage回void、輸入customType/content/display/details，沒有role選項。agent-session.js:1746-1755明確role=custom；1756-1757 nextTurn只進memory queue；1781-1789 idle+triggerTurn=false會appendCustomMessageEntry並刷新context，不呼叫模型。建議新的載入notice使用custom message＋triggerTurn:false，在fresh session_start context上執行；保留returned data/not instructions邊界，不把子代理輸出提升system權限。若產品真的需要systemPrompt提示需另外設計before_agent_start，不應把它稱作sendMessage的system message。

建議唯讀、有上限、拒絕symlink、metadata bounded reader：從目前branch中的background receipt／notice取candidate session IDs，再比對同owner/canonical cwd的manifest與lastRun。Branch-only可能漏掉其他branch仍屬同parent的工作；若採root掃描，須明定session-wide inventory而非當前branch，限制數量／bytes／duration、不讀prompt/native/output/credentials、不碰foreign owners。先聚合一次中性通知，只附ID、歷史狀態、證據及unknown原因。用owner+epoch fence隔離async scan遇switch/reload；empty/new無歷史case不通知。去重需另討論branch/reload與durable marker策略，不能宣稱exactly-once。disk無job mapping時不要偽造job receipt或恢復jobId。
