## 目前流程及證據

### Shell：主 run settlement gate

- `modules/shell-tools/extensions/timeout-ms.ts:290-291`：agent_start 設 busy；agent_settled 清 busy 並排通知。
- `modules/shell-tools/src/background-jobs.ts:296-305`：runner 回傳後記 endedAt、關 log、寫 terminal journal、pending.add，排一次 immediate。
- 同檔 `343-399`：notify 在 agentActive 時返回；真正提交為 `sendMessage(..., { triggerTurn:true, deliverAs:"followUp" })`。
- 結果：即使工作早已 terminal，主 run 工具／模型／retry／queued continuation 尚未 settled 時通知仍留在 extension pending，不進宿主 queue 或對話。
- `docs/adaptations.json:35-49` 記錄 2026-10-09 的有意設計：整個主 agent run 結束後，把当時全部已完成 pending shell 工作合併一則通知，不是等待所有背景工作完成。此政策本身導致 final text 後通知，非主要由 setImmediate 的事件迴圈延遲造成。
- 只改 followUp→steer 但保留 busy gate，不會取得工具期間提前注入的效果。

### Subagent：立即提交，但 followUp 等主 agent 原本準備停止

- `modules/subagents/extensions/subagent/background.ts:295-357`：await run；收尾、保存 terminal、更新 UI，finally 送 task_result；沒有 Shell 式 parent busy gate。
- `modules/subagents/extensions/subagent/index.ts:1194-1202`：task_result／control_result／query_result 都 triggerTurn:true、deliverAs:followUp；log_ready triggerTurn:false。
- Subagent runner 的完成包含 child 實際 close、native／guard／digest、commit 或 rollback／writer release；不能從 child 最後一則文字或 log 末尾推論整個 runner 已完成並提前發布成功。
- parallel／chain 的 task_result 在整個 run 回傳後發送；個別 finish callback 只更新 task 和 journal，不立即通知。單一 task 已完成但其他 task 仍執行是另一種 batch 等待，不等於宿主 delivery delay。

### 真實安裝宿主 Pi 1.1.0

- `node_modules/@earendil-works/pi-coding-agent/dist/core/agent-session.js:1782-1819`：streaming 且 triggerTurn:true 時，followUp 排入 agent.followUp；steer 排入 agent.steer。streaming＋triggerTurn:false 另存 pending custom messages，等待 turn 結束再 append，不等於立即影響當前請求。
- `node_modules/@earendil-works/pi-agent-core/dist/agent-loop.js:179-198`：每個 assistant＋tool batch 完成後讀 steering；只有內層工具／steering 流程原本將停止時讀 followUp。
- 同檔 `115-121`：選出的 queued messages 會在下一次 assistant request 前發出 message events 並進 context。
- `agent-session.js:2702-2710`：extension sendMessage 不回 async ack；host async rejection 由 send_message error 回報。callback 返回不是 persisted／delivered 確認。

## 建議方案（未實作）

1. Shell 把完成 batching 的邊界從「整個主 run settled」改成「下一個安全 turn 邊界」。runner 真正 terminal 後以一次 immediate 合併當時完成 pending，busy 時提交 steer、idle 時保留 triggerTurn:true 喚醒。不等待 still-running jobs，不在 session tree 任意位置寫入。不把 agent_end 當最終結束、不繞過 retry／generation／owner／retention／reentry／journal fences。這會改變既有 2026-10-09 batching 契約，須明確更新測試、README 和 provenance。
2. Subagent 保留 runner settlement／commit／writer barriers，對 task_result 改用 steer 以避免等待 parent final stop。log_ready 維持 triggerTurn:false；control_result／query_result 是否也改為 steer 应個別決策，不必一次更動所有 kinds。
3. 首版不改 parallel／chain per-task completion 通知；若仍觀察個別 task 終結等待 whole batch，另行設計 bounded partial completion，不能假稱整個 job 完成或重複入帳。
4. 不 abort 當前 provider stream，不重跑／回填舊通知、不新增 durable queue、輪詢或設定。完成落在已進行的 final provider request 時，至少仍須等待那則 assistant message 結束；這是不可消除的既有請求邊界。
5. UI 更早顯示 finished 與模型更早消費結果是不同需求；若需要 task 完成即時顯示，可另外更新現有 event-driven 面板／status，但不能將 UI 事件冒稱 session persistence 或 model delivery ack。
