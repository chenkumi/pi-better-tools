# 背景 Shell／Subagent 在 Pi 載入 session 時的中斷通知可行性

日期：2026-10-08。範圍：本專案及本機已安裝 Pi 1.0.0。使用者要求調查可行性，未要求實作；未修改runtime/source/provenance、真實settings/auth/session/checkpoint，未重送control或續接既有child。

## 結論

可在既有 extensions 的 `session_start` 加入 reconciliation，自動追加一則 TUI 可見、模型 context 可見且持久化的 custom message。不需修改 Pi 核心、不需啟用未選工具、不需 spawn 或呼叫 provider。這不是 `role:system` API；Pi 的 `sendMessage` 產生 `role:custom`。建議滿足「系統自動通知」意圖但不提升命令／子代理輸出為 system 指令。

建議預設 `{triggerTurn:false}`：立即記錄通知，主agent下一回合可見，但載入時不主動呼叫付費模型、不自動重新執行shell／resume child。如果另要求載入即讓agent回應，可另設明確 opt-in 的喚醒政策，不是此調查默認。

## 已確認現況及根因

### Shell

- `modules/shell-tools/extensions/timeout-ms.ts:235-239`：factory建立新的 ShellJobs，session_start只start，session_shutdown只shutdown；沒有歷史reconciliation。
- `modules/shell-tools/src/background-jobs.ts:134-154`：registry是記憶體Map，start只绑定當前session，沒有持久化job inventory。
- 同檔 `:194-207`：temp directory僅寫owner.pid及output.log，job ID／owner session／generation等在記憶體。不能從temp目錄可靠重建某個session的全部工作。
- 同檔 `:316-329`：完成通知只對current job發送，sendMessage不是持久化送達確認。
- 同檔 `:385-407`：shutdown先stopped=true及generation++、清pending，abort全部，最多等2秒，關閉／刪log並清Map。正常退出時的取消結果因此也不會通知parent。
- 同檔 `:49-75`：stale掃除只由parent PID或舊目錄年齡判斷temp housekeeping，不是job outcome／整棵process tree已死亡的證據。不能靠log存在／不存在推論完成。
- README `:68-77`：status/cancel限原session/runtime；quit/reload/new/resume/fork都取消背景工作，不跨replacement繼續。cancel request不保證tree已停止。

## 建議實作設計（未實作）

### A. 新工作使用durable最小journal

每個模組獨立保存自己工作，不建立plugin manager或互相共享執行registry。可用session appendEntry保存版本化lifecycle metadata，必要時外部atomic inventory處理SDK／no-session邊界；儲存方案需在實作計畫明定。記錄parentSessionId、canonical cwd、runtime incarnation ID、新大寫ULID job ID、toolCallId／childSessionId/taskId、accepted/started/terminal/shutdown evidence及通知identity。command只保存bounded preview且保持資料信任邊界，不複製prompt、credentials或整份output。

accepted intent應在可spawn/side effect之前可驗證寫入，與receipt映射一致；started、terminal outcome及shutdown原因分開記錄。必須辨識write failed與「寫入後但spawn前crash」窗口：intent不等於已開始，terminal失敗寫入則結果unknown。若寫入失敗須明定是否拒絕接受，不能默默承諾resume可辨識。持久化後才嘗試完成通知，但不把sendMessage returned記為ack。

正常shutdown在還有合法owner/entry API時保存shutdown_requested與terminal evidence，再做既有abort/cleanup，仍抑制舊generation觸發模型；崩潰時依accepted/start紀錄與無terminal evidence辨識管理中斷，不能依賴shutdown callback一定跑。

### B. session_start唯讀核對，再聚合一則通知

startup/resume/reload都核對；fresh/new無匹配紀錄不通知。以現在parentSessionId＋canonical cwd＋runtime incarnation fence限權，對照當前live registry／durable metadata；other-runtime若存活或無法辨識也只報unavailable/unknown，不跨runtime取消或接管。fork/clone複製舊entries不可把原owner工作算成本session。

Jobs副作用是session-wide、不是branch-local；不能僅用getBranch重建inventory，否則切branch/compaction漏掉仍受理的工作。getEntries／外部owner index用於嚴格限定的工作lifecycle資料；模型context通知仍追加目前active branch，避免把abandoned歷史指示重新引入。branch切換後是否重補需明定，不宣稱一個global notified marker在所有branch都可見。禁掃所有使用者session或私有prompt/output。

對Subagents只用bounded read-only metadata reader：不acquire、不rollback、不truncate、不resume、不重送accepted/delivery_unknown control、不spawn/provider。reject symlink／malformed／超額資料，數量、bytes、duration設上限；若掃描被限制必須提示「檢查未完成」，不能表示全無中斷。

通知分類：
- 有durable terminal outcome但完成通知未保存：提示「上次結果已有紀錄」，保留真實success/error，不當成失敗或重新執行。
- 有orderly shutdown evidence：提示「前次runtime退出／reload時已提出取消要求」，僅有runner settled證據才說runner結束；不聲稱所有descendant終止。
- 無terminal證據、原管理runtime不再可用：提示「背景管理已中斷，最後結果unknown，程序可能仍存活」。
- queued/intent但未started：提示未有開始證據，不捏造執行中。

通知custom type建議module-specific或共用協調的bounded聚合，display:true/triggerTurn:false。不覆寫原tool結果/status schema、不恢復原job registry、不自動重新啟動工作。

### C. 舊session只能保守fallback

舊receipt、status與完成custom messages可按owned ID收集candidate；codemode/nested calls可能沒有独立receipt entry，receipt前crash亦可能無紀錄。Shell temp logs不能補可靠outcome；Subagent manifest能補部分證據但缺background mapping。只報「歷史受理紀錄無可確認完成結果，原runtime工作不能沿用」，不能把absence當failed。精準、完整的既有工作中斷偵測無法追溯保證。

### D. 去重／送達

用可驗證的通知custom_message details之job+runtime+evidence fingerprint避免相同branch重複，證據更新可再補；不要只設notified=true就當送達。parent session file若flush失敗、async send failure或branch/reload競態，exactly-once不能保證。保存通知與marker最好同一entry並查實際session evidence，避免兩段寫入造成永久漏報；要處理成功結果已記錄但通知缺席、terminal在scan過程晚到、async scan後owner變更。純UI notify不進model context，不能滿足需求。模組未載入時無hook，不能承諾Pi核心仍会通知。

## 建議驗證（實作後才執行）

1. 單元用deferred barriers驗lifecycle reconcile、duplicate、更新、owner/generation/cwd、branch/fork/compaction、corrupt/oversize/symlink、write failure／spawn crash窗口，不新增sleep/idle timeout測試。

3. 結果已完成但notification缺席、manager unavailable但PID alive、queued未started、Subagent ready rollback versus successful lastRun、invalid/blocked checkpoint、same session foreign runtime。
