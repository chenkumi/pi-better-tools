# web_fetch 無瀏覽器 HTTP 相容模式可行性研究

## 結論與範圍

可行。建議保留 Chromium 優先，僅在確認指定 channel 的瀏覽器 executable 缺少時，改由受控 HTTP transport 取得靜態 HTML，沿用既有隔離 worker 的正文抽取與 Markdown/text 輸出。這是降級能力，不是與瀏覽器等價。

本輪僅讀取原始碼、既有測試與官方文件；未修改產品程式、設定或依賴，未移除／安裝瀏覽器，未實作或測試 fallback。透過現有 web_fetch 成功讀取兩份官方文件，只證明本次工具環境可抓取它們，不代表缺瀏覽器情境已復現。

## R1：失敗原因與依賴界線（原始碼確認）

- 根 package.json：playwright 1.64.1 是正式依賴；browser:install 為 playwright install chromium --no-shell；Node engines 為 ^22.22.2 || ^24.15.0 || >=26.0.0。
- modules/web-tools/src/fetch/service.ts:128–148、209–212：每次 fetch 需要 getBrowser，沒有 HTTP 分支。
- service.ts:82–100：已區分 executable 缺少、系統依賴缺少、權限、啟動逾時與未知原因，但最後全部轉成 BROWSER_UNAVAILABLE 字串。
- service.ts:2 靜態 import playwright。因此「沒有下載瀏覽器 binary」與「npm playwright 套件根本未安裝」是不同問題。第一階段只支援前者；不將破損 npm 安裝默默當成可用安裝。若將來要將 playwright 本身 optional，另需隔離 import、TLS 相容模組和依賴／打包驗證。
- Playwright 官方說明確認版本對應 browser binaries，chromium channel 的新 headless 支援 --no-shell 安裝。

影響：增加內部型別化 launch failure reason，保留現有安全錯誤文字，不以捕捉全部 BROWSER_UNAVAILABLE 或比對面向使用者提示文字決定 fallback。

## R2：抽取器可共用（原始碼確認）

- service.ts:336–345：目前拿到序列化 HTML 後呼叫 extractHtmlIsolated。
- modules/web-tools/src/fetch/extract-core.mjs:46–102：JSDOM → Readability/main/body → Turndown/text，未啟用 runScripts/resources；不需要 Chromium 即可解析已取得的 HTML。
- 同檔保留安全連結、表格、程式碼、登入／反爬警告、空內容拒絕與 1 MiB 抽取限制。
- modules/web-tools/tests/unit/fetch.test.ts:79–126、229–255 已有抽取、腳本不執行、輸出限制及 worker 共用案例；本輪只讀取，未執行。

影響：新 transport 不需再引進另一套 HTML-to-Markdown library；保持 worker 的取消、shutdown、容量與 5 MiB HTML 限制。

## R3：建議切換規則（方案，尚未實作）

第一階段不新增工具參數或全域設定；保留現有 fetch.channel（chromium/chrome），不要自動改用其他 channel 或個人 profile。

| 情境 | 建議行為 |
| --- | --- |
| 指定瀏覽器啟動成功 | 維持目前瀏覽器路徑 |
| 指定 executable 明確缺少 | 同一次呼叫內改走 HTTP，回報降級警告 |
| 系統套件缺少、權限拒絕、啟動逾時、未知失敗 | 保留現有原因與修復提示，第一階段不自動降級 |
| 網站 HTTP 錯誤、TLS／DNS／網路政策拒絕、CAPTCHA | 不藉 fallback 重試或繞過 |
| 取消、shutdown、總 deadline 到期 | 立即結束，不再啟動 fallback |
| 指定 waitForSelector 且瀏覽器缺少 | 明確失敗，說明 HTTP 模式無法履行動態等待，不靜默忽略參數 |

可先使用實際 launch 的已知缺 executable 分類，避免自行猜測不同 channel 的安裝路徑；不永久快取失敗（既有 fetch.test.ts:30–64 明確要求失敗不永久快取）。不要自動下載瀏覽器。

兩條路徑共用既有 queue、同一 deadline／AbortSignal 和抽取器；fallback 不重設 timeout，不重新 acquire queue。缺少瀏覽器的分支尚未導航，因此不需要重播已送出頁面請求。

結果建議在既有 warnings 加入「使用靜態 HTTP；未執行 JavaScript，內容可能不完整」。若新增 backend 資訊，應為向後相容的 additive data 欄位並同步 renderer／測試，不修改既有 extraction 的意義。

## R4：HTTP transport 的安全與資源要求（原始碼確認＋設計要求）

modules/web-tools/src/fetch/network.ts 提供 URL／所有 DNS 結果的公開位址驗證，但 ValidationCache 只保存 Promise<void>，沒有保存可綁定連線的已驗證 IP。service.ts:249–252 額外檢查 Playwright response.serverAddr。README 明確承認現有瀏覽器路徑仍有 DNS rebinding 競態，不能宣稱完整 SSRF sandbox。

因此不能只先 policy.validate，再呼叫預設 global fetch 自動跟隨 redirect：會失去逐跳與實際目的位址保障。

HTTP 分支驗收要求：

1. 僅 HTTP(S)，拒絕 URL 帳密、所有既有非公開 IP 類型；每個 redirect 檢查，限制跳數。
2. 將 DNS 檢查結果綁定實際連線；TLS 憑證及 SNI 仍對原 hostname 驗證，不關閉 TLS 驗證、不將 URL 直接改成 IP 草率替代。
3. 不使用全域 dispatcher 修改其他工具的網路行為。Node fetch 支援 per-request custom dispatcher；若選 Undici Agent，須明確宣告直接依賴，不能依賴 transitive package 恰好存在。另一候選是 node:http/https 的受控連線；其細節需實作前另核對，這次不宣稱已驗證。
4. 串流讀取並限制實際解壓後內容；不能只信 content-length，也不能先無界 response.text() 再檢查。錯誤、取消、重導向跳轉時關閉／取消 body 並清理連線資源。
5. 保持 HTML/plain text、attachment／PDF 拒絕、HTTP status 與空內容規則。plain text 應避免當作 HTML 解釋；HTML charset／BOM、gzip/br 與無 content-length 需測試。
6. 不載入 subresources、不執行 JavaScript、不提供個人 cookies／認證。不自動跟隨 HTML meta refresh 或 script 導航。

尚待收斂：選定並驗證安全 transport（fetch + scoped dispatcher 或內建 http/https）。這是實作主要成本；模式切換與抽取重用本身較直接。

## R5：修改範圍與驗收建議（尚未執行）

最小主要範圍：
- modules/web-tools/src/fetch/service.ts：launch reason、分支與共同生命週期。
- 新增模組內 HTTP transport；network.ts 以最小幅度支援已驗證 IP 綁定，避免改變瀏覽器原有策略。
- modules/web-tools/src/index.ts 的 description／promptGuidelines 與必要結果展示。
- 對應 unit/integration 測試；README、相關 docs、設定技能對此功能的說明及 provenance 依實際修改同步。
- 若新增直接依賴，才修改根 package.json／lockfile，執行額外跨模組與套件驗證。

必要測試：
- mocked launch 缺 executable 才走 HTTP；其他 launch 原因不切換；失敗不永久快取。
- 隔離 process 與空的 PLAYWRIGHT_BROWSERS_PATH，實際驗證無瀏覽器的靜態抓取；不移除使用者真實 cache。
- 瀏覽器可用時維持 JS 動態內容；HTTP 只回靜態內容且有警告。
- selector 明確拒絕降級、錯誤不重播、取消／shutdown 清理、共用 deadline／queue（不增加固定 sleep timeout 測試）。
- redirect 到私網／混合 DNS／DNS rebind、憑證錯誤、過大串流／解壓、charset、plain text、PDF／attachment／空頁／HTTP 錯誤。
- 真實缺瀏覽器 probe 與需要 server/process 的案例歸 web-tools integration；純分支／政策替身放 unit。

實作後依範圍執行 npm test、npm run typecheck、npm run lint、npm run test:module -- web-tools。改 provenance 執行 sources:verify；改根依賴或其他跨模組範圍依專案規範加 test:cross 及依賴變更要求的完整驗證。不能以 mock 通過代替真實無瀏覽器案例。
