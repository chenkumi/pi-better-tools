# Fork 遇到中斷性錯誤時狀態不回報（含 API 額度用盡）

## 症狀

`fork_status` 長期停在 `running`，來源 session 從未收到任何完成或失敗通知，直到手動 `fork_cancel` 才結束並回報 `cancelled`。使用者觀察到的情境是 API 額度用盡。

## 事故時間軸（同一 job，來自實際紀錄）

Job `01M52M47XTKFXET5YE7EMEAJ81`，來源 session `01a14537-…`，child session `01M52M47XT00BR9JH8FCE4EAK9`。

| 時間（UTC） | 事件 | 來源 |
| --- | --- | --- |
| 15:08:43 | Fork 啟動 | `.pi/forks/01M52M47XTKFXET5YE7EMEAJ81.json` |
| 15:34:13 / 15:34:55 / 15:43:13 / 15:44:29 | assistant `stopReason:"error"`，`errorMessage`＝「The ChatGPT user has reached their Subscription Sharing usage limit…」（共 4 次） | child session JSONL |
| 15:44:29 | 最後一次活動，之後 child session 完全沒有新條目 | 同上 |
| 15:48:08 | 我送出 `fork_cancel` 才結束，記錄 `status:"cancelled"`、`cleanup.childClosed:true`、`exitCode:0` | journal |

**關鍵推論：**`exitCode:0` 且取消能正常完成，代表 child 行程**一直活著**，不是崩潰死亡——它是「活著但永遠不完成」。整個 15:44–15:48 期間父行程完全不知道出錯。

## 根因

### D1：Fork 父行程在送出 prompt 後沒有任何 liveness 期限

`modules/fork/src/child.ts`：

- 唯一的 deadline 是送出 prompt **之前**的 `STARTUP_MS`（90 秒，line 153）。
- 送出 prompt 後，line 166 是 `await raceCancel(quiescent.promise)`——只與取消競速，**沒有 inactivity/watchdog 期限**。
- 也只監聽 `close`（line 97），**沒有** `proc.on("exit")`。Node 的 `close` 要等 stdio 關閉；若後代行程持有繼承的 pipe，即使 child 已死也不會觸發 `close`。

因此 child 只要不完成也不關閉，Fork 就永遠 `running`。

### D2：child 端 guard 只有「安靜」這條回報路徑，沒有錯誤逃生口

`modules/fork/src/child-guard.ts`：

- settlement 唯一訊號是 `send({ type:"settled", quiet:true })`，而它**必須**先滿足 `quiet()`：`ctx.isIdle() && !ctx.hasPendingMessages() && shell+subagents 計數為 0`（line 33–40）。
- `agent_settled`（line 59）觸發後若 `quiet()` 為 false，就每 1 秒輪詢直到 quiet；沒有上限、也沒有依錯誤結束的分支。
- 父行程只認 `message.quiet === true`（child.ts line 108），所以 guard 不送，父行程就永遠等下去。

**已排除的替代解釋：**`agent_settled` 並非因錯誤而不發出。在 host `packages/coding-agent/src/core/agent-session.ts:1874-1881`，`_emitAgentSettled()` 位於 `finally`，模型錯誤後仍會發出。所以 guard 有收到事件，是 `quiet()` 一直不成立。

**已由受控實驗確定（見下節 Run C／D）：**不是 `isIdle()`、也不是 `hasPendingMessages()` 單獨作祟，而是 **nested job 計數 > 0 使 `quiet()` 恆假**。pi-runtime 的 pending recovery 經 Run B 排除為必要條件。

### D3：狀態投影本身沒有任何 liveness 可觀察量（`fork_status` 因此必然看不出異狀）

使用者在事故期間查詢 `fork_status`，看到的是：`status:"running"`、`delivery:"pending"`、`holdsPermit:true`、`startedAt` 存在、無 `endedAt`、無 `cleanup`。這與一個正常工作中的 Fork **逐位元相同**，無法區分。原因有兩層，必須分開處理：

1. **沒有新資料（D1 的後果）**：`manager.ts` 的 record 只在收到事件時改動——phase 進入 running／finalizing、`settled` 後寫 result、`close` 後寫 cleanup（line 132、57、144）。child 卡住時這些事件都不會發生，所以投影「沒有變化」不是投影的錯，是根本沒有資訊可投影。父行程自己也不知道出錯。
2. **投影欄位本身就缺可觀察量**：`summarize()`（manager.ts line 252–258）只回傳 `jobId`／`forkSessionId`／`title`／`status`／`cancelRequested`／`delivery`／`model`／`thinkingLevel`／`createdAt`／`startedAt?`／`endedAt?`／`sessionPath?`／`cleanup?`／`holdsPermit?`／`persistError?`／`result|errorCode+usage`。**沒有** `lastActivityAt`、沒有 progress 計數、沒有 child pid liveness、沒有 `stderrTail`（`child.ts` line 181 有這個欄位，但 `record.cleanup` 只存 `childClosed`／`exitCode`，line 144，stderr 尾端從未落盤）。
3. **面板同樣沒有**：`live-widget.ts` line 20–40 的 `activity(job)` 只是 status → 字串的靜態映射（`running`、`cancelling`…），不含時間資訊；details 只列 Created／Started／Ended／Cleanup。所以 TUI 面板上一樣看不出停滯。

另外 `running` 是**單一平坦狀態**，同時涵蓋「正在工作」與「已經卡死」，狀態機沒有任何中間區分。

### 對照：Subagent 已有這道防線，Fork 缺

`modules/subagents/extensions/subagent/index.ts`：

- `SUBAGENT_INACTIVITY_TIMEOUT_MS = 300_000`（line 104），配合 `armInactivity()`／`activity()`（line 698、708）在 stdout 無進展時 `fail("timeout", …)`。
- `agent_settled` 後另有 `SETTLED_EXIT_GRACE_MS = 5000` 的退出寬限（line 100、784-799），未收到 terminal assistant message 就失敗。

也就是同一個 repo 內已有「不依賴 child 合作、以 inactivity 判定失敗」的成熟模式；Fork 沒有採用它。

## 受控重現（實測證據）

以真正的 Pi host（RPC）＋真正的 Fork child，搭自訂模擬 provider：parent 發出 `fork` tool call；child 的模型呼叫**在串流中途被中斷**，回傳與事故相同的 `stopReason:"error"`／subscription usage limit 訊息。環境在專案外隔離目錄（`%TEMP%/pi-fork-repro`），用 junction 指向 repo `node_modules`，未修改任何 repo 檔、未新增測試檔，`--offline`、無真實 credentials。

| Run | 條件 | 結果 |
| --- | --- | --- |
| A | 中途中斷；無 nested job；未載 pi-runtime | ~1.5s 內 `failed`／`CHILD_MODEL_ERROR`，通知送達（**無 bug**） |
| B | 同 A，加上 `pi-runtime` | ~3s 內同上（**無 bug**）→ 排除 pi-runtime 為必要條件 |
| C | 中途中斷；child 先啟動**長時背景 shell job**（600s） | **重現**：90s 後仍 `running`、`delivery:"pending"`、無 `endedAt`、無 `cleanup`、無通知；父側 debug 只到 `verified; sending prompt`，從未 `quiescent` |
| D | 同 C，但背景 job 於 15s 自行結束 | 19.2s 時 `failed`／`CHILD_MODEL_ERROR`，通知送達（**會自行恢復**） |

結論：

1. **觸發條件是「存在未完成的巢狀 job」，不是 provider 錯誤本身。** 錯誤只是讓 child 停滯；job 計數 > 0 才是鎖住回報的那一道門。
2. **Run D 證明設計本身會在 job 結束後恢復**（job-completed → wake-up → 再失敗 → settle → quiet）。所以缺陷不是「永遠不會回報」，而是「**只要有任何未完成 job，模型已死這件事就完全不可見，且沒有期限**」。事故中的 job 跑了 40 分鐘，終端使用者看到的就一直是「一切正常」。
3. **Run C 同時證實 D1 與 D3**：父側沒有 liveness 期限（否則不會等 90s 無反應），且 `fork_status` 投影無任何可區分的可觀察量。
4. Run A/B 是重要的**反向對照**：修正必須保留這條正常路徑，不得把單純的 provider 失敗變成卡住或誤判。

重播方式（保留完整驅動）：複製或重寫 `%TEMP%/pi-fork-repro/{provider.ts,drive.mjs}`；`REPRO_CHILD_MODE=nested REPRO_JOB_MS=600000` 即為 Run C，`REPRO_JOB_MS=15000` 為 Run D。四份輸出在 `result-*.json`。實驗結束後已確認無孤兒行程殘留。

## 這不只是額度問題

`child.ts` 已經正確處理的路徑，是「child 真的死掉且 `close` 被觀察到」（→ `CHILD_EXITED`）。會落入同樣無限等待的是**任何讓 child 活著但不進入 quiet 的錯誤**，例如：

- provider 持續失敗或重試耗盡後不再前進（本次案例）。
- provider 串流卡住、請求永不返回。
- nested shell／subagent 工作計數停在不為 0（child 的 quiet 條件因此恆假）。
- 後代行程持有繼承 pipe，使 child 已死但 `close` 不觸發。

因此**使用者的推測方向正確**：這是 Fork 缺少通用 liveness 防線的類別問題，不是額度專屬。反向也應注意：只針對「額度」加特例不是解法。

**實測證據（本輪）：**

- 專案外 harness，修正前後對照：修正前 Run C 停在 `running` 90s 無訊息；修正後 3s 內即為 `blocked`，journal 落盤 `{"status":"blocked","blocked":{"reason":"MODEL_ERROR","error":"…usage limit…","pending":{"shell":1,"subagents":0},"since":…}}`。

**刻意未做（非遺漏，需先有新證據）：**

- `blocked` **不設放棄期限**。原方案 A 提到 inactivity 期限，但 `activeJobCounts` 只有計數、沒有工作進展資訊，無法區分「長時間但正常的 job」與「已卡死的 job」；在此前提下任何固定門檻都可能錯殺合法工作（例如本專案自己的 `test:integration`）。因此本輪只做到「永不隱形」，並在 README 明列此缺口與補上期限所需的前提。
- 父側仍未監聽 `exit`、也未加 running 階段 inactivity watchdog（D1 的剩餘部分）。上述情境（child 活著但模型已死）已由 `blocked` 涵蓋；真正仍未被期限保護的是「child 卡住且作用中 job 永不結束」。
- 未加 `lastActivityAt` heartbeat（D3 的 B 部分）：`blocked` 已提供足以區分的可觀察量，heartbeat 另需落盤節流設計，屬後續。
- `blocked` 不觸發 `triggerTurn`，不會呼叫 parent 模型；中場狀態只經 `fork_status`／面板呈現。

## 建議修正方案（若日後要繼續）

維持既有契約（不捏造結果、不以未完成工作宣稱成功、取消不等於已清理、重啟標記 interrupted）。方案依據 Run A–D：必須修好 Run C，且不得弄壞 Run A／B／D。

**關鍵行為決策：模型已無法再執行時，已啟動的巢狀 job 該如何處理？**

- **A（建議）：不奪走進行中的工作，但立刻讓狀態誠實。** guard 在 `agent_settled` 且最後一則 assistant 為 `error` 時，不再等待 quiet，立即送出一個**非成功**的狀態訊號（帶 `pendingJobs` 計數）；父行程記錄為 `blocked`（可讀為「模型錯誤，等待 1 個 shell job」），`fork_status` 與面板同步呈現，並加上 inactivity 期限避免無限期。job 結束後仍走 Run D 路徑正常收尾。優點：保留 job 的副作用（例如測試輸出、已產生的檔案），且不改變現有「等待巢狀工作」的語意，只把不可見變成可見。
- **B：一旦模型錯誤立即終止巢狀 job 並回報失敗。** 實作最簡單，但會丟掉進行中的工作，等於把目前的等待設計改成 fail-fast，語意變動較大。

其餘修正項：

1. **child.ts 補 liveness 與行程死亡觀察（主要修正）**
   - 監聽 `exit` 之外仍以 `close` 作為 cleanup 證據；`exit` 已觀察到但 `close` 未到時失敗並保留 `childClosed:false`，不宣稱已清理。
   - 在 running 階段加入 inactivity 期限（比照 Subagent `SUBAGENT_INACTIVITY_TIMEOUT_MS` 的量級與 `activity()` 續期語意），以 stdout／RPC 進展續期；逾期即以明確代碼（如 `CHILD_STALLED`／`NO_PROGRESS`）失敗，並走既有 abort→EOF→TERM→KILL 終止階梯。
   - 續期訊號應取既有可觀測事件，不新增固定 sleep 等待。
2. **child-guard.ts 補 bounded 逃生口**
   - `agent_settled` 後若 `quiet()` 在有限時間內持續不成立，仍送出一個**非成功**的 settlement（例如 `settled { quiet:false, reason }`），讓父行程能提前以 `CHILD_MODEL_ERROR`（沿用既有映射）失敗，而不是無限期輪詢。
   - 必須保留現行「nested 工作未完成不得發布成功」與「連續兩次 quiet」規則：逃生口只能產生失敗，不能產生成功。
3. **manager.ts 讓狀態與通知必為終態**
   - 上述失敗都走既有 `complete()` 路徑（status `failed`、`errorCode`、`delivery` pending／submitted 語意不變），不得新增「停在 running 也算一種狀態」。
4. **文件**：`modules/fork/README.md` 的生命週期／完成判定段落需補上 liveness 期限、逾時代碼與 `exit` 與 `close` 的差異；依 AGENTS.md 修改 Fork 後同步相關說明。
5. **可觀察性（D3 修正）**：讓停滯在 watchdog 觸發**之前**就能被看見。
   - child 端以既有可觀測事件（stdout 行、RPC 回應、guard 輪詢）續期一個 heartbeat，父行程將其寫入 record 的新增欄位（例如 `lastActivityAt`／progress 計數）。
   - `summarize()` 與 `live-widget.ts` 的 `activity()`／details 一併呈現，使 `running` 之外的「多久沒有進展」可讀。
   - 超過門檻時由 manager 轉為新的終態（例如 `stalled`）並依一般路徑回報；**不得**因此宣稱成功或已清理。
   - 效能考量：heartbeat 若每次事件都 `persist` 會造成大量磁碟寫入，應節流（記憶體即時更新、落盤降頻）；欄位以 additive 方式加入，`schemaVersion` 與既有 record 驗證規則需一併確認，不破壞舊紀錄讀取。
   - `fork_status` 維持唯讀，**不**為了探測而新增 child RPC 或模型請求。

## 驗證計畫（紅先行）

1. **真實重現（本次事故）**：已於專案外以模擬 provider 完成（Run C）。進入 repo 的正式回歸測試需斷言：child 有未完成巢狀 job 且模型錯誤時，狀態必須在期限內轉為可區分的 `blocked` 或終態，**不得停在無訊息的 `running`**。
   - Run A／B／D 必須維持綠（維持既有正常路徑）。
   - 紅／綠一律使用模擬 provider，**不得**依賴真實額度用盡或付費模型。
2. **child 死亡但 close 未到**：child 產生持有繼承 pipe 的後代後死亡，斷言不無限等待且 `childClosed` 誠實為 false。
3. **quiet 永不成立**：驗證 bounded 逃生口會產生失敗且**不會**產生成功。
4. **既有契約回歸**：nested background shell 完成前不得發布成功、取消與 quit 扇出、`interrupted` 標記等既有 case 必須維持綠。
5. **停滯可觀察性**：以擬造的停滯 child 斷言 `fork_status` 投影在 watchdog 觸發前就能顯示「無進展」資訊（`lastActivityAt`／stalled 狀態），且 heartbeat 節流不造成每次 stdout 行都落盤。
6. **D2 未定條件判定**：上述紅測試同時應輸出 `isIdle()`／`hasPendingMessages()`／nested job 計數的實際值，用來判定本次事故是哪一個條件不成立，而不是留在推測。
