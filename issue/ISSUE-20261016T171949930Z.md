# Fork `CHILD_EXITED: CHILD_CLOSED: child exited before startup verification` 調查

## 結論（一句話）

那次 Fork 的 child 行程**根本沒有載入成功任何 extension**：當下 `C:\GitHub\pi-better-tools\node_modules` 正處於損壞狀態（`@earendil-works/*` 等 scoped 套件被刪除），而 android_emu 的 Pi extension 是從這個 repo 載入、依賴也解析到這裡。child 在 extension 載入階段就以 exit 1 結束，因此 guard 從未載入、從未送出 `rejected`，父行程只能觀察到 `close`，於是回報泛用的 `CHILD_EXITED`。

**這不是 Fork 邏輯的缺陷，是共用套件樹被並行破壞的一次性環境事故。**

- 來源專案 `C:\projects\android_emu`，parent session `01a14498-…`
- 受理 `2026-10-16T17:07:03.558Z`，`startedAt 17:07:03.587Z`，`endedAt 17:07:13.977Z`（存活約 10.4 秒）

## 證據鏈

### 1. child 什麼都沒寫

child 的 session 檔 `…2026-10-16T17-07-03-564Z_01M52TWX85W65MJ30XZBVTCENP.jsonl` 共 426 筆，**最後一筆是 `pi-better-tools.fork-origin`（index 425）**，時間即快照時間 17:07:03.564Z。除此之外沒有任何 child 自己產生的條目（沒有 `message/system`、沒有 `pi-runtime-state`）。健康的 child 在啟動時就會寫入系統訊息，因此這代表 child 在 **session_start 之前**就結束了。

### 2. 不是 guard 的設定檢查（已用最忠實重跑排除）

以 parent 記錄下來的完整參數重跑 child（相同 session 副本、`--model`／`--thinking`／`--tools` 18 個、`--exclude-tools`、`-e <真的 guard>`、`--approve`、相同 `PI_FORK_GUARD`）：

PROBE_FINGERPRINT=90f693b971682248   ← 與 journal 完全一致

PROBE_CWD_REALPATH=C:\projects\android_emu    PROBE_SESSION_ID=01M52TWX85W65MJ30XZBVTCENP

model／thinking／trust／cwd／sessionId／工具集合**全部符合 guard 期望並通過驗證**。同一次實驗的對照組故意把 expected cwd 寫成正斜線，就立刻得到 `CONFIG_CHANGED`／exit 1——這既證明檢查正常，也警告了這類重跑很容易自己製造假陽性。

parent 的工具清單由指紋反推（對已知工具池做 18 取 5 組合枚舉，唯一解）：
`bash,edit,find,grep,ls,monitor_start,monitor_status,monitor_stop,note,read,recall,subagent,subagent_cancel,subagent_message,subagent_status,tool_search,web_fetch,write`

### 3. 真正原因：共用 node_modules 在該時刻是壞的

同一分支上另一個工作（web-tools／setup CLI）的計畫自述事故：為做 baseline 歸因建立了 detached worktree 並在其 `node_modules` 建 junction，清理時 `rm -rf` 遞迴穿透 junction，**刪除了本倉庫 `node_modules` 內多個 scoped 套件，包含 `@earendil-works`**，以及 `node_modules/.package-lock.json`；之後以 `npm install --ignore-scripts` 修復。

修復時間可由檔案 mtime 直接看出（本地 UTC+8）：

| 時間（本地） | 事件 |
| --- | --- |
| 00:48–01:02 | 另一個工作的 `test:package` 窗口；期間發生 node_modules 破壞 |
| 00:59:01 | 本倉庫 fork 修正 commit `bb711b8`（樹已乾淨） |
| **01:07:03 → 01:07:13** | **android_emu 的 Fork child 啟動並以 exit 1 死亡** |
| 01:08:29 | `node_modules/@earendil-works/` 才被重建 |
| 01:09:14 / 01:09:46 | `@earendil-works/pi-ai`、`node_modules/.package-lock.json` 才重建 |
| 01:11:23 | `package-lock.json` 復原 |

**修復比 child 死亡晚了 76 秒**，所以 child 啟動時 `@earendil-works/*` 仍不存在。

為何 parent 沒事、只有 child 死：android_emu 的 Pi 行程（`ownerPid` 11688 屬於 parent）自當天早上就在執行，extension 早已載入記憶體；只有**新產生的行程**會重新解析並失敗。而 extension 位於 `C:\GitHub\pi-better-tools\modules\…`，其 `import "@earendil-works/pi-coding-agent"` 等會向上解析到 `C:\GitHub\pi-better-tools\node_modules`——正是被刪的那個目錄。

### 4. 症狀簽章已用安全方式複現

以一個 import 不存在模組的 extension 當作 `-e` 目標（不破壞任何真實目錄）重跑同樣的 child 啟動：

```
exit=1
[無任何 IPC]      ← guard 根本沒載入，所以沒有 rejected 訊息
stderr: Error: Failed to load extension "…\broken-guard.ts": Cannot find module '@earendil-works/pi-ai/…'
```

與事故完全相同的簽章：`exit 1` + 無 IPC + 無 session 寫入 + 父側只能看到 `close`。
（連 `Cannot find module '@exodus/bytes/…'` 這類訊息也確實出現在同一時間窗的其他行程。）

## 事故中真正失去的資訊

child 的 stderr 其實**有被父行程捕捉**（`child.ts` 的 `stderrTail`，上限 8 KiB），但在 `manager.ts` 寫入紀錄時只保留 `cleanup.childClosed`／`exitCode`，`stderrTail` 被丟棄：

- `modules/fork/src/child.ts:181` 產出 `stderrTail`
- `modules/fork/src/manager.ts:144` 只寫 `{ childClosed, exitCode }`

因此「Failed to load extension … Cannot find module '@earendil-works/…'」這行決定性訊息在記憶體中短暫存在後被丟掉，使用者只看到沒有診斷價值的 `CHILD_CLOSED`。這是本次調查最花時間的地方，也是可立即改善之處。

## 附帶發現（本次非成因，但屬同一類別）

- **child 依賴共用套件樹的完整性**：任何對該 repo 的並行寫入（git 操作、`npm install`、正在編輯 extension 原始碼）都可能讓新產生的 child 失敗，而 parent 完全健康。這是營運層面的注意事項，不是 Fork 邏輯錯誤。
- **guard 的 `rejected` 有遺失競態**：`child-guard.ts` 的 `reject()` 先 `process.send(...)` 再立即 `process.exit(1)`。若訊息未及 flush，parent 會把精確代碼（如 `CONFIG_CHANGED`）誤報成泛用的 `CHILD_EXITED`。本次**不是**由此造成（本次 guard 根本沒載入），但確實是可重現的獨立弱點：我在重跑中曾成功收到 `rejected`。
- **兩類失敗難以區分**：目前「guard 拒絕」與「child 載入失敗」在父側都可能是 `CHILD_EXITED` + 泛用訊息。

## 建議後續（未實作）

1. **持久化有界 stderr**：`complete()` 把 `stderrTail`（例如最後 2 KiB，遮蔽比照既有規則）寫入 `record.cleanup` 或 `record.result`，並由 `fork_status`／面板顯示。這一項即可把本次事故從「需要數小時推導」變成「一眼可見」。優先度最高。
2. **讓 `rejected` 可靠送達**：`reject()` 等 IPC callback（或以有界等待）再退出，讓精確代碼不再因競態流失。
3. **child 端載入失敗的自我辨識**：在 guard 之外加一個極輕量、無外部依賴的啟動 marker，讓 child 至少能區分「Pi 起不來」與「guard 拒絕」，parent 可據此給出不同指引。
4. **README 補營運注意事項**：明確寫出 child 依賴 package 樹完整性，並建議在共用樹被並行修改（npm install／git 操作）時不要派 Fork。
