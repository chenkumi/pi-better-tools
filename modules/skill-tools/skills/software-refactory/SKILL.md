# Software Refactory

在使用者指定範圍內簡化程式，保留既有契約與可觀察行為；行為變更依使用者已授權的需求處理。

## 判斷與執行

1. 讀取相關實作、呼叫端、測試與需求，檢查目前未提交的變更，界定本輪目標及行為基準。只有缺少會影響取捨的資訊時才詢問。
2. 找出可刪除的死碼、語意相同的重複邏輯、多餘狀態或轉接層。對有風險的候選記錄依據、受影響契約與驗證方法；小型局部修改可直接進行。
3. 按變更風險選擇既有測試、型別／靜態檢查或實際操作，記錄相關基準。缺少行為保障時補 characterization test 或可重播案例；保留已知錯誤的說明，勿將現況誤稱為正確規格。
4. 以可驗證的批次修改。完成影響同一行為的變更後執行相關檢查，依影響範圍決定是否擴大驗證。
5. 檢查最終 diff，確認沒有未授權的功能刪減、無關修改或驗證降級。交付修改理由、驗證結果與剩餘風險。

## 刪除與合併的依據

- 靜態引用不存在只是一項證據；檢查適用的動態載入、反射、設定、路由、插件註冊、生成流程及外部消費者。
- 公開 API、持久資料格式、相容層、權限與錯誤處理依實際契約判斷。必要性仍不明時保留該項，繼續已確認的修改。
- 合併前確認共同語意、變更原因與生命週期；名稱相同、程式相似或流程相鄰不足以證明應合併。
- 單一實作的介面或只轉發的 wrapper 可能承擔測試、相容性或依賴邊界，依其作用判斷。
- 評估是否減少認知負擔、狀態與耦合，不以行數、檔案數下降作為完成條件。

## 驗證與交付

- 比較同一基準下的結果，區分既有失敗、新增回歸、環境阻礙與授權的行為變更；既有失敗可能遮蔽回歸，不以「失敗數未增加」當作充分證據。
- 修正新增回歸或僅撤回本輪相關變更，保護使用者與其他工作的修改。已授權的行為變更不必重複確認。
- Git 專案直接檢查工作差異；只有使用者需要獨立補丁時另存 diff，限定本輪範圍。無版本控制時先保存將修改檔案的可恢復基準，避免覆蓋既有備份。
- 長程或分批工作將已完成項目、證據位置及下一步逐批寫入既有任務紀錄；短任務以修改與驗證結果交付。
- 使用者只要求分析時，交付候選與證據，不修改產品程式碼。
