# Software Refactory

在使用者指定範圍內簡化程式：刪除確認多餘的部分、合併語意相同的邏輯、降低狀態與耦合，同時保留既有契約與可觀察行為。行為變更只依使用者已授權的需求處理。使用者的即時指示優先於本技能內容。

## 完成條件與何時停下

完成指：本輪目標內的修改都已通過相關檢查；最終 diff 沒有未授權的功能刪減、無關修改或驗證降級；交付說明含修改理由、驗證結果與剩餘風險。完成的判準是認知負擔、狀態與耦合確實下降，行數或檔案數只是附帶結果。

- 使用者只要求分析時，交付候選與證據後停止，不修改產品程式碼。
- 只有缺少會影響取捨的資訊時才詢問；其他情況合理推斷並繼續。已授權的行為變更不必重複確認。
- 某項必要性仍不明時保留它，繼續已確認的修改，並在交付時列為待決項。

## 判斷刪除與合併

- **未被靜態引用不代表可刪。** 檢查適用的動態載入、反射、設定、路由、插件註冊、生成流程及外部消費者；靜態搜尋找不到這些引用。
- **契約決定去留。** 公開 API、持久資料格式、相容層、權限與錯誤處理依實際契約判斷，不依目前呼叫端是否使用。
- **合併需要共同語意。** 確認共同語意、變更原因與生命週期；名稱相同、程式相似或流程相鄰不足以證明應合併——日後各自演化時，錯誤的合併比重複更難拆。
- **薄層可能有作用。** 單一實作的介面或只轉發的 wrapper 可能承擔測試、相容性或依賴邊界，依其作用判斷。
- **風險分級處理。** 小型局部修改直接進行；有風險的候選先記錄依據、受影響契約與驗證方法。

## 建立行為基準

- 動手前讀取相關實作、呼叫端、測試與需求，並檢查目前未提交的變更，界定本輪目標與行為基準。
- 依變更風險選擇既有測試、型別／靜態檢查或實際操作，並記錄修改前的結果。
- 缺少行為保障時補 characterization test 或可重播案例。現況若含已知錯誤，保留說明，不要把現況誤稱為正確規格。
- 無版本控制時先保存將修改檔案的可恢復基準，避免覆蓋既有備份。Git 專案直接用工作差異比對；只有使用者需要獨立補丁時另存 diff，並限定本輪範圍。

## 修改與驗證

- 以可驗證的批次修改；完成影響同一行為的變更後執行相關檢查，依影響範圍決定是否擴大驗證。
- 比較同一基準下的結果，區分既有失敗、新增回歸、環境阻礙與授權的行為變更。既有失敗可能遮蔽回歸，「失敗數未增加」不足以證明沒有回歸。
- 出現新增回歸時修正它，或只撤回本輪相關變更，保護使用者與其他工作的修改。
- 長程或分批工作逐批把已完成項目、證據位置與下一步寫入既有任務紀錄；短任務直接以修改與驗證結果交付。

## 交付格式

- 修改摘要：每項修改的依據（為何可刪／可合併）與受影響契約。
- 驗證：實際執行的檢查與結果，區分既有失敗、新增回歸與環境阻礙；未執行的檢查寫明原因。
- 待決與剩餘風險：因必要性不明而保留的項目、未覆蓋的行為。
- 只做分析時，改交候選清單與各自的證據、風險與建議驗證方法。
