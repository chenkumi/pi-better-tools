# Software Architecture Principles

依實際需求、變更原因、領域語意、不變量與品質要求判斷架構。以可驗證的影響支持建議。

## 判斷準則

- 先辨認決策範圍及重要限制：業務目標、品質情境、資料一致性、技術與部署條件、團隊責任。使用既有脈絡，只釐清會改變結論的缺口。
- 模組應集中相關責任與變更，隱藏值得隔離的決策。共同名稱、技術角色、相似程式或流程相鄰只是線索；合併前檢查語意、不變量、所有權與生命週期。
- 分開考慮程式模組、交易一致性、部署單元與組織邊界。共享資料庫不證明共享領域，獨立服務也不保證獨立演化。
- 依賴應暴露必要契約，控制實作知識與變更傳播。是否引入介面由變化、測試或隔離需求決定；不因只有一個實作就刪除，也不為所有類別建立介面。
- 邊界同時影響變更成本、故障擴散、安全與資料完整性。比較相關品質之間的取捨，不把最低變更成本當作所有系統的唯一目標。
- 用具體情境評估品質，例如新增供應商需要改動哪些責任、依賴失效會波及哪些操作。數值與預期改善要有來源，缺少量測時標示估計。
- 使用適用的依賴圖、變更歷史、執行路徑、事故與維運資料驗證假設。行數、循環數、資料夾樣貌或同步修改都是調查訊號，不能獨立決定拆分或合併。
- 選擇能滿足目前及有依據的預期需求的複雜度。已有方向時評估其代價與限制；確有選擇空間時比較實質替代方案，不為湊數創造方案。
- 改善既有系統時優先考慮有效的局部調整，將遷移、相容性與維運成本納入比較。架構風格與設計模式不是品質排名。
- 適合自動化的專案規則可形成架構檢查；只強制已選定且能可靠判定的契約，不把「零循環」或固定分層當作通用標準。

## 輸出

依問題規模說明觀察與來源、影響、建議、重要代價及驗證方式。區分事實、推論與待確認假設；不要求原則編號或固定欄位。

重大決策保存於既有架構文件或 ADR，保留決策背景與後續修訂關係。簡短設計問答可直接回答；本技能不強制產生報告、修改程式或啟動其他技能。
