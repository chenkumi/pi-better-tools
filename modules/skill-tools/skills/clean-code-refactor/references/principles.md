# Clean code 原則與判斷

目標：讓程式碼容易讀懂、放心修改。每條原則都要對照「這次修改是否真的降低認知負擔」，而不是機械套用。

## 值得整理的訊號

- **重複的知識。** 同一條規則、常數、清單或流程寫了兩次以上：例如同一組允許值在 schema 與執行期驗證各寫一份、相同的錯誤碼讀取寫八次、同一段 settle-once 等待邏輯在兩個檔案逐行相同。合併成單一來源，讓兩處由同一個定義產生。
- **做太多事的長函式。** 驗證、資源準備、主流程、清理混在一起。拆成具名步驟，讓主函式讀起來像流程；步驟維持原本的呼叫順序與錯誤優先序。
- **副作用與純邏輯混雜。** 把可計算的部分（例如從歷史紀錄核對預算）抽成純函式，副作用（通知、停用、寫檔）留在邊緣。
- **魔術數字與重複字面值。** 同一個上限、預設值、標記字串散落多處時命名並集中。只用於提示文字或顯示的數字可保留字面值。
- **誤導的名稱。** 名稱與實際行為不符（例如名為 bytes 實際比字元數、名為 registerSearchTools 只註冊 ls）。改名讓名稱誠實；不改行為。
- **可證明的死碼。** 沒有任何呼叫端、或邏輯上不可達的檢查。

## 不要整理的情況

- **語意不同的相似程式碼。** 名稱相同或長得像，但變動理由、邊界或語意不同（例如一個丟棄超長行繼續讀、另一個直接報錯）時保持分開。錯誤的抽象比重複更難修。
- **為了消除重複要到處傳遞內部狀態。** 共用 closure 狀態的長函式硬拆，可讀性不一定更好。
- **熱路徑上刻意內聯的程式。**
- **既有風格。** 模組刻意的密集寫法、格式慣例不做整體重排；新程式碼跟著周邊寫法走。
- **安全敏感邏輯。** URL／DNS／私有位址判斷、SQL 政策、權限與確認閘門、憑證處理，只有在可證明逐字等價時才重構；有疑慮就不動。
- **對外契約。** 匯出給其他模組、測試或外部消費者的名稱與簽章不改；只新增。

## 判斷死碼

- 靜態搜尋找不到引用不等於可刪：檢查整個 repo（含測試、腳本、文件、其他模組），以及動態載入、註冊、反射、設定與外部消費者。
- 「不可達」要能從程式本身證明，例如同一個 const 在同一個 try 內已被檢查過。
- 曾被正式移除、後來又出現的檔案（例如雜湊與移除紀錄一致）屬於誤帶回的死碼，依原紀錄刪除並說明。

## 工具陷阱（實際發生過）

- **跳脫序列被破壞。** 透過 shell 管線、PowerShell `Set-Content`、或多層引號的 node/sed 腳本改寫原始碼時，`\uD800` 之類的跳脫會被展開成實際字元，寫檔時變成 U+FFFD，造成靜默的行為錯誤。原始碼一律用精確字串替換的編輯工具修改。
- **非 ASCII 內容被轉碼。** 用 PowerShell 管線（`git show ... | Set-Content`）還原檔案會依主控台編碼轉換非 ASCII 字元；需要逐位元組還原時用 bash 重新導向 `git show REV:path > path`，並確認 `git diff --quiet` 與該版本一致。
- **編輯遺失空白。** 精確替換若從字串邊界切掉空白（例如 `X = /re/` 變成 `X =/re/`），審查 diff 時要看到並修回。
- **重新序列化手寫格式的 JSON。** `JSON.parse` 再 `JSON.stringify` 會展開單行物件與內嵌陣列，造成大量無關差異。手寫格式的檔案改用文字層級的局部修改，改完重新解析並與物件層級的預期結果做 deep-equal 比對。
