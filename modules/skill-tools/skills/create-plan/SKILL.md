# 建立計畫
## 職責與交付
產出符合使用者需求、可執行且驗收條件明確的完整 Markdown 計畫。以唯讀方式調查專案，不修改程式碼或計畫檔案。
最終回覆呈現完整計畫與下列 handoff，不只交付摘要或變動片段。本技能完成於交付，不直接啟動後續技能，也不要求使用者手動寫檔。

```markdown
Plan Title: <計畫標題>
Plan Goal: <計畫目標>
Plan Path: <既有計畫的精確路徑；尚未建立則填 not yet created>
```

* 既有路徑僅代表來源，不表示本輪修訂已存檔。若前置條件阻塞，handoff 改列實際需要的下一步及缺失資訊。

## 規劃流程
1. **確認現況。** 閱讀適用的專案指示、相關文件與程式碼，確認變更範圍、技術限制及可用的驗證方式。
2. **補齊必要資訊。** 一般技術事實直接查證。
3. **計畫規模。** 依據複雜度決定使用`多步驟Checkpoint`還是`扁平清單`
4. **釐清決策。** 只詢問會實質影響範圍、方向或驗收的問題，以及自行查證後仍無法取得的必要資訊。集中提問，依問題採用選項或自由回答；選項說明各自影響。非阻塞事項可記錄合理假設並繼續，阻塞事項解決前不把受影響部分標為可執行。
5. **安排工作。** 說明預期成果、範圍與方法，按依賴關係拆成可獨立驗收的 checkpoint；簡單任務使用扁平清單。每項寫清楚變更對象、行動與可觀察結果，必要時列出相關檔案及職責。短程式碼片段可用來釐清介面或資料契約，避免提前撰寫完整實作。
6. **定義驗收。** 依變更風險、驗收目標與環境選擇足夠且成本合理的檢查，可組合自動測試、實際操作及靜態審查。優先使用相關的既有檢查；新增測試應驗證有意義的行為。區分本次變更的驗收失敗與既有、無關的失敗。

Bug 修復的驗收須保留原始問題的觸發條件與預期行為，可將復現步驟轉為等價的自動回歸測試並補充必要案例。若尚未重現，明列待確認的條件與前置工作，不宣稱已有復現證據。已有確認的 Draft 時，對應介面的驗收須引用具體畫面、輸出或互動行為。

## 計畫格式
以簡短的成果與方法說明開頭，包含 
- `Title`
- `Goal`
- `References`
- 工作項目與驗收
- `Open questions`

* 範圍排除項、檔案盤點及假設依需要列出。未決問題說明影響；多題可用 OQ 代號方便回覆，沒有未決問題時填「無」。
* 新項目使用 `[ ]`，驗證紀錄留空，不預填成功結果。`Max attempts` 使用已指定的上限，否則為 `3`。

### 工作項目與驗收
#### 多步驟Checkpoint
每個 checkpoint 對應一個可獨立判定完成的成果，包含 todo 與一個 `Verify`。`Depends on` 指明前置 checkpoint 及所需產出；引用的介面、型別或欄位須能從專案或計畫中定位，並區分現有與預計新增的名稱。

```markdown
## Plan
- [ ] 1. <階段完成後的成果>
    Depends on: <無，或前置 checkpoint 與所需產出>
    - [ ] <具體行動>
    - [ ] <具體行動>
    Verify:
      Tier: <1 / 2 / 3>
      Max attempts: 3
      Check: <可執行指令、操作步驟或審查範圍>
      Expected: <各項檢查的明確通過條件>
      Verification log:
```

`Tier` 標示主要驗收方式，補充檢查列在同一個 `Check` 中：
- **1：自動驗證。** 以測試或斷言判定行為。
- **2：實際操作。** 操作 CLI、API 或介面，對照具體預期結果。
- **3：靜態或推理審查。** 無法取得必要的執行證據時，寫清楚審查範圍，並在 `Verify` 加上 `Note`，說明未實際驗證的部分、信賴限制與後續驗證方式。

#### 扁平清單
```markdown
## Action items
- [ ] <具體行動1>
- [ ] <具體行動2>

## Verification
Max attempts: 3
Check: <驗證步驟或審查範圍>
Expected: <明確通過條件>
Verification log:
```

若只能靜態或推理審查，同樣加上 `Note` 說明限制。

### Open questions
* 如果沒有問題 可標示`無Open questions`，提供2~3個選項，包含一個建議選項，建議選項要描述原因。

### 格式
```markdown
## Open questions
- OQ1 : <問題1>
  - A: <選項A(建議選項)>
  - B: <選項B>
> 選擇<建議選項A>的理由
...
```

## 更新規則
- 以提供的既有計畫內容及精確路徑為基準，重新檢查受影響的程式碼、假設、依賴及驗收條件；只修訂需要更新的部分。
- 保留完成紀錄、驗證證據與 commit hash。已完成的工作若需要後續修正，新增對應工作，不改寫歷史成果。
- 保留仍適用的結構；切分或依賴已不合理時，調整受影響部分並說明原因。
- 記錄已回答的問題與決策，不重問；已不相關的問題說明原因後移除。
- 對稽核指出的問題保留證據並修訂受影響內容。尚未解除的阻塞須明列前置條件，不把計畫交付成可直接執行的狀態。

## 品質檢查
交付前確認需求覆蓋完整、範圍符合授權、步驟及依賴可執行，且引用名稱與目前專案或預定契約一致。驗收須對應使用者需求、問題證據與確認稿，包含明確的 `Check` 和 `Expected`。
檢查所選模式的必要欄位是否齊全，包括 checkpoint 的 `Tier`、兩種模式的 `Max attempts` 與 `Verification log`，以及僅能審查時的 `Note`。更新時確認歷史紀錄保留、受影響依賴一致，handoff 路徑與存檔狀態如實呈現。
