# Test Suite Tidy

整理既有測試：讓日常執行更快、移除重複與無用案例、把案例放到最低足夠的層級，同時**不降低缺陷偵測能力**。新增測試用 `test-case-creator`；本技能只處理既有套件。使用者的即時指示優先於本技能內容。

核心原則：測試的價值是它能抓到別的測試抓不到的缺陷，不是數量。「慢」與「多餘」是兩個問題，先診斷是哪一個，再選手段。零刪除、只改執行結構，是正當的結論。

## 完成條件與何時停下

完成指：每項改動有證據；整理前後被保護的行為不減少（案例數、通過數逐組對照，差異有說明）；有前後耗時對照；交付說明列出實際執行與未執行的分組（未執行不算通過）與剩餘風險。

遇到以下情況停下並回報，不自行決定：無法判斷案例是否為唯一保障；刪除會使某個契約失去任何自動化保障；要變快只能弱化斷言；手段會改變隔離語意（例如關閉 runner 的模組隔離）；基準本身不是全綠。

## 流程

1. **界定範圍與讀慣例**：讀專案的測試分組規則、runner 與文件（本專案為 `AGENTS.md` 驗證段與 `scripts/run-checks.mjs`）。保留來源專案的 runner。第三方快照的上游測試預設不動：只把發現列為建議，使用者明確要求才改。
2. **量測基準**：只量測受影響的組；基準耗時長（數分鐘以上）就放背景，不阻塞。優先用 runner 或 reporter 已產出的逐階段與逐案例耗時，不另外插樁。記錄各組耗時、案例數、通過數；可行時量覆蓋率（只用來找盲點）。基準不是全綠就先回報，不在紅燈上整理。
3. **診斷時間花在哪裡**（見下節），決定先做提速還是先做刪減。
4. **盤點候選**：靜態掃描與人工檢視，每個候選記錄檔案、案例、類型、理由。
5. **逐批處理並驗證**：一次一類或一個模組，每批獨立驗證、可獨立回溯。
6. **前後對照**：同條件重跑，比對耗時、案例數、通過數、覆蓋率；案例數減少必須逐項說明。

## 診斷：時間花在哪裡

先比較「案例耗時加總」與「整組牆鐘時間」：

- **差距大（案例只佔組時間幾個百分比）**：瓶頸是結構——逐檔序列啟動、轉譯／模組載入、重複建立昂貴資源。刪案例幾乎無助於速度，改執行結構。
- **少數案例佔大半**：看是否固定 sleep、真實 I/O、重複的昂貴 setup，逐一處理。
- **案例多且各自很快**：才以刪減重複與合併參數化為主。

提速手段，由低風險到高風險：

| 手段 | 做法與前提 |
|---|---|
| 提高檔案並行度 | 單元測試每檔獨立行程、使用隔離暫存目錄、不用固定 port 時才適用；整合、真實 host、對時間敏感的組維持原並行度 |
| 共用昂貴 setup | 不共享可變狀態才可共用，否則維持 |
| 以事件、假時鐘、注入時間取代固定 sleep／idle／watchdog | 不能改就刪，不保留 |
| 把真正慢的檔案歸入重型組 | 同步更新分組清單與文件 |
| runner 隔離或轉譯設定（如 Vitest `isolate`、轉譯快取） | 會改變模組狀態語意，列為建議由使用者決定 |

### 提高並行度的驗證規程

1. 先在單一組實驗，逐組驗證，不一次全改。
2. 案例數與通過數必須與基準完全一致。
3. 至少連跑兩次全綠。
4. 實驗取較高值驗證穩定，落地取保守值（例如驗證 6、採用 4），為時間型案例留餘裕。
5. 規則落在 runner 的單一處，並更新註解（舊註解與新行為矛盾必須修正）。

### 量測衛生

並行度與耗時對照很容易被機器負載污染：

- 基準與實驗不可同時跑；啟動前確認沒有殘留的測試行程，中止舊工作要確認行程樹真的結束。
- 前後兩次若有**沒被改動的組**，把它當對照：它若也變慢，這次耗時不可比，只比可比的組。
- 負載下的逾時失敗先單獨重跑：通過就歸為負載敏感 flake，記為剩餘風險，不當成回歸，也不放寬 timeout 掩蓋。

## 候選類型與處理

| 類型 | 處理 |
|---|---|
| 同一行為在單元、整合、真實 host 多層重複驗證 | 保留最低且足以抓到該缺陷的一層；上層只留「接得起來」的代表案例 |
| 只換輸入、斷言邏輯相同 | 合併為參數化；保留邊界值與每個等價類各一代表 |
| 測實作細節（私有函式、mock 呼叫次數與順序） | 改驗可觀察行為；無契約意義則刪除 |
| 斷言過弱（只驗不丟例外、只驗存在） | 補斷言；補不出有意義的斷言就刪除 |
| 測語言、框架或第三方行為 | 刪除 |
| 對應功能已移除 | 刪除，連同無人使用的 fixture 與 helper |
| flaky | 先找根因；修不了且無獨有保障時才移除並記錄 |

### 靜態掃描的注意

- 掃描腳本逐行解析，避免複雜正則（巢狀量詞可能回溯到卡死）。
- 「疑似無斷言」「同名案例」等啟發式只產生**候選**，必須逐項人工確認：斷言常在 helper 內；不同模組的對稱結構（如 observer／reflector 鏡像）是設計，不是重複。確認不了的不刪。

## 刪除前的證據

滿足至少一項才能刪或合併，並記錄於交付說明：

- 另一案例（寫出檔案與名稱）以相同或更強的斷言覆蓋同一行為；
- 被測行為或程式已不存在；
- 案例沒有可觀察斷言；
- 變異驗證：暫時破壞被測程式，刪／合併前後都至少有一個測試失敗。成本高，只用於少數高風險邏輯，不是常態要求。

「覆蓋率沒下降」只是必要條件：行被跑到不等於行為被驗證。

## 不可做的事

- 為了變快而弱化斷言、放寬容差、拉長 timeout 或讓測試靜默跳過。
- 刪除唯一保障安全性、授權、資源上限、清理或取消契約的案例。
- 順手修產品缺陷。發現缺陷另開回歸測試（先 red 後 green）獨立處理。
- 把 skip、環境阻礙、未執行算作通過。

## 文件與格式同步

改了 runner、分組或並行度，同步更新說明這些規則的文件（本專案為 `AGENTS.md` 與相關 README）。修改檔案保持原行尾（CRLF 檔不可變成 LF），不以文字模式腳本重寫導致行尾改變。

## 防止再次膨脹

新增案例前先問：這個行為已由哪一層保護？放在哪一層最便宜？每個 bug 的回歸測試放在能最早抓到它的最低層。單檔實測耗時超過專案重型門檻就歸入重型組。

## 交付

簡述：範圍、前後量測（耗時、案例數、通過數）、診斷結論（結構或案例）、改動與刪除清單（每項附證據）、實際執行與未執行的分組、剩餘風險與建議後續。沿用專案既有報告位置（本專案放 `plan/`）。
