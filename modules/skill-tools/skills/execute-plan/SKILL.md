# 執行計畫

依計畫完成實作並驗證結果。計畫的目標、範圍與驗收條件就是交付內容：不默默縮小、擴大或替換。使用者即時指示與本技能衝突時，以使用者為準。

## 開始前

1. 取得計畫：使用者給的路徑或對話中的計畫。完整讀完；若無法確定是哪一份，才向使用者確認。
2. 釐清計畫的目標、步驟、相依關係、checkpoint 與驗收條件。把步驟列入待辦清單追蹤進度。
3. 計畫與現況不符（檔案已改變、前提不成立）時，先以現況為準調整做法，並在最後回報差異；只有差異會讓計畫失去意義時才停下詢問。

## Git 版本控管

先執行 `git rev-parse --is-inside-work-tree` 判斷目前工作目錄是否由 git 管理。**未受管理時略過本節所有 commit 動作**，其餘流程照常。

受管理時：

- **起始狀態：** 動手修改前先 commit 作為計畫起點。
  - 工作樹有未提交變更：一併 commit 成起始狀態（訊息例：`chore: baseline before executing plan`）。
  - 工作樹乾淨：不建立空 commit，記錄目前 `HEAD` 作為起點。
  - 尚無任何 commit：建立初始 commit，仍以此為起點。
- **Checkpoint：** 計畫若有 checkpoint（里程碑、階段、驗收點），每個 checkpoint 的工作完成並通過該點的驗證後 commit，作為回滾點。訊息簡述 checkpoint 名稱與內容。該 checkpoint 沒有檔案變更時不建立空 commit，記錄目前 `HEAD` 即可。計畫沒有 checkpoint 時，除起始 commit 外不額外 commit。
- **commit 範圍：** 只納入本次變更且未被 `.gitignore` 排除的檔案；不納入 `.env`、憑證、金鑰、連線字串等機密或大型產出物，發現時停止納入並告知使用者。
- **邊界：** 遵守專案的 commit 慣例與 hooks，hook 失敗就修正原因，不使用 `--no-verify` 或略過簽章。不 push、不改寫歷史（amend、rebase、reset、force）、不建立或切換分支，除非使用者要求。
- 是否回滾由使用者決定；你只提供各回滾點的 commit hash，不主動回滾。

## 執行

- 依相依順序推進，彼此獨立的步驟可平行處理。做到計畫定義的完成狀態為止，不在中途停下請求審查或確認「是否繼續」。
- 已授權的範圍內，可逆且屬於計畫的動作直接進行。只有破壞性或不可逆操作、真正的範圍變更、或只有使用者能提供的輸入才停下詢問。
- 每個步驟完成後，用該步驟的驗收條件做真實檢查（測試、型別檢查、建置、實際執行變更後的指令），規則見「驗證與重試」。不以「語法正確」代替驗證。
- 範圍外的發現（既有 bug、順手的清理、額外文件或測試）不直接修改，列在最後作為建議。
- 計畫的某部分被卡住時，完成其餘所有部分，並明確說明被卡住的項目、原因與已嘗試的做法。
- 計畫內容不明確時，採用計畫文字與周邊程式碼最直接支持的解讀，並記下假設。

## 即時更新進度

計畫檔案是可觀測進度的文件，讓他人隨時打開就知道做到哪裡，因此進度必須即時更新，不可做完才一次補寫：

- 開始一個步驟前，先在計畫中把它標為進行中；完成並通過驗證後，立即標為完成，再開始下一個。同一時間只有一個進行中的步驟（平行處理時各自標示）。
- 沿用計畫既有的進度標記（核取方塊、狀態欄位等）；沒有時用 `[ ]` 待辦、`[~]` 進行中、`[x]` 完成、`[!]` 被卡住，標在步驟開頭。
- 被卡住、跳過或與計畫不同的項目，當下就在該步驟旁以一行註記原因。
- 建立 checkpoint commit 後，立即把該 commit 的 hash 寫在該 checkpoint 上，作為計畫裡可查的回滾點；起始 commit 的 hash 寫在計畫開頭。
- 每次更新只改動進度標記、驗證紀錄與 commit hash，不改寫計畫的其他內容。已完成項目的歷史紀錄不改寫，後續需要修正時新增項目。
- 計畫只存在對話中時，以待辦清單即時反映相同狀態。

## 驗證與重試

- 每個步驟（或 checkpoint）的驗證，最多嘗試 3 次。上限的優先序：使用者指示 > 計畫中該項驗證自帶的上限欄位（如 `Max attempts`）> 預設 3。每次嘗試都是一次真實檢查，每次失敗後先診斷並修正，再進行下一次。
- **每次驗證都在計畫中留下紀錄**：寫在該步驟或 checkpoint 之下，一次一行，格式為 `[第幾次/上限] Error|Succeed: <執行摘要>`，例：

```
[1/3] Error: 型別檢查失敗，parseConfig 回傳型別不符
[2/3] Succeed: 型別檢查與單元測試通過
```

- 計畫該項驗證已有紀錄欄位（如 `Verification log`）時，寫進該欄位；沒有才寫在該步驟或 checkpoint 之下。
- 摘要寫執行了什麼檢查與結果（失敗要含原因），單行、不含機密。紀錄在驗證當下寫入，不事後補寫，也不覆蓋先前的紀錄。
- 計畫是檔案時，直接編輯該檔案加入紀錄與進度，除此之外不更動計畫內容；計畫只存在對話中時，把紀錄保留在待辦清單與最終回報。
- 通過即停止重試。用完上限仍失敗，視為該項被卡住：不繼續重試也不當作通過，不建立該 checkpoint 的 commit，改做不依賴它的其餘部分，並在回報中說明。

## 完成回報

結束時簡潔回報，讓只讀最後一則訊息的人也能掌握全貌：

- 完成了什麼、與計畫的差異與所做假設。
- 實際執行的驗證與結果（含各項重試次數）；未執行的檢查要明講並說明原因，不算通過。
- 未完成或被卡住的項目。
- 範圍外的建議。
- 若有 git：起始 commit 與各 checkpoint commit 的 hash 與簡述，方便使用者回滾。
