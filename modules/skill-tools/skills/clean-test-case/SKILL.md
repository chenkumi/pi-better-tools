# Clean Test Case

測試是可執行的規格：失敗時讀名稱就知道哪個行為壞了，紅燈代表真有缺陷，重構實作時測試不必跟著改。測試程式碼的品質標準與正式程式碼相同。

本技能處理測試的「乾淨度」。選擇哪些案例、邊界與測試層級，交給 `test-case-creator`；兩者可併用。

本技能只給原則與判斷問句，不規定具體寫法。語言、框架與工具依專案現況選擇。

## 範圍

- 預設只改測試檔。整理時順帶發現的其他問題（正式程式碼、專案慣例、無關模組）列出並詢問，不併入同一批改動。
- 測試無法用公開方式觀察被測行為時，才考慮在正式程式碼加最小的觀察點：不得改變既有行為，不得改讀私有狀態代替，並在交付時明講。
- 先讀專案的測試設定與執行方式，用專案指定的命令執行，不自行猜測；直接執行單檔失敗時，先確認是否因為執行方式與專案不同。

## 工作流程

1. **掃描**：用搜尋找出形式上的壞味道（見下方清單），計數並分類，先呈現規模再動手。固定等待要再分三類，各自處理：被測行為本身就是時間者保留並加註解；有可觀察條件者改條件等待；只為製造時間差者改可控時間（見「等待與時間」）。分類前不動手改。
2. **分批**：按類別或模組分批處理，一批只做一類修改。
3. **逐批驗證**：每批改完執行受影響的範圍；整理前後結果應一致。
4. **抽樣審查語意問題**：搜尋找不到「測實作而非行為」「過度替身」。挑替身最多或最常隨重構而壞的測試，逐一問「重構後它會不會壞」，並明講這部分是抽樣而非全面。

## 原則與判斷問句

### 結構與命名

- 前置、操作、斷言分段，一個測試一個操作、驗證一個行為。同一概念可有多個斷言，不為「一測試一斷言」拆碎。
- 名稱說清楚情境、動作與預期，能直接當失敗訊息。問：只看名稱，能不能知道哪個需求壞了？
- 失敗訊息要指出原因，不只是「預期為真」。

### 測行為，不測實作

- 驗證公開契約：輸入、輸出與可觀察的副作用。問：重構後測試需要修改嗎？若失敗，是行為真的變了嗎？
- 只替換程序邊界（網路、檔案、時間、隨機、外部服務）。優先真實物件，其次簡化實作，最後才是記錄呼叫的替身。只有副作用本身就是需求時，才驗證「有沒有呼叫」。

### 資料與預期值

- 只呈現與本測試相關的資料，無關欄位交給共用的建構方式。
- 有意義的值用名稱表達，不留神祕數字。
- 預期值來自規格或獨立參考，不用被測邏輯的同一套計算得出；測試內不放分支與迴圈。
- 測試可小幅重複，但每個案例應能獨立讀完，不為去重複逼讀者跳轉。

### 獨立與可重複

- 不共享可變狀態、不依賴執行順序；單跑、整批跑、換順序結果相同。
- 時間、亂數、環境、埠與路徑都應可控或動態取得，不依賴執行當下的外部狀態。
- 結果由程式自動判定，不需要人看輸出。

### 等待與時間

- 等待必須綁定到可觀察的條件，不靠猜測的時間長度。問：我在等什麼？它有沒有可觀察的信號？
  - 等狀態成立：以有上限的條件等待，逾時時說明在等什麼。
  - 驗證「某事沒有發生」：讓後續動作經過同一條有序通道，作為已處理完的證據，不靠多等一會兒。
  - 背景工作：使用工作本身的完成信號；沒有公開信號時，先由測試輸入製造信號（例如讓被執行的指令先寫一個標記檔，測試等那個檔案出現），仍不行才見「範圍」的觀察點規則。
  - 輪詢逾時必須讓測試失敗並說明在等什麼；不可讓迴圈安靜結束，由後面不相關的斷言去失敗。多處需要時抽成共用的等待 helper。
- 為了讓兩個時間點不同而睡一小段時間，是「時間不可控」的症狀。問：能不能由測試決定現在是幾點？應注入時鐘或使用可控時間，不用睡眠換取差異。
- 被測行為本身就是時間（逾時、保持、延遲）時，可使用真實時間，並加註解說明為何不能換成條件。
- 不穩定的測試先找根因（共享狀態、時間、順序、競態），不以重試或加長等待掩蓋；不得無條件跳過或註解掉。診斷順序：單獨跑 → 在人工 CPU 負載下跑 → 降低並行度跑 → 與退回自己改動的程式比較。失敗耗時恰好等於某個逾時設定時，打到的是逾時本身，要用時間記錄找出時間花在哪一步。仍無法重現就明講根因未確定，不以推測當結論。

## 壞味道清單（供掃描）

- 名稱看不出需求
- 一個測試驗證多個不相關的行為
- 測試內有分支或迴圈
- 預期值用被測邏輯的公式算出（循環論證）
- 替身過多，重構一次壞一片
- 依賴順序或共享狀態
- 以固定時間長度等待
- 輪詢逾時後迴圈安靜結束，沒有讓測試失敗
- 同一段等待迴圈複製貼上多處，沒有共用 helper
- 被跳過、被註解的測試，或沒有斷言的測試
- 失敗訊息無法指出原因

跳過若有明確條件（平台、環境）屬正常，須說明條件；無條件跳過才是壞味道。

## 驗證與輸出

- 說明實際執行的範圍與結果；區分產品失敗、測試工具錯誤、環境阻礙與未執行。跳過與未執行不算通過。
- **有效性驗證（變異檢查）**：對修改過的測試，暫時破壞被測實作，確認預期的那個斷言失敗，再還原並確認工作樹沒有殘留改動。只看「有失敗」不夠，要確認是哪個斷言先失敗。無法破壞（如純外部依賴）時，說明未驗證。
- **負向斷言必做變異檢查**：斷言「沒出現、沒呼叫、沒發生第二次」的測試，最容易因為等得不夠或排空不完整而恆真。改動其等待方式後，一定要讓實作做出那件不該發生的事，確認測試會失敗；重複執行通過不能代替。變異要涵蓋「立即發生」與「稍後才發生」兩種形式，並看是哪一行先失敗：立即型常在前面的等待就被抓到，沒碰到你改的那行斷言；只有延遲型的變異失敗在該斷言，才證明那段等待與斷言真有作用。
- **新增或改動等待、斷言 helper 時**：單獨驗證它的失敗路徑真的會失敗（條件不成立 → 以名稱失敗）、成功路徑會回傳值；可用暫時的測試檔驗證，驗完刪除。
- **同步更新分類標記**：消除慢速原因後，同步調整專案用來標示慢速或分流的標記（命名、分組、設定），並確認改歸預設執行範圍後仍通過；標記留著，測試就持續被排除在日常執行之外。
- 交付列出：處理的壞味道與數量、保留未動的項目與原因、順帶發現但未處理的問題、未執行的驗證範圍。
- 覆蓋率只在實際量測時提供，且不等於行為完整性。
