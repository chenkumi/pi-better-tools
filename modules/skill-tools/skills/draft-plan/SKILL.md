# 草擬設計

把使用者的想法或修改目標，變成他們能看著做判斷的具體草稿，並把決策逐項落實成設計文件。目標是讓使用者看得出「改前與改後差在哪」，不是寫完整規格。使用者即時指示與本技能衝突時，以使用者為準。

適用於方向已大致確定、需要用具體草稿做選擇的階段。需求本身仍模糊、尚在釐清問題與範圍時，先釐清需求；純粹的架構取捨（模組邊界、依賴方向）若不需要草稿，用架構評估處理即可。已有確認的設計文件時，沿用並更新它，不另建。

## 先建立設計文件

設計一開始、提出第一個草稿之前，先建立文件，不要等討論結束才寫：

- 有 `note` 工具時，用類別 `design` 建立；否則依專案既有慣例（現有的設計文件目錄與格式）建立，沒有慣例就在工作目錄建立一份 Markdown。路徑由工具或慣例決定，不自行發明命名規則。
- 初始內容：標題、目標（使用者想達成什麼）、背景與既有約束、待決策清單（尚未決定的項目），以及空的「已決策」區。
- 後續一律編輯同一份文件，不另開新檔。文件路徑告知使用者一次即可。

## 先理解，再畫草稿

- 先讀相關的既有設計文件、程式碼與慣例，沿用正式設計與既有約束；不重新發明已有的元件、命名或流程。
- 目標或範圍有會改變設計走向的疑點時才詢問；其他情況做出合理假設、寫進文件的「假設」，繼續推進。
- 把目標拆成待決策項目，依影響大小排序，一次只提出一項讓使用者決定。

## 用最小的呈現讓使用者判斷差異

選能讓使用者看出差異的最小形式，精細程度只要足以解決當前待決策的問題：

- **UI：** wireframe、圖稿或可互動的草稿；只畫與決策有關的部分，標出與現況的差異。
- **API、CLI、檔案格式：** 具體的輸入與輸出範例，含一個典型情境與一個邊界／錯誤情境。
- **狀態變更：** 流程圖或狀態轉換表，列出起始狀態、事件、結束狀態與副作用。
- **資料或架構：** 變更前後的精簡對照（結構、欄位、相依方向）。

一個項目有多種可行做法時，並列 2–3 個草稿，各用一句話說明取捨並給出推薦；不列沒打算採用的選項。避免把細節畫到超過決策所需。

## 即時記錄決策

使用者對一個項目做出決策後，**立即**把該決策寫入設計文件，再進入下一項，不累積到最後：

- 寫入內容：決策結果、採用的最終草稿（wireframe、範例或轉換表）、一句理由、被排除的替代方案。
- 該項從「待決策」移到「已決策」；使用者改變先前決策時，更新該條並註明變更，不留下互相矛盾的版本。
- 使用者尚未決定的事項保持在「待決策」，不替使用者決定；你的推薦只標為推薦。
- 每次寫入後簡短告知更新了什麼，並提出下一個待決策項目。

## 完成

所有待決策項目都已決策（或使用者明確擱置）時，整理文件使其可獨立閱讀：目標、最終設計、決策與理由、仍待處理的事項與風險。回報固定欄位與一份摘要（已決定了什麼、尚有什麼未決）。不在本技能中開始實作；實作由使用者另行指示。

```
Design Path: <設計文件的精確相對路徑>
Status: <已全部決策 | 尚有待決策項目>
```
